## 0. 结论速览（TL;DR）

### 0.1 对核心问题的直接回答：**"白点"能不能不再需要人工反复调？**

**能。但要分清三件不同的事**（这是本次调研最重要的一次概念切分）：

| 做法 | 白点是否消失 | 本质 | 本项目适用性 |
|---|---|---|---|
| **A. 用算法猜白点**（自适应/自动 tune） | ❌ 不消失，只是换人猜 | 仍是"场景端点"参数化，只是由统计量驱动 | 已有（`auto_tone`），历史三次真机证伪 |
| **B. 把白点变成设备常量**（sigmoid / ACES 2.0） | ✅ **参数从架构中删除** | 曲线锚点 = 中灰 + **显示白/峰值亮度**；输入域无界（渐近） | ★ 推荐主线 |
| **C. 把白点硬编码进固定曲线**（Blender AgX） | ✅ 消失（但固定 log 域） | -10..+6.5 EV 固定映射，LUT 固化 | 可选，灵活性差于 B |

**为什么 A 永远治不好**（本项目实测已证实，见 §1）：在 filmic 的参数化里，白点不是独立自由度——`output_power = log(grey)/log(−black/(white−black))`（darktable `filmicrgb.c:2593-2600`），**改白点 ⇒ 曲线形状（中灰以上斜率）必变 ⇒ look 漂移**。R-2/R-3 的 `cp` 补偿、拟合残差从 8~10 恶化到 12.7~19.55、"只改白点重拟合把某些 look 弄得更差"，全部是这一个耦合的表现。**这是参数化的结构性缺陷，不是调参水平问题。**

**B 的量化收益**（本次逐行复刻计算，口径与全表见 §8 附录 A）：在**同一白纸亮度**（≈204 LSB，即 R-3 交付配方水平）下：

| 架构 | 白纸(2.30EV) | 死白起点（≤1 LSB/0.1EV） | 线性域单调可逆 |
|---|---|---|---|
| 现行 filmic（白点 4.0，R-3 实测，无 LUT 口径） | 205.4 | **3.55 EV** | ❌ 有硬平顶（数学上不可逆） |
| darktable sigmoid（contrast 1.2，默认参数族） | 204.1 | **4.25 EV** | ✅ 严格单调 |
| ACES 2.0 tone scale（peak≈55 nit，中灰重锚前） | 197.7 | **4.60 EV** | ✅ 严格单调 |
| darktable sigmoid（默认 contrast 1.5） | 219.2 | 3.65 EV | ✅ |

⇒ **同白纸亮度下，sigmoid 比现行 filmic 多留 0.7 EV、ACES 2.0 多留 1.05 EV 的高光层次**；更本质的是 filmic 的"死白"是**硬平顶**（多个输入 → 同一输出的信息不可逆丢失，R-2 §0 已实测），而 sigmoid/ACES 2.0 的曲线对任意输入都有唯一输出（ACES 2.0 官方还提供解析反函数 `tonescale_inv`）。

### 0.2 与本项目结合的三条路线（详见 §5）

- **P-A（过渡，最小侵入）**：把 `[38]` 从"风格参数"降级为"场景估计 + 用户偏置"，预设也走自适应白点；用"中灰斜率恒定"重参数化替代现有的 `cp` 补偿兜底。零新增 pass。
- **P-B（根治，推荐主线）**：`kFsFilm` 的影调层从 filmic 三段多项式换成 **generalized log-logistic（darktable sigmoid 同源数学）**；白点参数从 preset schema 中删除，换成 `display_white_target` + `contrast` + `skew`（全部是设备/风格量，与场景无关）。
- **P-C（最强，迁移最大）**：整体换 **ACES 2.0 输出变换**（Hellwig 2022 JMh + hue 表 + cusp 表）；获得感知均匀、hue 保持、反向可逆与业界标准一致性，代价是需要相机→ACES 的输入变换链。

### 0.3 一个必须知道的守恒律

"白纸够白"与"白纸之上还有层次"争的是**同一段显示灰阶**（8bit 下上限 ~246.5，R-1c/R-2 已证）。**没有任何架构能同时给足两者**——换架构买到的是 ①白点参数消失（风格稳定）②同白纸亮度下多 0.7~1.05 EV 层次 ③线性域可逆。**买不到"白纸更白且层次更多"**。若最终交付 8bit JPEG，量化上限是物理事实；要兑现"可逆"必须提高中间/输出位深（10bit HEIF）。

## 1. 问题的本质：为什么"白点"会成为一个人工参数

### 1.1 filmic 家族的白点 = 场景端点，且与曲线形状强耦合

**darktable `filmicrgb.c`**（①[原文]，`https://github.com/darktable-org/darktable/blob/master/src/iop/filmicrgb.c`）：

```c
// filmicrgb.c:2593-2600
static inline void _compute_output_power(const dt_iop_module_t *self, dt_iop_filmicrgb_params_t *p)
{
  p->output_power = CLAMPF(logf(p->grey_point_target / 100.0f)
                           / logf(-p->black_point_source / (p->white_point_source - p->black_point_source)),
                           min, max);
}
```

- 默认值（①[原文] `filmicrgb.c:170-172`）：`grey_point_source 18.45%`、`black_point_source −8.0 EV`、`white_point_source +4.0 EV`；`security_factor` 默认 **0**（`:178`）。
- **`output_power` 是 `white_point_source` 的函数** ⇒ 白点一动，中灰以上的对数域斜率（对比）就变。这就是本项目 `cp` 补偿要救的东西。

**本项目逐字同型**（`core/engine/src/render/FrameRenderer.cpp:13442-13447`）：

```cpp
auto derive_power = [&](float wv) {
  const float bl = std::min(b, wv - 0.2f);
  const float wh = std::max(wv, bl + 0.2f);
  return std::log(kGrey) / std::log(-static_cast<double>(bl) /
                                   static_cast<double>(wh - bl));
};
```
⇒ 与 darktable `_compute_output_power` **同一公式**；本项目 filmic 就是 darktable v5 的参数化（与 `docs/research/01-darktable.md` 的逐字取证一致）。

### 1.2 darktable 自己的自动白点也是"手动 + 耦合"

**①[原文] `filmicrgb.c:2656-2680`**：

```c
static void apply_auto_white_point_source(dt_iop_module_t *self)
{
  ...
  const float white = get_pixel_norm(self->picked_color_max, DT_FILMIC_METHOD_MAX_RGB, work_profile);
  float EVmax = CLAMP(log2f(white / (p->grey_point_source / 100.0f)), 1.0f, 16.0f);
  EVmax *= (1.0f + p->security_factor / 100.0f);
  p->white_point_source = EVmax;
  _compute_output_power(self, p);          // ★ 白点变 ⇒ power 重算 ⇒ 形状变
  ...
}
```

- 触发方式 = **用户点 color picker 手动框选**（`color_picker_apply`，`:2701-2715`），**不是每帧自动跑**。
- `apply_autotune`（`:2682-2731`）= 一次设定 grey/white/black 三个值 + 重算 power，"auto tune levels" 按钮。
- ⇒ **业界最成熟的 filmic 实现，其"自动白点"也仅是"一次性 picker + 保险系数"，同样存在白点↔power 耦合。** 我们的困境不是我们独有的工程缺陷，是这套参数化的固有性质。

### 1.3 本项目已有的自适应机制（预设没走）

`core/engine/src/render/FrameRenderer.cpp:13342` `updateFilmicEV()`（①[原文] 本仓）：

| 机制 | 位置 | 作用 |
|---|---|---|
| `st.valid && auto_on` 门 | `:13362` | **auto_tone 关 ⇒ 全部自适应代码不执行**；预设 `auto_tone = 0` |
| 黑点 = P0.1 分位，下限钉 −7.654 | `:13388-13389` | darktable autodetect 语义 |
| 白点 = P99，`white_hl` 开时用 max 上探（`+0.4EV security`，幅度闸 `white_probe`，默认 `[44]=0.5`） | `:13405-13415` | 治"P99 对 <1% 强光源失明" |
| `w_floor = min(2.438, w99 + [43])` | `:13427-13430` | **治"釉面/白瓷密集高光点变白斑"**（2026-10-03 红杯真机） |
| `w = clamp(w, w_floor, 4.556152) + ev_shift` | `:13431` | 物理钳制 + 渲染域平移（v0.10.31） |
| `cp` 补偿（上探前后 power 比，clamp [1.0,1.6]，只补不降） | `:13440-13453` | 救"上探导致中灰以上对比回落" |

槽位（`core/engine/src/film/FilmParams.h`）：`[35] auto_tone`（`:135`，默认 0）、`[42] white_hl`（`:190`，默认 1）、`[43] white_floor`（`:195`，默认 0）、`[44] white_probe`（`:201`，默认 0.5）、`[37]/[38]` 黑白点、`[5..10]` shoulder/toe latitude。

**已有失败史（必须读，`FilmParams.h:130-135` 逐字）**：v0.10.19 默认关是"**三版真机证伪**"的结果——0.10.16 中间调低/水壶过曝/天空过饱和、0.10.17 全面糟糕化、0.10.18 power 5.17 无改善；根因写得很清楚：**"自动分位定端点把 power 推离固定曲线的 3.62 设计值"**。
⇒ **这三次失败不是"自适应不行"，而是"在 filmic 参数化里自适应端点必然改形状"**——正是 §1.1 那个耦合。任何"让预设走自适应白点"的方案（P-A）都必须先解决形状冻结，否则会重演 v0.10.19。

### 2.2 与 1.x 的本质差别

②[官方文档] `https://docs.acescentral.com/background/about-aces-2/` 逐字列出的差别：

- 全新设计的渲染变换（Output Transforms）：**更温和的 tone scale（中灰对比更低、高光滚降更缓）**、"更直观的参数控制"、"**更鲁棒的 gamut mapping（更好的感知均匀性、更少裁剪伪影）**"、"为反向变换优化性能"。
- 结构上拆成 **Rendering Transform（决定外观）+ Display Encoding（只做设备编码）**（①[原文] `https://docs.acescentral.com/system-components/output-transforms/technical-details/rendering-overview/` 与 `docs.acescentral.com/system-components/output-transforms/implementer-notes/`：rendering target 与 display device 两个正交选择）。

**与 ACES 1.x 的三个结构性差异**（①[原文] 代码级）：

1. **在感知外观模型空间里做色调映射**：链路 = `ACES RGB → ACES to JMh → Tonescale(J only) → Chroma Compression(M only) → Gamut Compression(J&M) → White Limiting → Display Encoding`（①[原文] 同上 rendering-overview）。
2. **JMh 来自 Hellwig 2022 CAM 的简化版**（②[官方文档] 逐字："derived using a simplified version of the [Hellwig 2022](https://doi.org/10.1002/col.22792) Color Appearance Model"；J=lightness、M=colorfulness、h=hue）。J 单独做 tone scale、M 单独做 chroma compression ⇒ **hue 保持**成为设计约束（ACES 1.x 的 per-channel 做法做不到）。
3. **tone scale 由显示峰值亮度参数化**（见 2.3），**没有"场景白点"这个参数**。

### 2.3 tone scale 公式与全部常数（①[原文]，可逐行移植）

来源：`https://github.com/aces-aswf/aces-core/blob/main/lib/Lib.Academy.Tonescale.ctl`（96 行，全文可读）。

**参数预计算 `init_TSParams(peakLuminance)`**（①[原文] `:30-74`）常数逐字：

| 常数 | 值 | 含义 |
|---|---|---|
| `n_r` | 100.0 | 归一化白（nits） |
| `g` | 1.15 | surround / contrast |
| `c` | 0.18 | 18% 中灰锚点 |
| `c_d` | 10.013 | 18% 灰的输出亮度（nits）★ |
| `w_g` | 0.14 | 不同峰值亮度之间的灰变化 |
| `t_1` | 0.04 | 阴影 toe / flare 补偿 |
| `r_hit_min` / `r_hit_max` | 128 / 896 | "hitting the roof" 的场景参考值（SDR / 10000nit） |

推导链（`:46-58`）：`r_hit = 128 + (896−128)·log(n/100)/log(10000/100)`；`m_0 = n/100`；`m_1 = ½(m_0+√(m_0(m_0+4t_1)))`；`u = ((r_hit/m_1)/((r_hit/m_1)+1))^g`；`m = m_1/u`；`w_i = log2(n/100)`；`c_t = c_d/100·(1+w_i·w_g)`；`g_ip = ½(c_t+√(c_t(c_t+4t_1)))`；`g_ipp2 = −(m_1(g_ip/m)^(1/g))/((g_ip/m)^(1/g)−1)`；`w_2 = c/g_ipp2`；`s_2 = w_2·m_1`；`u_2 = ((r_hit/m_1)/((r_hit/m_1)+w_2))^g`；`m_2 = m_1/u_2`。

**正变换（Michaelis-Menten + flare）**（①[原文] `:77-86`）：

```
f = m_2 · ( x / (x + s_2) )^g          # x = 场景线性 ACES2065-1
h = f² / (f + t_1)                     # flare / glare
Y = h · n_r                            # 输出 = cd/m²
```

**反变换**（①[原文] `:88-96`，官方提供解析反函数）：

```
Z = clamp(Y, 0, n/(u_2·n_r));  h = (Z + √(Z(4t_1+Z)))/2
f = s_2 / ( (m_2/h)^(1/g) − 1 );  return f
```

**数值（②[官方文档] tone-mapping 页 "Values" 表，peak luminance → ACES 输入值处的输出）**：100 nit 时输入 0.18→10.000、1.0→45.757、2.0→63.988；1000 nit 时 0.18→14.512、1.0→106.564、2.0→205.783。

**关键推论**：`x → ∞` 时 `f → m_2`（有限），曲线**严格单调、无硬平顶**；`x` 无上界 ⇒ **不存在"输入超过某值后输出恒定"的区间**。这正是"白点参数"消失的数学原因。

### 2.4 Hellwig 2022 在代码里的样子（①[原文]）

`https://github.com/aces-aswf/aces-core/blob/main/lib/Lib.Academy.OutputTransform.ctl`（1702 行）：

- 观察条件常数（`:62-64`）：`L_A = 100.`（适应亮度）、`Y_b = 20.`（背景亮度）、`surround[3] = {0.9, 0.59, 0.9}`（Dim surround）；`model_gamma = surround[1]·(1.48+√(Y_b/ref_luminance))`（`:71`）。
- 后适应锥响应压缩（`:185-198`）：`F_L_Y = Rc^0.42`；`Ra = F_L_Y/(cam_nl_offset + F_L_Y)`（`cam_nl_offset` 取 CAM16 的 0.29 系）。
- **表驱动**（`:42-45, :136-150`）：`tableSize = 360`（1° 步长的 hue 表）、`TABLE_reach_M[]`、`TABLE_hues[]`、`TABLE_gamut_cusps[][3]`、`TABLE_upper_hull_gamma[]`。
- 无彩色的快速路径（`:226-260`）：`Achromatic_JMh` / `JMh_to_Achromatic` 直接走 Y，省掉完整 CAM 计算。

### 2.5 CTL/CLF 资产在哪、能否离线烘焙

| 资产 | 位置 | 形态 |
|---|---|---|
| 核心算法 | `github.com/aces-aswf/aces-core` → `lib/Lib.Academy.{Tonescale,OutputTransform,ColorSpaces,DisplayEncoding,Utilities}.ctl`（共 2858 行） | **CTL 源码**（Apache-2.0） |
| 预设输出变换 | `github.com/aces-aswf/aces-output` → `d60/{dcdm,p3,rec709,rec2100,srgb,displayP3}/Output.*.ctl` + `InvOutput.*.ctl`（+ D65 目录） | **CTL 预设**，共 100+ 个 |
| **CLF** | **`aces-output` 仓库内 CLF 文件数 = 0**（本次实测：`tar tzf aces-output.tgz \| grep -ci clf → 0`） | ❌ 官方 2.0 未随附 CLF |

- ①[原文] 官方明确推荐：**"It is recommended, if your software supports it, to port the core algorithm."**（`docs.acescentral.com/system-components/output-transforms/implementer-notes/`）；退路才是"为每个预设预计算 LUT，并提供让用户加自定义 LUT 的方法"。
- ②[官方文档] CLF 是通用算子链容器（矩阵/1D/3D LUT/ASC-CDL/log shaper），v3.0 正在 SMPTE 标准化：`https://docs.acescentral.com/clf/introduction/`。
- ⇒ **离线烘焙路径**：官方 CTL 无 2.0 CLF ⇒ 需自行用 CTL 渲染器（或 OCIO 2.x 的 ACES 2.0 内置实现）在 ACES 输入域上采样，生成 3D LUT（如 65³）+ 1D shaper。**但注意**：tone scale 的输入域无界，1D/3D LUT 必须配 log shaper（如 ACEScct）与滞回域，否则高光端采样不足——这正是官方劝"port the algorithm"的原因。

### 2.6 移动端落地的现实路径与代价

| 路径 | 实施代价 | 精度/风险 |
|---|---|---|
| **移植核心算法（推荐）** | 单 pass 内新增：ACES→JMh（2 个 3×3 矩阵 + 1 次 pow(0.42) 的锥响应压缩）、tone scale（1 次 pow + 3 次乘加）、chroma compression（cusp 表插值 + 1~2 次 pow）、gamut compression、JMh→RGB。**约 60~120 ALU/px + 2 张表纹理**（hue 表 360~364 项 RGBA32F ≈ 6 KB；cusp 表同量级）。X300 上 1080p 全屏 pass 完全可行（对比现有 filmic 15 次乘加，增量可观但非瓶颈） | 最高（与参考实现一致），**且提供解析反函数**（逆变换性能是 ACES 2.0 的设计目标之一） |
| **预烘焙 3D LUT + log shaper** | 资产：1D shaper（4096×1）+ 3D LUT（33³/65³，tetrahedral）；显存 65³×RGBA16F ≈ 2.1 MB；**零额外 ALU** | 中；高光端与色域边界有插值误差；**不支持自定义参数**（换个 peak luminance 就要重烘）；官方明确这是退路 |
| **只借 tone scale（不借 JMh）** | 只需 §2.3 的 96 行公式（5 个标量参数），per-channel 或 luma 域应用 | 失去 ACES 的 hue 保持/gamut 压缩，但**白点参数同样消失**（这是我们最想要的部分） |

**结论（Q1）**：ACES 2.0 用了感知模型（Hellwig 2022 简化版 JMh），tone scale 是显示峰值亮度参数化的 Michaelis-Menten + flare；资产是 **CTL（无官方 CLF）**；移动端推荐**移植核心算法**（60~120 ALU + 两张小表），退路是 CTL 离线烘焙 3D LUT + log shaper。

## 4. 感知均匀空间在 tone/gamut mapping 的实践（Q3）

### 4.1 Oklab / OKLCh（①[原文] `https://bottosson.github.io/posts/oklab/`）

- 定义（①[原文] 逐字给出）：`XYZ(D65) → M1 → (l,m,s) → 逐分量立方根 → M2 → (L,a,b)`，
  `M1 = [[+0.8189330101,+0.3618667424,−0.1288597137],[+0.0329845436,+0.9293118715,+0.0361456387],[+0.0482003018,+0.2643662691,+0.6338517070]]`，
  `M2 = [[+0.2104542553,+0.7936177850,−0.0040720468],[+1.9779984951,−2.4285922050,+0.4505937099],[+0.0259040371,+0.7827717662,−0.8086757660]]`。
- 2025 年作者补记的采用面（①[原文]）：Photoshop 渐变默认插值、CSS Color Level 4/5、Unity/Godot。
- **用于 tone mapping / gamut mapping 的标准做法**：在 OKLCh 里**只压缩 C**（保持 L、h）——Björn 的 gamut clipping 文章（`https://bottosson.github.io/posts/gamutclipping/`）给出的"投影到 sRGB 色域边界"即此思路；比 per-channel clip 的 hue 偏移小得多。
- **代价**：逐像素 2 个 3×3 + 3 次 cbrt（或 pow(1/3)）≈ 30~50 ALU；GPU 上 cbrt 可用 `exp2(log2(x)/3)`，或改用多项式近似。

### 4.2 CAM16 / CAM16-UCS 与 Hellwig 2022

- CAM16 的算法改进（①[原文] arXiv:1802.06067 "Algorithmic improvements for the CIECAM02 and CAM16 color appearance models"）——把 CIECAM02 的迭代求根改为解析解，**这是 CAM16 能进实时管线的关键**。
- **Hellwig & Fairchild 2022**（①[原文] DOI `10.1002/col.22792`）是 ACES 2.0 选用的模型；ACES 代码里体现为：适应亮度 `L_A=100`、背景 `Y_b=20`、Dim surround、锥响应压缩指数 `0.42`、`cam_nl_offset`、`F_L_n` 归一化（§2.4）。
- **实践意义**：CAM16-UCS/Hellwig 的 J、M 提供"感知亮度/彩度"的正交分解 ⇒ tone scale 只作用 J、chroma compression 只作用 M，**hue 天然保持**。这是 ACES 2.0 相对 per-channel 做法的根本优势，也是 darktable 在 sigmoid 4.6 里加 primaries（attenuation/rotation/purity）想逼近的效果。

### 4.3 2024–2026 的新做法（①[原文] arXiv 检索结果，均为摘要级）

| 论文 | 日期 | 一句话机理 |
|---|---|---|
| [Oklch+: A Three-Parameter Extension of Oklab for Improved Color Difference Prediction](http://arxiv.org/abs/2606.05255v1) | 2026-06 | 在 Oklab 上加第三个参数（明度相关修正）改善色差预测，仍保持闭式可逆 |
| [Chroma-gated, differentiable OKLCH interpolation: Continuous Oklab fallback for color-cast reduction](http://arxiv.org/abs/2606.15352v1) | 2026-06 | 用可微的 OKLCh 插值 + 彩度门控做去色偏，避免 hue 折线 |
| [Helmlab: A Two-Space Family of Analytical, Data-Driven Color Spaces](http://arxiv.org/abs/2602.23010v3) | 2026-02 | 解析+数据驱动的双空间族，面向 UI 设计系统的感知均匀 |
| [Deep chroma compression of tone-mapped images](http://arxiv.org/abs/2409.16032v1) | 2024-09 | 学习式彩度压缩，专治 tone mapping 之后的彩度/色相伪影（正是 ACES 的 chroma compression 位置） |
| [A Gamut-Mapping Framework for Color-Accurate Reproduction of HDR Images](http://arxiv.org/abs/1711.08925v1) | 2017-11 | （经典基线，非新）HDR 色域映射框架，常被后续工作引用 |

**我们的可用结论**：如果要给现有 CCM/gamut mapping v5 升级，**Oklab/OKLCh 的"C-only 压缩"是最低成本、最高收益的一步**（不需要 CAM16 的完整框架）；ACES 2.0 的 cusp 表法则是"更贵但更准"的另一档。

### 5.2 三条做法的本质差异（一句话）

- **做法 1/2/9（filmic 自适应）**：白点是**场景端点参数**，改它就改形状 ⇒ 永远需要"重拟合 + 补偿"，**不可持续**（用户判断正确）。
- **做法 4/5/6（峰值检测 / EETF / 元数据）**：回答的是"**内容峰值是多少**"，是**输入侧估计问题**，本身很成熟（libplacebo 的参数表可以直接抄）。
- **做法 3（sigmoid / ACES 2.0）**：回答的是"**根本不需要知道场景峰值**"——曲线对无界输入渐近收敛，**把估计问题消掉**。这是唯一"免人工调"的正解。

### 5.3 为什么做法 3 是对的（本项目可验证的判据）

用 §8 的判据（8bit、≤1 LSB/0.1EV、同一白纸亮度）比较：filmic 4.0 = 3.55 EV（**硬平顶**，信息不可逆丢失），sigmoid c=1.2 = 4.25 EV（**严格单调**），ACES2 ≈55nit = 4.6 EV（**严格单调 + 官方解析反函数**）。同时白点参数**从 preset schema 里消失** ⇒ 用户永远不需要再问"白点设多少"。

## 6. 与本项目现状的结合（Q5）

### 6.1 现状（一句话结构）

```
[RAW/HR] → CCM → kFsFilm(filmic spline, per-channel 三段多项式, 由 [4]/[5..10]/[37]/[38] 决定)
        → kFsOut(highlightRolloff + gamut v5 + split/sat/mono + 真 sRGB OETF)
        → kFsStyle(编辑器：显示域胶片曲线 + 清晰度 + 褪色 + 暗角)
预设：params 里固定 filmic_white_ev = 4.0（R-3 交付）、auto_tone = 0
```

- `kFsFilm` 的 CPU 侧系数来自 `computeFilmicSpline(ev_black_, ev_white_, cp*[4], lat_sh, lat_toe)`；白点只通过 `ev_white_` 进入，而 `ev_white_` 在 `auto_tone=0` 时 = `[38]`。
- **接口点唯一且清晰**：`updateFilmicEV()` 的白点来源 + `computeFilmicSpline` 的参数化。

### 6.2 方案 P-A：预设也走自适应白点（最小侵入，先解 look 稳定性）

**目标**：让 `[38]` 从"风格常量"变成"场景估计 + 用户偏置"，同时**保证同预设跨场景观感一致**。

| 要素 | 设计 |
|---|---|
| 槽位语义 | `[35] auto_tone` 扩展为三态：`0` = 固定（兼容旧预设）；`1` = 黑白点全自动（现状）；`2` = **仅白点自适应 + 黑点仍用 `[37]`**（新增，预设用这一档） |
| 白点估计 | 复用 `measureSceneStats()`（已有，零新增 pass）：`w = clamp(max(P99, min(P_max+0.4, P99+white_probe)), w_floor, 4.556) + ev_shift`，`white_probe` 用 `[44]=0.5`（已由真机红杯案例标定） |
| 下限保护 | `[43] white_floor` 必须开（建议 `0.5`）：`w_floor = min(2.438, w99+0.5)`——这正是"釉面/白瓷密集高光"的解药 |
| **形状冻结（关键）** | 现有 `cp` 只补中灰以上斜率（clamp ≤1.6，只补不降）。**升级为"中灰斜率恒定"重参数化**：离线对每个预设算出 `contrast(w)` 映射表（w∈[2.0,4.6] 共 27 档，步长 0.1），运行期按 `w` 线性插值取 `contrast` 下发给 `computeFilmicSpline`。这样白点变化**只改变肩部位置、不改变中灰斜率**，look 一致性从"事后补偿"升级为"事前约束" |
| 风格承载 | 白点不参与风格：风格全部由 `[4] contrast`、`[5..10] shoulder/toe latitude`、sat/split/mono、`[34] LUT` 承载（与 R-3 的 `--lat-split` 结论一致：解耦 shoulder/toe 是唯一有正收益的新自由度） |
| 实施代价 | **零新增 pass、零新增资产**；CPU 侧每帧一次已有直方图 + 27 项表插值（纳秒级）；preset schema 需加"白点模式"字段（`schema` 2 → 3） |
| 风险 | ①重演 v0.10.19（用 `white_probe=0.5` + `white_floor` + `cp`/斜率表三道闸兜）；②`4.556` 上限仍在（R-1c 的 `highlightRolloff` 246.53 硬上限也未解，属引擎级决策） |

### 6.3 方案 P-B（推荐主线）：影调层换 generalized log-logistic

**为什么是它**：darktable 把它作为**新装机默认**（②[官方文档] sigmoid 手册），意味着它经过最大规模的用户验证；公式 20 行、参数 5 个、无场景端点；且与 Blender AgX 的"primaries + 无界曲线"思想同源（darktable 4.6 明说是受 AgX 启发）。

**①[原文] 公式**（`sigmoid.c:300-309`，逐行）：

```
film_response = (film_fog + x)^film_power
paper_response = magnitude · ( film_response / (paper_exp + film_response) )^paper_power
```
**①[原文] 参数求解约束**（`sigmoid.c:325-380`）：
```
f(scene_zero) = display_black_target      # 默认 0.0152 (%)
f(scene_grey) = MIDDLE_GREY = 0.1845      # 中灰锚定
f(scene_inf)  = display_white_target      # 默认 100.0 (%) = 显示白
中灰处斜率只由 contrast 决定（与 skew 无关）
paper_power = 5^(−skew)
film_power  = ref_slope / temp_slope      # 数值求解（本次复刻：默认参数下 film_power = 1.5）
```
**本次复刻数值**（③[未验证]，逐行照抄 `sigmoid.c` 的 `commit_params` + `_generalized_loglogistic_sigmoid`，sRGB OETF、8bit）：

| contrast | 中灰 0EV | 白纸 2.30EV | 白瓷 2.0EV | 3.0EV | 死白起点 |
|---|---|---|---|---|---|
| 1.0 | 119.0 | 192.0 | — | — | 4.80 EV |
| **1.2** | 119.0 | **204.1** | 194.7 | 222.3 | **4.25 EV** |
| 1.5（默认） | 119.0 | 219.2 | 209.7 | 235.6 | 3.65 EV |
| 1.8 | 119.0 | 230.5 | 221.7 | 243.8 | 3.20 EV |
| 2.2 | 119.0 | 240.6 | 233.4 | 249.7 | 2.80 EV |

（skew = −0.3 时 contrast 1.5 的等效：白纸 212.4、死白 3.90 EV；skew 是"把对比从暗部搬到亮部"的独立旋钮）

**迁移接口点**：

| 层 | 改动 |
|---|---|
| shader `kFsFilm` | 三段多项式求值（15 mul+add）→ log-logistic（2 次 pow + 4 mul/add）。**同 pass，零新增纹理** |
| CPU `computeFilmicSpline` | 5×5×2 系统求解 → `commit_params` 式解析求解（~20 次 pow，亚毫秒）；`FilmicSpline` 结构体从 15×2 系数缩到 5 个标量 |
| preset schema | `filmic_black_ev`/`filmic_white_ev` 废弃 → `sigmoid_contrast`/`sigmoid_skew`/`display_white_target`（后者固定 100，不进 UI）；`[37][38]` 保留为"兼容/自定义"通道或直接弃用 |
| 拟合工具链 | `tools/preset-exp/recipe-fit.py` 的 `Evaluator` 把 filmic 段换成 sigmoid 段即可复用（R-1 的目标曲线与判据不变） |
| 不变 | CCM、gamut mapping v5、`kFsOut` 的 rolloff/sat/split、LUT、颗粒/halation/暗角/清晰度**全部不动**（作用点都在影调之后） |

**收益**：白点参数消失；同白纸亮度下死白起点 +0.7 EV；线性域严格单调（无不可逆平顶）。

### 6.4 方案 P-C：整体换 ACES 2.0 输出变换（储备）

**代价清单**（逐项，不评价"值不值"）：

| 项 | 内容 |
|---|---|
| 新增 ALU | 锥响应压缩（1 次 pow(0.42)）+ 2 个 3×3 + tone scale（1 pow）+ chroma compression（1~2 pow）+ gamut compression |
| 新增资产 | hue 表 360~364 项（`TABLE_reach_M`/`TABLE_hues`/`TABLE_gamut_cusps`/`TABLE_upper_hull_gamma`，RGBA32F 合计 ≈ 12 KB 级别）；若走 LUT 路线则 65³ RGBA16F ≈ 2.1 MB + 1D shaper |
| 新增链路 | 相机线性 → **ACES2065-1** 的输入变换（需要 IDT/矩阵，我们目前是 CCM → sRGB 线性） |
| 迁移 | 全部预设重新标定；`kFsFilm`/`kFsOut` 的分工要重构（ACES 的 rendering transform 已含 gamut/white limiting） |
| 中灰重锚 | ACES 2.0 的 18% 灰目标输出是 **10.013 nits**（①[原文] `c_d`），100 nit SDR 下 8bit ≈ 90 LSB，**比本项目现行中灰（113.7~127.6）暗**；迁移必须显式决定"是否接受 ACES 渲染意图"或做中灰重锚（会等比例拉低死白起点） |
| 收益 | hue 保持 + 感知均匀 + 无白点 + **官方解析反函数** + 与 ACES/SMPTE 生态一致（未来 DNG/ACES 工作流无障碍） |

### 6.5 离线验证方案（三方案通用）

1. **曲线级**（毫秒级，最先做）：把 `tools/preset-exp/r2-white-point.py` 的链路换成新曲线，跑同一套判据（
   §8 的 `analyse()`：EV 网格 0.05、64 行中位数去 dither、死白起点 = 此后整段 8bit 极差 ≤1 LSB 的起点）。
2. **场景矩阵注入**：合成 / 真机 DNG 抽取高光 EV 分布，覆盖 R-2 §5 记录的三个真实失效场景：
   ① 密集小面积高光（釉面红杯，w99 ≈ 1.03 EV，占比 0.002%）；② 大面积近饱和（白壶，4.1% 像素被压进 245+）；③ 边缘白墙经 LSC 3~5× 抬升（+2.5~3 EV）。
   **必须补的一张卡（R-2 自认的最大证据缺口）：真机 DNG 高光 EV 直方图**——没有它，白点/曲线的验收判据只能靠外推。
3. **look 一致性指标（新增，用于 P-A/P-B 验收）**：固定预设、扫场景白点 w∈[2.0,4.6]，度量
   ①白纸输出（230 EV 处）极差；②高光段斜率（2.6/3.0 EV）极差；③中灰输出漂移。判据建议：①②的跨场景标准差 ≤ 现固定白点配方在同场景集上的标准差（即"自适应的引入不得让风格方差变大"）。
4. **回归护栏**：沿用 R-3 的做法（`BuiltinPresetCurveTest.declared` 钉住实测值 + 余量），新增曲线族的数值护栏；595 单测全绿是硬门槛。

### 6.6 真机 A/B 方案

- **场景六件套**（每场景 3 档曝光，共 18 张/方案）：白瓷盘、釉面红杯（近距离、点光源）、白墙逆光窗、阴天天空、暗光室内（无强光源）、高饱和红光（查 hue path）。
- **对照臂**：①现状（白点 4.0 固定）；②P-A（自适应 + 斜率冻结）；③P-B（sigmoid）。
- **读判据**：死白起点（脚本判 8bit 平顶）、白纸/白瓷 LSB、中灰 LSB、高光段斜率、以及人工"高光是否糊"盲评（每臂 18 张随机顺序）。
- **附加客观项**：导出 10bit PNG 复算（验证"线性域可逆"是否在交付链上真的兑现）。

### 6.7 是否存在"比自适应更好"的替代架构？

**有，而且业界已经完成了迁移**（这是我们最强的外部佐证）：

- darktable：新装机默认 workflow = **sigmoid**（②[官方文档]），而不是 filmic。
- Blender：4.0 起默认观感 = **AgX**（固定曲线），5.0 进一步内置 **ACES 2.0**（②[官方文档] 5.0 release notes）。
- ACES：2.0 的 tone scale **根本不提供场景白点参数**（①[原文] `Lib.Academy.Tonescale.ctl` 全部参数由 `peakLuminance` 决定）。

⇒ **"自适应白点"是在 filmic 参数化内部的局部最优；换掉参数化才是全局最优。** 我们的 `auto_tone` 三次真机证伪，恰好是这个行业结论的一次独立复现。

## 8. 附录 A：本次数值实验的口径与结果（③[未验证]，可复现）

**口径**（与 R-2/R-3 的可比性说明）：

- 输入 `s = 0.1845 · 2^EV`（中灰 18.45% = 0 EV），EV 网格 −1.0 ~ +9.0，步长 0.05。
- 输出统一为**线性显示值 → 真 sRGB OETF → 8bit**（`c≤0.0031308: 12.92c`；否则 `1.055c^(1/2.4)−0.055`）。
- "死白起点" = 从该 EV 起，此后每 0.1 EV 的输出差**恒 ≤ 1 LSB** 的最小 EV（与 R-2 的 `analyse()` 同判据）。
- **纯曲线口径**：不含 gamut mapping / primaries inset / LUT / highlightRolloff。因此与 R-2/R-3 的"含引擎链路"数值不可逐位比较，只用于**架构间排序**。

**复刻正确性自检**：sigmoid 默认参数下复刻得到 `film_power = 1.5000`（= contrast 1.5，与 `commit_params` 的设计约束"中灰斜率只由 contrast 决定"一致）、`fog = 0.00143`、`paper_exp = 0.354355`；ACES 2.0 在 peak=100 nit 下 `r_hit = 128.0`、`m_1 = 1.0385`、`m_2 = 1.0471`、`s_2 = 0.91986`——与 `init_TSParams` 的常数定义一致。**仍属③[未验证]：未与官方产物的逐像素对拍。**

**ACES 2.0 全表**（peak luminance 扫描，③[未验证]）：

| peak | 中灰 0EV | 白纸 2.30EV | 白瓷 2.0EV | 3.0EV | 上限 | 死白起点 |
|---|---|---|---|---|---|---|
| 55 nit | — | 197.7 | — | — | — | 4.60 EV |
| 100 nit（标准 SDR） | **90.3** | 175.5 | 165.0 | 197.6 | 254.7 | 5.25 EV |
| 500 nit | 45.9 | 112.3 | 102.1 | 137.1 | 251.6 | 7.10 EV |
| 1000 nit | 32.7 | 87.6 | 78.7 | 110.1 | 248.7 | 7.90 EV |

（ACES 2.0 的 peak 越高，归一化后画面越暗——这是"渲染意图"，不是 bug；+12 EV 处 f = 1.0071，略超 1.0，由后续 White Limiting / Display Encoding 兜住。）

**单调性检查**：sigmoid(c=1.5) 与 ACES2(100 nit) 在 −1 ~ +11 EV 全段**线性域严格单调**（相邻 0.02 EV 输出差恒 >0），8bit 输出亦单调；`f(+12EV)`（sigmoid）= 0.999983、`f(+20EV)` = 1.000000（渐近不发散）。**filmic 在高光端是硬平顶**（R-2 §0 实测：白点 2.7471 时从 2.75 EV 起 `kFsFilm` 输出恒 `0.998535`）。

## 10. 未解问题与证据缺口（诚实标注）

1. **缺真机 RAW 高光 EV 直方图**（R-2 §7 已记为最大缺口）。所有"白点该多少/死白起点该多少"的判据目前都建立在引擎注释里的零散真机日志（1.02 / 2.47~3.0 / 5.494 EV）之上。**建议单开一卡**：真机 DNG 的高光 EV 分布统计（含 LSC 前后、P99/P99.9/max/占比）。
2. **ACES 2.0 的"中灰 10.013 nits"渲染意图**与本项目现行中灰（113.7~127.6 LSB）口味差异，必须真机拍板；**本次未做中灰重锚后的完整重算**。
3. **8bit 交付下的收益上限**：本文所有"死白起点"判据都在 8bit 上定义；sigmoid/ACES 2.0 的"线性域可逆"只有在**中间/输出位深 ≥10bit** 时才真正兑现。项目导出链的位深决策未在本次调研范围内。
4. **darktable AgX 模块的引入版本**为"手册存在性推断"（5.0 有 / 4.6 无），**未取到发布公告原文**。
