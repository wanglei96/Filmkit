# 引擎架构与执行框架调研（多引擎可切换 · 前沿实践 + 选型）

> 本文回答四件事：①「引擎插槽」该怎么切（一手对照物 = bjzhou/PhotonCamera）
> ②执行框架留 GLES 还是迁 Vulkan / 上 Halide ③色彩管理用 OCIO / ACES CLF 还是离线烘焙
> ④新引擎怎么落地并验收。
>
> **取证口径**：PC 侧一手副本 `/tmp/pc-arch`，`git log -1` = `b9cf590`（2026-10-13，"feat: independent point metering"）。
> 行号仅对该 commit 有效。10 号文档取证的是 `d584bc9`（2026-09-30），本文行号与之**不同**，引用一律以本文为准。
> 本项目侧数据取自工作区实读（`FrameRenderer.{h,cpp}`、`FilmParams.h`、`.zcode/memory/`），
> 标注「实读」；外部资料标注链接；推断一律标「**未验证**」。
> 本文**不含生产代码**，伪码/表结构仅供契约设计用。

## 0. 结论速览

1. **引擎插槽的价值不在"多几个 look"，在把"手调"变成"可替换的契约"。**
   PC 的 9 个在役引擎共用同一条公共管线，引擎只接管**一个 pass**（`applyEngineTone`），
   输入是 `uProfileToEngineTransform` 变来的目标相机域线性 RGB，输出是**线性 sRGB**（硬契约）。
   影调黑白点反复手调的根因是"参数钉在唯一一条链上"；插槽化后，黑白点由**引擎自己拥有**，
   公共管线不再承担这个责任。

2. **架构契约最小集 = 6 项**：引擎 ID（稳定字符串）、输入域、输出域（固定线性 sRGB）、
   EV 域（Linear / Curve）、资产 manifest（含源 SHA-256）、失败语义（严格失败，不静默 identity）。
   PC 把这 6 项全部显式化（`RawRenderingEngine.kt:10-101`、`RawRenderingEngineToneAlgorithm.kt:9-15`）。

3. **执行框架：GLES 留用，Vulkan 作期权，Halide 只用于离线烘焙。**
   本项目当前痛点（纹理 752MB、+100MB RGBA16F、pass 数）**不是 API 层级的问题**，
   是 pass 划分与中间缓冲生命周期的问题 —— 迁 Vulkan 不会自动解决，但 Vulkan 的
   **显式内存别名（image aliasing）+ input attachment** 是唯一能**结构性**解决它的手段。
   代价：14436 行 `FrameRenderer.cpp` / 63 个 program / 67 个 draw call 调用点全量重写（实读）。
   建议：**阶段 1–3 不迁**，把它作为"引擎数量 ≥5 或 NN 引擎上马"时的期权。

4. **色彩管理：运行时不做 OCIO 解释器，做「离线 OCIO/CTL 烘焙 + 运行时严格域标注」。**
   OCIO 2.6（2026-09）已支持 SMPTE ST 2136-1 CLF 读写与 Vulkan/HLSL GPU 测试框架
   （[release notes](https://opencolorio.readthedocs.io/en/latest/releases/ocio_2_6.html)），
   但移动端运行时嵌入的收益/体积比不划算（**体积未实测，见 §7 未解问题**）。
   CLF 的**正确定位是资产交换格式 + 离线校验格式**，不是运行时输入格式。

5. **资产分发：官方 LUT 一律「用户导入」，不进 APK。** ARRI Look Library 的再分发条款
   仍未确认（10 号文档 §3.5 已标）；官方 LUT Generator 页面明确 "LUT Generator does NOT support LogC4"
   需另下 LogC4 3D LUT Package（[ARRI LUT Generator](https://www.arri.com/en/learn-help/learn-help-camera-system/tools/lut-generator)，实抓）。
   ACES core transforms 是 **Apache-2.0**（可再分发），这是相对 ARRI look 资产的关键差异。

6. **引擎是会被下线的**（本次新取证）：PC 的 Fuji 引擎（shaderId 9）已于
   `56d33aa`（2026-10-09）移除，**成本 = 33 个文件改动，含一次 Room 数据库迁移（+42 行）**
   （§1.8）。这条决定了架构契约的两条硬要求：
   **引擎注册表集中化** + **引擎私有参数不进 DB 列**（否则每加删一个引擎都要一次 schema 迁移）。

## 1. 一手取证：PC 的引擎插槽架构

### 1.1 分层与数据流（`b9cf590`）

```text
┌─────────────────────── 公共管线（引擎不可见） ───────────────────────┐
│ RAW 解码 → MFNR 堆栈 → 去马赛克 → 降噪 → 白平衡 → 源相机标定          │
│   → 线性 ProPhoto（共享工作空间；测光 / PGTM / 曝光都在这里）          │
│   → 公共 PGTM（usePhotonHdr 策略）                                    │
│   → 公共曝光（uProfileExposureLinearGain）                            │
└───────────────────────────────┬──────────────────────────────────────┘
                                │  profile 域线性 RGB（ProPhoto）
┌───────────────────────────────▼──────────────────────────────────────┐
│  ★ 引擎插槽（RawEngineTonePass.render）                              │
│    uProfileToEngineTransform (mat3)  ← 等效相机矩阵，逐引擎一份        │
│    → applyEngineTone(color)          ← 引擎自己的 shader 片段         │
│    → applyBlackWhiteLevels(color)    ← 公共黑白点（在引擎域之后）      │
└───────────────────────────────┬──────────────────────────────────────┘
                                │  线性 sRGB（引擎输出契约，编码只做一次）
┌───────────────────────────────▼──────────────────────────────────────┐
│  公共编辑（ColorRecipe）→ 单次 sRGB 编码（RawSrgbPass）→ 锐化 → HDR → 保存 │
└──────────────────────────────────────────────────────────────────────┘
```

证据：`RawEngineTonePass.kt:493-503`（`main()` 的 4 行顺序 + 注释
"Engine tone and adjustment passes have a linear-RGB output contract.
RawSrgbPass performs the single display encoding after all linear-domain adjustments are complete."）。

**关键工程量事实**：整个引擎插槽在 PC 侧只值**一次 fragment pass**。
它不接管 RAW 前端、PGTM、公共曝光、HDR、锐化、编码。这是"插槽"能被 9 个在役引擎共用的前提。

### 1.2 引擎接口契约（5 方法，`RawRenderingEngineToneAlgorithm.kt:17-58`）

| 方法 | 作用 | 行号 |
|---|---|---|
| `prewarm()` | 捕获前无标定也可先编译 shader（预热，避免首次出图卡顿） | `:29` |
| `render(input)` | 主渲染：绑 FBO → 绑资源 → draw → 返回输出纹理 | `:60-79` |
| `bindColorResources(prog, res)` | 引擎私有 uniform / 纹理绑定（纹理单元 2/3 给 HNCS） | `:408-420` |
| `renderHdrReference(input, gain, coord)` | HDR 参考：算 base curve 的增益比（单通道输出） | `:81-159` |
| `release()` | program + 引擎私有纹理释放 | `:422-437` |

**抽象基类持有 GLES 生命周期**（`:22-26`：`program` / `hdrReferenceProgram` / `hdrBaseCurveProgram`
/ `hdrBaseCurveTextureId` / `hdrBaseCurveFramebufferId`），子类**只提供 shader 定义 + 资源绑定**。
这是"引擎作者只需写色彩科学，不需要写 GL 样板"的分工。

引擎 shader 定义（`:9-15`）：

```kotlin
data class RawEngineToneShaderDefinition(
    val engineUniforms: String,      // 引擎私有 uniform 声明
    val engineFunctions: String,     // 引擎私有函数体（含 applyEngineTone）
    val profileUniforms: String = PROFILE_EXPOSURE_COMBINED_UNIFORMS,
    val profileFunctions: String = "",
    val includeAdobeProfilePipeline: Boolean = false,  // DCP 路径开关
)
```

`:342-505` 的 `combinedFragmentShader()` 把这些字符串**拼进**公共 shader 模板。
即：**引擎 = 一段可注入的 GLSL + 一份资源绑定 + 一份渲染计划**，不是"一个独立渲染器"。
这个设计对 Mali 极其友好 —— 公共部分（varying/uniform/精度声明/片元输出）只写一次，
不存在"每个引擎一份完整 shader"的编译期爆炸。

> ⚠️ **对本项目的直接映射**：本项目 shader 是 C++ raw string 常量（`kFs*`）+
> `tools/validate-shaders.sh` 提取交 glslang（`.zcode/memory/facts.md:29`）。
> "字符串拼接生成 shader"这条路本项目已有能力（`FrameRenderer.cpp` 14436 行里大量 `R"(...)"`），
> 但**必须**把拼接产物落盘再做 glslang 校验 —— 见 §2.4 失败策略。

> ⚠️ **重要事实修正（本次取证）**：10 号文档记的是 "10 个引擎"（其副本 `d584bc9`，含 Fuji）。
> 本文取证的 `b9cf590` 只有 **9 个** —— Fuji 已于 **`56d33aa`（2026-10-09，"refactor: remove Fuji film simulation"）移除**。
> 枚举条目数实测：`grep -c "^    [A-Z][A-Za-z]*($" RawRenderingEngine.kt` = **9**；
> `raw/` 目录下无 `Fuji*` 文件，`assets/` 下无 `fuji/` 目录。
> **它的 shaderId `9` 随之下线，但按"ID 永不复用"纪律，9 号不应再分配给新引擎**（`5` 号同理，历史遗留空缺）。
> 引擎会被移除 —— 这本身就是架构契约必须处理的情形，见 §1.8。

三个可直接抄的工程细节：

1. **shaderId 是持久化的**：0,1,2,3,4,6,7,8,10（+ 已下线的 9）—— **5 空缺不复用**。
   这是"枚举值一旦发布就不再变动"的纪律（`.zcode/memory/facts.md:36` 记本项目同样纪律：
   "[29] 空槽不复用"）。
2. **`fromPersistedName` 有旧名迁移映射**（`:92-99`）：
   `"HncsCcm"` / `"HncsLut"` → `Hncs`。旧的持久化字符串**永远**能被读回来。
3. **`workingColorSpace` 的语义被注释钉死**（`:30-32`、`:38-39`、`:45`）：
   Lumix/Canon/Leica 标 `SRGB` 是"输出/调整空间"而非"sRGB 编码域" ——
   这正是本项目 NN 链路踩过的坑（域错配 2px 能量爆 10×，`.zcode/memory/lessons.md`）。
   **注释不够，要有类型**（见 §2.2）。

### 1.4 资产组织与哈希校验

以 HNCS 为例（`HncsProfile.kt`，751 行）：

| 文件 | 字节 | 角色 |
|---|---|---|

**校验链**（`HncsProfile.kt:351-500`，全部 `require(...)`，失败即抛）：源文件 SHA-256（`:474`）
→ 编码 SHA-256（`:351`）→ magic（`:358`）→ schema 版本（`:359`）→ 表类型/companding/点数/码值上限
（`:368-371`）→ 源 float 的 FNV1a-64（`:372`）→ payload 解压字节数（`:482`）→ payload SHA-256（`:483`）
→ float 计数（`:489`）→ 每个区间 offset/count 边界（`:493-495`）→ 全表 finite（`:500`）
→ **单调性**（`:384` `require(value >= previous)`）→ 端点（`:390-391` 首=0、末=codeValueMax）。

**这一串校验的意义**：它保证"引擎输出的确是那个真实数据算出来的"，不是"看着像"。
10 号文档 §2.6 已提炼为"全程哈希校验 / 严格失败 / 真实数据约束 / 域标注显式化 / JVM 回归测试"。

### 1.5 失败策略

PC 的口径（10 号文档 §2.6 已提炼，此处给出**代码级证据**）：

- 白点/CCT 求不出、表缺失、校验不符 → `require` 抛异常（`EquivalentCameraCalibration.kt:50`、
  `:75`、`:82`；`HncsProfile.kt` 全篇）→ **拒绝渲染**，无默认 5000K 回退、无 identity 纹理伪装；
- `render()` 在 program 编译失败时 `return null`（`RawRenderingEngineToneAlgorithm.kt:62`）——
  **不画错误的图**；
- `bindEngineResources` 里 `requireNotNull(input.hncsRenderPlan)`（`HncsToneAlgorithm.kt:186-188`）
  —— 没有渲染计划就直接失败，不猜。

> **本项目适配建议（重要区分）**：PC 是 Kotlin/JVM，`require` 失败 = 一张照片不出图。
> 本项目的失败面更大：native + JNI + 启动路径。`.zcode/memory/facts.md:80` 记录过
> "只改 C++ kCount 忘改 Kotlin ⇒ 装包后启动即崩"。
> **建议分层**：引擎**内部**严格失败（绝不静默 identity）；引擎**外部**捕获 →
> 标记该引擎不可用 + UI 提示 + 日志字段 → 照片回落公共管线并在元数据标注引擎 ID。
> 即"严格失败"管的是**数据真实性**，不是"让 App 崩"。

### 1.6 引擎参数面 vs 本项目 FilmParams（**本文最关键的本项目风险点**）

PC 的引擎参数**不在一张全局数组里**：
- 引擎选择 = `RawRenderingEngine` 枚举（持久化为**字符串**，`fromPersistedName` 容错迁移）；
- 引擎私有参数 = 各 `*Profile` 持有的 `*RenderPlan`（数据类），随资产走；
- 引擎私有 uniform = `engineUniforms` 字符串 + `bindEngineResources` 逐项下发。

本项目相反：**单一扁平 `float` 数组 `FilmParams`，`kCount` 已从 36 → 43 → 48 → 56 → 59 → 60 → 78 → 88 → 96 → **98**（`FilmParams.h:35`，实读）。

```cpp
// core/engine/src/film/FilmParams.h:10-17（实读，逐字）
// 契约**四处**必须同步（ADR-1 铁律；漏一处 = 启动崩溃）：
//   ① 本常量；② Kotlin 侧 `CameraPresets.neutral()` 的 `DoubleArray(N)`；
//   ③ `fromDoubles` 的 `if (n > idx)` 解析防呆；④ 下发点
//   `CameraController.setFilmParams` 的长度兜底。
// v0.10.196 真实事故：只改了本常量（59→60），Kotlin 侧仍是 59 ⇒ 下发点写
// `filmParams[59]` 越界 ⇒ **装包后应用启动即崩**。改这里必须四处一起改。
static constexpr int kCount = 98;
```

**结论：引擎参数绝不能继续往 `FilmParams` 里塞。** 若 5 个引擎各带 10 个参数，
`kCount` 会奔向 150+，而"四处同步"的暴露面随槽位数线性增长，每次改动都是一次
潜在的启动崩溃。**方案见 §2.5。**

### 1.7 引擎切换的 UI 面（PC 形态，实读）

**可直接抄的三点**：

1. **引擎专属参数条件显示**（`:560`/`:607`）—— 引擎 A 的参数 UI 只在选中 A 时出现，
   这要求参数面**按引擎分组**，而不是塞进一张全局参数表。**与本项目 `FilmParams`
   扁平数组的冲突点就在这里**：扁平数组没有"参数属于哪个引擎"的概念。
2. **引擎角标出现在多个 UI 面**（转盘 / 预设管理 / 顶栏）—— 说明"引擎"是**一等公民**，
   不是某个深层设置项。
3. **持久化用字符串**（`fromPersistedName`），不是整数索引。

**⇒ 对本项目的 UI 含义**（阶段 3 的输入）：
`CameraPresets.kt` / `ParamControls.kt`（`facts.md:105` 记"参数表单一来源 = `ParamControls.kt`"，
2026-10-13 由 PS-3 从 `EditorScreen.kt` 逐字搬移）是引擎参数 UI 的落点；
引擎选择应新增**独立控件**，且**引擎专属参数不得进入全局滑杆表**
（`CAMERA_NO_SLIDER_SLOTS` / `CAMERA_TUNABLE_SLOT_PARAM` 是现有的"哪些槽位不进 UI"机制，
可作为"引擎参数不进全局表"的现成先例）。

### 1.8 引擎下线：真实成本样本（**本次调研最有价值的量化证据**）

`56d33aa`（2026-10-09，"refactor: remove Fuji film simulation"）的完整改动清单
（GitHub commits API 实查：**33 个文件**）：

**两个关键洞察**：

1. **`GalleryDatabase.kt` 是 +42 行**（不是删除）—— 新增了 `MIGRATION_49_50`：
   Room 数据库从 v49 → v50，为**移除一个列** `rawFujiFilmSimulation` 做**整表重建**
   （patch 原文注释："Android 11 SQLite requires a table rebuild to remove a column.
   Preserve all remaining values, column defaults, and indices."）——
   即用 `PRAGMA table_info` 读出全表定义 → 逐列重建（跳过被删列）→ 重建索引。
   **⇒ 引擎下线会触碰已存照片的数据库 schema。这是新增引擎时通常想不到的隐性成本。**
2. **持久化层是"三点对称删除"**：`MediaMetadata`（读照片元数据）、`CameraPresetJsonCodec`
   （读预设）、`UserPreferencesRepository`（读偏好）各有一行 `FujiFilmSimulation.fromPersistedValue(...)`。
   注意 `fromPersistedValue` 这个模式本身就是"未知值不崩"的兜底 ——
   但**删除枚举项**时这三处仍必须一起删（否则编译不过）。
   **⇒ 说明"引擎 ID 的读取点"必须是可枚举的清单，而不是散落各处。**

**⇒ 对架构契约的直接要求**（写进 §2）：

| 要求 | 理由 |
|---|---|
| 引擎注册表**集中在 1 个文件** | 现状已如此（`RawRenderingEngine.kt`），要保持 |
| UI / 持久化 / DB / 本地化 **由注册表驱动**，不逐引擎手写 | 9 个语言的字符串各删 3~4 行是纯机械劳动，可自动化 |
| 引擎 ID 的**读取点清单化**（一处 `enum` → 一处解析表） | 避免"删枚举要改 3 处持久化" |
| DB 侧**不存引擎私有列**，存 `engineId` + 参数 JSON | 否则每加/删一个引擎都要一次 Room 迁移（+42 行/次） |
| 引擎下线要有**迁移路径**（旧照片 → 回落公共管线 + 保留原始 engineId 供回溯） | 用户的老照片不能因为引擎下线就打不开 |

**新增引擎的成本对照（推算，未经实测）**：按同一 commit 的对称性，
新增一个引擎 ≈ **15–25 个文件**（资产 + 3 个实现文件 + 注册表 + 调度 + UI + 持久化 + 字符串 ×9），
**若引擎参数进 DB 列则为 30+ 文件 + 1 次 Room 迁移**。
这条推算支持 §2.5 的方案 B（引擎参数走独立 JSON 通道，不进 DB 列）。

### 2.2 域标注：从"注释"升级为"可校验的结构"

PC 用注释标域（`RawRenderingEngine.kt:30-32`）。本项目被域错配坑过
（`lessons.md`：域错配 2px 能量爆 10×），**注释不足以防复发**。建议：

```cpp
// 伪码（契约设计，非生产代码）
struct DomainTag {
  ColorSpace space;      // kLinearSRGB / kAWG4 / kProPhoto / kBT2020 / kHNCS / ...
  TransferFn transfer;   // kLinear / kLogC4 / kLogC3 / kPQ / kHLG / kSRGB_OETF
  EvAnchor   ev;         // kSceneRelative / kLogMidGray / kDisplayReferred
  float      whiteLuma;  // 该域"中性 1.0"对应的场景亮度（可选，用于 EV 换算）
};

struct EngineContract {
  std::string id;              // 稳定字符串 ID（"arri.logc4.awg4"，绝不复用）
  DomainTag   input_domain;    // 引擎期望的输入
  DomainTag   output_domain;   // 固定 = {kLinearSRGB, kLinear, kDisplayReferred}
  DomainTag   param_ev_domain; // 参数里 EV 类数值的解释域（Linear / Curve）
  AssetSet    assets;          // manifest + payload（见 §2.3）
};
```

**校验（离线 + 运行时可做的最小集）**：

| 校验项 | 判据 | 强度 |
|---|---|---|
| 域链往返 | `A→B→A` 逐点 \|Δ\| < 1e-6（float32 域） | 强（离线必做） |
| mat3 白点 | 矩阵 × 该域白点 = [1,1,1]（±1e-6） | 强 |
| mat3 条件数 | `cond(M) < 1e3`（超过即色域桥接不可信） | 中 |
| 中性轴 | 灰阶 R=G=B 输入 → 输出 R=G=B（look 可有意破坏，需显式声明） | 中 |
| 单调性 | 曲线表逐点 `v[i] >= v[i-1]`（PC `HncsProfile.kt:384` 同款） | 强 |
| 端点 | 曲线首末值 = 声明值（PC `:390-391` 同款） | 强 |
| 运行时域断言 | 引擎加载时校验 `input_domain` vs 公共管线当前域，不符**拒绝挂载** | 强 |

### 2.3 资产组织（建议目录 + manifest schema）

```text
app/src/main/assets/engines/<engine_id>/
  manifest.json          # 清单（唯一入口）
  <payload>.hcurve       # 曲线表（uint16 或 float32，带 magic）
  <payload>.clut         # 3D LUT（立方体或四面体索引，带 magic）
  calibration.json       # 等效相机 / 色域桥接矩阵
```

`manifest.json` 建议字段（对齐 PC `HncsProfile` 的校验链）：

| 字段 | 说明 | 必需 |
|---|---|---|
| `schemaVersion` | manifest 结构版本（不匹配即拒绝） | ✅ |
| `engineId` | 稳定字符串 ID | ✅ |
| `assets[]` | 每项：`file` / `role` / `sha256` / `bytes` / `magic` | ✅ |
| `sources[]` | 每项：`origin`（官方包名+版本+URL）/ `sha256` / `retrieved`（日期） | ✅ |
| `generator` | 生成脚本路径 + `sha256`（离线烘焙链可复算） | ✅ |
| `domains` | `input` / `output` / `paramEv`（§2.2 的 DomainTag 序列化） | ✅ |
| `license` | `redistributable`（bool）/ `terms_ref`（条款链接或本地文件名） | ✅ |
| `validation` | 离线校验结果摘要（往返残差、单调性、白点） | 建议 |

**为什么 `sources` 和 `generator` 是必需**：这是"可离线复算"的前置条件。
本项目惯例是"可离线复算 + 真机 A/B + 数值判据"，若 manifest 不记录源哈希与生成脚本，
半年后的复算无法证明"资产还是那份资产"。

### 2.4 失败策略（本项目版）

| 场景 | 行为 | 依据 |
|---|---|---|
| manifest 缺失 / schema 不符 | 引擎 **unavailable**，UI 灰显 + 原因码 | PC `require` 语义的本项目适配 |
| 任一资产 SHA-256 不符 | 同上；**绝不**用 other-version 资产顶替 | PC `HncsProfile.kt:351` |
| 曲线非单调 / 端点不符 | 同上 | PC `:384`、`:390-391` |
| 域断言失败 | 同上 | 本项目新增（PC 无显式断言） |
| shader 编译/链接失败 | 引擎 unavailable；**必须**写日志字段（如 `engOk=0`） | `lessons.md`：`prog_ != 0` 先查 + 诊断三字段 |
| 引擎渲染中途失败 | 本次出图回落公共管线；元数据标注 `engine=fallback:<id>` | 本项目新增 |
| 离线校验残差超标 | **不上线**该引擎（CI/脚本门禁） | 本项目惯例 |

> **glslang 门禁的强制项**：本项目 shader 拼接若引入引擎片段，
> `tools/validate-shaders.sh` 必须能提取**拼接后的完整 shader**（含引擎片段）过 glslang。
> 现有脚本从 `FrameRenderer.cpp` 的 `R"(...)"` 提取（`facts.md:29`），
> 拼接路径需要额外产出一份"展开后的 shader 快照"供校验 —— 否则回到
> "Mali 静默编译失败 ⇒ 整链不生效"的老坑（`lessons.md`，v0.10.196/197 两连坑）。

### 2.5 FilmParams 扩展：不破坏兼容的方案

**现状（实读）**：`kCount = 98`，四处同步铁律，历史事故一次（v0.10.196 启动崩溃）。
槽位已被 E4-1/E2-2/E2-11/SG-1 等多个特性批次占满（`FilmParams.h:19-34` 的沿革注释）。

**三个方案**：

| 方案 | 做法 | 代价 | 兼容性 | 评价 |
|---|---|---|---|---|
| **A. 继续扁平扩展** | 引擎参数直接加 `[98..N]` | 每引擎 +5~15 槽；`kCount` 奔 150+ | 需要四处同步 × N 次 | ❌ 不可持续（暴露面线性增长） |
| **B. 独立参数通道（推荐）** | `FilmParams` 只留**一个**槽 `[98] engine_slot`；引擎私有参数走**独立 JNI 通道**（JSON / KV） | JNI 签名扩展 1 处；Kotlin 侧新增序列化；prefs 新增一个 JSON 字符串 | 老预设（长度 98）→ `engine_slot` 缺省 = 0 → 走现有链路 → **逐位一致** | ✅ 推荐 |
| **C. 全量 JSON 化** | `FilmParams` 整体替换为 JSON | 全部 98 槽读写路径重写；性能（每帧解析）风险 | 需要全量迁移 + 双读期 | ⚠️ 收益不足（YAGNI） |

**方案 B 的契约草案**（伪码）：

```cpp
// FilmParams.h —— 只加 1 个槽
static constexpr int kCount = 99;   // +[98] engine_slot（0 = 现有 native 引擎）
float engine_slot = 0.0f;           // 98: 0=公共管线（现状）; 1..N=注册的引擎索引

// 独立通道（新增 JNI，不进 FilmParams）
// Java: com.filmkit.app.EngineBridge.setEngineParams(String json)
// 形如：{"engineId":"arri.logc4.awg4","params":{"look":"k1s1","intensity":0.7}}
struct EngineParams {
  std::string engine_id;                    // 稳定字符串，与 manifest 对齐
  std::vector<std::pair<std::string,float>> params;  // 有序 KV（可复算、可 diff）
};
```

**为什么 `engine_id` 用字符串而不是整数**：PC `fromPersistedName` 的存在证明了
"整数索引会随枚举增删漂移，字符串不会"。整数字段只在 `FilmParams[98]` 里做
"快速槽位选择"，真值仍以字符串为准（`[98]` 与 JSON 不一致时以 JSON 为准并告警）。

**为什么参数用有序 KV 而不是 `map<string,float>` 无序**：本项目"可离线复算"要求
参数序列化**字节稳定**（同参数两次渲染 CRC32 逐字节等价，`facts.md:102` 的判据口径）。

**预设迁移路径**：
1. 老预设（无 `engine_slot`）→ 缺省 0 → 现状链路 → **零回归**（可用现有 CRC32 判据证明）；
2. 新预设写 `engine_slot` + `engineParams` JSON，**同时**保留扁平数组（双写期）；
3. 双写期结束（建议 ≥2 个版本）后，扁平数组只留公共参数。

**已知实测（`.zcode/memory/facts.md`）**：

- `hr_wavelet` 曾占 **≈752 MB 纹理 + ≈103 全分辨率 pass/张**（`:45`，已默认关，模块保留）；
- P3 拆双 pass 的 3a 输出纹理 `tex_rcd_a_` = **+100 MB RGBA16F**（`:45`，即 1 张全分辨率 RGBA16F）；
- 连拍（独立渲染线程）峰值 **+455 MB**、常驻 **+1.96 GB**（`:102`）；
- `rcdAMs+rcdBs` 实测 **15~61 ms**（3 pass 量级）。

**带宽推算（量级估算，非实测）**：一个全分辨率 RGBA16F pass 的
"读 1 + 写 1" = 200.6 MB。若按 103 pass 计 ⇒ **≈20.7 GB/张**。
手机 LPDDR5X 的有效带宽（多 IP 共享）量级 40 GB/s ⇒ **≈0.5 s**。
这与"752 MB 纹理"、"连拍常驻 1.96 GB"的观测量级自洽。
**⇒ 本项目后链的瓶颈是"pass 数 × 全分辨率中间缓冲"，不是 API 开销。**

### 3.2 Vulkan compute vs 现有 GLES

**GLES 侧已付的代价（`lessons.md` GL/Mali 段，全部真机实锤）**：

| 坑 | 后果 | Vulkan 是否结构性解决 |
|---|---|---|
| `imageStore` 目标必须 `glTexStorage2D`（`glTexImage2D` 写入全丢） | 一次全黑级返工 | ✅ **是**（Vulkan 无 immutable/mutable 之分，`VkImage` 创建即固定） |
| `r16f/rgba16f` image 禁 load+store 混用 | 需要额外 ping-pong | ⚠️ 部分（格式能力需查 `VkImageFormatProperties`，但至少**可查询**而非静默失败） |
| `image2DArray` "计算照跑写入全丢" | 同上 | ✅ 是 |
| Mali 拒绝混链 GLSL 版本（vs 300 es + fs 310 es） | init 失败整链黑屏 | ✅ 是（SPIR-V 单 IR，无版本链概念） |
| glslang ES profile 的 image 格式只放行 `r32f`（校验盲区） | 校验通过真机失败 | ✅ 是（SPIR-V 校验更严，`VK_LAYER_KHRONOS_validation`） |
| image uniform 无默认精度 ⇒ 必须显式 highp | 静默错值 | ✅ 是（SPIR-V 无精度声明概念） |
| 同 context 销毁重建 `FrameRenderer` ⇒ Mali 分配失败 | 需连 context 一起销毁 | ⚠️ 部分（Vulkan 内存由应用管，但**责任也转移到应用**） |
| Mali 不在 context 间轮转命令流 | 分片/sleep/线程降优先级全部无效 | ⚠️ 未知（**未验证**，Mali Vulkan 调度行为需实测） |

**Vulkan 的真实收益（按对本项目痛点的贡献排序）**：

| 收益 | 机制 | 对本项目的量化影响 | 依据 |
|---|---|---|---|
| **显式内存别名** | `VkImage` + `VkDeviceMemory` 可由应用复用；`VK_KHR_image_aliasing` / 手动绑定 | 直接打 752 MB / +455 MB 峰值 —— 中间缓冲**生命周期不重叠即可共享内存** | 本项目纹理痛点为主 |
| **Input attachment / subpass** | tile-based 上片内读，不落主存 | 相邻 pass 融合可省一次全分辨率往返 = **200 MB/pass** | Vulkan 核心特性 |
| **Specialization constants** | 编译期常量特化 | 63 个 program 可缩为少数模板 + 特化（编译期与运行期开销双降） | Vulkan 核心特性 |
| **Descriptor indexing（`VK_EXT_descriptor_indexing`）** | bindless 纹理数组 | 引擎热插拔时不用重编 program（**bindless = 插槽的天然载体**） | 扩展存在（Khronos registry） |
| **subgroup 操作** | `VK_KHR_shader_subgroup_*`（ballot/vote/rotate/extended types） | 归约类 pass（直方图、统计、min/max）显著简化 | 扩展存在 |
| **cooperative matrix** | `VK_KHR_cooperative_matrix`（ARM 是贡献者之一） | **NN 引擎（HDRNet 类）的推理加速**；通用 ISP 无收益 | 见下 |
| **async compute queue** | 独立队列与 graphics 重叠 | 收益取决于 Mali 是否真正并行（**未验证**） | — |

**cooperative matrix 的取证结论（Khronos 一手）**：
`VK_KHR_cooperative_matrix`（[规范](https://raw.githubusercontent.com/KhronosGroup/Vulkan-Docs/main/appendices/VK_KHR_cooperative_matrix.adoc)，实抓）
—— "Cooperative matrix types are medium-sized matrices ... primarily supported in compute shaders,
where the storage for the matrix is spread across all invocations in some scope (usually a subgroup)
and those invocations cooperate to efficiently perform matrix multiplies."
**贡献者含 `Kevin Petit, Arm Ltd.`**（同文件 `Contributors` 段）。
ARM 另有 `VK_ARM_cooperative_matrix_layouts`（16 个 `VK_ARM_*` 扩展之一，实查 Vulkan-Docs `appendices/`）。
**⇒ cooperative matrix 在 ARM 生态是"有官方参与的标准路径"，但 Mali 具体型号的支持矩阵未取证（见 §7）。**

**迁移代价（必须如实标注）**：

| 项 | 规模 | 口径 |
|---|---|---|
| 重写量 | 14436 行 `FrameRenderer.cpp` + 1427 行头 | 实读 |
| shader 迁移 | 63 个 program → SPIR-V（GLSL→SPIR-V 可用 glslang，但**语义差异需逐个核对**：`texelFetch` / `imageStore` / 精度 / barrier 语义） | 实读 + 推断 |
| draw 路径 | 67 处 `glDrawArrays` → `vkCmdDraw` + pipeline/descriptor 管理 | 实读 |
| EGL → Vulkan | `EglCore.cpp`（display/context/surface 复用模型）整体重写 + swapchain 管理 | 实读 |
| Camera2 路径 | `ImageReader` → `AHardwareBuffer` → `VkImage`（`VK_ANDROID_external_memory_android_hardware_buffer`） | 推断（**未验证**） |
| 双后端维护 | 若保留 GLES 后备（vivo X300 专项，但崩溃面不允许无退路）⇒ **两套渲染器长期共存** | 风险 |

**结论（§3.5 汇总）**：Vulkan 的收益是**结构性**的（内存别名 / subpass），但它的代价是
**全量重写 + 双后端维护**。本项目的当务之急（黑白点反复手调）**不是** API 层级问题 ——
把 Vulkan 当"引擎数量 ≥5 或 NN 引擎上马"时的期权，是更优的资源配置。

### 3.4 "GPU-driven ISP" 现代做法

| 做法 | 机制 | 对本项目的适用性 |
|---|---|---|
| **Persistent threads / persistent kernel** | 一次 dispatch 常驻，work queue 分发 | 减少 dispatch 开销。本项目 67 个 draw 点、单张 2–3 s（`facts.md:102` 实测 2091–3336 ms），dispatch 开销**不是**瓶颈 ⇒ ❌ 收益低 |
| **Tile-based 显式控制** | `VK_EXT_shader_tile_image`（读 tile 内存）、`VK_QCOM_tile_shading` / `VK_QCOM_tile_properties` | Mali 是 TBR，但这两个扩展是 **Qualcomm 专属**；ARM 侧只有 `VK_ARM_render_pass_striped`（另有 `VK_ARM_performance_counters_by_region`）。**Mali 上的显式 tile 控制手段未取证**（§7） |
| **Subpass / input attachment（PLI）** | tile 内相邻 pass 融合，不落主存 | ✅ **最高性价比**：本项目相邻半分辨率/全分辨率 pass 多，融合可省整轮往返。**但 GLES 2.0+ 也有 `EXT_shader_pixel_local_storage`（`lessons.md` 未见使用记录）—— 待评估** |
| **Async compute** | 计算与图形队列重叠 | ⚠️ Mali 上的真实并行度 **未验证**；且本项目后链是"计算密集型串行链"，重叠空间有限 |
| **Compute-only 管线**（放弃 fragment） | 全 compute + storage image | 本项目已有 1 处 `glDispatchCompute`（色差中值/PC3D 类）；全 compute 化的收益主要是"可显式控制 workgroup 与 barrier"，代价是失去 TBR 的片上带宽优势 ⇒ ⚠️ 需实测 |

> **对 3.4 的整体判断**：本项目瓶颈是**内存带宽 + pass 数**，
> 真正的解法是**减少全分辨率中间缓冲的往返次数**（融合 pass / 降分辨率 / 别名复用），
> 这与用哪个 API 关系不大 —— 但在 GLES 里做"别名复用"几乎不可能（驱动管内存），
> 在 Vulkan 里是应用的责任与自由。**这是 Vulkan 唯一不可替代的收益。**

### 3.5 执行框架建议（结论）

```text
                    ┌────── 现在做（阶段 1–3）──────┐
留用 GLES 3.x ──────┤ 引擎插槽（架构收益最大）        │
（63 program / 67 点）│ 域标注 + 资产校验（§2）        │
                    │ pass 融合 / 中间缓冲复用（GLES 内可做的部分）│
                    └──────────────────────────────┘
                    ┌────── 期权（触发条件明确）──────┐
迁 Vulkan ──────────┤ 触发 A：引擎数 ≥5，bindless 收益 > 迁移成本 │
                    │ 触发 B：NN 引擎上马，需 cooperative matrix │
                    │ 触发 C：显存/峰值再次成为硬阻塞（>1 GB）    │
                    └──────────────────────────────┘
                    ┌────── 旁路（不进引擎）──────┐
Halide ─────────────┤ 离线烘焙 / 原型 / 复算对照   │
                    └────────────────────────────┘
```

**"不迁 Vulkan"的代价也要如实标注**：不做内存别名，本项目就持续背着
"每张全分辨率中间缓冲 100 MB × N" 的成本；`hr_wavelet` 那种 752 MB 的模块
未来仍会周期性出现。**这是用户可拍的板**（AGENTS.md：性能取舍必须实测，
不许拍脑袋替用户做决定）。

### 4.2 ACES 2.0：CTL / CLF 能否直接进引擎

**取证（一手）**：

- `ampas/aces-dev` 已更名为 **`aces-aswf/aces-core`**（README 实抓：
  "This repository was named `aces-dev` in versions of ACES prior to the 2.0 release"）；
- 仓库结构（GitHub contents API 实查）：只有 `README.md` / `LICENSE` / `CHANGELOG.md` / `lib/`，
  而 `lib/` 下只有 **5 个 CTL 文件**：
  `Lib.Academy.ColorSpaces.ctl`、`Lib.Academy.DisplayEncoding.ctl`、
  `Lib.Academy.OutputTransform.ctl`、`Lib.Academy.Tonescale.ctl`、`Lib.Academy.Utilities.ctl`；
- License：**Apache-2.0**（README 实抓）—— **可再分发**（这是相对 ARRI look 资产的关键优势）；
- CTL 语言：C 风格、`float`/`half`、有 `min/max/pow/log10`，**不能直接被 GLSL 消费**；
  需要离线翻译或手写等价实现（对照 CTL 逐行）。

**CLF（Common LUT Format）**：

- OCIO 2.6 支持 **SMPTE ST 2136-1 CLF** 读写；SMPTE 版本与 Academy/ASC CLF v3 高度相似
  （release notes 原文："very similar to version 3 of the Academy/ASC CLF specification.
  The main changes are a slightly different header and stricter requirements about ordering"），
  OCIO 写出的文件同时带 `compCLFversion="3"` 和 `xmlns="http://www.smpte-ra.org/ns/2136-1/2024"`；
- CLF 是 **XML + 浮点能力**，比多数厂商 LUT 格式更强。

**"值不值得做运行时 CLF 解释器"—— 建议：不值得。** 理由：

| 论点 | 说明 |
|---|---|
| 解释器 = 重实现 OCIO 的一半 | CLF 的算子集（LUT1D/LUT3D/Matrix/Log/Range/Exponent/ACES 各类）需要"解析 → 图求值 → GPU shader 代码生成"三段，等价于 `GpuShaderUtils.cpp`（43 KB）+ `GpuShader.cpp`（22 KB）的工作量 |
| 运行时成本 | XML 解析（Android 上 expat/pugixml 另加依赖）+ 图求值 + shader 生成，全部发生在**用户等待出图的路径上** |
| 收益可被离线覆盖 | 引擎资产是**固定的、随包发布的**，不是用户每次导入的。离线烘焙一次 → 运行时只做 LUT 采样 + 曲线查表，**零解析、零图求值** |
| 唯一例外 | **用户导入的 CLF 文件**（如未来支持"用户拖入一个 .clf 当 look"）—— 但那时更好的选择是**离线/首次导入时烘焙成 LUT 缓存**，而不是每次渲染解释 |

**⇒ 建议的运行时架构**：**"烘焙后 LUT + 曲线表 + 严格域标注"**，
CLF/CTL/OCIO config 全部停在离线侧。

### 4.3 色彩管理取舍建议（汇总）

| 选项 | 运行时嵌入 | 离线使用 | 建议 |
|---|---|---|---|
| OCIO 运行时库 | 体积/依赖/非官方平台风险 | — | ❌ 不嵌 |
| OCIO 离线（Python/CLI） | — | 域链校验 + 烘焙 + 格式转换 | ✅ **必做**（CI 门禁） |

### 5.2 引擎版本演进与下线：不破坏旧预设（六条铁律）

| 铁律 | 做法 | 一手依据 |
|---|---|---|
| **ID 只增不改** | 引擎 ID 用稳定字符串，发布后**永不复用**；枚举整数值也不复用（PC 的 5/9 空缺） | `RawRenderingEngine.kt:10-74` |
| **旧名永久可读** | `fromPersistedName` 保留历史别名映射 | `RawRenderingEngine.kt:92-99` |
| **参数带版本** | 引擎参数 KV 里带 `paramSchema`；老预设缺字段 → 取该引擎的"无效果默认值"（不是 0） | 本项目惯例：`FilmParams.h:27-33`（"`[95] = 0` = **整链旁路**（零 pass、零纹理、零成本）"） |

**再加两条本项目特有的**：

**铁律 4：引擎下线必须留迁移路径**（§1.8 实证：Fuji 下线改了 33 个文件 + 一次 DB 迁移）。
具体：
- 引擎 ID 的**读取点集中在一张解析表**（不散落在 `MediaMetadata` / `CameraPresetJsonCodec` /
  `UserPreferencesRepository` 三处各自调用 `fromPersistedValue`）；
- 旧数据里出现**未知 engineId** → 不崩、不静默改值：回落公共管线渲染，
  并在元数据里**保留原始 engineId**（供未来引擎回归时复用）；
- **引擎私有参数不进 DB 列**（现以 `rawFujiFilmSimulation` 这类列存在），
  改为 `engineId` + 参数 JSON 两列 —— 这样未来加删引擎**零 schema 迁移**。

**铁律 5：引擎下线时，已存照片的渲染结果必须可解释**。
若某张照片曾用引擎 A 渲染并保存，A 下线后重新渲染会得到不同结果 ——
这必须在 UI 上说明（"该照片使用的引擎已不可用，以下为公共管线结果"），
而不是静默换一个链重新出图（用户会以为渲染坏了）。

**铁律 6：引擎升级若改变输出 → 旧预设必须能"钉住旧版本"**。
做法：预设里记 `engineId` + `engineVersion`；引擎资产 manifest 保留历史版本的 SHA-256。
升级后旧预设默认走新版本，但提供"按当时的版本重渲"的能力（资产多版本共存的代价 = 资产体积 × 版本数，
如 HNCS 672 KB/版本，可接受）。

## 6. 落地路线图

以"插入一个新引擎"（ARRI / AgX / HDRNet 任一类）为对象。
每阶段给**验收判据**（口径 = 本项目惯例：可离线复算 + 真机 A/B + 数值判据）。

### 阶段 0：契约与基线（**前置，不写引擎**）

| 交付 | 内容 |
|---|---|
| 引擎契约头 | `EngineContract`（§2.2）+ `EngineParams` 通道（§2.5）+ manifest schema（§2.3） |
| 域标注与断言 | 域链往返校验器（离线）+ 运行时域断言 |
| 基线快照 | 现状链路的**逐位基线**（同一 RAW 的成片 CRC32 + 关键统计） |

**验收判据**：
1. `FilmParams` 只增 1 槽（`[98] engine_slot`），老预设路径 **CRC32 逐字节等价**（对齐 `facts.md:102` 的判据口径）；
2. 域链往返校验器对现有 CCM/影调链跑通，`A→B→A` 残差 < 1e-6；
3. 基线快照入库（可复算脚本 + 期望值）。

### 阶段 1：离线正确性（**不进引擎**）

对本项目样张 DNG 走完整离线链（Python），实现目标引擎的色彩科学，
与**官方工具**（ARRI Reference Tool / Resolve 用同一 LUT；或 aces-core CTL 的参考实现）对照。

**验收判据**：
1. **逐点复算**：自实现曲线 vs 官方 LUT/CTL，全表 `max|Δ| < 1e-6`（ARRI 白皮书公式）或
   `max|Δ| < 1 LSB`（官方 LUT 的量化域）；
2. **域链正确性**：与 OCIO 的同一变换对照，`ΔE2000` 中位数 < 0.5 / p99.9 < 2.0（显示域）；
3. **死白起点 EV**：出图到达 255 的输入 EV，与官方参考的差 < 0.1 EV；
4. **高光层次预算**：死白前 1 EV 内的可辨 LSB 数 ≥ 官方参考的 90%；
5. 离线脚本入库，可一键复算（含 manifest 的源 SHA-256 校验）。

### 阶段 2：引擎内挂载（**单引擎，公共管线不动**）

把阶段 1 的产物以**最小侵入**接进现有链：
新增 1 个 pass（`kFsEngineTone` 类），输入 = 现有链的引擎输入域，输出 = 线性 sRGB；
资产走新目录 + manifest 校验；`FilmParams[98] = 1` 启用。

**验收判据**：
1. **零回归**：`[98] = 0` 时成片与阶段 0 基线 **CRC32 逐字节等价**；
2. **离线↔真机一致**：真机成片 vs 离线链出图，`ΔE2000` 中位数 < 1.0（考虑 GPU 精度与量化）；
3. **资产校验生效**：篡改任一资产 1 字节 → 引擎 unavailable + 日志原因码，**不出现**错误出图；
4. **shader 门禁**：拼接后的完整 shader 过 `tools/validate-shaders.sh`，且**真机日志**确认 program 链接成功
   （对齐 `lessons.md` "先查 `prog_ != 0` + 诊断三字段"）；
5. **成本实测**（不是估算）：该 pass 的耗时（ms）+ 新增纹理字节数（MB）+ 峰值显存增量，
   写入 facts 供后续拍板；
6. **真机 A/B**：同场景 A/B 出图，人工确认 + 数值判据（不能只看数值 —— `facts.md:83`
   记录过"离线指标与真机观感严重背离"）。

### 阶段 3：独立引擎化（**多引擎 + 切换 UI**）

补齐：第二/第三个引擎、`engineId` 持久化与迁移映射、切换 UI（对齐 `CameraTopSheet` 的
`RawRenderingEngineSettingsPanel` 模式，`CameraTopSheet.kt:519`）、引擎 unavailable 的 UI 表达、
预设兼容（§5.2 三铁律）。

**验收判据**：
1. **切换**：任意两引擎互切，产物**无串扰**（引擎 A 的参数不影响引擎 B 的输出）；
2. **预设兼容**：阶段 0 的老预设在新版本上打开 → 出图 CRC32 与阶段 0 基线等价；
3. **引擎不可用**：删除任一引擎资产 → 其余引擎正常工作 + 该引擎 UI 灰显 + 明确原因；
4. **资产体积**：APK 增量实测（MB），与估算（§1.4：单引擎 0.5–9 MB）对照；
5. **回归矩阵**：N 个引擎 × M 个预设 × K 个场景的成片清单 + CRC32，一次跑完（可离线复算）；
6. **决策点**：此时用实测数据回答"要不要迁 Vulkan"（§3.5 的触发条件 A/B/C）。

### 阶段划分的依赖图

```text
阶段 0（契约/基线）
   └─→ 阶段 1（离线正确性）──┐
                              ├─→ 阶段 2（引擎内挂载）──→ 阶段 3（独立引擎化）
       资产获取（合规 §5）────┘                              │
                                                       └─→ 【期权】Vulkan 评估
```

## 附 B：术语对照

| 术语 | 含义 |
|---|---|
| 引擎插槽 / tone pass | 公共管线中唯一由引擎接管的一个 pass |
| 等效相机 | 把手机 RAW 变换到目标相机传感器色彩域的线性 3×3 矩阵 |
| 域标注（DomainTag） | 显式声明"这段数据在什么色彩空间 + 什么传递函数 + 什么 EV 锚" |
| PLI | Pixel Local Storage / Input Attachment，tile 内相邻 pass 不落主存 |
| 别名（aliasing） | 同一块显存被多个生命周期不重叠的资源复用 |
| 死白起点 EV | 输出到达 255 所需的最小输入 EV（本项目影调判据） |
| 层次预算 LSB | 死白前单位 EV 内可分辨的量化级数（本项目影调判据） |
