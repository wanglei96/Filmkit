# Spektrafilm：JPEG/R 保存长尾复核

2026-11-25，vivo V2509A。复核 [0.14.52 当轮实拍](spektrafilm-app-cam16-20261125.md) 的两个异常：Provia 进入保存队列早 147 ms，但保存阶段由 505 增至 1,197 ms；用户移动手机时能感觉到轻微取景卡顿。这是两个时间窗口，不应归为同一个光谱问题。

## 固定输入真机对照

使用已安装 Release DEX，切换 0.14.51／0.14.52 的 ARM64 库；每条路线固定同一 3072×4080 RGBA、HDR 增益图和 EXIF，保持 Q100 4:4:4。ABBA 每组 13 次，两条路线共 104 次，以下中位数剔除每组首次（96 个热样本）；线程 Java priority 4，观测 nice 10，起止 Thermal Status 0。

| 路线 | JPEG/R 编码墙钟，旧 → 新 | 调用线程 CPU，旧 → 新 |
|---|---:|---:|
| Gold 200 / Endura | 140.0 → 140.3 ms | 138.0 → 138.6 ms |
| Provia 100F 直扫 | 133.1 → 129.2 ms | 131.4 → 127.7 ms |

全部编码最大 155.5 ms，墙钟减调用线程 CPU 最大 7.6 ms，编码窗口未观测到 GC。每条路线的输出 SHA-256 都一致，Android 解码保留 HDR 增益图。临时文件写入中位约 8–9 ms；回放不经过 MediaStore，不能用于解释其发布延迟。

## 实拍长尾和取景

- 11 月 23–25 日从设备历史日志筛选 36 张全尺寸 Q100 4:4:4 JPEG/R、内嵌 EXIF 实拍。编码中位 148 ms（104–755 ms），MediaStore 发布中位 235.5 ms（35–764 ms），写入中位 30.5 ms（20–53 ms）。0.14.52 之前已出现 600–700 ms 级编码尾部。
- 只读核查四张实拍 JPEG。慢的 Provia 底图 DQT/DHT 与已知 turbo 输出一致、与现有 stb 回退不同，不支持「底图走了回退」。日志没有记录对应编码区间的显式 App GC；不能由此排除全部等待。固定输入未复现 659 ms，不支持把单张慢样本判为 JPEG/R 算法回归，慢因未定。
- Provia 后续处理窗口的最长交付间隔约 326 ms：本帧原生 draw 295.1 ms，当前帧直方图读回 292.8 ms，交换缓冲约 0.3 ms。它在快门后 1.923 s，RAW `chain` 已进入而光谱尚未开始；读回墙钟可能包含前序 GPU 工作。Gold 的 345 ms 窗口里纹理时间戳间隔峰值 200 ms，提交耗时峰值 53 ms，聚合峰值不保证来自同一帧。四张快门初期约 369 ms 的纹理间隔也单独记账。

## 诊断变更

`CameraController` 增加保存队列等待和准备、编码、媒体库各步骤的调用线程 CPU 计时。`RenderClient` 在拍照期间增加 ≥150 ms 单次回调／交付间隔的关联日志。没有改优先级、保存顺序、预览行为或成像。ARM64/x86_64 Release 打包任务和 Release JVM 测试通过；该诊断构建未签名、未安装。
