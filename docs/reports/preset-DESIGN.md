# FilmKit 预设（Preset）设计方案 v3

> 架构师 2026-10-11 ｜ 状态：**待用户审阅**（未派实现卡）
> 前置文档：`editor-preset-RESEARCH.md`（791 行调研，已交付但**未向用户汇报过**）、
> `editor-ADR.md` ADR-19 v2、`editor-E4-film-params-DESIGN.md` §4。
>
> **v3 相对 v2（ADR-19）的修订原因**（用户 2026-10-11 指出的三个偏差）：
> 1. **预设被做进了编辑器**（E3-1a/E3-1c 已实现），而用户要的是**拍照界面**的预设为主；
> 2. 查看页「**胶片**」面板（在「编辑」旁边）应与**拍照界面的预设同源同步**；
> 3. **胶片 / 颗粒功能没做** ⇒ 预设里最核心的"胶片质感"目前是空壳，必须先补引擎。

---

## 0. 一句话定位

**预设 = 一份"可命名、可分组、可分享的胶片风格配方"，一处定义、三处使用：拍照时套用（烘焙进成片）、查看页套用（对已有照片）、编辑器套用（后期微调）。**

对标物 = **darktable `styles`（整图风格）+ Fuji X Weekly 的机内 recipe（拍摄前配方）**，
**不是** PC（PhotonCamera）—— 它根本没有预设功能，只有"整包设置备份/恢复"（调研 §2.1）。

---

## 1. ★ 一条预设包含哪些配置（本方案的核心）

分五层。**"配置"= 用户能感知的一条预设里的内容**；括号内是引擎槽位号（`FilmParams.h`）。

### 第 1 层 · 元数据（不进引擎，纯描述）

| 字段 | 例 | 说明 |
|---|---|---|
| 名称 `name` | `CineStill 800T` | 用户可改 |
| 分组 `group` | `胶片` / `我的` / `人像` | 面板里按分组切换 |
| 分类 `category` | `CineStill` / `柯达` | 内置包按品牌（复用 `LutLibrary` 的分类） |
| 说明 `note` | "Vision3 500T 去 remjet，光晕是标志" | 列表里一行小字 |
| 收藏 `favorite` | ★ | 置顶 |
| 来源 `source` | `builtin` / `user` / `imported` | 内置只读，不可删 |
| `id` / `createdAt` / `schema` | — | 稳定 id（重命名不改）、创建时间、**格式版本**（槽位语义漂移时靠它迁移） |

### 第 2 层 · 色彩与影调（**拍照 + 后期都生效**）

| 组 | 参数 | 槽位 | 量程 | 状态 |
|---|---|---|---|---|
| 曝光 | 曝光补偿 | `[0]` | −3…+3 EV | ✅ |
| 白平衡 | R / G / B 增益 | `[1..3]` | 0.5…2.0 | ✅ |
| 影调 | 对比度 | `[4]` | **0.01…2.0**（`CONTRAST_UI_RANGE`；1.0 = 恒等） | ✅ 两侧都生效（U-3 接线拍照侧） |
| 影调 | **肩部** latitude R/G/B | `[5..7]` | 0…1 | ✅ 引擎已接线（E4-4）· **仅拍照链路** |
| 影调 | **趾部** latitude R/G/B | `[8..10]` | 0…1 | ✅ 引擎已接线（E4-4）· **仅拍照链路** |
| 影调 | 基准影调强度 | `[28]` | 0…1 | ✅ |
| 影调 | filmic 黑点 / 白点 | `[37][38]` | EV | ✅ |
| 色彩 | 分区饱和（暗 / 中 / 高） | `[20..22]` | 0…2 | ✅ |
| 色彩 | 分离色调（暖 / 冷） | `[23][24]` | −1…1 | ✅ |
| 色彩 | **单色（黑白）** | `[25]` | 0/1 | ✅ |
| 层间 | 暗部 R/G/B 增益 | `[69..71]` | 0.5…1.5 | ⚠ 引擎待做（E4-6） |
| 层间 | 中间调 R/G/B 增益 | `[72..74]` | 0.5…1.5 | ⚠ 引擎待做（E4-6） |
| 层间 | 高光 R/G/B 增益 | `[75..77]` | 0.5…1.5 | ⚠ 引擎待做（E4-6） |

> **层间效应 = 胶片"三层乳剂互相抑制"的物理量**（Kodak 高光偏暖 / Fuji 冷高光的机制）。
> 9 个槽位是超集：三区设成同值即退化为"全局 RGB 增益"，R/G/B 同值即退化为"纯亮度分区"。

### 第 3 层 · 胶片质感（**拍照 + 后期都生效** —— 用户点名的"胶片功能"）

| 组 | 参数 | 槽位 | 量程 | 状态 |
|---|---|---|---|---|
| **颗粒** | 强度 | `[26]` | 0…100 % | 🔧 **引擎重写中**（E4-3 已派卡） |
| **颗粒** | 尺寸 | `[27]` | 20…6400 ISO | 🔧 同上 |
| **颗粒** | 中间调偏置 | `[60]` | 0…100 | 🔧 同上 |
| **颗粒** | 枢轴（峰值移向暗部） | `[61]` | 0…1 | 🔧 同上 |
| **光晕** | 强度 | `[62]` | 0…1 | ❌ 未实现（E4-5，最重） |
| **光晕** | 触发阈值 | `[63]` | 0…1 | ❌ 同上 |
| **光晕** | 半径 | `[64]` | 0…1 | ❌ 同上 |
| **光晕** | 暖度（红橙） | `[65]` | 0…1 | ❌ 同上 |
| **暗角** | 强度 | `[66]` | −1…0 | ✅ 已实现（E4-2） |
| **暗角** | 半径 | `[67]` | 0…200 % | ✅ |
| **暗角** | 羽化 | `[68]` | 0…200 % | ✅ |

> 颗粒的算法规格已定案（对齐 darktable `grain.c`：3 八度 simplex + 相纸响应 LUT + ISO 尺寸），
> 且**修掉三个现存缺陷**：尺寸语义倒置（现在"数字越大颗粒越细"）、噪声是"块状"而非颗粒、
> 坐标按屏幕像素（换分辨率观感就变）。

### 第 4 层 · 资源引用（LUT）

| 字段 | 说明 |
|---|---|
| `lut.id` | 42 个内置 LUT（按品牌分 7 类）+ 用户导入的 LUT |
| `lut.strength` | 0…150 %（`[34]`，与拍照页既有量程统一） |

**缺失语义**：预设里没有 LUT ⇒ 套用时**不动**当前 LUT（不是"清空"）。
**资产缺失**：预设引用的 LUT 被删了 ⇒ 降级为"无 LUT" + 明确提示，不静默。

### 第 5 层 · 仅后期（**拍照时无效**，编辑器专属）

| 参数 | 槽位 | 为什么拍照用不了 |
|---|---|---|
| 清晰度 | `[78]` | 显示域 USM，输入必须是已成片 |
| 色温 / 色调 | `[88][89]` | 相对**原片白点**的偏移，RAW 链路没有"原片" |
| 高光 / 阴影 / 白色 / 黑色 | `[90..93]` | 显示域分区增益 |
| 褪色 | `[94]` | 抬黑场 |

> ⚠️ **这是硬架构事实**（`FilmParams.h:403` 与 `:423` 两处明确记载）：
> 这些槽位**只被编辑器链路 `kFsStyle` 读取**，拍照链路 `kFsOut` 零引用。
> ⇒ 一条含这些参数的预设，在拍照界面套用时**那几项不生效**。
> **处理方式（本方案拍板）**：拍照侧打开预设面板时，**把"仅后期"参数灰显并标注"仅后期"**，
> 而不是假装生效（ADR-12：不做假滑杆）。

### ★ 1.6 字段能力矩阵（架构师 2026-10-11 实测，**本方案最重要的一张表**）

预设里能存什么，**不由设计文档决定，由两条渲染链路实际读什么决定**。架构师用脚本抽取了
`FrameRenderer.cpp` 三个 pass 的 `p.<字段>` 引用，结论如下：

| 槽位 | 参数 | 拍照链路 | 编辑器链路 | 进预设？ |
|---|---|---|---|---|
| `[0]` | 曝光 | ✅ `passFilm` | ✅ `passStyle` | ✅（拍照侧被 prefs 覆盖层重写 ⇒ 不会顶掉用户曝光） |
| `[1..3]` | 白平衡 R/G/B | ✅ | ✅ | ✅ |
| `[4]` | 对比度 | ✅ **U-3 接线前是错的**（见表下说明） | ✅ | ✅ |
| `[5..10]` | 趾部 / 肩部 latitude（per-channel R/G/B） | ✅ **E4-4 已接线**：`passFilm` → `updateFilmicEV` → `computeFilmicSpline`（CPU 侧 3×2 个 5×5 系统）→ `kFsFilm` 逐通道三段多项式 | ❌ **无落点**：编辑器链路走 `kFsStyle`（显示域输入、链内无 filmic），影调由 `[4]` contrast + 影调分区 `[90..93]` 承担 | ⚠ **仅拍照链路有效**（编辑器侧套用**无视觉效果**，三处入口 UI 需按此灰显/标注） |
| `[20..22]` | 分区饱和 | ✅ `passFilm` | ⚠ 只读 `[21]` | ✅（编辑器只认中调，UI 是一个滑杆写三槽） |
| `[23][24]` | 分离色调 | ✅ `passFilm` | ✅ **U-1 已接线**（`passStyle` 同式：同系数、同 Rec.709 分区权重） | ✅ **两侧都生效** |
| `[25]` | 单色（黑白） | ✅ `passFilm` | ✅ **U-1 已接线**（显示域去色到 luma，在 LUT **之前**，与拍照链路同序） | ✅ **两侧都生效**（"黑白预设"在编辑器里**会**变黑白） |
| `[26][27][60][61]` | 颗粒 | ✅ `passOutput` | ✅ `passStyle` | ✅（E4-3 已重写） |
| `[28]` | 基准影调强度 | ✅ `passFilm` | ❌ | ❌ **已排除**（引擎色彩科学状态：原文"非风格化"，且被 `tonePref` 覆盖层重写 ⇒ 非用户风格；P-5b） |
| `[31..33]` | 色彩外观层 | ✅ `passFilm` | ❌ | ❌ **已排除**（引擎标定层："治寡淡"的色彩科学层，`[32]`/`[33]` 原文标"中性占位"；P-5b） |
| `[34]` | LUT 强度 | ✅ | ✅ | ❌ 由 `lut.strength` 承载（E3-1a 已排除） |
| `[37][38]` | filmic 黑点 / 白点 | ✅ `passFilm` | ❌ | ✅ **仅拍照侧有效** |
| `[62..65]` | 光晕 | ❌ 未实现 | ❌ 未实现 | ⏳ 等 E4-5 |
| `[66..68]` | 暗角 | ✅ | ✅ | ✅（两条链路逐字相同） |
| `[69..77]` | 层间效应 | ❌ 未实现 | ❌ 未实现 | ⏳ 等 E4-6 |
| `[78]` | 清晰度 | ✅ **U-4 已接线**：`passOutput` 的 `srgbEncode` 之后（显示域）加 16-tap 两环中半径 luma USM，与 `kFsStyle` 同偏移/同权重 | ✅ | ✅ **两侧都生效** |
| `[88][89]` | 色温 / 色调 | ✅ **U-3 已接线** | ✅ | ✅ **两侧都生效** |
| `[90..94]` | 影调分区 / 褪色 | ✅ **U-4 已接线**：同处显示域（OETF 之后），影调分区/褪色**逐字照抄** `kFsStyle` 的同名段 | ✅ | ✅ **两侧都生效** |
| `[30][35][36]` | 过曝提示 / auto_tone / local_tone | 工程旋钮 | 部分 | ❌ **必须排除**（见裁决 A3） |

> **这张表解释了为什么"一套预设"必须带作用域**：一条含 `[37][38]` 黑白点的预设，
> 在拍照侧有效、在编辑器侧**现在完全无效**（等 U-2）。如果不标注，用户会以为"套了预设没反应"。
> **处理**：① UI 按当前场景过滤 + 灰显标注；② 引擎侧补齐接线（§9.5 分卡逐条消除）。
>
> ★ **U-1（2026-10-11）已消除本表 `[23][24]` / `[25]` 两行**：用户指令"不统一的要统一掉"
> 的第一批落地 —— 含 `[25]` 的**黑白预设现在在编辑器里会变黑白**，分离色调也同式生效
> （证据见 `u1-editor-mono-split-REPORT.md`；两侧公式逐字相同，差异只有 luma 的域）。
>
> ★ **U-3（2026-10-11）已消除本表 `[88..94]` 一行**（拆成 `[88][89]` 两侧生效 +
> `[90..94]` 仅后期）**并让 `[4]` 名副其实**：
>  - `[88][89]` 色温/色调 → 拍照链路 CPU 侧折成 RGB 增益，**与编辑器链路同一个
>    `tempTintGain`、同一次乘法**（ADR-14 裁决 1）⇒ 两侧都生效、零额外 GPU 成本；
>  - `[4]` 对比度 → 接入 `computeFilmicSpline` 的 `contrast_param`，与内部补偿 `cp`
>    **相乘**。⚠️ **本表 `[4]` 行此前就标 ✅ 是错的**（U-3 实测：`cp` 初值 1.0 且只被
>    自动白点上探改写，`p.contrast` 在 `passFilm` 链路上**零引用**；§9.2 表当时已标 ❌，
>    两张表本身不一致，以 §9.2 为准）—— U-3 后 ✅ 才成立。
>  证据见 `u3-camera-contrast-wb-REPORT.md`。
>
> ★ **U-4（2026-10-11）已消除本表最后两个「仅后期」槽位 `[78]` 与 `[90..94]`**：
> 拍照侧落点 = `passOutput` 的 **`srgbEncode` 之后**（= 显示域，与 `kFsStyle` 的输入域
> 相同）⇒ 影调分区/褪色的公式**逐字照抄** `kFsStyle`（系数、权重定义、区间、先后序），
> 清晰度用同偏移/同权重的 16-tap 两环（唯一实现差异 = tap 需过同一
> `highlightRolloff`→`srgbEncode` 链才与中心同域 —— 那侧的 `chainLuma` 域提升在拍照链路
> 无处可提升，曝光/WB/对比度都在更早的 pass 里）。`[39]` sharpen **不复用**（OETF 前的
> 小半径、语义不同）。证据见 `u4-camera-display-domain-REPORT.md`。
> **至此本表再没有"仅后期"的槽位** ⇒ P-5 的"仅后期"提示在拍照界面**不再有实例**；
> 剩下的单侧槽位全是"仅拍照"（`[5..10]`/`[37][38]`），等 **U-2** 补编辑器侧显示域曲线。
>
> ⚠️ **E4-4 的实测结论（2026-10-11）**：`[5..10]` 是**只对拍照链路生效**的一类 ——
> 编辑器链路 `kFsStyle` 里**没有 filmic**（它的输入是已成片的 sRGB 显示域，重跑影调
> 曲线没有域依据），本卡按规格**不新增曲线**（"不做两套互相打架的影调旋钮"）⇒ 编辑器
> 侧这 6 个槽位**永远无视觉效果**，P-5 的灰显文案应为"**仅拍照**"，不是"待接线"。
> 编辑器侧的影调自由度 = `[4]` contrast + 影调分区 `[90..93]`。

### 明确**不进**预设的内容

| 项 | 理由 |
|---|---|
| 裁剪 / 旋转 | 构图相关，ADR-16 已隔离在独立通道；Lightroom 真实预设文件里也没有 crop |
| 局部调整 `[79..87]` | 坐标虽归一化，但"画面哪块该亮"依赖具体内容 ⇒ 套到别的照片上那块通常什么都不是（v1 不做） |
| RAW 解码槽 `[39..59]` | 描述"这张 RAW 怎么解"，不是风格；套用会把拍摄者的解码设定强加给另一张照片 |
| 颗粒随机种子 | 引擎内部按"输出尺寸 + 拍摄时间戳"派生（预览恒 0 不闪、成片每张不同） |
| 漏光 / 边框 | 纯 2D 装饰叠加，与成像链无关，将来走 UI/导出层 |

## 2. 预设出现在哪里（三处入口 + 同步关系）

**一处定义**（prefs 单键 `presets_v1` JSON），**三处读取**：

| # | 位置 | 现状 | 目标行为 |
|---|---|---|---|
| 1 | **拍照界面** | tab「预设」里**只有"标准"一项**（`CameraPresets.names` 硬编码单元素）⇒ 等于没做 | 完整预设列表（内置胶片包 + 用户预设）。**选中即生效**于取景预览，拍摄时烘焙进成片 |
| 2 | **查看页「胶片」**（「编辑」旁边） | **置灰** + "胶片预设将在后续版本提供" | 打开**同一份**列表；选中 → 在照片上实时预览 → 「保存副本」或「进编辑器微调」 |
| 3 | **编辑器底栏「预设」** | ✅ 已实现（E3-1a/E3-1c：保存/分组/套用/删除/强度） | 保留，读**同一份**数据 |

**同步规则**：
- 任一处保存 / 删除 / 改名 → 另两处立即一致（同一数据源 + 变更通知，不各存一份）。
- **数据模型统一**：现有两套 schema 必须合并（见 §6 风险 R1）。
- 三处的**套用语义**不同（这是设计，不是不一致）：
  - 拍照 = 把预设展开成**完整 96 槽**下发给引擎（拍摄时生效）；
  - 查看页 / 编辑器 = **稀疏覆盖**到当前参数（"缺失 = 保留当前值"，天然支持"这条预设只改色彩"）。

**为什么拍照侧必须是"完整展开"**：引擎需要完整参数数组；而稀疏是唯一真源，
展开 = `标准基线 + 预设里的槽`（纯函数，编辑器侧已有同型实现，复用不重写）。

## 3. 强度（Amount）

| 项 | 决定 | 依据 |
|---|---|---|
| 量程 | **0…150 %**（100 % = 预设原样） | 与拍照页 LUT 强度量程统一（用户 2026-10-10 已拍板） |
| 数学 | `p_new = 恒等值 + (p_预设 − 恒等值) × amount` | 参数域缩放（Lightroom 路线）；我们是命名槽位，与 Lightroom 同构 ⇒ **零额外渲染** |
| 必须相对**恒等值** | 不是 0，也不是当前值 | 大量槽的恒等值是 1.0 / 0.01 / 单位阵；相对 0 缩放会让"对比度 1.5 @ 50 %"变成 0.75（画面变灰） |
| 逐类语义 | 增益/强度/LUT ✅ 直接缩放；矩阵 `I+(M−I)a`；非线性曲线（趾肩）❌ 不缩放；离散枚举 ❌ 不缩放（<50 % 整条不套用） | 已实现并单测覆盖（E3-1c，27 条用例） |
| 拍照侧 | 拍照界面**也提供强度**（选完预设出现一条滑杆） | 与后期一致；引擎本就支持 LUT 强度 |

**强度不进预设 JSON** —— 它是"套用时的参数"，不是预设的一部分（E3-1c 已按此实现）。

## 4. 内置胶片预设包（"胶片功能"的主体）

## 7. 架构师裁决（2026-10-11，基于 `preset-shooting-side-RESEARCH.md`）

> 该调研报告 833 行 / 27 个实测 URL，架构师已抽查关键论断（Fuji recipe 字段、
> "曝光补偿不能进 recipe"、VSCO 的"预设与质感层打架"bug）与代码事实（槽位号、链路读取范围），
> **论证成立**。以下裁决为最终口径。

### 裁决 A1：schema = **语义名（线格式）+ 索引键（内存）** ✅ 采纳调研建议

- **持久化 / 交换格式**：`params: {"grain_amount": 55.0}`（语义名，E4 §4.2 形态）
- **内存模型**：保留 `slots: Map<Int, Double>`（`presetSnapshot` / `scalePresetSlots` 零改动）
- **决定性理由**：槽位语义漂移**已真实发生两次**（`[5..10]` shoulder/toe → filmic latitude；
  `[26][27]` 颗粒）。索引键 JSON 一旦漂移，`"5":0.0` 到底是旧 shoulder 还是新 latitude
  **已无法分辨 ⇒ 信息丢失、无法自动迁移**；语义名可以写迁移函数。
  且 ADR-19 定案的"参数域缩放强度"**前提就是参数带语义**，业界对标物（Lightroom `.xmp`、
  RawTherapee `.pp3`）全是命名键值。
- **代价**：约 120–180 行 + 2–3 条单测，**全部集中在 `EditorExport.kt` 预设段（:1520-2020）**，
  不触及引擎 / 契约 / shader。
- **★ schema 版本升到 2，旧数据（schema=1）直接拒绝，不写迁移函数**：
  依据 = 预设功能**首次出现在 v0.11.11（versionCode 360）**，而用户明确"这个包先不测"，
  此前所有版本无预设代码 ⇒ **真实设备上不存在 `presets_v1` 数据**。
  升版本号是零成本保险：万一某台设备上存过旧格式，会被"拒绝 + 诊断日志"而不是被误读。
- **新增映射表 `FilmParamKeys`**（语义名 ↔ 槽位，代码里唯一维护），加单测钉死双向一致性；
  **未知键必须报错**（不做静默忽略 —— 项目有多次静默失败事故）。
- **体积**：`"26"` → `"grain_amount"`，每预设约 +200 B ⇒ 500–900 B/条，100 条约 50–90 KB，
  prefs 单键可接受（**实测后确认，不拍脑袋**）。

### 裁决 A2：**预设本体 与 拍摄态 必须分离** ✅ 采纳，但 v1 只做本体

- **进预设本体**（三处共用）：风格参数 = LUT + 影调 + 色彩 + 胶片质感（能力矩阵中 ✅ 的那些）
- **不进预设本体**（= 拍照界面的当前状态）：曝光补偿、ISO、快门、焦距、闪光、对焦模式
- **反例证据**：Fuji 的 Custom Settings 槽连"对焦偏好与声音设置"都存 ⇒ 粒度太粗，
  根本无法与后期侧共用。**正面证据**：Fuji 官方明说 Color Chrome
  "can either be applied **while shooting** or when processing RAW files in-camera"
  = **同一套参数定义、两种应用时机** —— 这正是我们要的形态。
- **v1 不做 `shooting` 段**（YAGNI）：预设 = 纯风格。将来若用户要"预设带曝光补偿"，再加可选段，
  届时查看页/编辑器忽略该段。
- **顺带确认**：拍照侧 `[0]`/`[28]`/`[30]`/`[34]`/`[35]` 本来就被 prefs 覆盖层重写
  （勘察 G-4）⇒ 预设里即使有 `[0]`，也不会顶掉用户在拍照界面调的曝光补偿。

### 裁决 A3：排除列表修正 —— 新增排除 `[30]` `[35]` `[36]` ⚠ **审核发现的实际缺陷**

E3-1a 的 `presetSlotIncluded()` 只排除了 `[34]` / `[39..59]` / `[79..87]`。
架构师核对 `FilmParams.h` 后发现三个**非风格槽位**会被存进预设：

| 槽位 | 实际语义 | 为什么必须排除 |
|---|---|---|
| `[30]` | `zebra_thr` 过曝提示阈值（显示域，**仅预览 passOutput 使用**） | 它是**预览辅助开关**。存进预设 ⇒ 套用后**凭空打开/关闭别人的过曝斑马纹**（编辑器链路 `passStyle` 也读它） |
| `[35]` | `auto_tone`（黑白点自动的实验开关） | 引擎模式旋钮，不是风格；且默认值受用户设置影响 |
| `[36]` | `local_tone`（暗部线性提亮比例，**标定旋钮**） | 引擎标定参数，同一张照片在不同标定下观感不同 ⇒ 不是可分享的风格 |

### 裁决 A4：预设层 与 质感层 的交互语义（避免 VSCO 那个真实 bug）

调研发现 VSCO Capture 有真实 bug：**"选了 preset 后再调 bloom/halation，preset 效果消失"**
（VSCO 官方人员确认为 bug）。我们必须显式定义：

- **预设 = 一次性写入参数快照**。套用后，预设里的每个参数就是当前参数值。
- 之后用户手动调任何滑杆 = **改当前状态，不回写预设**（Lightroom 语义）。
- **强度滑杆例外**：拖动强度 = 从 `presetBase` 重算（E3-1c 已实现）⇒
  **会覆盖用户在套用后做的手动调整**。这是已知行为，**UI 需要一句提示**（"调强度会重新套用预设"）。
- **不存在"效果层"概念** ⇒ 结构上不可能出现 VSCO 那种"预设与质感层互相取消"。

### 裁决 A5：字段作用域在 UI 上必须显式

按 §1.6 能力矩阵：当前场景链路**不读**的槽位，在预设面板里**灰显 + 标注**
（"仅后期" / "仅拍照" / "暂不支持"），**不做假滑杆**（ADR-12）。

### 用户拍板（2026-10-11）

1. **拍照界面预设入口**：**已经有了**（底部面板的「预设」tab）—— **不新增入口**，
   把它**做实**（列表从"只有标准"变成真实预设）。⇒ P-2a
2. **查看页「胶片」套用后去向**：**直接进编辑器**（不做"保存副本"）。⇒ P-3
3. **编辑器「预设」保留**：后期存配方要有（R5 关闭）。

## 8. 样片指纹结论与配方重调路线（2026-10-11）

调研报告 = `preset-sample-fingerprint-RESEARCH.md`（750 行）｜数据 = `tools/preset-exp/fingerprint/*.json`。

### 8.1 用户质疑的答案：**样片分析走得通，而且否掉了"从 LUT 反推"**

| 预设 | 拿到的最强样本 | 证据强度 |
|---|---|---|
| 理光负片 | **同一台 GR IIIx、同场景的 Negative/Positive/Standard 三联图**（构图偏移 1–2px） | ⭐ ① **成对样片**：可算"风格净效应"，**完全排除场景与光线** |
| 徕卡一瞬 | Imaging Resource 的 M9 标准化场景（Wayback 存档，5216×3472 **机内 JPEG**，含 **ColorChecker 24 色 + 6 级灰阶**） | ⭐ ② 标准化场景：可定量提取曲线与色彩响应 |
| 徕卡黑白 HC | **没查到**（IR 序列不含 B&W 档；dpreview 从未完整评测 M9，存档只剩 60×60 缩略图） | ❌ 只有 M9「Contrast +2」间接推断（已标注） |

**实测目标指纹**：
- **M9**：S 形曲线 —— 暗部陡（52→85 斜率 **1.31**）、中灰陡（85→122 **1.36**）、**高光强压（200→243 仅 0.64）**；
  黑 52→28.6、白 243→233.4；**饱和度增益 1.178**
- **理光负片**：**对比度几乎不变**（p95−p5 比 **1.0247**）、平均亮度 **+5.53**、
  **饱和度 ×0.772（−22.8%）**、中性区 **b\* −1.7~−1.8**（去黄偏蓝）；影调 = 中间调提亮 + **高光不压**

### 8.2 ★ 核心发现：**三条 LUT 的曲线形状与目标不匹配，调 `lut_strength` 无解**

按线性混合 `out = in + s·(lut(in) − in)` 逐点反解：
- `leica_m9`：暗部要 **s=1.42**、中灰要 **s≈0**、高光要 **s=−2.04** ⇒ **同一个 s 无解**
- `ricoh_negative`：高光段**方向直接反了**（输入 235：目标 241.1，我们 **220.9**）
- `leica_b_w_hc`：中灰斜率 1.15 vs 高对比参考 **1.6~1.75** ⇒ **它并不"高对比"**

⇒ 这也证明架构师最初"从 LUT 反推参数"是**错的路子**：会把 LUT 的缺陷一起固化进配方。

### 8.3 ★★ 架构师交叉验证：**调研的参数建议有一半在拍照链路不可用**

调研只看数值，不知道引擎链路能力。按 §1.6 能力矩阵逐条核对：

| 调研建议 | 拍照链路 | 编辑器链路 | 裁决 |
|---|---|---|---|
| `contrast[4]` 重建对比度 | ❌ **`passFilm` 不读它** | ✅ | 拍照侧改用 `[5..10]`（E4-4 已接线）+ `[37][38]` 端点 |
| `monochrome[25]=1`（黑白那条） | ⚠ **在 LUT 之前去色 ⇒ 会毁掉黑白 LUT 的通道混合**（蓝压黑/绿提亮），加了反而变平淡灰 | ❌ | **不加**（维持既有决定，测试已钉死） |
| `[0]` 曝光补亮度 | ⚠ 拍照侧被用户的曝光设置**覆盖层重写** | ✅ | 拍照侧改用 `tone_strength[28]` / `[37][38]` |
| `[5..10]` 趾部/肩部 | ✅ **E4-4 已接线** | ❌ 无落点 | 影调重建的**主工具**（拍照侧） |
| `sat_shadow/mid/high` | ✅ `passFilm` 读三档 | ⚠ 只读 `sat_mid` | 可用 |
| `lut_strength` 降到 0.3~0.5 | ✅ | ✅ | 采纳 |

### 8.4 路线（三步）

1. **现在**：三条预设的定位是"**风格化**"，**不是"还原厂家成片"** —— 现在有数据证明这一点。
   用户先看 `0.11.12` 的观感（颗粒/暗角/整体味道），观感反馈优先于数值。
2. **E4-4 已交付** ⇒ 具备"按目标曲线重调配方"的工具：LUT 强度降 **0.3–0.5**（只留色彩风味）
   + `[5..10]` 重建曲线形状 + `[37][38]` 端点 + `sat_*` 补饱和。
   **采纳调研 §5.4 的建议**：把三条的"输入→期望输出"目标曲线写进**回归单测**（容差 ±4/255）。
3. **长期 = LUT 重建（E4-7b）**：M9 样片里有标准 ColorChecker ⇒ 可用
   "标准色卡值 → M9 输出"做**定量校准**，替掉来源不明的第三方 LUT。
   **这是"还原"与"像那么回事"的分界线，需用户拍板投入。**

### 8.5 诚实标注

- **颗粒维度本次没做成**：M9 样片平场 RMS 仅 1.288/255（ISO160 太低）、Ricoh 官方样片 747×1120
  分辨率不足 ⇒ 颗粒仍走 E4-3 的 darktable 路线，**不由样片标定**。
- **理光三联图不能 100% 排除"分三次拍摄、曝光有微差"**（构图偏移 1–2px 支持同机位，但不是证明）。
- **黑白 HC 的目标数字全是间接推断**（用 M9 Contrast +2），不是该模式本身的实测。

## 9. 参数统一方案（用户 2026-10-11 指令："不统一的要统一掉，缺的补上"）

> 用户原话质疑："**影调重建拍照侧和编辑器侧不一样？还是什么意思？不统一的要统一掉，缺的补上。**"
> **用户是对的，这一条推翻了本方案 §1.6 的"按链路能力灰显"路线** ——
> §1.6 的矩阵仍然有效（它描述**现状**），但它不该是**目标状态**：
> 风格参数的语义应当**与链路无关**，同一个滑杆在拍照与后期必须是一回事。
> §1.6 的"作用域标注"（P-5）因此降级为**过渡期措施**，补齐完成后应当**全部消失**。

### 9.1 为什么现在两侧不一样（澄清，不是辩解）

1. **输入域不同**（这是真实的技术约束）：拍照链路的输入是 **RAW 线性域**（ACEScg 工作空间），
   编辑器链路的输入是**已成片 sRGB JPEG（显示域）**。⇒ 同一个"风格参数"在两条链路上的
   **实现位置与数学**必然不同（例：暗角在拍照链路的 LUT 之前、在编辑器的显示域）。
2. **分卡历史**（这是需要纠正的部分）：E2 系列只做编辑器侧、E4 系列只做拍照侧，
   于是"谁被分到哪张卡"变成了"哪条链路有这个参数" —— **这是工程顺序的副作用，不是设计**。

⇒ **结论：统一 = 让两条链路都实现同一套风格参数**（各自在自己的域里实现，语义对齐）。

### 9.2 完整风格参数清单与缺口（以**编辑器参数面板**为基准，它是现有最完整的一份）

| # | 参数 | 槽位 | 拍照链路 | 编辑器链路 | 要补 |
|---|---|---|---|---|---|
| 1 | 曝光 | `[0]` | ✅ 但被 `baseEvPref` **覆盖层重写** | ✅ | ⚠ 语义统一（见 §9.4） |
| 2 | 对比度 | `[4]` | ✅ **U-3 已补**（接入 `contrast_param`，与 `cp` 相乘） | ✅ | — |
| 3 | 色温 / 色调 | `[88][89]` | ✅ **U-3 已补**（CPU 侧折增益并入 `[1..3]`） | ✅ | — |

### 9.3 补齐方案（各自域内实现，语义对齐）

**编辑器链路 `kFsStyle` 补 4 项**（显示域实现，注意与拍照侧**效果对齐**）：
| 参数 | 显示域实现 | 代价 |
|---|---|---|
| `[25]` 单色 | 去色（luma）—— 注意：**黑白 LUT 自带通道混合**，`[25]` 只在用户显式选"黑白"时置 1 | 极低 |
| `[23][24]` 分离色调 | 阴影/高光加法偏移（照 `kFsFilm` 的 `uSplit` 三行同式） | 极低 |
| `[5..10]` 胶片曲线 | 显示域 **per-channel S 曲线**（等价于把 filmic 的 toe/shoulder 形状作用在显示域；`latitude` 的数学可直接复用 `computeFilmicSpline`，只是端点取 0/1 而非 EV） | 中 |
| `[37][38]` filmic 黑白点 | 同上曲线的端点（显示域黑点/白点） | 中（与上一行同卡） |

**拍照链路补 6 项**：
| 参数 | 拍照侧实现 | 代价 |
|---|---|---|
| `[4]` 对比度 | 接到 `computeFilmicSpline` 的 `contrast_param`（现在 `cp` 只服务 gamma 回退补偿 ⇒ 与用户值**相乘**） | 低 |
| `[88][89]` 色温/色调 | 在 CPU 侧折成 RGB 增益、与 `[1..3]` 相乘（与编辑器 `[88][89]` 同法，规格已在 ADR-14 裁决 1） | 低 |
| `[90..93]` 影调分区 | 放 `passOutput`（**显示域**，OETF 之后）—— 与编辑器同域同式 | 低–中 |
| `[94]` 褪色 | 同上（抬黑场） | 低 |
| `[78]` 清晰度 | RAW 域已有 `[39] sharpen`（小半径轻度锐化、OETF 前）；**不复用**（语义不同），在 `passOutput` 显示域加中半径 USM | 中 |

**验收口径（一致性怎么证明）**：两条链路**各自对同一组"目标曲线"负责** ——
拿同一张三通道灰阶输入，拍照成片与编辑器输出的"输入亮度 → 输出亮度"曲线应落在同一目标带内
（容差 ±4/255，即调研 §5.4 给的那套基线）。**不要求逐位相同**（域不同），要求**观感一致**。

### 9.4 决策点：曝光 `[0]` 的语义（**需用户拍板**）

| 方案 | 含义 | 代价 |
|---|---|---|
| A | 预设**不含**曝光（避免与用户的曝光补偿打架） | 零 |
| **B（架构师推荐）** | 预设的 `[0]` = **相对用户基准曝光的偏移**（`[0] = baseEvPref + presetEv`）—— 拍前能看到效果、不冲掉用户的实时调整 | 低（改一行覆盖层） |
| C | 预设的 `[0]` **覆盖**用户曝光 | 零，但用户会觉得"我的曝光被预设吃了" |

### 9.6 用户第 2 条需求（预设可编辑 / 新增 / 展示全部参数）的设计要点
