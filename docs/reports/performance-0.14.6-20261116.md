# 0.14.6 性能回归首轮实测（2026-11-16）

## 结论与边界

拍照变慢的主要区段已经定位到 **PC3D 的逐样本完整协方差配对距离度量**，包含协方差取样、矩阵构建、正则化和求逆；噪声传播也有明显成本。不能把整个增量都叫作“矩阵求逆成本”，更不能据此删除完整度量。

生产成像代码、版本号、已安装 APK 均未修改。本轮只增加独立真机诊断入口，未出包。两个保持输出的候选仍停留在诊断工具：协方差提前复用明显更慢；相同配对距离复用只有有限收益，未进入生产。

尚未完成：同场景 0.14.0/0.14.6 三次冷机 App A/B、每张独立温控记录、真实上下文优先级查询、预览回调/执行/GPU 的独立时间线。因此这是瓶颈定位结果，不是性能修复完成或最终画质验收。

## App 实测

- 设备：V2509A / Mali-G1-Ultra MC12。
- `dumpsys package`：versionName=0.14.6，versionCode=803。
- 会话开始 Thermal Status=0；较后采样检查为 1，退后台后回到 0。没有每张采集温控，不能把整组都称为 Thermal 0 冷机样本。
- 用户确认手机固定后，以音量键触发前三张；应用持续运行，不改相机设置。曝光由现有 AE 自行调整，不是相同 RAW 的重放。
- 三张均真实走四帧采集、FrameRenderer、JPEG/R444 编码和相册保存，无渲染失败。

三张 PC3D 中位 3282.73ms，总渲染中位 5741.26ms。后两张仍持续三秒以上，首张分配或 shader 编译不能解释全部回归。高光准入均为 `no_clipped_pixels`，MergeBayer 仍生成普通融合及完整噪声图；不能把卡顿限定为“接受了短帧恢复”的场景。

`uploadMs` 的实际边界是 t0 到融合开始，包含上传、时域配准和高光准入，**不是纯纹理上传**。准入时间已包含其中，不能再次相加。PC3D 时间包含在 dnMs 中，也不能重复相加。

JPEG/R444 编码为 172 / 195 / 194ms，日志 `nativeFail=false`。它不是这三张数秒级后处理的主因。

设备保留的 0.14.0 日志有 12 张，PC3D 中位 471.45ms，总渲染中位 2844.34ms。这组是历史不同场景，只作回归线索，**不据此宣称精确加速比或质量等价**。此前记忆中的 5.2–6.5s 也不是本轮匹配基线。

## 预览证据与测量盲点

静置取景多数为 29–32 FPS；第一张处理期记录 `8,11,14,18,29`，后两张附近最低约 14 FPS，出片后恢复约 30 FPS。

采集附近三个 `preview_arrive_gap` 为 742 / 736 / 749ms，对应 `preview_gap` 为 767 / 752 / 757ms。但以下代码事实使“到达停顿=HAL停帧”的旧注释不成立：

1. `CameraController.kt` 的 `SurfaceTexture.setOnFrameAvailableListener` 显式绑定 `render.looper`。
2. `RenderClient.frameAvailable` 在这个回调里记录 arrive，再 post 同一个 FilmRender 队列。
3. RAW ImageReader 回调也绑定 `render.looper`。

所以 arrive 是 **FilmRender 实际执行回调的时刻**，包含消息队列阻塞，不能直接代表传感器或 HAL 真正产帧。现有日志足以证明卡顿，尚不足以把约 740ms 分配给 HAL、RAW 回调拷贝或渲染队列各多少。

同样，`engine.still_start` 的 `eglLow=1,eglPriExt=1` 只能证明带 LOW 请求的上下文创建成功。`EglCore::init` 没有 `eglQueryContext(EGL_CONTEXT_PRIORITY_LEVEL_IMG)`；HIGH/LOW 的实际返回级别仍待查询。Khronos 的 IMG_context_priority 规范明确：优先级是 hint，创建成功也可能被分配为其他级别。

## 独立 GPU 基准

复用 `tools/check-highlight-device.cpp`，新入口：

```text
--pc3d-bench FILE --size N --repeats N
```

直接提取当前 `FrameRenderer.cpp` 的 `kFsPc3d`，在同一真机运行。输入是确定性的 RGB16F 图、逐像素两张 RGBA32F 六分量协方差、带符号交叉项及排除掩码。K=5，与 App 的 11×11 核一致；分别测 MOIRE=0 和 1.5。每种配置先预热一次，再测三次中位；计时含提交、glFinish 和一次错误检查，不含分配、编译、预热和读回。

1024² 拆解组增加高反差彩色纹理，覆盖平滑区、纹理区、边界和掩码。下面是 **同组输入** 的结果，单位 ms：

| 配置 | MOIRE=0 | MOIRE=1.5 |
|---|---:|---:|
| 原生产 shader，三附件，16 条带 | 152.18 | 163.45 |
| 原 shader 组尾复测 | 153.67 | 153.76 |
| 只启用一个输出附件，仍保留原计算 | 154.73 | 152.40 |
| 保留完整配对距离，编译移除输出协方差传播 | 103.38 | 102.00 |
| 保留传播，以普通距离替换配对矩阵度量 | 25.74 | 27.87 |
| 关闭局部噪声分支，仅作诊断 | 24.23 | 21.15 |
| 提前复用完整协方差（候选） | 205.81 | 217.87 |
| 仅复用完全相同的两路配对距离（候选） | 146.49 | 150.85 |
| 原 shader，1 条带 | 154.73 | 153.08 |
| 原 shader，64 条带 | 156.65 | 153.91 |

解释：

- 减少附件写出几乎不改善本组耗时；MRT 写出不是这组里的主要增量。但附件仍然分配，**不能据此排除纹理占用、首次分配或大图带宽问题**。
- 完整配对度量是主要热点，传播也不可忽略。消融会改变编译、寄存器活跃期和权重，成本不具可加性，不能用表格相减声称精确阶段耗时。
- 两个保持输出的候选，在 MOIRE 两档、RGB/方差/带符号协方差三附件上，读取后的 float 每一位都与原版一致。提前缓存反而慢约三分之一；不能因为“少读纹理”就认定更快。
- 相同距离复用只在 `extra==0` 时复用原 dy，其他情况仍执行完整矩阵距离。首趟有小幅收益，第二趟落在组内波动附近，尚不能解释或解决 App 数秒回归。
- 单独增加条带数没有改善本组总耗时；此基准没有同时运行预览，不能用它宣称 64 条带改善或不改善预览 FPS。
- 两项破坏权重/传播的消融只是诊断，**严禁并入成片链**。

较早的平滑纹理组也做了尺寸对照：1024² 原版单趟约 118–120ms；2048² 约 567–574ms，单附件约 568–570ms，协方差缓存约 788–791ms。高反差组与平滑组输入不同，不混算收益；所有结果均为后台独立 pbuffer context，不能代替 App 并发、热状态及整链验收。

## 代码审计

- `runPc3d`、MergeBayer、HighlightNoise、HighlightResolve 仍调用 `drawStriped(16)`。
- `drawStriped` 保持全尺寸 viewport，以 scissor 切带、每带 flush；没有恢复旧的缩 viewport UV 错误。
- still 的 pass fence 窗口仍在；PC3D 主滤波仍是两趟，不能把一个条带化 pass 误认成一个条带 job 的实测耗时。
- 新的 raw noise、RGB resolve、D4 covariance 和 filter covariance 走惰性创建，没有进入旧 warmup。
- 旧版已有 GpuTimer::endMs 的 glFinish；不能把它未经测量归为本次新增的数秒回归。
- 本轮没有硬件计数器/编译器 spill 报告。“缓存更慢可能因寄存器压力”仅是假设，不写成已证实的 spill。

4080×3072、PC3D scale=1 时新增纹理的逻辑存储估算：

| 纹理 | 字节 |
|---|---:|
| 原生 RAW noise，一张 RGBA32F | 200540160 |
| D4 covariance，两张 RGBA32F | 401080320 |
| PC3D 两组全尺寸 covariance，共四张 RGBA32F | 802160640 |
| RGB resolve，一张 RGBA16F | 100270080 |
| 上述合计 | 1504051200 |

**两张全尺寸 RGBA32F 是约 401MB，不是 200MB**。这里是纹理格式的逻辑字节数，不是已测物理驻留、PSS 或显存峰值；未包含其他中间纹理，scale>1 的低分辨率两组还会另占空间。

## 下一步顺序

1. 修正可观测性：查询真实 HIGH/LOW 优先级；把预览回调到达、FilmRender 入队/开始/完成、SurfaceTexture 时间戳和 RAW 回调拷贝放在可区分的时间线上。不能简单搬整个回调线程，里面还有依赖渲染线程的现有操作。
2. 在单独测试目标里细分完整配对度量的取样、矩阵求解和传播活跃期；优先查成熟实现的完整对称矩阵求解和编译器生成结果。保持六分量、原正则化、全部样本、双路权重和噪声传播，拒绝 scalar/低精度近似。
3. 给准入的 guide、双向求解、observable support、mask assessment 各自计时。现有约 1.1s 不能全部归给其中一个函数，更不能先跳过准入来换时间。
4. warmup 新资源和资源生命周期单独做实测，记录内存峰值与预览代价后再决定；不能一次盲目多分配 1.5GB。
5. 有候选收益后，再做相同 RAW 的真实 FrameRenderer+JPEG 差分、同场景冷机至少三次、预览时间线和画质验收；交付包按项目版本/签名/JNI 纪律执行。
