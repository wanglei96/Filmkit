# P0+P1 设计：HDR 高光灰块（短帧对齐注入 + 无真值区重建）

- 版本：0.12.102（已实现）
- 日期：2026-10-28
- 范围：只动 HDR 多帧的高光链路；不动徕卡预设、不动 LUT、不动 filmic 曲线。
- 关联：0.12.21（sat-fix 收口）、0.11.86（HR 条件重建）、0.12.10（HL 标记回滚）、
  PC 源码 `GlesMgcRawSpatialShaders.kt`（Bento，Apache 2.0）与 `docs/engine-hdr-exposure-fusion-design.md`。

## 1. 问题

HDR+ 包围曝光（0/0/+2.2/−1.5EV）开着时，高光反光区仍有**中性灰块**（L 84–89 / C\* 2–4）。
真机日志指纹（110647 / 110703）：

| 字段 | 值 | 含义 |
|---|---|---|
| `brk` | 0 | 引擎判定"非 bracket" |
| `hlMarkOn` | 0 | 无短帧真值标记 |
| `aeSat` | 0.0034 | AE 统计的**融合后**饱和率，**不是**短帧饱和率（HDR 下 App 没算短帧 sat） |
| `hlCnt` | ~8000 | 高光重建仍在跑 |
| `hdrEv` | 0/0/+2.2/−1 | 采集侧确实是 HDR 四帧 |

根因链（已查证）：

```
hdr_active 分支只改了 frame_scale/gain，bracket_on 仍只认旧 short_ratio
  ⇒ bracket_on=0 ⇒ sat-fix 跳过（参考帧饱和区不修复）
  ⇒ DFT 收缩以参考帧为基准（a = d²/(d²+cs²)，差异大时采信 r0）
  ⇒ 长帧饱和值原样进入 HL/filmic
  ⇒ HL opposed 只能邻域外推 ⇒ 中性灰块
```

注意：短帧（−1.5EV）大概率有真值，但**本次日志没有短帧 sat 字段**，不能断言
"真值都在"。P1 的 App 透传（4.1）会把这个数补上；P0 先用 `hlCnt` 与成片判断。

两处次要问题：
1. sat-fix 在 `stage("align")` **之前**跑，直接用同坐标短帧 —— HDR 四帧手持有位移时注入错位值（鬼影/彩色边）。
2. 短帧归一后**低于基准**（错位/降噪影响）时仍被注入，没有 fallback（GCam Bento 的 `normalizedIntensityError` 判据）。

## 2. 现状链路（相关段）

```
4 帧 upload
  → capturePyr(ref) → tex_pyr1_（1/2 sat map）
  → align 循环（帧 1..3）→ offs[0..2] / tex_off_[0..2]（tile 位移场）
  → [P0 在此插入] sat-fix：ref + short(帧3) + sat_map + off[2] → tex_ref_fix_
  → DFT 融合（fft_raws[0] = ref_fuse_tex_）
  → HR wavelet（hr_raw=1，默认开；条件重建用 hr_fix_mark_）
  → RCD → CCM → HL(opposed) → filmic
```

关键既有资产：
- `kFsMfnrSatFix`：参考帧饱和修复（R16UI，G 通道三态标记 0/1/2），已有 satFrac 面积判据（0.11.99/0.12.15 验证过）。
- `kFsHrMask`：已支持 `uFixMark` 条件重建（标记 ≥1 跳过），当前因 `hr_fix_mark_=0` 未生效。
- `tex_off_[2]`：帧 3（短帧）的 tile 位移场，DFT 同款格式。

## 3. P0：短帧对齐注入 + fallback

### 3.1 改动

1. **入口**（`FrameRenderer.cpp` submitRawBurst 内）：

```cpp
// 旧：const bool bracket_on = short_ratio_ok > 1.01f;
// 新：HDR 四帧同样有短帧真值（帧 3 = −1.5EV，frame_scale[3]=2.82），sat-fix 必须跑
const bool bracket_on = short_ratio_ok > 1.01f || hdr_active;
```

2. **顺序**：把 `if (bracket_on) { passMfnrSatFix(...) }` 从 align 前移到 align 循环之后、DFT 之前；`hr_fix_mark_ = tex_ref_fix_` 同步移动。`ref_fuse_tex_ = tex_ref_fix_` 保持。
   - ⚠️ **必须在 sat-fix 前重算参考帧的 1/2 灰度**：align 循环会逐帧覆盖 `tex_pyr1_`/`fbo_pyr1_`，循环结束时里面是**最后一帧（短帧）**的 1/2 金字塔，不是参考帧的。sat-fix 的 `uSatMap` 要的是参考帧饱和面积（satFrac），直接用会拿错帧的统计。实现只重跑 `passMfnrPyr`（1/2 域单 pass，不重跑金字塔/readback，<1ms）。
   - 重新 capturePyr 不会影响 DFT（DFT 只读 raw 纹理，不读 tex_pyr1_）。

3. **shader**（`kFsMfnrSatFix`）：
   - 新增 uniform：`uOff`（sampler2D，tile 位移）、`uOffTiles`（ivec2）、`uMinErr`（float）。
   - 新增 `offAt(vec2)`（与 `kFsMfnrFuse` 同式双线性）与 `shortAligned(ivec2)`：
     **逐通道网格亚像素 4-tap 双线性**（照抄 `linSub`，R 只与 R 插值，零色度污染），
     不是整数位移（见第 5 条）。
   - 短帧采样由 `texelFetch(uShort, p)` 改为 `shortAligned(p)`。
   - fallback **软门控**（不新增 0/1 分支，避免边界斑点）：
     ```glsl
     float ratio = sNorm / max(r, 1.0);
     float fbW = 1.0 - smoothstep(0.90, max(1.0 - uMinErr, 0.91), ratio); // 越低越不可信
     float wCons = max(sSat, fbW);
     float sVal = mix(sNorm, sValCons, sSat);   // 去向仍只由 sSat 决定（旧语义不变）
     v = mix(v, max(v, sVal), w * (1.0 - fbW)); // fallback 只**压注入权重**
     used = (no_info || wCons >= 0.5) ? 0u : 1u;
     ```
     ⚠ 与初稿的三处差异（初稿写法有错）：
     1. 初稿 `smoothstep(1.0-uMinErr, 0.90, x)` 的 edge0 > edge1 —— GLSL 规范对
        `edge0 >= edge1` 的结果**未定义**，必须写成 `1.0 - smoothstep(lo, hi, x)`。
     2. 初稿 `mix(sNorm, sValCons, wCons)` 在 fallback 时会把值抬到 `sValCons`
        （孤立高光 = `wl×uScale`，是"短帧饱和时的下界"），对"短帧偏暗"的采样等于
        造一个更亮的假高光。正确去向是**退回参考帧原值**（不注入），所以 fallback
        只乘在注入权重 `w` 上。
     3. 饱和判据用 4-tap 的 **max**（`smax`），不是插值值：插值会把未饱和 tap 平均
        进来，把"部分饱和"伪装成有真值。`sSat`（注入量）仍用插值值，与旧行为逐位同口径。
   - 其余（satFrac 5×5、0.94 软过渡、`sValCons = mix(wl*uScale, wl, satFrac)`）**逐字不动**。

4. **标记**（沿用三态，P1 的 HR 消费；P0 期间 HR 被 `c.bracket` 关，标记只落盘不消费）：
   - 2 = 长帧本身未饱和（`r < 0.98·wl`）
   - 1 = 短帧有真值且已注入
   - 0 = 短帧也饱和 / fallback ⇒ 无真值

5. **采样精度**：直接**亚像素**，不做整块平移。
   - 位移场是 mosaic 域浮点（`mfnrAlign` 的亚像素精化），DFT 的 `linSub` 已在用；
     整块取整会白丢精度，且高光边缘 1px 错位在 2–3× 放大下可见。
   - 复用 `kFsMfnrFuse` 的 `linSub` 同式：mosaic 视为 2×2 相位网格，逐通道 4-tap
     双线性（R 只与 R 插值，零色度污染），位移可以是任意亚像素。
   - 成本：每高光像素 4 次 `texelFetch` + 双线性，~30 行，性能可忽略。
   - `uMinErr = 0.02`：软门控上界（`sNorm/r = 0.98` 开始退保守值，`0.90` 退到底）；
     标定旋钮，不写死。

### 3.2 预期效果（含一个必须提前说明的连锁反应）

- `brk=1`、`hlMarkOn=1`。
- 有真值区：参考帧被短帧值替换 → DFT 的 `d²≈0` → 输出真实高光；P0 期间 HR 被
  `c.bracket` 关（见下），标记 1 在 P1 恢复 HR 后用于跳过重建。
- 无真值区（短帧也饱和/fallback）：标记 0 → 暂保留 plateau（P1 处理）。
- 大面积饱和（satFrac≈1）：仍取 `wl` 保守值（0.11.99 的"蓝天"约束，不动）。

⚠️ **`c.bracket=1` 会触发 `pe.hr_raw=0`**（`FrameRenderer.cpp:12997`，0.11.94 的
"bracket 下短帧已有真值，film 域 HR 只会抹平"门控）。也就是说 P0 一开，
**小波 HR 会被整体关掉**，无真值区（标记 0）没有任何重建，灰块会以"小面积 plateau"
的形式留下。这不是 bug，是该门控的现有语义；P1 就是修它（见 4.1）。

⚠️ **`hlCnt` 不会下降**：HL 判据是 `v >= 0.987`，sat-fix 修复后的高光值仍 > 0.987，
HL 照样进（`max(v, refavg+chroma)` 只抬不压，不会改坏）。所以验收不能看 `hlCnt`，
要看灰块面积和 HL 的实际改变量（P0 不改 HL 的 `fix_mark`，v0.12.10 的品红教训不冒）。

### 3.3 副作用与对策

| 副作用 | 对策 |
|---|---|
| 高光 **plateau 内部** 位移本身不可靠（无纹理，SAD 失配） | 亚像素只解决采样精度，不解决位移估计；P2 用 collar 光流（PC `BentoRegionAdmission`）替换 plateau 区的位移 |
| 短帧噪声 ×2.82 | fallback 只挡"低于基准"，不挡噪声；靠 DFT 的 σ² 模型吸收（P3 再校） |
| fallback 若做成逐像素硬判据（`sNorm < r*0.98`），噪声/错位会在边界来回翻 → 斑点 | 已按 3.1 实现为**软门控** `fbW = smoothstep(1.0-uMinErr, 0.90, sNorm/r)`，按权重退保守值，不做 0/1 切换 |
| 小波 HR 被 `c.bracket` 关掉（12997） | P0 接受（有真值区不需要 HR）；P1 改门控（4.1） |
| 大面积灰块仍在 | 预期；P1 修 HR 门控，P2 再考虑 inpaint |

## 4. P1：无真值区重建（先修 HR 门控，guided 只作备选）

### 4.1 先修门控，而不是新写算法

现状有三件事叠在一起：

1. `hr_raw=1`（默认开）走 darktable filmic 的 à trous 小波 HR（`kFsHr*`），已支持
   `uFixMark` 条件重建（0.11.86）：标记 ≥1 的像素跳过重建。
2. `FrameRenderer.cpp:12997` 的 `if (c.bracket) pe.hr_raw = 0`（0.11.94）按"bracket
   就关 HR"一刀切——P0 后 `c.bracket=1` ⇒ HR 整个关掉，**标记 0 的无真值区也没人管**。
3. HDR 下 `c.short_sat = -1`（App 只在旧 bracket 时算短帧裁切比）⇒ 引擎无法判断
   "短帧到底有没有丢信息"。

P1 的修法（**实际实现**，比初稿更小：不新增参数、不改 App、不碰 AE）：

| 改动 | 内容 |
|---|---|
| 门控条件 | `if (c.bracket) pe.hr_raw = 0` → `if (c.bracket && !c.hdr) pe.hr_raw = 0`。`c.hdr` = 本条链走的是 HDR 四帧 ⇒ HR 保持开启，由三态标记做条件重建 |
| 条件重建 | 不变：HR 的 `uFixMark` 用 P0 输出的三态标记；标记 0 才重建，1/2 跳过 |
| App 透传 | **不需要**（初稿方案作废，理由见下） |
| 开关 | 复用 `hr_raw`；HDR 下若用户手动关 HR 仍有效 |

为什么放弃 `short_sat` 判据（初稿 4.1 的第一版）：

1. HDR 下 App 不传 `short_sat`（= −1），要透传得改 JNI 链路 + `CameraController`；
2. 更要命的是 `c.short_sat >= 0` 会让 `passAutoExposure` 的 `bracket_metering` 变 true，
   `force_hl` / `sat_frac` 跟着变 ⇒ **与灰块无关的曝光行为一起改**（设计 §7 已警告过）；
3. 三态标记本身就是"逐像素的信息有无"，比全图 `short_sat` 精确：短帧整体饱和 0.3%
   也可能恰好是画面里那片高光；标记 0 才重建、1/2 跳过，正是想要的语义。

旧 bracket（非 HDR）**保持关 HR**（`!c.hdr`）⇒ 该路径零回归；HDR 是唯一新开的口子。

这样"有真值区"和"无真值区"第一次被分开：有真值 → 短帧值 + 跳过重建；无真值 → 小波
inpaint。**不需要先写 guided。**

### 4.2 若 P1 数据不够：guided 备选（公开算法）

先看数据，满足以下任一才进：

- 无真值区灰块面积仍 > P0 的 50%；
- 小波 inpaint 出现明显色斑/色带。

届时的做法（**修正：不在 RAW mosaic 域做**——guided 需要 RGB 邻域，mosaic 域只能按
相位凑，会引入色度污染）：

- 位置：CCM 之后、filmic 之前的**线性 RGB 域**（D4，与 `tex_work_` 同域）。
- mask：P0 的三态标记（RAW 尺寸）按像素对齐传过来，标记 0 = hole。
- 算法：darktable `highlights.c` guided 模式——用未裁剪像素的局部色度/亮度比做
  guided filter 传播；**不做全局色比**（避免假色）。
- 开关：复用 `hr_raw`，但 guided 与 wavelet 是**二选一**（同一开关的两种实现），不叠加；
  HDR 下优先 guided（它在 D4 域，能看见 RGB 邻域），非 HDR 维持 wavelet。
- 判据：hole 区 a\*/b\* 必须落在 5×5 邻域未裁剪像素的范围内，不得出现新色带。

## 5. 日志与验收

新增/变化的日志字段（`raw.render`）：

| 字段 | 来源 | 验收 |
|---|---|---|
| `brk` | 现有 | HDR 下变 1 |
| `hrMarkOn` | **新增**（0.12.102） | 变 1 = HR 真拿到了三态标记（P1 生效的直接证据） |
| `hlMarkOn` | 现有 | **恒 0，不作判据**：它由 HL 的 apply 写，而 HL 自 v0.12.10 起不传标记（传 0）。两个消费点不能共用字段，故 HR 另记 `hrMarkOn` |
| `hlCnt` | 现有 | **不承诺下降**（见 3.2；HL 判据是值，不是信息有无） |
| `bentoFix`（新增，可选） | sat-fix 统计 | `inj/fb/keep` 三数，用于确认注入量 |

成片判据（同场景、HDR 开、filmic/sigmoid 各一张）：

1. **灰块面积**：`L>80 且 C*<6` 的像素占 `L>80` 像素的比例（全图，含大面积白墙）。
   基线（110647 filmic / 110703 sigmoid）：**0.494 / 0.824**（绝对像素 72,682 / 627,362）。
   目标 ≤ 基线 50%（P0）/ 20%（P1）。**另需**裁出粉色高光区（x 600–1450、y 1600–2400）
   单独目视，避免大面积白墙稀释指标。
2. **鬼影**：100% 裁切目视 + 高光边缘梯度；**不用"与单帧差分"**（单帧/HDR 曝光与噪声不同，差分不可靠）。
3. **无假色**：灰块区 a\*/b\* 落在 5×5 邻域未裁剪像素的范围内。
4. **性能**：`raw.render.passMs` 增量 ≤ 50ms（含重新 capturePyr）。
5. **零回归**：HDR 关时 `brk=0`、逐位行为不变（J10）。

## 9. 0.12.103 追加：剩下的灰斑不是 sat-fix，是 HL 判据

0.12.102 真机（2026-10-28 13:43:41，粉色蝴蝶高光）：

| 证据 | 值 | 含义 |
|---|---|---|
| `brk` | 1 | sat-fix 跑了 |
| `hrMarkOn` | 1 | wavelet HR 拿到三态标记（该张 [41] 开着） |
| App `bracket.actual` sat | `0.0000`（帧 0/1/3） | **参考帧零饱和**，p995 = 0.573 |
| `hlCnt` | 6210 | RAW 域高光重建仍在处理 6210 个 photosite |
| 灰斑实测 | L 84.8 / C\* 1.7；周围粉色 C\* 20–28 | 高光被去色成中性 |

参考帧零饱和 ⇒ sat-fix 没有 `r ≥ 0.94·wl` 的像素可修 ⇒ **P0 对这张图无事可做**。
6210 个"高光"全部是伪的：`kFsHlApply` 的判据 `v ≥ uHlClip(0.987)` 判在 **WB 后**域，
本机 R 增益 1.77 ⇒ RAW 只要 56% 满阱就跨过阈值；opposed 的 `refavg` 再把 G 抬起
（`hlRgG 1.08 / hlBgG 0.99` = 中性比例）⇒ 粉色高光被抹成中性灰。

修法（0.12.103）：HL 重新接 `hr_fix_mark_`，但只跳**标记 2**（长帧 RAW 未饱和，
`r < 0.98·wl`），标记 1（长帧饱和 + 短帧真值）仍走 opposed —— v0.12.10 否决的是
"标记 ≥1 全跳"，标记 1 不跳就不会重演品红。非 HDR 无标记图 ⇒ 判据逐位不变。

验收：`hlMarkOn` 变 1；同场景 `hlCnt` 应从 6210 掉到接近 0；灰斑消失。
风险：真饱和区（天空/白墙）标记为 0/1 ⇒ 仍走 HL，无回归。

## 10. 0.12.104：0.12.103 没清干净的原因（0.94–0.98 这一段）

## 11. 0.12.105：真正的错在判据的域（不是标记、不是 sat-fix）

0.12.103（标记 2 跳过）和 0.12.104（sat-fix 只对 r≥0.98 注入）都没治好灰斑。

## 12. 0.12.106：灰块的真正来源 —— 高光滚降的"趋白"起点

`kFsOut` 的 `highlightRolloff()` 同时干两件事，之前共用一个常量 `knee = 0.80`：

| 动作 | 作用 | 是否该从 0.80 开始 |
|---|---|---|
| 等比压缩 `cc = c·(lc/l)` | 防 >1 溢出，**严格保色相** | 是（软肩要早，才有层次） |
| 趋白 `mix(cc, vec3(lc), smoothstep(knee,1,l))` | **去色**（把颜色推向纯白） | **否**（只有真过曝才该白） |

|---|---|
| 灰块 RAW（9343 px） | (0.699, 0.444, 0.698) ⇒ R/G 1.59（品红），**0.8% 饱和** |
| 同区 CCM 后 C\* | ≈ 10（与 ACR/libraw 的 10.3 同量级 ⇒ 输入并不是灰的） |
| 成片 C\* | 1.1 |
| diag.stats `rgByBand`（最亮带） | D4 11.0 → FILM-out 23.6 → **D5 0.0162** |

⇒ 去色发生在 FILM-out → D5 这一段 = `kFsOut` 的滚降，不是 HL / defringe / 降噪 / RCD。

"灰块中间夹品红块"也由此解释：同一块高光的 l 在 0.80–0.95 之间起伏，
l<0.80 完全不去色（保留品红）、0.85 去 16%、0.90 去 50% ⇒ 斑驳。

## 14. 0.12.119：黄绿斑 = sat-fix 的位移串色（真机单变量实锤）

### 现象与排除过程

同一场景（HDR bracket，`hdrEv=[0,0,2.2,-1]`、`brkRatio=2.828`）出现**粉底上的黄绿云斑**
与**蓝天的绿斑**。逐个排除：

| 变量 | 结果 | 结论 |
|---|---|---|
| `hl_rb_recon`（HL 的 RB 反推，唯一会"压值"的 HL 分支） | 关掉后**斑仍在** | 不是它 |
| 0.12.116 的 D4 域降噪混合（gEx 判据） | 斑仍在，且换位置 | 不是降噪 |
| **0.12.118：只关掉短帧注入** | **斑完全消失** | **是 sat-fix** |

### 机制

HL 的 `kFsHlApply` 是 `outv = max(v, refavg + chroma)` —— **只抬不压**，物理上不可能
把 B 压低。全链里唯一会压低通道值的是 `kFsMfnrSatFix` 的短帧注入。

而它的位移来自 **DFT 的 tile 级场**（tile 内常数，非亚像素）。在"粉色物体 / 白色反光"
这类高对比边界上，1~2px 误差就把邻区的低 B 搬进来 ⇒ B 偏低、G 不变 ⇒ **黄绿**。
蓝天边缘同理（B 饱和区紧邻暗部）。

### 修法（0.12.119）

注入前用 4 个**同相位、长帧未饱和**的邻居做局部一致性检查：

```glsl
sad += |shortRaw(q, dOff)·uScale − rq| / wl;      // 只用未饱和邻居（独立证据）
bool offTrust = (cnt > 0) && (avgSad < 0.06);      // 6% 满阱
```

- 可信：正常注入，保留短帧真值；
- 不可信 / 周围全饱和（无可验证证据）：**不注入、也不标"有真值"**，交给 HL 的
  参考比 `max` 重建 —— 它的语义不会压值。

真机结果：**黄绿消失**，同时大面积高光仍由短帧真值托底（不是退回灰块）。

### 与 Bento 的对应

PC 用 **collar 光流**在高光边界单独估流（裁剪区内部的光流不可信）。本判据是同一意图的
**可验证替代**：不引入光流，只否决"这个位置不可信"的注入。若要进一步对齐 PC，可把
局部一致性升级成边界光流，但那需要重投影场，不是当前瓶颈。

### 灰块的独立机制（0.12.112 已证）

灰块是**色度纹理被降噪抹平**（同场景只动降噪滑杆：`dn=0.33` → C\*<6 占 30.6%，
`dn=0` → 1.7%）。0.12.112 用"高光取原图"解决，随后 113~116 在 D4 域找判据失败
（灰块与伪彩在 D4 域不可分），0.12.117 把该层停用。

⇒ 正确做法是 **RAW 域 mask 驱动**（Bento 的 `w × (1 - mask)`），不是 D4 域启发式。

## 15. 0.12.127：绿斑/绿边的真正根因（sat-fix 注入污染 HL 色度统计）

### 15.1 决定性证据：hlChroma 超出物理范围

真机日志（2026-10-28 17:20，0.12.126，`FILMKIT_20261028-172000.dng` / `172005.jpg`）：

```
hlChroma = [-2.191, -0.037, -0.328]
hlSum    = [-2386.2, -182.5, -392.4]
hlCnt3   = [1089, 4908, 1195]
```

`hlChroma[c] = hlSum[c] / hlCnt3[c]`，且 HL 工作在 WB 线性域：

- 统计样本要求 `0.2·cl < v < cl`，`cl = 0.987·max(gain[c],1)`
- `refavg(p) = ((cbrt(对立通道均值))…)³ ≤ 满阱 gain[c]`
- 满阱（本机）= (1.75, 1.00, 1.65)

⇒ 单个样本的 `v − refavg` 最低只能到 `0.2·cl − gain[c]`，即 **−1.40**。

**平均值 −2.191 在物理上不存在。** 唯一的解释是 `refavg` 的 3×3 邻域里含有
**超过满阱的值** —— 而全链只有一处会产生这种值：**sat-fix 注入的短帧归一值**
（`sNorm = (s−bl)·uScale+bl`，−1EV 短帧 `uScale = 2.82`，可达 2.8×满阱）。

后果链：

```
注入值 > 满阱 → refavg 被抬高 → 统计样本 v−refavg 大负 → uChroma 大负
→ apply: outv = max(v, refavg + chroma)
   · R：refavg_R − 2.19 < v_R ⇒ 永不触发，保持饱和值
   · G：chroma_G ≈ 0 ⇒ 仍按 refavg_G 抬高
→ 只有 G 被抬高 ⇒ 粉底上的绿斑 / 轮廓绿边
```

与既有真机对照完全一致：0.12.118「只关掉注入 → 黄绿完全消失」。

### 15.2 第二个根因：0.12.124 的 inpaint 用错了样本

`sValCons`（短帧也饱和时的保守值）在 0.12.124 被换成 `inpaintClipped`。
Bento 的 clipped inpaint 是从**周围未裁剪像素**扩散，它成立的场景是「大面积平滑高光」
（天空、白墙）；用在**粉色物体上的孤立高光点**时，采样到的周围值是粉色：

```
inpaint → 粉色 × uScale(2.82) → 注入到 G（最先饱和的通道）
→ G 单独升高 13~30% ⇒ 高光点变绿
```

大面积饱和区则退到 `wl0 × uScale = 2.82×满阱`，三通道一起被顶高 ⇒ 过亮、再被
filmic 压成色块。

### 15.3 修法：删掉三样东西，只留一个判据

`sValCons` / `satFrac` 面积插值 / 4-photosite L2 fallback 全部删除。注入判据只剩
**短帧自己饱没饱和**（`smax` = 采样邻域 4 个同相位 tap 的原始最大值）：

```glsl
float sSat = smoothstep(0.95, 1.0, smax / wl);          // 只由短帧决定
float w    = clamp((r - wl*0.98) / (wl*0.02), 0.0, 1.0); // 长帧饱和边界软过渡
float k    = w * (1.0 - sSat);
v = mix(v, max(v, sNorm), k);                            // 只抬不压
used = (k >= 0.5) ? 1u : 0u;
```

- `smax < 0.95·wl`：短帧有完整真值 ⇒ 注入 `sNorm`（可 > 满阱，交给 filmic 压显示域）
- `smax → wl`：短帧也饱和，没有真值 ⇒ **权重 0，不注入**，保持长帧饱和值，
  由 HL 的 opposed 统一重建（三通道同一套 refavg + chroma，天然保通道比例）

「不注入」优于「注入保守常量」的理由：饱和是**逐通道**发生的（G 的 WB 满阱 = 1.0，
R/B = 1.75/1.65），任何逐通道常量注入都会破坏三者比例；而 opposed 在 apply 里对
三通道用同一套判据，不会单独抬某一个通道。

### 15.4 配套：HL 色度统计的口径

`kFsHlChroma::refavg` 只采纳**三态标记 = 2（长帧本身未饱和、值为真测量）**的邻域样本：

```glsl
if (uMarkOn != 0 && texelFetch(uFixMark, q, 0).g != 2u) continue;
bool ok = (cnt.x > 0.0) && (cnt.y > 0.0) && (cnt.z > 0.0);
if (!ok) continue;   // 任一通道取不到干净样本 ⇒ 该样本无法外推，整体跳过
```

- 两趟（偏差 / 计数）走**同一个样本集合**，`sum/cnt` 才是真均值；
- `uMarkOn = 0`（单帧 / 无 sat-fix）时逐位回到旧口径，零回归；
- `hlMarkOn` 诊断字段语义同步改为「chroma 统计按干净样本口径运行」。

### 15.5 可验证的验收点

| 字段 | 0.12.126 | 0.12.127 期望 |
|---|---|---|

### 15.6 与 Bento 的关系（为什么不直接搬 rewriteWeight）

PC 的 `oWeight = existingWeight × (1 − maskWeight)` 让裁剪像素**退出融合权重**，再用
clipped inpaint 补洞 —— 那是因为它的短帧对齐不可靠，宁愿空间猜也不愿搬错值。

我们这条链的短帧对齐（mfnrAlign + collar flow + 逐相位亚像素采样）是可用的，所以
**保留真测量**优于 inpaint 猜测：把参考帧的饱和值替换成短帧真值，融合时 `a→1`
自然保留它（`kFsMfnrFft` 的收缩权重在差异大时信任参考帧）。

也就是说：`sat-fix` 与 `bentoRewriteWeight` 是同一意图的两种实现 —— 前者保留测量、
后者保留空间一致性。只有当短帧确实没有真值（`smax → wl`）时，我们才退回后者，
而那一步现在由 HL 的 opposed 承担（它本身就是一种从邻域外推的 inpaint）。

## 16. 0.12.128：轮廓上的残余黄绿 = 逐 photosite 注入的通道撕裂

### 16.1 0.12.127 的验证（真机 17:34:44）

hlCnt3   = [2709, 9994, 3971]           ← 样本数反而增加（口径变干净）

成片的**大面积绿斑**消失。

### 16.2 残余在哪里

用户在灯/白斑的高光**轮廓**上仍能看到一圈黄绿。真实 DNG（173441.dng）的 2×2 块统计：

| 块内饱和 photosite 数 | 块数 | 占比 |
|---|---|---|
| 0（完全未饱和） | 3,062,740 | 97.744% |
| **1~3（部分饱和）** | **1,421** | **0.045%** |
| 4（全饱和） | 69,279 | 2.211% |

那 1,421 个部分饱和块**全部落在高光轮廓上** —— 数量极少，但正好是人眼最挑剔的位置。

### 16.3 机理：逐 photosite 注入必然撕裂通道

同一 2×2 块里，G 的 WB 满阱 = 1.0，R/B = 1.75/1.65 ⇒ 亮度爬升时 G 先撞阱、
R/B 还没撞。旧的逐步长注入只看**单个 photosite** 自己饱没饱和：

```
G 位置：r = 1.00·wl ≥ 0.98·wl  ⇒ 进入 ⇒ 用短帧真值抬高
R 位置：r = 0.60·wl <  0.98·wl  ⇒ 不进入 ⇒ 保持原值
```

结果只有 G 被抬 ⇒ 轮廓一圈黄绿。这不是参数问题，是**决策粒度**问题：
饱和是逐通道发生的，而注入必须是块级一致的。

### 16.4 修法：2×2 块级一致决策

```glsl
float rmin    = min4(长帧 2×2 块);   // 块内最小电平
float smaxAll = max4(短帧 2×2 块);   // 块内最大电平（4 个 photosite 各自的短帧 tap 上限）
float blockSat = clamp((rmin - 0.98wl) / 0.02wl, 0, 1);   // 四个都饱和
float shortOk  = clamp((0.98wl - smaxAll) / 0.02wl, 0, 1); // 四个都有真值
float k = w * blockSat * shortOk;
v = mix(v, max(v, sNorm), k);
```

- **全饱和块**（69,279 个）：没有未饱和通道可做色度参考，短帧真值是唯一信息，
  且面积大、亮度梯度小（位移误差也小）⇒ 注入，保住高光层次；
- **部分饱和块**（1,421 个）：R/B 未饱和，它们的比例已经给出正确色相 ⇒ 不注入，
  交给 HL 的 opposed（`refavg` 由 R/B 外推，色相天然一致）；
- 三个软过渡都取 2% 满阱宽度 ⇒ 交界处无硬边。

这是 Bento「按 mask 决定谁参与」的同一意图，但掩码取在**块**级而不是 photosite 级：
颗粒度对了，色度才不会在块内被撕开。

### 16.5 验收

## 17. 0.12.129：移除 sat-fix 注入，只保留三态标记

### 17.1 最后暴露的现象：灯内部一条水平分界线

用户样片（圆灯，过曝）显示：灯内部**上方白、下方偏暖，中间一条水平分界线**，
分界线只在灯内部，背景没有。

分界线的位置 = **短帧的饱和边界**穿进灯内部的地方：

| 位置 | 短帧状态 | 走哪条路 | 色比来源 |
|---|---|---|---|
| 线上方 | 也饱和 | 不注入 → HL 的 opposed | 满阱比例的 opposed 外推 |
| 线下方 | 还有真值 | 注入短帧归一值 | 短帧逐 photosite 实测 |

两条路径的**色比语义不同**，所以只要并存，接缝必然出现 —— 0.12.119~128 的每一版
（SAD 门、collar flow、inpaint、L2 fallback、块级判据）都只是在**挪这条接缝的位置**，
没有消除它。

### 17.2 更根本的原因：域不对

本 pass 工作在 **WB 之后**（满阱逐通道 = `gain[c]`，本机 2.25 / 1.0 / 1.53），
而 opposed 的语义建立在"三通道满阱相同"之上。

darktable 的 `highlights` 跑在 **white balance 之前**（raw 域，clips 全通道 = 1.0），
所以它的 `refavg` 外推与任何实测值天然同尺度。我们放在 WB 之后，
"注入的真值"与"外推的估计值"不在同一套色比语义里 —— 这是 0.12.102~128
反复出现黄绿/暖斑的公共根因。

### 17.3 修法

`kFsMfnrSatFix` 不再注入（也不再读短帧）：

```glsl
float r = float(texelFetch(uRef, p, 0).r);
uint mark = (r < wl * 0.98) ? 2u : 0u;      // 只生成三态标记
oColor = uvec4(uint(clamp(r, 0.0, 65535.0) + 0.5), mark, 0u, 1u);
```

- 参考帧原样进入融合，**只有一条着色路径**（HL 的 opposed）⇒ 不可能再有接缝；
- 标记 2/0 仍供 HL 的色度统计做口径（§15.4），统计不受影响；
- 短帧真值若有效，应由**融合**（`kFsMfnrFft` 的收缩权重 / `kFsMfnrFuse` 的 satW）
  在融合阶段接管，而不是融合之后做二次替换 —— 这是 HDR+ 原版的分工。

### 17.4 代价（已知，与用户取向一致）

大面积过曝区（灯、天空、窗）失去短帧带来的高光层次，统一渲染为 opposed 重建的平色。
这类区域本来就没有可分辨的细节，而"色比一致 + 无色边"是更高的优先级。

### 17.5 验收

| 观察点 | 期望 |
|---|---|
| 圆灯内部 | **水平分界线消失**，整块同一色温 |
| 白斑轮廓 | 青绿/黄绿圈消失 |
| `hlChroma` | 仍应在 ±0.4 内 |
| `hlMarkOn` | 1 |

## 18. 0.12.130：HDR 多曝光改走空间域 satW 融合（用户拍板方案 A）

### 18.1 为什么必须换融合路径

HDR+ §5 的式 6/7 频域收缩是为**等曝光 burst** 设计的：它假设各帧信号相同、
只有噪声独立。多曝光下这个假设不成立 —— 长帧在饱和处的值与短帧归一后的值
相差整档，频域收缩只能判成"运动/不一致"并把 `a` 推向 1（信任参考帧），
于是**短帧在高光处完全没有贡献**。

0.12.102~128 的全部尝试（sat-fix 的逐 photosite 注入）都是在融合之后做二次替换，
而替换必然带来色比撕裂：饱和是逐通道发生的（G 的 WB 满阱 = 1.0，R/B = 2.25/1.53），
任何"逐通道给一个值"的操作都会在块内/路径间制造接缝。分界线、黄绿边、暖斑
都是这一件事的不同表象。

### 18.2 改法

```cpp
if (hdr_active) use_dft = false;   // 多曝光强制走 kFsMfnrFuse
```

`kFsMfnrFuse` 自带 `satW`：

```glsl
float satW(float lin, int ch, float sc) {
    float sat = gainAt(ch) * uSatK * sc;      // uSatK = 0.98
    return 1.0 - smoothstep(sat * 0.92, sat, lin);
}
```

饱和帧的权重**连续**降为 0，未饱和的短帧自然接管。这是**整像素加权**而不是
逐通道替换 ⇒ 三通道的结果都由各自的真实测量加权得到，色比天然一致。
它也正是 PC 的 `w × (1 − mask)` 语义。

连带效果：0.12.129 删掉的 sat-fix 现在有了正确的替代 —— 短帧真值由**融合**
接管，而不是融合之后再做二次替换（0.12.129 的注释里已经写明这是 HDR+ 的
原版分工）。

### 18.3 代价

暗部少了频域收缩的降噪增益（mismatch 权重 + 加权平均仍在）。用户已拍板
质量优先且高光优先，故选空间域。

### 18.4 验收

| 观察点 | 期望 |
|---|---|
| 日志 `fuse` 字段 | `"mm"`（不再是 `"dft"`） |
| 白斑周围的灰圈/绿边 | 消失（高光在融合阶段就由短帧真值接管，D4 不再带伪造色度） |
| 粉底上的局部灰斑 | 消失或显著减少（PC3D 面对的是真实测量的色度，不是重建伪值） |
| 灯内部 | 无分界线（0.12.129 已解决，本版保持） |
| `hlChroma` | 仍应在 ±0.4 内 |
| 暗部噪声 | 可能略高于 0.12.129（频域收缩的增益没了）—— 这是本次的已知取舍 |

## 19. 0.12.131~132：A 的回滚 + allSat 强制启用（补齐遗漏记录）

### 19.1 0.12.131：回滚 A

0.12.130 的 `if (hdr_active) use_dft = false;` 真机确认切到了 `fuse="mm"`，
但样片出现**比 129 更明显的水平分界线**。根因在 `kFsMfnrFuse` 自己的兜底：

```
短帧未饱和 → 四帧加权 → v = 短帧归一值（可达 2.8×满阱）
短帧也饱和 → 四帧权重全 0 → v = r0（参考帧饱和值 = 1.0×满阱）
```

两者相差整整一档，而分界线的位置正是短帧的饱和边界 —— 和 0.12.102~128 的
sat-fix 是同一个坑，只是这次藏在融合的兜底分支里。**任何"有真值/没真值"的
二分都会留下接缝**，除非有 inpaint 把两侧连起来。⇒ 回滚到 129 的单路径状态。

### 19.2 0.12.132：allSat 强制启用

灯面偏暖的数值原因：三通道全饱和时本域的值恒为满阱比例
`(gainR, gainG, gainB) = (2.254, 1.000, 1.525)`；opposed 的 `refavg` 只能把 G
抬到 `((∛2.254 + ∛1.525)/2)³ = 1.89` ⇒ 归一化 `(1.19, 1.00, 0.81)`，明显偏暖。
这不是"色相没保住"，而是 opposed 的语义（三通道满阱相同）在 WB 域不成立。

改法：`const bool grecon_on = true;`（不再受 `hl_grecon` 设置控制）。三通道全饱和
⇒ 真实色度不可知 ⇒ 中性白 + luma 锚。真机确认灯面变白。

**遗留问题（本版修的就是它）**：luma 锚取的是"三通道满阱的 luma"，而真实亮度
远高于满阱（短帧在灯芯也饱和 ⇒ 真实值 ≥ 2.8×满阱）⇒ 灯面"白但灰"。
0.12.132 的日志还有一个**字段缺陷**：`hlGRecon=0`（读的是设置入参），而
allSat 实际已强制启用 —— 133 起该字段恒 1，反映真实着色路径。

## 20. 0.12.133（方案 B）：mask 跨域 + PC3D 收手 + 全饱和区 inpaint

三块同属一套 RAW 域饱和掩码，缺任何一块都会在别处留下接缝。

### 20.1 块 1：RAW 饱和掩码沿 alpha 跨域（RCD → CCM → D4）

- 掩码源 = HL 已有的**块级膨胀掩码** `tex_hl_dil_`（3×3 photosite 一块，
  块内任一通道饱和即置位，已做过 darktable 的 3/5/7 块环形 dilate）。
  它就是 PC/Bento 语义里的 RAW highlight mask（`kFsHlMask` 逐字对应
  `hlVal = raw/whitePoint[c] ≥ 0.987`），**复用而不是重算**：同一事实算两遍
  只会引入第二套阈值。
- `kFsRcdChroma` / `kFsRcdChromaB` 按**源 mosaic 坐标** `p/3` 读它，写进输出
  alpha；alpha 随 RGB 一起被 fbo 几何旋转到 D3/D4（不需要传递旋转参数）。
- 透传：`kFsCcm`、`kFsCaCorr`、`kFsColorSmooth`、`kFsHdrMertens`（取 zero 帧的
  alpha）。全部只透传、不参与任何计算。
- 未跑 HL（`hl_mask_tex_ == 0`）时 `uMaskOn=0` ⇒ alpha 恒 0，逐位回到 132 行为。

### 20.2 块 2：PC3D 在高光处收手（`w × (1 − mask)` 的逐样本版）

**只 mix 中心像素是不够的**：高光像素即使最后被 mix 回原值，它作为**邻域样本**
仍然参与了粉底像素的加权平均 —— 绿边正是"白斑的重建色度被摊进粉底"。所以：

1. `kFsPc3d` 的主循环里，每个采样点的 `w` / `w2` 乘 `(1 − mask)`（样本权重 0）；
   自引导参考 `gref` 的 3×3 同样排除 —— 高光色度是重建值，不该进参考。
2. 输出处再 `mix(resColour, orig, mask)`（中心保护，双保险）。
3. 两趟都启用（`scale == 1` 时第一趟是唯一平滑趟；`scale > 1` 的低分辨率趟不启用，
   见 §20.5 的已知限制）。

语义与 PC 的 `oWeight = existingWeight × (1 − maskWeight)` 一致：高光退出平均，
而不是"平均完再改回来"。代价是 PC3D 多 ~150 次 texelFetch（只在 `uMaskOn=1` 时
执行），`pc3dMs` 字段可直接读。

### 20.3 块 3：全饱和区亮度 inpaint（替代"满阱 luma 锚"）

两个新 pass，都在 **MFNR 路径 + 真有更短曝光（`frame_scale > 1`）** 时才执行：

**① `kFsMfnrShortVal`（短帧真值图，raw 尺寸 RGBA16F）**
短帧按**与 sat-fix 完全同一套位移场**（collar flow 修正后的 tile 场）亚像素采样，
`linSub` 4 个同相位 tap，`× frame_scale`；`a = 1` 表示该位置短帧未饱和。
它不参与融合，只提供"哪里有真值"。

**② `kFsHlInpaint`（融合之后、HL 之前，替换 `tex_fused_` 供 HL/P0 消费）**
对每个 photosite：

| 条件 | 输出 |
|---|---|
| 长帧未饱和（mark != 0） | 原样（真测量） |
| 长帧饱和 + 短帧有真值 | 短帧值（真实 scene-referred 高光） |
| 长帧饱和 + 短帧也饱和 | 3 环（8/16/24 photosite）× 8 方向、权重 `1/d²` 的归一化卷积；无样本时退回短帧满阱 `gain[c]·scale`（物理下界） |

为什么这次不会有分界线（130 的病）：三条分支在短帧饱和边界处**收敛** ——
边界上的真值本来就是 `scale×满阱`，扩散值同一量级，深处退回的也是它。
而 132 的满阱 luma 锚把灯面钉在 1.0×满阱，这就是"白但灰"。

HL 全链路口径不受污染：mask / chroma 统计只用 mark=2（长帧未饱和）的样本，
而 inpaint 只改 mark=0 的像素。HL apply 的 allSat 分支拿到的 `lv` 变成 inpaint
后的真实亮度 ⇒ 中性白 + 正确亮度。

### 20.4 验收（真机日志字段）

| 字段 / 观察点 | 期望 | 说明 |
|---|---|---|
| `hlMaskTx` | **1** | RCD 拿到了掩码（alpha 链生效） |
| `hlInp` | **1** | inpaint 真跑了（短帧真值 + 标记都有效） |
| `hlInpMs` | 数十 ms 量级 | 成本可读，不藏 |
| `hlGRecon` | **1** | 132 起 allSat 强制启用（字段已修正） |
| `pc3dMs` | 高于 132（≈+50~100%） | 掩码权重让每格多 4 次采样 |
| `hlChroma` | ±0.4 内 | 保持 |
| 蝴蝶白斑绿光晕 | 消失 | 块 2 |
| 粉底灰斑 | 消失 | 块 2 |

### 20.5 已知限制（写清楚，不假装全覆盖）

1. **AMaZE 档 / 双线性档**不走 RCD 三段 ⇒ 没有 alpha 链 ⇒ PC3D 不收手（旧行为）。
   默认 RCD 档不受影响。
2. **PC3D `scale > 1`**（暗光高噪声，低分辨率首趟）时，首趟的低分辨率图不带 mask，
   只有全分辨率第二趟收手。高光问题主要出现在亮场景（`scale = 1`），故本版先覆盖
   这一支；`pc3dSc` 字段可确认走了哪支。
3. **叠加档 `pc3d = 2`**：PC3D 之后还会跑 P4 色度平滑，P4 不读 mask ⇒ 高光会被
   再平滑一次。默认替换档（`pc3d = 1`）不受影响。
4. inpaint 只覆盖"参考帧饱和"的 photosite；短帧在灯芯也饱和的深处给的是
   `scale×满阱`（下界），不是真实峰值 —— 真实值不可知，给下界是唯一诚实的表示。

## 21. 0.12.133 事故与 0.12.134 修正：inpaint 的判据粒度错了

### 21.1 现象（真机 2026-10-28 20:04）

- 整个灯面**黄绿**：实测显示域 RGB `(0.888, 0.974, 0.835)`（G 高 9.6%、B 低 14%）。
  同一盏灯在 0.12.132 是 `(0.954, 0.950, 0.931)` —— 中性。
- 灯的外圈出现**细碎彩色噪点**（用户截图）。
- 日志：`hlInp=1`、`hlInpMs=2.5`（太快 = 绝大多数像素走单点分支）、`pc3dMs=386`。

### 21.2 根因：单通道注入撕裂色比（和 0.12.128 同一个错，换了位置）

0.12.133 的 inpaint 判据是 `mark == 0`（**本 photosite** 饱和），注入的是
**该 photosite 的短帧逐通道值**。灯面的真实情况是：

```
G  满阱 = 1.00×gain，真实亮度 1.2×gain ⇒ G 饱和
R  满阱 = 2.25×gain，1.2 < 2.25      ⇒ R 未饱和（真值 1.2）
B  满阱 = 1.53×gain，1.2 < 1.53      ⇒ B 未饱和（真值 1.2）
```

于是 G 位置被填短帧值（短帧归一后 ≈ 2.8×gain_G），R/B 保持真值 1.2：

```
注入后：G 2.82  vs  R 1.2 / B 1.2   ⇒  G 高 2.35 倍  ⇒  灯面全绿
```

HL 的 allSat 救不了：它的判据要求**三通道都** ≥ 0.99×满阱，而 R/B 是未饱和的
真值 ⇒ 该像素走普通 opposed（`max(v, refavg+chroma)`，只抬不压）⇒ **保留 2.82**
⇒ 绿被原样送进 D4。边缘的彩点则是短帧逐通道噪声 ×2.82、又因为 PC3D 收手
（块 2）不被平滑 —— 两个改动叠加的结果。

一句话：**注入的判据粒度必须与"色度是否可知"的粒度一致**。单个 photosite
饱和 ≠ 色度不可知（其余通道还有真值）。这与 0.12.128「逐 photosite 注入必然
撕裂通道」是同一条规律，只是 128 在 sat-fix、133 在 inpaint。

### 21.3 0.12.134 的改法

**① 判据收紧到 2×2 块三通道全饱和**（与 `kFsHlApply` 的 allSat 同一口径）：
8 邻域取三通道值，`R ≥ 0.99·gainR && G ≥ 0.99·gainG && B ≥ 0.99·gainB` 才注入。
部分饱和像素**一律不碰**，交给 opposed（= 0.12.129 的路径）—— 那里 R/B 有真值，
G 由立方均值从 R/B 外推，色相天然一致。

**② 注入量改成标量亮度 k**（不再是逐通道值）：
- 短帧真值图只存 `归一化亮度 = 短帧值 / gain[c]`（已 ×scale）⇒ 三通道可比；
- inpaint 对 k 做归一化卷积，输出 `gain[c] × k`；
- 三通道比例恒为 `gain`（满阱比例）⇒ 色度由下游 allSat 统一改写成中性白，
  **不可能再出现逐通道色噪**。这与 0.12.132 的"白"是同一套语义，只是亮度不再
  钉死在 1.0×满阱。

**③ k 的两支平滑（分开，不能合并）**：
- 中心有真值 → 只做 3×3（±1 photosite）平滑：压掉单点噪声与 1px 对齐误差，
  又不跨过明暗边界把邻区低亮度搬进来；
- 中心无真值（短帧也饱和 = 灯芯最亮处）→ 3 环（8/16/24）× 8 方向、`1/(d²+1)`
  扩散；环上也没有有效样本时退回 `scale`（短帧满阱下界）。

### 21.4 验收

| 观察点 | 0.12.133 | 0.12.134 期望 |
|---|---|---|
| 灯面 RGB | (0.888, 0.974, 0.835) 黄绿 | 中性（R≈G≈B，±2%） |
| 灯面亮度 | 0.90（不亮） | 高于 132（0.94）—— 真实亮度在 allSat 之外仍有提升 |
| 灯外圈彩点 | 明显 | 消失（不再有逐通道注入） |
| `hlInpMs` | 2.5 ms | 上升（k 的多 tap 平均；只在高光区付出） |
| `hlMaskTx` / `hlInp` | 1 / 1 | 仍为 1 / 1 |
| 分界线 | 无 | 无（部分饱和区回到 129 的单路径） |

| 0.12–0.25 | 0.0044 / 0.0040 | 0.0041 / 0.0038 | 0.0043 / 0.0038 |
| 0.25–0.50 | 0.0031 / 0.0029 | 0.0027 / 0.0029 | 0.0029 / 0.0028 |
| **> 0.50** | **0.0026 / 0.0027** | **0.0085 / 0.0102** | **0.0092 / 0.0106** |

**暗部逐桶完全不变，亮部涨 3.5~3.9×。** 这就是"整体彩噪"的全部来源 ——
不是降噪链坏了，而是**高光不再被色度降噪**：

- 0.12.133/134 的 PC3D 收手是**无条件**的（中心是高光也不平滑）；
- 0.12.134 又去掉了输出 mix —— 但 mix 只是把结果换回原值，真正的伤害是
  "高光内部一次色度平均都没做"。

### 22.2 收手的语义错了：该排除的是"样本"，不是"中心"

132 的灯面中性白 `(0.932, 0.926, 0.907)` **正是 PC3D 平滑出来的**。
高光色度由 HL 重建、本身是平滑的低频量；要防的是它作为**样本**被搬进邻居
（绿边），不是它自己被平滑。0.12.135 改成：

```glsl
center_lit = hlMaskAt(xy) > 0.5;
keep = (uMaskOn > 0 && !center_lit) ? (1 - mask(sample)) : 1;
w *= keep;  w2 *= keep;
wm = min over { w[i] : keep[i] > 0.5 };   // 排除项不能参与 min
ws = (w - wm) * keep;  w *= ws;           // 再归一化
```

**`wm` 必须跳过被排除项**：把某个样本乘成 0 会压低 `min`，而
`(w−wm)/|w−wm|` 归一化会把其余三个**放大** —— 逐样本 mask 的归一化陷阱，
不写这一条，排除反而变成增强。

结果：`center_lit=1` 的像素与 132 逐位同构（灯面回中性）；`center_lit=0` 的
像素不再吸收高光色度（绿边保持修复）。

### 22.3 inpaint 止损：数据说它没有收益

灯面 RAW 逐通道分析（`FILMKIT_20261028-201831.dng`）：

```
发光面三通道同时饱和：0.82 / 0.82 / 0.83   ← 同时，不存在"G 先撞阱"
未饱和部分归一化 RAW：0.857 / 0.841 / 0.857  ← 三通道一致 = 中性，亮度≈满阱
```

即：灯的真实亮度就在 **1.0~1.2×满阱**，短帧（−1.5EV，scale=2.82）归一后的
`k ≈ 1.0~1.2` ⇒ inpaint 能给的亮度提升只有 0~20%，显示域几乎看不出来；
而它把短帧的逐点噪声与 1~2px 对齐误差搬进高光 ⇒ 灯面**亮度台阶**（用户看到的
"色彩断层/黄色色块"）。更糟的是 133/134 的 `k` 没有夹住，个别 `k<1` 把灯面
压得**比 132 更暗**（显示域 0.890/0.898 vs 0.932）。

⇒ `kHlInpaintOn = false`（默认关；短帧真值图也不生成，100MB 纹理与全屏 pass
成本归零）。代码全部保留，改一个常量即完整 A/B 通路。

**亮度提升这条线不该靠"事后填值"**：真正的多曝光信息应该由 HDR/Mertens
（或 satW 融合 + clipped inpaint）在**融合阶段**带入，那是另一条独立的工作线。

## 23. 0.12.136：绿光晕/品红斑块的真正根因 = HL 判据只认"三通道全饱和"

### 23.1 数据（粉色陶瓷椅背的镜面反光，DNG 逐 photosite）

```
WB 域实测   R 1.671   G 1.000   B 1.510
满阱        R 2.217   G 1.000   B 1.510
             ↑ 未饱和   ↑ 满阱    ↑ 满阱
⇒ 饱和通道数 nsat = 2（不是 3）
```

`kFsHlApply` 的 allSat 判据要求 **三通道都** ≥ 0.99×满阱 ⇒ 这类像素永远进不去，
落到 opposed 的 `max(v, refavg + chroma)`：

```
G 位：refavg_G = ((cbrt(R)+cbrt(B))/2)³ ≈ 0.95 < v = 1.00  ⇒ 不抬，保持 1.00
R 位：未饱和 ⇒ 不进入
⇒ 输出色比 (0.754 : 1.00 : 1.00) = 青绿  ← 用户看到的"绿色光晕"
```

若反光的通道饱和顺序相反（R 先满阱），同一套逻辑给出 `(1.00 : 0.85 : 0.90)` =
品红 —— 用户圈出的 2、3 号"品红斑块"是同一个机制的另一半。

**这不是 PC3D 造的，也不是 inpaint 造的。** 0.12.133~135 我一直在 PC3D 上打转
（收手 → 权重排除 → 语义修正），方向从一开始就错了：PC3D 只能"摊开"或"保留"
这个伪色，它没有能力修正它。相反，135 为了保留伪色而收手，还额外把亮部色噪
抬了 3.5×（§22.1）。

### 23.2 修复：判据从"三通道全饱和"改成"≥2 通道饱和"

```glsl
int nsat = 0;
if (Rv >= uSatClip.x * 0.99) ++nsat;
if (Gv >= uSatClip.y * 0.99) ++nsat;
if (Bv >= uSatClip.z * 0.99) ++nsat;
if (nsat >= 2) { /* 按参考比重建三通道 + 实测 luma 锚 */ }
```

为什么这不是"放宽阈值"而是**域语义的修正**：

- darktable 的 allSat 判据是三通道全饱和，前提是 **raw 域满阱相同**（三通道同时
  到顶）。我们的 HL 跑在 **WB 之后**，满阱逐通道不同（2.217 / 1.0 / 1.510）——
  三通道"同时"饱和只是恰好同比例的特例。
- 两个通道顶到满阱就已经证明**真实亮度 ≥ 满阱**；此时第三个通道只剩"下界"信息，
  色比不可知 ⇒ 与全饱和同样处理（参考比 → 中性白 + 实测 luma 锚）。全饱和是其特例。
- **nsat = 1 不动**：真实的红色 LED / 彩色光源只饱和一个通道，放宽到 1 会把它们
  洗白。这是本改动与"无脑放宽"的区别。

对该像素的数值结果：

```
lv  = 0.2126×1.671 + 0.7152×1.000 + 0.0722×1.510 = 1.179
den = 0.2126×0.9848 + 0.7152 + 0.0722×0.9925    = 0.996
sc  = 1.184  ⇒  输出 (1.166, 1.184, 1.175)  ← 中性白，且比原来的 max 值更亮
```

### 23.3 同时回退 PC3D 的掩码逻辑（0.12.136）

高光先被 HL 修成中性白之后，PC3D 摊开的就是"白"——不需要、也不应该为它改变
平滑语义。回退到 132 的逐位行为，`uOrig/uMaskOn/keep/wm` 全部删除。

alpha 链（RCD→CCM→CA/CS/Mertens）保留但**当前无消费者**：留着是因为它只多一次
texelFetch，且下一轮若要在 defringe/P4 层做同样的"样本排除"还需要它。
日志 `hlMaskTx` 仍为 1（表示 alpha 写了），但**不代表 PC3D 在使用**。

| 观察点 | 期望 |
|---|---|
| 粉色椅背的镜面反光点 | 中性白，周围无绿光晕 / 品红环 |
| 柜内小灯 / 椭圆灯 | 灯面均匀白，左上角黄斑消失（边缘的部分饱和也进 nsat≥2） |
| 灯面断层 | 无（inpaint 仍关闭） |

| 日志 `hlChroma` | 仍在 ±0.4 内 |

## 24. 0.12.137：高光边缘的淡绿光晕（136 的判据没覆盖"未饱和的光晕环"）

### 24.1 现象与用户的关键信息

用户：「问题只剩高光边缘淡绿色光晕，**这个光晕在 DNG 里也是有的（淡白色）**」。

这句话把范围钉死了：光晕的**亮度结构是真实的**（RAW 里就有），出问题的只有**颜色**。

### 24.2 数据：RAW 是粉白，成片是绿

粉色陶瓷椅背镜面反光，DNG 逐 photosite（WB 域，中性白 = 1.0）：

| 区域 | R | G | B | R/G | B/G |
|---|---|---|---|---|---|
| 高光核心（r<4px） | 1.700 | 0.985 | 1.326 | 1.73 | 1.35 |
| 光晕内环（4–8px） | 1.321 | **0.807** | 1.022 | 1.64 | 1.27 |
| 光晕外环（8–14px） | 1.021 | 0.623 | 0.750 | 1.64 | 1.20 |
| 背景（24–50px） | 0.301 | 0.230 | 0.223 | 1.31 | 0.97 |

**RAW 里光晕的 G 是三个通道里最低的**（R/G 1.64）—— 即"粉白"。成片里这一圈却是
淡绿（G 相对最高）。**色相被翻了 180°。**

### 24.3 为什么会翻

- 136 的 `nsat ≥ 2` 判据只改**2×2 块里至少两个通道到满阱**的像素 —— 那是高光
  **核心**（G/B 满阱、R 0.754）。
- **光晕环的像素全部未饱和**（R 0.60 / G 0.81 / B 0.68 归一化，nsat = 0）⇒ 判据
  根本不碰它们。
- 那一圈的绿只能来自 **RCD 在饱和边缘的插值伪彩**：G 在 Bayer 里有 2× 采样密度，
  亮度陡变处沿梯度被拉高；PC3D（核 11）再把它摊成 3~10px 的光晕。
- ACR/AMaZE 在同位置不给这个伪彩 —— 这就是"RAW 看是白、我们看是绿"的差别。

### 24.4 修复：PC3D 输出处对亮部去饱和

```glsl
float yl  = dot(resColour, LW3);
float gHi = smoothstep(0.70, 1.00, yl);
resColour = mix(resColour, vec3(yl), gHi);   // 只动 luma ≥ 0.70 的亮部
```

为什么放在这里、用 luma 门控（而不是用 mask）：

- **luma 门控天然区分**：光晕 luma≈0.93（gate≈0.77）、高光核心≥1.0（gate=1）、
  粉底/灰块 luma≈0.25~0.36（**gate=0，逐位不变**）。
- 用 mask 反而错：mask 是"RAW 饱和"标记，光晕环**未饱和**不在里面；而 dilate 后
  的 mask 又会把 9px 外的粉色背景包进来，去饱和后变成"灰环"。
- 放在 PC3D 输出 = 所有色度处理（含伪彩摊开）之后、defringe/film 之前。

不去 RCD 层修伪彩：那是结构性缺陷（换 AMaZE 才根治），而在**亮部去饱和**是影像学
的通用做法（ACR 的高光恢复同样把接近白点的区域推向白）。

### 24.5 验收

| 观察点 | 期望 |
|---|---|
| 高光边缘的光晕 | 淡白（不再绿），亮度结构保持 |
| 高光核心 | 白 |
| 粉底 / 灰块 | 逐位不变（luma < 0.70，gate=0） |
| 红色苹果、彩色物体 | 不变（luma 远低于 0.70） |
| 亮部的真实暖色高光 | 会更接近白（这是本改动的已知代价，与 ACR 行为一致） |

## 25. 0.12.140：光晕应该透出"背景色"，不是灰也不是白

### 25.1 139 为什么等于没改

139 用 136 的成片做离线核算（不需要真机）：

```
光晕环（2–12px, luma 0.60–0.75）  R/G 1.233
背景   （15–45px）                R/G 1.313
```

`gHi = smoothstep(0.70, 1.00, luma)` 在 luma=0.66 处只给出 **0.03** 的混合系数
（0.03×0.85 = 0.026）⇒ 光晕 R/G 只从 1.233 变到 1.249，离背景 1.313 还差得远。
**阈值起跳点定在光晕亮度之上，等于没改。**

第二个错：139 的 alpha 用的是**膨胀后**的掩码（`tex_hl_dil_`，核心外 9px 都标 1），
于是光晕被判成"核心"、走了 G 封顶分支，根本进不了背景混色分支。

### 25.2 140 的三处修正

1. **alpha 改传未膨胀掩码**（`tex_hl_mask_`）：mask=1 只覆盖真正的饱和核心，
   光晕（未饱和）⇒ mask=0，正确分流。
2. **阈值 0.45–0.75**：覆盖光晕的实际亮度区间（0.66~0.93）。对背景像素无害 ——
   它们的目标色 = 自身色度 × 自身亮度，mix 恒等。
3. **只在"背景确实更暗"时混**（`bgL < 0.75 × yl`）：12px 内全是亮的（灯面内部、
   大反光）说明它是核心的一部分，不混；也避免取到灰墙把光晕染灰（137 的灰块同型）。

光晕的目标色 = `bgC × (yl / bgL)`，即**背景的色度 + 本像素的亮度**：
散射光的物理颜色就是"背景色被照亮"，既不是中性灰（137 的错），也不是纯白。

### 25.3 离线预测（136 成片实测值代入 140 公式）

| 0.66（外环） | 0.67 | 1.231 → **1.285** | 1.312 |
| 0.93（内环） | 0.85 | 1.231 → **1.300** | 1.312 |

B/G 1.120 → 1.10（背景 1.09）。**落到与背景相差 1~2%** ⇒ 既不再偏绿（原先差 6%），

## 26. 0.12.142：停止在 D4 层打补丁，回到分层机制

### 26.1 用户判断是对的

136→140 三版，我做的事是：去饱和 → G 封顶 → 混背景色。每一版都换一个症状
（绿 → 灰 → 粉+灰块+反光色块），因为**都是在 D4 层给"已经错了的色度"找补**。
这不是调参能解决的 —— 是分层机制没理清。

### 26.2 真正的 bug：allSat 判据跨 2×2 块取值

`kFsHlApply` 用 `neighborOfChan8(p, want)` 取三通道。R 位 (x,y) 的 B 会先命中
**右下** (x+1,y+1)，而那个 photosite 属于**下一个** 2×2 块。于是：

```
光晕像素自身   R1.32 / G0.81 / B1.02   （全未饱和，是真实测量）
右下邻居       R1.67 / G1.00 / B1.51   （饱和核心）
⇒ 8 邻域 nsat = 3 ⇒ 被 allSat 改写成中性白
⇒ 光晕的真实色度（R/G 1.63）被抹成 1.23 ⇒ 粉底上显绿
```

**"2×2 块 = 一个 RGB 像素"是 Bayer 的物理单位**，块内是否饱和只能由块内四个
photosite 决定。0.12.141 加了 `blockRGB()` 严格按块取值（G 位两枚取平均），
不跨块 —— 光晕不再被核心污染，回到 RAW 的真实色度。

这是 136 引入 nsat≥2 时埋下的 bug：判据放宽是对的，取值方式错了。

### 26.3 D4 层的三个补丁全部删除

`kFsPc3d` 只做它本来该做的事（色度平滑 + guided upsample）。G 封顶、去饱和、
混背景色一律移除 —— 它们都在和"RAW 的真实色度"打架。

### 26.4 高光趋白归位到 film 的 highlightRolloff

`white0` 1.00 → **0.88**（0.88→1.00 平滑到全白）。理由：
- 0.12.111 把起点定在 1.0 的前提是"filmic 输出 ∈[0,1]，只有真超上限才溢出"。
- 但显示域 **0.88~1.0 这一段已经是视觉上的白**（sRGB 0.94 以上几乎分不出色相），
  让这一段保留色度，正是"高光周围一圈彩色雾"的来源（光晕显示域 luma≈0.93）。
- 只动 `l > 0.88`：灰块（0.36）、粉底（0.55）逐位不变 —— 0.12.106 的"过渡带被
  洗白"教训不会重演（那次起点是 knee=0.80 且作用于**线性**亮部，范围完全不同）。

### 26.5 分工（这才是"机制"）

| 层 | 职责 | 对应实现 |
|---|---|---|
| RAW（WB 后） | 饱和像素重建：判据按 **2×2 块**｜重建按参考比｜部分饱和 ≥2 通道 | `kFsHlApply` + `blockRGB` |
| RAW → D3 | 去马赛克（饱和边缘的插值伪彩是它的已知缺陷） | RCD 三段 |
| D4 | **只做色度降噪/平滑，不改色相** | PC3D / P4 |
| 显示域 | 高光趋白（rolloff）、gamut、OETF | `highlightRolloff` / filmic |

**剩余已知缺陷（诚实记录）**：RCD 在饱和边缘的插值伪彩（G 采样密度 2× 导致）
仍然存在，142 靠 highlightRolloff 把 l>0.88 的那部分压掉；彻底解决要换 AMaZE
（`demosaic=2` 已有 CPU 实现，但还没接进成片链），那是独立的一轮工作。

## 27. 0.12.143：绿不是色度，是"宽度"——PC3D 首趟把 1px 伪彩摊成 3~10px 的雾

### 27.1 142 的光晕其实是中性的

对 142 成片的用户截图逐环测量（显示域）：

| 区域 | R/G | B/G |
|---|---|---|
| 背景（粉底） | 1.305 | 1.098 |
| 光晕 r=18px | **1.035** | 1.002 |
| 光晕 r=28px | 1.033 | 1.003 |
| 光晕 r=40px | 1.026 | 1.006 |

**光晕的色度几乎是中性（R/G 1.03），像素值层面没有"绿"。** 绿色感来自
**同时对比**：一个中性亮区放在饱和粉底上，视觉系统会朝补色方向感知它。

### 27.2 放大这个错觉的是"雾的宽度"

中性本身只会在 1~2px 的过渡带上出现（那是 RCD 在饱和边缘的插值伪彩）。真正让它
变成"一圈明显绿边"的，是 PC3D 在 `scale=2` 时的**低分辨率首趟**：

```
gaussdown(1/2) → 低分辨率 PC3D 平滑（高光与光晕在 1/2 域被平均）
              → guided upsample → 伪彩被摊到 3~10px 宽
```

宽度一大，同时对比的效应就压不住了（142 的日志 `pc3dSc=2`）。

### 27.3 改法：只在首趟排除高光样本

```glsl
// 首趟（低分辨率）：mask 按 uDown 映射回全分辨率，高光样本权重 0
w *= keep;  wm = min over { w[i] : keep[i] > 0.5 };  ws = (w - wm) * keep;
// 第二趟（全分辨率）：不排除 —— 逐位保持 132
```

两个关键点：
1. **只在首趟**：135 的教训是"第二趟也收手 ⇒ 亮部色噪 3.5×"。首趟排除只影响
   "哪些色度被带进低分辨率金字塔"，第二趟照常降噪。
2. **`wm` 必须跳过被排除项**：把样本乘成 0 会压低 `min`，而 `(w−wm)/|w−wm|`
   会把其余三个放大 —— 排除会变成增强。

配合 142 的 `white0=0.88`（高光趋白），期望：伪彩不再被摊宽 → 只剩 1~2px 的
过渡带 → 视觉上不再成"环"。

### 27.4 剩余缺陷（下一步才是 AMaZE）

RCD 在饱和边缘的 G 伪彩是**源头**，143 只是不让它被放大。彻底解决要换成 AMaZE
（`demosaic=2` 的 CPU 实现已在仓库里，还没接进成片链）。

## 28. 0.12.147：淡绿光晕的真凶是 `color_smooth` 的"中性旁证"（不是 PC3D / 不是 HL）

### 28.1 现象与坐标

用户截图（478×970，粉勺镜面白高光特写）。在成片 4080×3072 里定位到该高光
（JPG `(806,1676)`，对应 DNG sensor `(x=1676, y=2265)`），量得**过渡带**
（`luma 0.66~0.78`，宽 4~8px）的色度：

| 区域 | R/G | B/G |
|---|---|---|
| 粉底（14px 外） | 1.31~1.35 | 1.12~1.14 |
| **过渡带** | **1.01~1.04** | **1.02** |
| 高光核心 | 1.04 | 0.99 |

过渡带比**核心还中性**（1.01 < 1.04），且从核心到粉底没有单调过渡 —— 这解释
了"一圈淡绿"：中性的亮带被饱和粉底包围，同时对比把它读成补色。

### 28.2 RAW 真值：那里是粉的，且未饱和

DNG 逐 photosite（`/tmp/mosaic.npy`，2×2 块，WB 域）：

| JPG 坐标 | RAW R | RAW G | RAW B | R/G | 饱和 |
|---|---|---|---|---|---|
| (800,1650) | 0.572 | 0.176 | 0.408 | 3.25 | 否 |
| (808,1652) | 0.714 | 0.210 | 0.523 | **3.40** | 否 |
| (804,1656) | 1.487 | 0.444 | 1.154 | 3.35 | 否 |

与粉底同色相（R/G 3.3）、甚至更饱和。**没有任何"紫/绿"的真实成分。**

libraw/AHD 在同一位置给 `R/G 1.42`（粉）；我们成片给 `1.03`（中性）——
色度被洗掉约 90%。

### 28.3 定位过程（排除法，每一步都有数）

1. **HL 饱和重建**：过渡带 `nsat=0`（R 0.82 / G 0.25 / B 0.67，满阱 2.23/1.0/1.51），
   `v < uHlClip × 满阱` ⇒ 三个分支（allSat / R-B / 普通 G）**都不进**。不是它。
2. **PC3D**：142 已删掉 D4 层全部色度修补，只剩 143 的"首趟样本排除"；且
   `pc3dSc=2` 时首趟在 1/2 域、排除的是 mask=1 的核心。不是它。
3. **`passDefringe`**（`prog_df_`，日志 `df/dfCavg`）：判据是
   `br0 = B−R > thr && gr0 = R−G > 0` ⇒ **紫象限**。粉色过渡 `R > G > B`
   第一条就挡住。不是它。
4. **`passColorSmooth`**（`prog_cs_`，日志 `csK/csOk/csOn`）：判据是"**局部色度峰**"
   + 两侧中性 ⇒ 命中后**去饱和到 15%**。

离线用 libraw 线性输出复现该判据（`/tmp/cs_phase.py`），在光晕带
（JPG x 780~860 / y 1620~1700）得到 **143 个命中**，色相分布：

| 色相 | 个数 | ch 中位 |
|---|---|---|
| 紫 `B>R>G` | 97 | 0.273 |
| 绿/青 `G 最大` | 27 | 0.286 |
| 粉 `R>B>G` | 19 | 0.261 |

而 RAW 真值是粉 —— 这 143 个里的绝大多数是**饱和边缘的伪彩**。
去饱和 15% 把它们压成中性：`(0.404,0.284,0.396) → (0.302,0.284,0.301)`，
预测 `R/G 1.063`，实测成片 `1.028`。**对上了。**

### 28.4 机理：饱和核的 `clip 白` 被当成了"中性旁证"

判据要成立需要"两侧更中性"。而饱和核心三通道全顶满阱、经 HL 重建后是
**中性白（ch ≈ 0）**。于是：

```
中心（真实粉过渡） ch = 0.23
核心侧探测点       ch = 0.00   ← 这是"信息缺失"，不是"中性"
粉底侧探测点       ch = 0.17
⇒ peak_ok = (0.23 > 1.05×0.17) && (0.00 < 0.5×0.23) = true
⇒ 中心被判成伪彩，去饱和 85%
```

**"一侧是 clip 白"不能证明"中心是伪彩"** —— 这是判据的语义缺陷，与像素无关、
与场景无关。v0.10.206 设计时只考虑了"两侧都是普通中性背景"的情形。

### 28.5 修法：掩码上的探测点不参与"中性"判定

2×2 块级饱和掩码 `tex_hl_mask_` 已经由 RCD 写进 alpha（0.12.133 块 1）、
经 CCM 透传（`kFsCcm` 保留 `s.a`）—— `color_smooth` 只是没读它。

```glsl
// 0.12.147：落在饱和掩码上的样本没有真实色度信息，不能参与"两侧中性"的判定
float cs[6] = {...};  bool satp[6] = { a3.a > 0.5, ... };
float mx_side, mn_side; int nv = 0;
for (int i = 0; i < 6; ++i) {
    if (satp[i]) continue;
    mx_side = max(mx_side, cs[i]);  mn_side = min(mn_side, cs[i]);  ++nv;
}
if (nv == 0) { oColor = vec4(c0.rgb, c0.a); return; }   // 全是饱和核：无真值，不动
bool side_ok = (mx_side < uSideK * ch0) && (nv >= 4);
bool peak_ok = (ch0 > uPeakK * mx_side) && (mn_side < uSideK * ch0) && (nv >= 2);
```

**替换值不动**（仍是去饱和 15%）—— 只改"能不能判"。

### 28.6 为什么不动替换值（三个方案都被离线否决）

| 替换方案 | 紫向残留 ch（6 张均值） | 结论 |
|---|---|---|
| 去饱和 15%（现行） | 0.034~0.040 | 紫边压得最狠，但把真色度一起洗了 |
| 沿梯度 ±6 亮度插值 | 0.110~0.132 | 端点落在伪彩带内 ⇒ **把伪彩搬回来** |
| 沿梯度 ±12~18 + 非饱和端点 | 0.126~0.196 | 同上，越远越糟 |
| 环带外 8 方向背景色度 | 0.126~0.224 | 紫边区域背景本身就是紫 ⇒ 更糟 |

结论：`color_smooth` 在 D4 上**没有真值**，任何"填充"都是猜。能做的只有
"该压的还压、不该压的别压" —— 这正是 28.5 那条判据修正。

### 28.7 紫边风险评估（为什么不会回归）

- **紫向（`B>R>G`）**：真正的紫边两侧是普通背景（非饱和），掩码不介入 ⇒
  逐位回到 0.10.209 的行为。`defringe` 的结构性判据（`B>R>G` + 窄带性 + 贴强边缘）
  仍然兜底。
- **绿/青向**：中心 `G` 最大，饱和核侧的样本被排除后，`mn_side` 来自另一侧，
  判据要求"至少一侧明显更中性" —— 与旧式等价。
- **暖向（`R` 最大）**：唯一行为变化 = 不再被 clip 白"证明"成伪彩。暖色窄带
  本来就没有"红边"的需求（用户历史反馈中从未出现）。

### 28.8 附带：AMaZE 接入完整链（`demosaic=2`）

v0.10.172 的 AMaZE 是独立第一支：原始 u16 → 自行线性化/WB/LSC → CPU AMaZE，
**绕开 HL 饱和重建与 P0 降噪**。当时 `amaze-REPORT.md §0` 的"不优于 RCD"结论
混入了两个变量，已不可归因。

0.12.147 把 AMaZE 并入 `c.rcd` 分支：读回 `tex_mos_`（HL 前置 + P0 之后的线性
mosaic，与 RCD 逐字节同源）→ `AmazeDemosaic` → `passAmazeUp` → CCM/P4/
color_smooth/PC3D/defringe/film **完全共用**。`c.dn` 也改为
`(rcd || demosaic==2)`，两档的差异只剩去马赛克算法本身。

日志 `amazeSrc` 由 `burst0/single` 改为 **`p0`**；`amazeMs` 含读回 + CPU + 上传。

### 28.9 验收（看日志 + 看画面）

| 字段 | 期望 |
|---|---|
| `csOn` | 1（color_smooth 仍在跑） |
| `demosaic` / `amazeSrc` | `amaze` / **`p0`**（切到 Amaze 档时） |

| `pc3dSc` | 1 或 2（与本改动无关） |

画面：粉勺/粉椅背高光外**那一圈淡绿消失**，过渡带回到粉白；紫边不回归；
灯面中性白不变。

## 29. 0.12.148：AMaZE 全红 = 浮点 `glReadPixels` 口径错（147 的回归）

### 29.1 现象

147 切到 Amaze 档后**成片全红**，RCD 档正常。

### 29.2 根因

`runAmazeFromMosaic` 读回 `tex_mos_`（RGBA16F）时用了：

```cpp
glReadPixels(0, y0, w, nr, GL_RGBA, GL_FLOAT, buf.data());   // ✗
```

ES 3.0 **只保证** `(GL_RGBA, GL_UNSIGNED_BYTE)`；浮点图像读回依赖扩展，X300 上
`(GL_RGBA, GL_FLOAT)` 读 RGBA16F 拿到的是无效数据。项目里早有这条结论
（`kFsStatPack` 的设计动机、"上一版 PFM dump 失败"的记录），147 接入时没沿用。

读回的垃圾 mosaic 喂进 AMaZE ⇒ 输出错色 ⇒ 全红。

### 29.3 修法

```cpp
std::vector<unsigned short> buf(...);
glReadPixels(0, y0, w, nr, GL_RGBA, GL_HALF_FLOAT, buf.data());   // ✓
cfa[i] = halfToFloat(buf[... * 4]);
```

这是本项目一直在用的组合（`logPassDiag` 读 RGBA16F 诊断像素就是 HALF_FLOAT）。

另加**读回自检**（比出一张红图好）：

```cpp
if (!(vmax > 1e-6f) || !std::isfinite(vmin) || !std::isfinite(vmax))
  return false;   // 全 0 / NaN ⇒ 口径错了，直接失败（照片优先红线）
dbg_amaze_min_ = vmin;  dbg_amaze_max_ = vmax;   // 日志 amazeR
```

验收：Amaze 档日志 `amazeR` 应形如 `[0.0001, 2.2]`（下限≈噪声底、上限≈R 满阱
2.23）。若为 `[0,0]` 或出现 inf，说明读回仍然错，成片会直接失败而不是出红图。

## 30. 绿光晕残留：RCD 抖动经 PC3D 平均成中性（下一步的落点）

147 只修了"`color_smooth` 不再把真色度当伪彩压掉"，残留仍在。链条是三级：

1. **RCD 在饱和边缘产生色度抖动**：离线 D4（不含 HL）实测该过渡带 R/G 在
   **0.93~1.55** 之间逐像素跳（RAW 真值 R/G 3.40、平滑）。
2. `color_smooth` 之前会压掉一部分（146 及以前 ⇒ 整条带被压成中性）。
3. **PC3D 把剩余抖动做色度平滑** ⇒ 高频抖动被平均成"低饱和的平均色" ⇒ 中性带。

所以 147 之后残留量 = 「RCD 抖动经 PC3D 平均后的残余」，**不可能靠 D4 层再压**。
离线已验证：任何"填充值"方案（去饱和 / 亮度插值 / 环带外背景色度）在紫向都
会把伪彩搬回来（§28.6 表）。

**下一步（唯一有普适性的落点）**：在 `kFsRcdChroma` 里，对"本 2×2 块三通道都有
实测值、但紧邻饱和块"的像素，chroma **不走自由插值**，而用 `blockRGB` 的块内实测
色比 × 自身亮度。理由：块内四个 photosite 是同一束光的测量，未饱和时其色比就是
真值；伪彩恰恰来自跨块插值。掩码（`tex_hl_mask_`）已在 RCD 输入里，不需要新纹理。

### 29.4 更正（0.12.149）：第二个错是**读错了通道**，不是读回格式

148 改成 `GL_HALF_FLOAT` 后仍然全红，日志 `amazeR=[0,0]`、`amazeMs=0`。两个独立的错：

**① 读 `.r` 拿不到 mosaic。** `kFsRawDenoise` 的输出是**按通道分量**放的：

```glsl
oColor = vec4(ch == 0 ? v : 0.0, ch == 1 ? v : 0.0, ch == 2 ? v : 0.0, 1.0);
```

即每个 photosite 只有自己那个 RGB 分量有值，其余为 0（这正是 HL 要用
`mosAt(p) = at3(texelFetch(...).rgb, chanAt(p))` 读它的原因）。读 `.r` 只在 R 位置
拿到真值，G/B 位置全是 0 ⇒ 喂给 AMaZE 的是"只有 R 有值"的 mosaic ⇒ **全红**。

```cpp
const int k = ((y & 1) << 1) | (x & 1);
const int ch = pattern[k];
const float v = halfToFloat(buf[(i * w + x) * 4 + ch]);   // ✓ 按 photosite 通道
```

**② `amazeMs`/`amazeR` 被 `passCaCorrect` 清零。** 148 把帧首清零加进了
`passCaCorrect`，而它在 AMaZE 之后、日志之前执行 ⇒ 诊断字段永远是 0，把"读回失败"
和"读回成功但通道错"混成了同一个读数。149 把清零移到 `finishStillChain` 帧首。

**教训**：诊断字段的清零点必须与"它被写入的时刻"对齐；跨 pass 清零等于把诊断
本身变成误导源（这类坑在 v0.10.198 的 `csOn` 上已经踩过一次）。

## 31. 0.12.150：AMaZE 档两个"静默缺失"——LSC 和饱和掩码

149 修好读回后 AMaZE 能出图了（`amazeR=[0, 1.31~1.89]`、`amazeMs≈0.9~1.7s`），
但用户指出两处观感异常：镜头阴影没生效、HDR 观感不对。排查出两个**静默缺失**
（不报错、不崩溃，只是少了一步）。

### 31.1 LSC 没接

原先的判断是错的：「LSC 已在 P0 内乘过」。事实：

- `kFsRawDenoise`（P0）的 uniforms 只有 `uBlack/uWhite/uGain` + 噪声模型，**没有 uLsc**
- LSC 是 **RCD 自己在 shader 里乘**的（`lscAt(p)`，见 `kFsRcd*`）

AMaZE 档跳过 RCD ⇒ 整档没有镜头阴影矫正 ⇒ 四角变暗、亮度分布偏离 ⇒ Mertens
的融合权重随之失真（这就是"HDR 观感不正常"）。

修：在 `runAmazeFromMosaic` 的 AMaZE 输出后按 `c.amaze_lsc` 乘 LSC 网格（双线性，
与 `lscAt` 同口径）。

### 31.2 饱和掩码没进 alpha

`kFsAmazeUp` 输出 `vec4(rgb, 1.0)` —— alpha 恒 1。而 `color_smooth`（0.12.147 的
判据修正）靠 alpha 里的 `tex_hl_mask_` 区分"饱和核"与"真实色度"。

alpha 恒 1 的后果：每个探测点都被判成饱和 ⇒ `nv == 0` ⇒ 函数直接 return ⇒
**伪彩抑制在 Amaze 档整档失效**。RCD 档有 133 块 1 的 alpha 链路，Amaze 档没有。

修：`kFsAmazeUp` 加 `uHlMask/uMaskOn/uMaskSize`，按 `hlMaskAt(p) = mask[p/3]` 写
alpha（与 `kFsRcdChroma` 的 `hlMaskAt` 逐字同口径）。

### 31.3 当前 AMaZE 档的链路完整性

| 环节 | 状态 |
|---|---|
| HL 饱和重建前置 | ✓ 共用（P0 的输入） |
| P0 RAW 域降噪 | ✓ 共用（`c.dn` 已含 `demosaic==2`） |
| LSC | ✓ **150 补齐** |
| 去马赛克 | AMaZE（CPU，读回 `tex_mos_`） |
| 饱和掩码 → alpha | ✓ **150 补齐** |
| CA 校正 / CCM | ✓ 共用 |
| HDR 侧帧 + Mertens | ✓ 共用（**侧帧仍走 RCD**） |
| P4 / color_smooth / PC3D / defringe / D-1 / film | ✓ 共用 |

**仍未接**：HDR 侧帧（bracket 的短帧）走的是 RCD 而不是 AMaZE。侧帧只贡献融合
权重，但主/侧两帧的去马赛克伪彩不同，Mertens 在高光边缘可能有轻微不一致。
让侧帧也跑 AMaZE 的代价是 **每帧 1~1.7s × 帧数**（4 帧 ≈ +5s），暂不做 ——
这是成本取舍，不是遗漏。

### 31.4 `amazeR` 的读法

`[min, max]` 是读回的 mosaic 值域（WB 域）。判读：

- `min = 0.0`：正常（黑阶以下 clamp 到 0）
- `max`：本帧最亮的 photosite。有饱和时 ≈ R 满阱（本机 2.23）；饱和少时低于它
  （149 那次 `clipB` 只有 1/89/18，max 1.31~1.89 合理）
- `[0, 0]` 或 inf：读回错了

## 32. 0.12.151：侧帧也走 AMaZE + 上传改 half

### 32.1 侧帧

150 只让主帧走 AMaZE，bracket 的侧帧（HDR 融合用）仍走 RCD。这留下一个真实的
观感问题：**主/侧两帧的饱和边缘伪彩不同**，Mertens 拿两张"伪彩不一样"的图做
加权融合 ⇒ 高光边缘发脏。侧帧只贡献权重，但两张图必须同源。

151 让侧帧也走 `runAmazeFromMosaic` + `passAmazeUp`，失败时 `hdrFail("side_amaze")`
（回落到 zero 链，照片优先红线不变）。

`amazeMs` 现在累计**所有帧**（主帧 + 侧帧）的读回/CPU/上传 —— 评估总成本必须看它。

### 32.2 上传改 GL_HALF_FLOAT

目标纹理是 RGB16F，之前用 `GL_FLOAT` 上传 150MB ⇒ 驱动力要给 12.5M 像素做一次
float→half 转换。151 在 CPU 侧先转（`grain::floatToHalf`）再传 75MB，语义等价。

### 32.3 性能账（如实拆，不拿它当借口）

单帧 `amazeMs` 的真机读数（149，4080×3072）是 **0.92~1.68 s**，其中：

| 段 | 量级 | 能否省 |
|---|---|---|
| 读回 `tex_mos_`（RGBA16F，按 photosite 通道取） | ~150 ms | 省不掉（P0 在 GPU） |
| half↔float 转换（12.5M 读 + 37.5M 写） | ~100 ms | 只能改位运算实现 |
| **CPU AMaZE** | **~500~900 ms** | 需要 SIMD / GPU 版 |
| 上传 RGB16F | ~300 ms（151 起减半） | 已减 |

桌面 8 线程实测 247 ms；手机慢 2~4× 属于正常（大核少、内存带宽低）。

**与 PC 的差距不在算法，在实现位置**：PC 的 AMaZE 跑在 GPU 上，没有
"读回 + 上传"这一对胶水成本。我们的 `amaze-REPORT.md §2.2` 曾估算 GLES 多 pass
版需要 240 tap/px（≈3.0 Gtexel）⇒ 0.8~1.5 s，显存峰值 500~600 MB，当时判为
不可行 —— 那个估算针对的是 **fragment 多 pass** 实现；如果要追 PC 的速度，
正确的方向是 **compute shader（ES 3.1）或 tile 内共享中间场**，不是把 CPU 版
逐 pass 翻译。这是独立一轮的工作量，不在本轮范围。

结论：4 帧全 AMaZE 的 `amazeMs` 预期 **4~7 s**。先看实测；若总时长不可接受，
下一步是合并"读回→CPU→上传"的往返，而不是砍侧帧。

## 33. 0.12.152：PC 用的是 **CPU 版 LibRaw**，不是 GPU —— 方向纠正

用户给了 PC 仓库（github.com/bjzhou/PhotonCamera）。查证结果推翻了我之前的假设：

| 项 | 我之前的说法 | 实际 |
|---|---|---|
| PC 的 AMaZE 实现 | GPU（shader） | **CPU：`LibRaw/src/demosaic/amaze_demosaic.cpp`**（1653 行） |
| tile 尺寸 | 以为更大 | `AMAZETS` 默认 **160**，与我们 `kTs=160` 相同 |
| 并行 | OpenMP | `#pragma omp parallel for collapse(2)`（我们用 std::thread + 原子队列） |
| 加速手段 | — | **22 处 SIMD**（SSE/NEON）+ `array2D` 布局 + `rt_math`/`sleef` |

**结论：GPU 版 AMaZE 不是正确答案。** 真实的 2~3× 差距在 SIMD，不在"CPU vs GPU"。

### 33.1 我们自己的实现其实不差

离线基准（M 系，4080×3072，同一份 `AmazeDemosaic.cpp`）：

```
-O3              167.4 ms
-O3 -ffast-math  169.9 ms      ← fast-math 无效（甚至略慢）
```

比 `amaze-REPORT.md` 记录的 247ms 还快。所以手机上的 1~1.7s **不是算法烂**，
而是"手机 CPU + 搬运成本"。已回滚 `-ffast-math`（实测无效，不留无效改动）。

### 33.2 成本拆解（152 新增诊断）

`amazeMs` 现在拆成三段并**累计所有帧**（主帧 + 侧帧）：

| 字段 | 含义 |
|---|---|
| `amazeRd` | `glReadPixels` 读回 `tex_mos_`（RGBA16F，半精度） |
| `amazeCpu` | `AmazeDemosaic` 本体 |
| `amazeUp` | float→half 转换 + 上传 RGB16F |
| `amazeMs` | 三者之和（所有帧） |

判读：若 `amazeCpu` 占比 ≫ 其余，则下一步是 SIMD；若 `amazeRd/Up` 占比大，
则先优化搬运（例如让 P0 额外输出一张单通道 mosaic 纹理，读回量减半）。

### 33.3 侧帧 AMaZE 失败会关掉整个 HDR（151 的 bug）

151 写成 `hdrFail("side_amaze")`：侧帧的 AMaZE 一失败，`hdr_ok=false` ⇒
**整段跳过 Mertens 融合** ⇒ 成片退化成单帧 ⇒ 表现正是"包围曝光没走"。

152 改为**回退 RCD**跑侧帧（侧帧只贡献融合权重，算法不一致的代价远小于丢掉
融合），并留痕 `hdr.side_amaze_fallback`。

## 34. 0.12.153：「AMaZE 的 HDR 跟没有一样」= App 侧把 AMaZE 档排除在多帧之外

### 34.1 日志证据

| 时间 | 事件链 |

### 34.2 根因：`mfnrShouldTrigger` 写死 `demosaic == 1`

```kotlin
fun mfnrShouldTrigger(mode, rawMode, demosaicRcd, iso, exposureNs) {
    if (!rawMode || !demosaicRcd) return false     // ← AMaZE 档永远 false
```

- v0.10.172 的 AMaZE 是**独立分支**（原始 u16 自起一条链，绕开 P0/HL），MFNR 对它是空转 ⇒ 当时排除是合理的
- 0.12.147 起 AMaZE 改吃 `tex_mos_`（HL 前置 + P0 的输出），与 RCD **同一条前链** ⇒ 这条排除变成纯阻塞

而且 bracket 的触发判据本身不含 demosaic（`hdrBracketsActive = hdrFusion>=1 && ...`），
但它只挂在 `if (trigger) startBurst(...)` 里 ⇒ **MFNR 不触发，bracket 也永远不跑**。
两个现象是同一个根因。

### 34.3 修法

```kotlin
// 判据从「必须是 RCD」放宽到「走融合前链的档」
if (!rawMode || !demosaicFused) return false
// 调用点：demosaic != 0（0 = 快速/双线性，走 passRaw 内联，不在该链上）
val trigger = mfnrShouldTrigger(mode, rawMode, demosaic != 0, liveIso, liveExposureNs)
```

单测 `MfnrTriggerTest` 补 `amaze_isNotExcluded`：Amaze 档必须触发、demosaic=0 必须不触发。

### 34.4 同一次实测的 AMaZE 成本拆解（单帧）

```
amazeRd  = 116 ms     读回 tex_mos_
amazeCpu = 458 ms     AmazeDemosaic 本体
amazeUp  = 463 ms     float→half 转换 + 上传 RGB16F
amazeMs  = 1058 ms
```

**搬运（579ms）比算法（458ms）还多。** 这是明确的下一步优化点：
- `amazeUp` 的 37.5M 次标量 float→half 是嫌疑（162 MB/s 远低于 GPU 上传带宽）
- 可选：NEON 批量转换、或让 P0 额外输出单通道 mosaic 让读回量减半（50MB→25MB）

修好触发后 4 帧全 AMaZE，`amazeMs` 预期 **~4.2 s**。这是当前实现的硬成本，

## 35. 0.12.154：AMaZE 的 `clip_pt` 口径错了 —— 高光只对 R 生效

### 35.1 样片对比（230019 amaze vs 230035 rcd，同场景隔 16s）

| | AMaZE | RCD |
|---|---|---|
| 整体 | 明显更暗、发灰 | 正常 |
| 笔记本屏幕 | **糊成一片白**（无内容） | 能看清文字/图标 |
| 风扇扇叶 | 纹理糊 | 纹理清楚 |

方向和 AMaZE 应有的表现（更锐、伪彩更少）完全相反 ⇒ 不是算法问题，是**输入口径**问题。

### 35.2 根因：`clip_pt` 是标量，而我们的输入是逐通道 WB 域

LibRaw（PC 用的那份）里：

```cpp
float initialGain = 1.0f;
for (c...) if (pre_mul[c] > initialGain) initialGain = pre_mul[c];   // = max(gain)
const float clip_pt  = 1.0f / initialGain;
const float clip_pt8 = 0.8f / initialGain;
...
if (cfa[indx] > clip_pt8 || Gintvha > clip_pt8 || Ginthha > clip_pt8) { /* 饱和分支 */ }
```

**前提**：输入域里所有通道**满阱相同**（未做逐通道 WB 的归一化 raw）。
`clip_pt` 是**标量**，一个阈值同时判三个通道。

我们的 `tex_mos_` 是 **WB 域**（满阱 = gains = 2.23 / 1.0 / 1.51）。原来传
`clip_pt = max(gains) = 2.2258` ⇒ `clip_pt8 = 1.78`：

| 通道 | 满阱 | 饱和值能否 > clip_pt8(1.78) |
|---|---|---|
| R | 2.23 | 能 |
| G | 1.00 | **永远不能** |
| B | 1.51 | **永远不能** |

⇒ **AMaZE 的高光判据只对 R 生效**，G/B 的饱和像素被当成真实测量值参与插值。
3×3 邻域里只要有 G/B 饱和，色差估计就被污染 —— 高光糊成一片白就是这么来的。

### 35.3 修法：把输入域还原到 AMaZE 的前提

```cpp
// ① 读回时除以该 photosite 的 WB 增益 ⇒ 满阱统一为 1.0
const float vn = halfToFloat(...) / max(gains[ch], 1e-6f);
// ② clip_pt = 1.0（归一化域满阱）
AmazeDemosaic(cfa, w, h, pattern, 1.0f, rgb);
// ③ 输出乘回 WB 增益（下游 CCM/LSC/film 都是 WB 域口径）
rgb[i*3+c] *= gains[c];
```

日志 `amazeR` 的判读随之改变：0.12.154 起它是**归一化域**，正常范围 `[~1e-4, 1.0]`，
不再是 `[~1e-4, 2.23]`。

### 35.4 这条也是"抄 PC"最容易抄错的地方

LibRaw 的 `initialGain` 是**全通道最大值**，它成立的前提是 libraw 传进来的
`image[][]` 还没乘 `pre_mul`。我们直接把 WB 后的 mosaic 塞进去，等于把
"已经按通道拉平过一次"的数据又按标量阈值判饱和 —— 两个口径叠在一起。

**教训**：抄实现前先对齐**输入域契约**，不是抄参数。`clip_pt` 不是"满阱"，
它是"归一化域的裁剪点"。

## 36. 0.12.156：命中像素按「是否贴饱和核」分流替换（不再整体去饱和）

| 081620.jpg | 08:16:20 | 1 | 同上 |

`csOn=1` ⇒ color_smooth 在跑。所以"明显绿边"不是"pass 没开"，而是 **147 的

**注意**：07:54 那两张是 `csOn=0`（color_smooth 参数没开），不能用来判断本改动。

### 36.2 为什么"只回滚"是错的（用户否决）

- 回滚到 146 的判据 ⇒ 绿边变"淡"但仍在，灰块回到"大面积" ⇒ **净收益为零**
- 147 的判据在语义上是对的（clip 白的 ch≈0 是信息缺失，不是中性旁证）
- 真正的问题：**命中的像素有两类，却被同一个替换值处理**

### 36.3 分流

| 类别 | 特征 | 替换值 |
|---|---|---|
| **贴饱和核** | 有任一探测点落在 `tex_hl_mask_`（alpha>0.5） | **±12 非饱和端点按亮度插值** |
| 不贴饱和核 | 普通窄带伪彩（紫边/彩线） | 去饱和 15%（原行为，结构性安全） |

端点取 **±12** 而不是 ±6：伪彩带经 PC3D 后有 4~10px 宽，±6 仍落在带内（离线实测
紫向残留 0.11~0.13），±12 在带外。插值结果还要**夹在两端色度最大值内**，防过冲
出新彩边。

「沿亮度的色度插值」的物理依据：色度在亮度单调变化处本来就该平滑过渡；
"白核 → 粉底"正是这种渐变，去饱和把它洗成中性才是错的。

### 36.4 仍待验证

- 若光晕带变成**粉白**（而不是中性/灰）⇒ 方向正确，灰块与绿边同时收敛
- 若变"太粉" ⇒ 端点仍落在伪彩带内，需要把端点推到 ±16/±20
- 若紫边回归 ⇒ `near_sat` 判断把真紫边也归入了插值分支，需要把"贴饱和核"
  收紧成"贴饱和核**且**中心是暖向"

### 36.5 RAW 真值：过渡带本应"比粉底更红"

`082344.dng`（对应 AMaZE 成片 082350.jpg），同一条垂直剖面，WB 域逐 2×2 块：

| 区域 | RAW R/G | RAW B/G | 成片 R/G | 成片 B/G |
|---|---|---|---|---|
| 粉底（y=2050） | **2.81** | 1.94 | 1.40 | 1.15 |
| 过渡带（y=2092~2116） | **3.13** | 2.11 | **1.15** | 1.22 |

**R/G 方向相反**：RAW 里过渡带比粉底**更红**（2.81→3.13），成片却更中性（1.40→1.15）
⇒ R 被洗白 = **灰带**。这不是去马赛克造成的（RCD/AMaZE 两档现象相同）。

**B/G 方向一致**：RAW 过渡带 1.94→2.11，成片保持 1.15→1.22 —— 这个青是**真实的**
镜面散射分量，不是伪彩，不应该去压。

⇒ 用户看到的"黄绿边" = 灰带（R 被压）+ 真实青偏（B 高）+ 同时对比。

### 36.6 所以 156 的方向是对的

156 对"贴饱和核"的命中像素改用 ±12 非饱和端点按亮度插值 ⇒ R 不再被去饱和压掉，
过渡带回到"白 → 粉"的单调过渡（R/G 约 1.2~1.3，而不是 1.15）。

验收（看粉色勺面那条细白高光的外缘）：
- 过渡带的 **R/G 应该 > 1.20**（现在 1.15）
- **B/G 仍会在 1.2 附近**（真实分量，不动）
- 观感：白高光外缘从"青灰"变"淡粉"

## 37. 0.12.157：P0 也执行「高光不降噪」—— 同一条原则漏了一层

### 37.1 用户实测定位

> 把【raw】降噪强度调 0 就不会了

灰带 + 黄绿边**消失**。这是决定性证据：问题在 **P0（RAW 域 bilateral）**，
不在去马赛克、不在 CCM、不在 film。也解释了为什么 RCD / AMaZE 两档一模一样
—— 它们吃的是 P0 的同一份输出。

### 37.2 我的疏漏（用户指出）

「高光不降噪」这条原则，昨天只落实在 **PC3D（D4 色度平滑层）**：
mask 收手（133 块 1 + 143/145）+ 首趟样本排除。

而 **P0 是 RAW 域的 bilateral，是独立的一层** —— 那条 mask 根本没传到 P0，
P0 对高光边界的处理完全是旧的。

**教训**：一条成像原则（"合成值 / clip 值不该参与降噪"）必须逐层落实并逐一验收，
只做最显眼的那一层，会得到"改了但没用"的假象。

### 37.3 机理

P0 的权重是 `w = exp(-0.5·d² - 0.5·r²/6.48)`，`d = (wAt(c) − w0) / sr`。

对比真实测量值之间的 0.3 亮度差：`sr ≈ 0.0036` ⇒ `d ≈ 83` ⇒ `w = 0`（保护正常）。

**但 HL 重建值是 scene-referred 的合成值（> 1，实测落点 1.0~1.24）**：

- `wAt()` 把它们**钳到 1.0** ⇒ 与同样被钳的中心白核之间 `d = 0`
- ⇒ **权重最大**，一个无噪声、色度按参考比重构的合成样本，以最高权重混进
  真实测量值旁边 ⇒ 粉/白过渡带被抹平成中性 ⇒ **灰带**

### 37.4 修法

```glsl
// 中心是重建值 ⇒ 整块是合成值，直接输出、不做邻域运算
if (c0 > 1.0) { oColor = <本通道原值>; return; }
...
float c = fused0(p + ivec2(dx, dy));
if (c > 1.0) continue;      // 重建样本权重恒 0
```

判据用 `> 1` 而不是 mask：本域**中性白 ≡ 1.0**、任何通道满阱都 ≥ 1.0，
真测量的归一化值不可能超过 1（`kNoDn` 路径同样成立，不依赖 mask 是否传下来）。

### 37.5 仍未统一的两层（下一步）

| 层 | 域 | 高光收手 |
|---|---|---|
| P0 `kFsRawDenoise*` | RAW mosaic | ✓ **157** |
| PC3D | D4 色度 | ✓ 133/143/145 |
| P4 `kFsChromaDenoise` | D4 色度 | ✗ 未查 |
| D-1 / wavelet | D4 | ✗ 未查 |

P4 和 D-1 也在 D4 上做色度/多尺度处理，同样可能把高光边缘抹平。按本条原则，
它们应该用同一张 mask 做同样的收手。**这是下一轮要逐一验收的。**

// 156 的分流整段删除，恢复：

|---|---|

## 39. 0.12.159：镜面高光应当趋白，不该用物体的参考比

### 39.1 用户指出

> 灰块中间的粉色你看着不难受吗？跟物体根本不是一个颜色，**高光中心不是应该趋白吗**

截图（08:43，粉色塑料表面的一条高光带）：高光里夹着粉，与周围的灰白混成一片。

### 39.2 根因：allSat 用 `uRefGlobal`（全图池化参考比）重建色度

```glsl
float rg = max(uRefGlobal.x, 1e-3);
float bg = max(uRefGlobal.y, 1e-3);
outv = (c == 0) ? rg * sc : ((c == 1) ? sc : bg * sc);
```

粉色物体主导的场景里，全图池化比偏粉（R/G 大）⇒ 高光被重建成 **粉 × 亮度**。

**但两类饱和区的物理含义不同**：

| 类型 | 面积 | 真实色度 | 正确做法 |
|---|---|---|---|
| **镜面高光**（塑料/陶瓷反光） | 小 | 反射**光源色**，与物体无关 | **趋白** |
| **大面积饱和**（天空、灯面） | 大 | 由周围同色区决定 | 参考比 |

原实现一刀切用参考比 ⇒ 镜面高光被染成物体色。

### 39.3 修法：按饱和区面积在中性白与参考比之间插值

```glsl
vec3 rrA = refRatiosW(uv);
float satFrac = 1.0 - clamp(rrA.z, 0.0, 1.0);   // 32块窗口的饱和率
float wRef = smoothstep(0.25, 0.65, satFrac);   // 小高光→0，天空/灯面→1
float rg = mix(1.0, max(uRefGlobal.x, 1e-3), wRef);
float bg = mix(1.0, max(uRefGlobal.y, 1e-3), wRef);
```

面积代理用参考场第 1 级的饱和率（32×32 块内未截断样本占比）——这是本层唯一
拿得到的"面积"量，不需要新纹理。

阈值依据：镜面高光在一块 32 块窗口里占比通常 < 20%，天空/灯面 ≈ 100%。

### 39.4 与 157/158 的关系

- 157：P0 不再平滑 HL 重建值（防止合成值污染真实测量）
- 158：撤销 156 的端点插值（防止背景色搬入）
- **159：修正"重建成什么颜色"**（镜面高光 → 中性白）

三条合起来才是完整的：**谁参与平滑 / 用什么替换 / 重建值该是什么颜色**。
前两版我只改了前两条，颜色这条一直是错的，所以高光始终偏物体色。

### 39.5 更正（0.12.160）：光晕带走的不是 allSat，是 `uRbRecon` 分支

159 只改了 `nsat>=2` 的 allSat 分支，用户实测"毫无改善"。日志给出原因：

```
hlRgG = 1.1857 / 1.1296     ← 参考比仍偏红 13~19%
hlRef2Hit = 100, hlRefGHit = 0
```

**粉色高光上 R/B 先饱和**（物体色偏粉 ⇒ R 先顶满阱），这类像素走
`uRbRecon` 分支，而那个分支同样：

```glsl
vec3 rr = refRatiosW(uv);
float est = (c == 0) ? 0.5 * (Gv + Bv / bg) * rg : ...;   // 仍然 × 参考比
```

⇒ 照样染成物体色。**普通 G 分支（`c==1`）也一样。**

160 把三处分支统一成同一口径：

```glsl
float satFr = 1.0 - clamp(rr.z, 0.0, 1.0);
float wR = smoothstep(0.25, 0.65, satFr);     // 小高光→0（中性白），大面积→1（参考比）
float rg = mix(1.0, rr.x, wR);
float bg = mix(1.0, rr.y, wR);
```

**教训（第三次同型）**：HL 的色度重建有三条并列分支（allSat / R-B / 普通 G），
任何"重建口径"的修正必须**三条同时改**。改一条的收益会被另外两条吃掉，
而日志里 `hlRgG/hlBgG` 是**参考场统计**、不是最终输出 ⇒ 单看它无法判断改了没有。

## §40 Bento collar flow 审查：0.12.122 的移植从上线起就是 no-op（0.12.161）

用户 2026-10-29 要求"审查一下借鉴 PC 的 bento 算法是否写对"。逐个文件对照
`PhotonCamera`（`/tmp/pc_repo`）后确认：**没写对，而且是静默无效**。

### §40.1 PC 的原版结构（两张纹理，不是一个 w 通道）

`BentoRegionAdmission.kt` + `GlesMgcRawSpatialShaders.kt::bentoCollarSupport`：

| 输入 | 来源 | 语义 |
|---|---|---|
| `alignment` | 前向金字塔对齐 | 每 tile 的 flow（xy） |
| `support` | **独立的** `renderBentoCollarSupport` | confidence ∈ [0,1] |

support 的硬条件（shader 原文）：

```glsl
float confidence = valid >= 4.0 && clipped == 0.0
    ? (agreement / valid) * (1.0 - smoothstep(0.75, 2.0, fbError))
    : 0.0;
```

`clipped` = tile 内 4×4 采样点落在高光掩码上的个数 ⇒ **tile 里只要有一个高光点，
confidence 恒 0**。于是 `isSupported()` 把它排除出 collar，`tileHasHighlight`
又在分组前就把它归入要修的连通区。这套语义**完全依赖 support 与 flow 分离**。

### §40.2 我们的移植错在哪（源码级，可复算）

① **support 被塞进 flow 的 w 通道，而 w 恒为 1.0**

`capture` 里打包位移场：

```cpp
std::vector<float> pack(tiles_w_ * tiles_h_ * 4, 1.f);   // ← 全部填 1
for (int t = 0; t < tiles; ++t) {
  pack[t*4+0] = a.off[t*2+0];
  pack[t*4+1] = a.off[t*2+1];
  pack[t*4+2] = 1.0f;                                    // ← w 从未被写
}
```

② 而 `kFsCollarFlow` 第一行就是 `if (c.w >= uMinSupp && ...) { oColor = c; return; }`
⇒ **恒真 ⇒ 每个 tile 原样返回 ⇒ 整个 pass 是 no-op**（只多一次全屏 draw）。

③ 即便去掉入口也不对：collar 收集里的 `if (o.w < uMinSupp) continue;` 同样恒假
⇒ highlight 内部的坏 flow 会被当成"可信邻居"，插值结果仍是错的。

④ 附带三处偏差：

| 项 | PC | 0.12.122 |
|---|---|---|
| clamp 上界 | `uGridSize-1` | `uTiles-1`（`uTiles` 是尺寸 ⇒ 越界 1 格） |
| collar 计数 | 去重后的 tile 数 | 采样次数（clamp 后同一 tile 重复计数）|
| 分组 / 兜底 | 8-连通分量 + 全图中值 | 无（逐 tile 8 邻域）|

`tools/check-collar-flow.py` 的用例⑤是这个反证的可执行版本。

### §40.3 0.12.161 的改法（回到 PC 的结构）

- **GPU 只做 support**（`kFsCollarSupport`）：读参考帧 RAW，tile 内 4×4 采样
  （与 PC 同构），`v >= white*0.98` 判裁剪 ⇒ `supp = (valid>=4 && clipped==0)`。
- **CPU 做分组/collar/中值**（`collarFlowFix`，照 `BentoRegionAdmission` 逐段）：
  8-连通分组 → 组内 ±`COLLAR_RADIUS(4)` 的 supported tile 作 collar →
  `weight = 1/(dx²+dy²)` 插值 → `collar < 4` 退全图 supported 中值 →
  `supported < 4` 整张不修（PC 的 `resolveGeometry()==null`）。
  tile 只有数百个，一次 readback + 一次 upload（数 KB）。
- **日志**（防再次静默无效）：`collarSupp` / `collarRegions` / `collarCReg` /
  `collarGReg` / `collarTiles`。

### §40.4 明确未实现的部分

PC 的 `agreement` 项需要**反向金字塔对齐**（`alignPyramids(reference→short)`），
我们只有单向对齐 ⇒ 本 support 是**二值**（0/1），不含 PC 的质量加权。
因此 collar 插值权重只有 `1/d²`，没有 `conf` 因子。

这不影响 Bento 的核心语义（高光内部 flow 不参与），但**不能声称与 PC 逐位一致**。
补 agreement 是一条独立的工作（要加一整趟反向对齐，成本与正向同量级）。

### §40.5 影响范围与验收

生效条件 = `satfix_on`（有 bracket 且短帧可用）。当前样片 `brk=1`、`brkRatio=2.828`
⇒ 这条链在跑，之前一直用的是**未经修正的**错位位移场。

验收看日志：

| 字段 | 期望 |
|---|---|
| `collarSupp` | 明显 > 0（可观测 tile 数），且 < tiles |
| `collarTiles` | > 0（实际被改写的 tile 数）|
| `collarCReg` | ≥ 1（至少一个区走了 collar）|
| 画面 | 高光边缘的黄绿/灰带应变窄或消失；若不变，说明主因不在 sat-fix 采样 |

**不要把这版当成"灰块已解决"**：它修的是"以为在跑其实没跑"的那一环。灰块的
其他成分（P0 的 HL 重建值扩散、color_smooth 的去饱和）若仍在，日志会给出新的
区分依据（collarTiles>0 但画面不变 ⇒ 主因在别处）。

## §42 边缘"渗水"：USM 过冲收紧（0.12.163）

真机 2026-10-29 10:05（阳台地砖的护栏阴影，用户截图）：明暗交界处出现一条比两侧
都浅的窄带，"像渗水"。用户明确：**与降噪无关**（关 RAW 降噪不消失）。

### §42.1 定位

`kFsOut` 的 `sharpenLuma`（FilmParams[39]，真机 0.5）是乘法 luma USM：

```glsl
gain = uSharpen * (l0 - lb/16) / max(l0, 0.01);
c *= 1.0 + clamp(gain, -0.4, 0.4);
```

`(l0 − lb/16)` 是高频一阶项 ⇒ 阶跃处亮侧 gain>0（提亮）、暗侧 gain<0（压暗），
两侧各出一条描边。±0.4 的限幅 = **最多 40% 的过冲**。它在 kFsOut（降噪链之后），
与 denoise/HL 无关 —— 与用户"和降噪没关系"一致。

离线量化（film_d5 上复刻 highlightRolloff 之后的 USM + sRGB 编码，地砖阴影 ROI）：

| 限幅 | 显示域过冲（8bit） |
|---|---|
| ±0.4 | max **13.5 LSB** / P99 5.8 |
| ±0.12（采用） | max **8.4 LSB** / P99 5.5 |

### §42.2 本版改动

`clamp(gain, -0.4, 0.4)` → `clamp(gain, -0.12, 0.12)`：正常纹理的 detail/l0 < 0.1
（锐度感知保留），只在阶跃处砍掉极端过冲。

### §42.3 未决

13.5 LSB 是否足以解释用户看到的"渗水"**尚未证实**：几次多尺度模板匹配
（4 旋转 × 4 尺度）都指不到截图那块（最高相关 0.77 且落在天空），说明截图出自
10:02 那张（0.12.162），而那张的 JPG/DNG 没有拷进 test_temp。需要那块像素才能
给出剖面，判断过冲到底是 13 LSB 还是更大。

## §44 亮缝"渗水"= D4 比 AHD 软，不是 tone curve（0.12.165）

### §44.1 排除过程（每一步都是单变量）

| 假设 | 证据 | 结论 |
|---|---|---|
| P0 / 降噪 | 关 RAW 降噪仍在；离线 P0 on/off 的 D4 差 <1% | ✗ |
| AMaZE | 用户：RCD 也会；离线 AMaZE 32px、RCD 26px，都宽 | ✗ |
| PC3D / defringe | 离线同 ROI：宽度 26→26px、G 通道不变；日志 nBand 只动 <10 个像素 | ✗ |
| tone curve（filmic） | **用户：切 sigmoid 也一样** | ✗ |
| DCP vs filmic 引擎 | PC 的 DCP 只是其中一套引擎；`DarktableFilmicToneAlgorithm` 与我们的同源 | ✗ |

### §44.2 真正的差异在 D4 的"锐度"

同一条亮缝（`y=3400` 水平剖面）：

| | 缝宽 | 对比（峰/背景） |
|---|---|---|
| RAW 原始波形 | **34 px** | 4.3× |
| 我们 D4（RCD 离线） | 26 px | 4.8× |
| 我们成片 | 24 px | 1.5× |
| libraw AHD | **14 px** | 2.6× |

RAW 本身就是 34px 的软坡（阳光穿过栏杆缝隙的 penumbra）。**AHD 把它压成 14px 的硬阶
（那是去马赛克的锐化伪影）**，我们的 RCD/AMaZE 只到 26px。

所以差距不是"我们把边弄宽了"，而是**我们没有把 RAW 的软坡收紧**。tone curve 再怎么调
都不会改变 26px 这个宽度 —— 这正是用户"切 sigmoid 也一样"的原因。

### §44.3 0.12.165：D4 层大半径 USM

`kFsUsmDown`（1/8 box 低频，等效半径 8~16px）+ `kFsUsm`（相对增益 `k·(l−lb)/l`，
clamp −0.35~+0.55），位置 = **film 之前**（tone 之前，所以与 sigmoid/filmic 无关）。

离线实测（同 ROI，k=1.0）：

| 参数 | 缝宽 | 对比 | 背景 |
|---|---|---|---|
| 原始 | 25 px | 5.80× | 0.0347 |
| r=6 k=0.8 | 12 px | 12.75× | **0.0122（−65%，暗环）** |
| **r=8 k=1.0（采用）** | **18 px** | **7.69×** | 0.0337（−3%，无暗环） |
| r=12 k=1.0 | 18 px | 8.22× | 0.0334 |

r=6 会产生明显暗环（背景被压掉 65%），所以取 r=8（1/8 图 + 双线性上采样）。

### §44.4 验收

日志 `usmOn`：1 = 执行。画面：暗部亮缝应变窄约 1/4、边缘更实；背景亮度不应变化
（若背景变暗，说明低频半径不足，需加大到 12）。
