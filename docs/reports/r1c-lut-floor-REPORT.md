## 2. ② 结论：0.30 是三档里最优的

| 预设 | 0.30 | 0.40 | 0.50 | 判定 |
|---|---|---|---|---|
| 徕卡一瞬 编辑器 | **10.46** | 11.08 | 11.59 | 0.30 最好（单调变差） |
| 徕卡一瞬 拍照 | **8.33** | 8.95 | 9.45 | 0.30 最好（单调变差） |
| 理光负片 编辑器 | **8.38** | 9.77 | 10.04 | 0.30 最好 |
| 理光负片 拍照 | **10.68** | 11.80 | 13.38 | 0.30 最好 |
| 徕卡黑白 两条 | **8.98 / 12.02** | 同 | 同 | 不受约束 |

**LUT 强度越大，两条链路的残差都单调变差**（三条预设、五个指标，无一例外）—— 因为三条 LUT 的
曲线形状与目标本来就不匹配（`preset-DESIGN.md` §8.2 的核心发现）：LUT 在这里提供的是**色彩风味**，
不是影调。所以"能表达色彩的最小强度"就是最优解，即**贴着下限的 0.30**。

### 2.1 裁决 1 的代价（"LUT 不可归零"值多少）

| 预设 | R-1b（M9 `lut = 0` / 理光 `0.177`） | R-1c（`lut = 0.30`） | 代价 |
|---|---|---|---|
| 徕卡一瞬 编辑器 | 8.84 | **10.46** | **+1.62** |
| 理光负片 编辑器 | 8.47 | **8.38** | **−0.09（无损，甚至略好）** |
| 徕卡黑白 编辑器 | 8.98 | 8.98 | 0 |

* **M9 +1.6 是"LUT 不可归零"的全部代价**（编辑器链路；拍照链路反而从 6.34 变 8.33 —— 但 R-1b 的
  M9 拍照 6.34 是 `lut = 0` 的解，两者不可直接比"好坏"，只能比"同一判据下的残差"）。
* **理光无损**：这条 LUT 的高端压暗方向与"负片整体抬暗部"部分一致，R-1b 的 0.177 是被"压过头"
  卡住的局部解；下限抬到 0.30 后曲线维度重新补偿，编辑器残差**反降 0.09**。

### 2.2 为什么 LUT 不可归零（架构师裁决理由，逐字记录）

`lut_strength = 0` 意味着这条预设只剩**影调**（对比度 + 胶片曲线 + 饱和 + 黑白点）。而徕卡一瞬的
色彩特征是**色相选择性**的偏移 —— 红色浓、蓝绿偏青、品红倾向 —— 只有 **3D LUT** 能表达：

* `saturation`（`[20..22]`）在灰阶上严格恒等（`mix(vec3(l), c, s)` 对 `c = l` 仍是 `l`），只动彩度不动色相；
* `split`（`[23][24]`）是**成对色向量**，只能把整幅推暖/推冷，做不出"红浓而蓝绿偏青"；
* `tint` / WB 增益是**全局**轴向偏移，同样无选择性地作用在全部色相上。

⇒ 归零后"徕卡一瞬"名不副实（用户点进去拿不到徕卡的色彩）。**色彩风味的价值 > 纸面残差**。

## 3. ③ 裁决记录（R-1b 上报的三件事，架构师已拍板）

### 裁决 1：LUT 强度下限 **0.30**（不接受 0）

* 落点：`recipe-fit.py --lut-min 0.30`（默认值；`set_lut_min()` 同时改三处下界：`PBOUND[0,0]`
  钳位界、`GRIDS[0]` 逐维网格、`R1_LEVELS[0]` + `STARTS` 起点池 —— 只改下界，不动维度顺序与量程）。
* 配方落点：`builtin.json` 的 `lut.strength = 0.3`（M9 / 理光）；黑白 1.0 不受影响。
* 理由与代价见 §2.1 / §2.2；三档证据见 §1。

### 裁决 2：接受理光 `filmic_black_ev = −11.97` **贴边** UI 滑杆（−12 … −1）

* **参数的"可表达性" > 纸面残差**：`SettingsScreen.kt` 的黑点滑杆范围是 −12 … −1，配方值一旦
  超出这个范围，用户在 UI 上**拖不到**（一拖就跳变）= 这条配方不可编辑。
* R-1b 已按这个纪律把搜索下界收到 −12（当时解 −11.9652，代价：拍照 8.86 → 10.14、编辑器 8.13 → 8.47）；
  R-1c 复拟合落在 **−11.9963**（更贴边）。这是**主动让步**，不是搜索失败。
* 判据：只要 −12 是 UI 的硬下界，"贴边"就是可达集合里的最优点，**接受**。

### 裁决 3：接受 **minimax 折中**（不接受 camera-only）

* 预设是**同一组参数**同时喂两条链路（拍照 = filmic → `kFsOut`；编辑器 = `kFsStyle` 显示域）。
* 实测两条链路的最优解**互斥**：M9 拍照能到 **0.39** 的那组参数在编辑器上是 **21.55**；
  编辑器最优 **5.59** 的那组在拍照上是 **65.77**。
* 只优化拍照（camera-only）⇒ 编辑器崩到 21.6，**违背"两条链路统一"这条产品前提**（U-1…U-6
  的参数统一工作全部建立在此之上）⇒ 取两者的 minimax 折中，接受 10.46 / 8.38 / 8.98。

## 4. ④ 硬天花板（已写入 `preset-DESIGN.md` §8.5，待办在 §9.5）

**拍照链路必然超差 ≥5.37 —— 这是数学，不是搜索不够。**

* `kFsOut` 的 `highlightRolloff`（`core/engine/src/render/FrameRenderer.cpp:4741-4748`，R-1d 核对行号
  与源码一致）：`knee = 0.80` + 指数软肩 `knee + (1−knee)·(1 − e^{−u})`，在 `srgbEncode` **之前**作用
  ⇒ 线性显示域被封在 `0.80 + 0.20·(1 − 1/e) = **0.9264**` ⇒ `srgbEncode` 后**最高 246.53/255**
  （实测：cam 输入 1.0、LUT 关闭）。
* 理光负片的目标曲线在输入 **250** 处要 **251.9**，而拍照链路的物理上限是 **246.53** ⇒ **数学上
  至少差 5.37**；实测该点在拍照链路只有 **240.05**（实际超差 **11.85** = `builtin-curves.json`
  的 `max_camera`）⇒ 这不是"搜索没到位"，是结构封顶。用 LUT 只会更低（`ricoh_negative` 的
  高端对角线压暗：250 → 234；实测 cam = 1.0 在 `lut.strength = 0.177` 时降到 243.3）。
  （注：编辑器链路在同一点是 248.94 —— 两条链路不可混用，248.9 不是拍照数字。）
* 另两条目标的最大输入是 243（→ 233.4 / 244.4），都在 246.53 **之下**，不受这条约束。
* ⇒ `preset-DESIGN.md` **§8.5** 已诚实标注；**§9.5** 末尾已记待办：
  "若要支持'高光不压'的负片风格，需评估 `highlightRolloff` 是否该可调（引擎级决策）"。
  **本卡不改引擎。**

## 6. ⑥ 诚实标注

1. **徕卡黑白的目标曲线是间接推断**：该模式**没有样片**，用 M9 `Contrast +2` 的实测曲线代替
   （调研 §4.5）⇒ 它的残差里含"目标本身可能就不对"的成分，三条里可信度最低。
   （这也是它三档不变、并且本卡没有对它做任何决策的原因。）
2. **理光三联图可能有微差**：Negative / Standard / Positive 三轮不能 100% 排除"分三次拍摄、
   曝光有微差"（构图偏移 1–2 px 支持同机位，但不是证明）⇒ 目标曲线本身带不确定度。
3. **拍照链路的 `b*` 与饱和是"外推"，未直接测量**：工具从 filmic 之后接起，`kFsFilm` 的 split 段
   **未建模** ⇒ b\* 只能在**编辑器链路**上实测（−1.706）。拍照侧之所以可信，靠的是
   `kFsFilm:447` 与 `kFsStyle:5493` 的 split 段**逐字同式**
   （`out += warm·ws·(0.05, 0.02, −0.04) + cool·wh·(−0.03, 0, 0.05)`）—— 这是**推理**，不是测量。
4. **未真机验证**：全部数字来自**离线 GL 工具**（在本机跑 `FrameRenderer.cpp` 的真源码 + 引擎
   uniform），没有在 Android 真机上核对过成片；GPU 驱动差异、float16 帧缓冲、dither 都可能让
   真机数字与这里不同。**观感验收仍需真机。**
