# 同一张照片的 RAW / Spektrafilm 重叠试验 · 2026-11-25

## 依赖和改动

基线为 `693013e` 加已有计时插桩，画质、参数和调度与 0.14.50 相同。vivo V2509A 的安装版本为 0.14.50（847）。试验目标不是单个阶段归零，而是同 RAW 两路线的整引擎都可重复地省下数百毫秒，且取景不退化。

- 仍串行：本张 RAW 配准／高光准入 → 融合 → 去马赛克／降噪／色彩前链 → 最终线性 RGB → Hanatos → 曝光／扩散 → DIR 等。没有提前读取未完成的场景纹理。实际 HDR 增益图仍消费本张的最终场景像素。
- 可提前：纸面眩光的**未模糊随机场**只依赖本张的固定种子、配方和尺寸；HDR 的 1024 点中性响应只依赖本张曝光和配方参数，不读场景像素。在完整 MFNR 结束、`finishStillChain` 开始时，让一个 CPU 工作者处理这两项；RCD 等 RAW 后段按原顺序跑。读取线性 RGB 完成后取结果，纸面眩光仍在原位置做完整模糊和合成。直接正片扫描没有纸面眩光。计算仍用既有 FP64 和完全相同的随机流；没有跨张缓存。
- 第二轮在高光掩模、位移等已上传后，提早释放已无读者的 CPU 高光 RGB 导引及对齐金字塔，再试相同重叠。以原基线比较这个组合，不单独给提前释放归因。Gold 的预生成场需要 `3072 × 4080 × 8` B，约 **95.6 MiB** 的额外活跃全帧数据；这不是预先假定的 RSS 增量。

## 真机回放

每行每边两次。同一真实四帧 RAW、3072×4080、PC3D/颗粒关、独立 still 上下文、合成取景并发、回放额外 `stageSync=0`。含高光首轮 ABBA，无高光和释放导引复测 BAAB。24 次运行始末 Thermal Status 均为 0；仍可见 major faults 和前后链耗时波动，不能把每组总时间差都归给调度。回放校验四帧哈希；每个配方／夹具的所有输出与首件比对，18 次比较的 RGBA、增益图、JPEG 和诊断统计逐字节一致。

新库 Gold 的准备任务提交后 **251–295 ms** 完成，Provia **41–49 ms**；提交到最终线性 RGB 读回结束分别是 **676–1146 ms / 681–886 ms**（含 CPU、GPU 和等待，不是 GPU 净耗时）。12 次候选均在读回结束前算完，收口等待 **<0.04 ms**。以下为中位数，单位 ms：

Gold 首批旧版两次引擎为 5329 / 3037 ms，前者进程记录约 25.6 万 major faults，后者约 2682 次；约 451 ms 的表面差不能归因。可信变化是 Gold 的扫描眩光局部少 **129–181 ms**，两路的尾部中性探针移出了关键路径。但 Gold 在无高光和复测中未体现相当的整引擎净收益，Provia 的方向没有在各组复现。合成取景最多间隔部分恶化，不能据此宣称真实取景退化，也不能认为没有风险。这里没有相机采集、真实预览、EXIF、应用 JPEG/R 保存及发布，不是快门到保存 A/B。

## 决定和下一步

撤回两版候选，不发包、不安装。ARM64/x86_64 Release 构建通过；恢复后的 ARM64 库与试验起点逐字节一致，SHA-256 `0816e980316f749329e42b859b95a6965dd6741ffb83d1ed1fa64209b3bc4f41`。保留此前计时插桩。没有走全配方和真实快门验收，因为没有达到选用标准。

同一张还想靠重叠获得**两路线**显著收益，必须找到两路线共同而且规模够大的可并行工作。不要继续扩大配方预计算线程：直接扫描的 HDR 探针原来只有约 13–15 ms。如果再尝试流式交接，先标出最后一段 RAW GPU pass 的逐行依赖、所有全图归约以及首批**最终**线性行实际可用的时点；只将已经最终确定的行交给完整 FP64 Hanatos，并在全图曝光/空间处理前汇合。此前合并转换与 Hanatos、双 PBO 都没有给出稳定净收益，不重复把缩短单一字段视为达标。要做其它整链优化，先复用预热后的进程做交错回放，使首轮进程缺页和持续调度噪声不掩盖共同热点的收益，再回到实拍保存及取景验收。
