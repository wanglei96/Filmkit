## 1. 结论

- **18:21 补采后的同输入结论优先于初轮假说**：主窄紫带在 P4 前的 D4 已存在；本次实际 P4+D1 之后，固定灯罩弧带的品红正值总量只增加约 0.75%。不能再把本张主要归因为 P4/D1 凭空造色。逐阶段与完整参考实验见第 7--10 节。
- **不重新启用高光重建**：用户提醒的历史副作用确有真机记录，且不限于旧 scalar inpaint。0.14.2 云朵 A/B 中 RAW opposed 开启出现灰斑，关闭后消失且紫边未回归，0.14.3 因此默认关闭。新的原版单帧实验只作因果诊断，不撤销该决定。
- 两张原始 JPEG 的灯罩边缘确有细紫线，不只是聊天截图缩放造成。两张都运行 P4 + D-1，PC3D 关闭，强边缘门关闭。
- 0.14.26 长帧保护确实执行；本次症状不能简单说成旧保护没生效，也不能据此排除融合/去马赛克阶段。
- 实际生产 shader 的受控实验确认：D-1 可以把掩码内的品红色度带到掩码外。18 组输入全部出现；P4 在其中 2 组较弱亮度阶跃、较高噪声方差条件下也出现。这是确定的处理机制，不是这两张照片唯一根因的证明。
- PC3D 开关不是单一降噪核的纯 A/B：开启路径还消费 `color_smooth -> color_median`，关闭路径虽然计算这两步、日志写 `csOn/cmOn=1`，输出却没有接入 P4。这是既有路径差异，并非本轮新发现的版本回归。
- 既有六级小波数值回归通过，没有发现分解/重建公式算错的证据。当前不能把问题直接定为“P4 核算错”或“PC3D 一定更好”。

## 3. 代码事实

### P4 / D-1 的饱和处理

- `kFsChromaDenoise` 在中心 `uSatMask > .5` 时原样输出，但 `p4Accum` 的邻居没有饱和排除。
- `kFsChromaDown`、`kFsChromaBlur`、`kFsChromaAtrous` 不接饱和 mask，完整六级 B3 卷积会跨掩码边界。
- 只有 `kFsChromaApply` 在最终重建时对 mask 中心旁路。中心不动不等于中心的色度没有进入外侧像素的变换。
- 当前 `kFsPc3d` 在自引导参考和主采样权重中使用 `1-maskAt(neighbor)`，与上述机制不同；不据此声称其完整输出对所有掩码内变化严格不敏感，因为梯度、降采样和引导上采样还有独立依赖。

这里的 `tex_satm_dst_` 来自参考 RAW 的物理裁切与膨胀，不是融合/resolve 后逐通道的“无效颜色真值”。参考帧裁切而短帧成功恢复的颜色，不应一律当成坏样本。后续不能简单扩大这个 mask、关掉大片区域降噪，或把核内全部去色。

### 前置处理消费差异

`finishRawPipeline` 的前置 `passColorSmooth` 和两次 `passColorMedian` 先产生 `tex_cm_`。
PC3D 接收它；PC3D 关闭时 `p4_src` 仍为 0，P4 接收原 `tex_scene_`。日志的 `csOn/cmOn` 只说明执行，不能证明结果进入成片。
此前 `guide-mask-pc3d-20261117.md` 已记录此行为，并明确不能把“跳过无人消费的计算”优化偷换成“把结果接入 P4”。本轮继续遵守这一边界。

`kFsColorSmooth` 不是注释标题所说的纯原版中值，而是含色度峰判据与固定保留 15% 色度的旧自定义模块；`kFsColorMedian` 也包含阈值、亮度补偿与 clamp 适配。不能为消紫边直接把它们无条件接入普通档并称为原版修复。

## 4. 可重跑实验

```bash
python3 tools/check-chroma-wavelet.py
python3 tools/repro-chroma-highlight-edge.py \
  --json test_temp/purple-lampshade-20261117/chroma-core-influence.json
```

第一项通过：六级 GPU 对独立 coarse+detail 重建、六个噪声带增益、亮度/非负域、关闭恒等、饱和中心旁路、P4 signed covariance。
Starlet 分解的参考是 scarlet2 原始 `wavelets.py` 的 generation=1，非 darktable EAW/BayesShrink；不能把上述数值通过理解为实拍质量通过。
参考入口：`https://pmelchior.github.io/scarlet2/_modules/scarlet2/wavelets.html`。

第二项使用 Apple M1 实际 GL shader，1077 draws。ES300 仅机械改为 core330；保持输入/P4/最终输出的 half-float 边界和 D-1 的 FP32 中间缓冲，运行全部六级，没有删采样或改公式。

18 个夹具覆盖直线/曲线、三种亮度阶跃、三种噪声方差。输入 A/B 外侧逐字节相同，只在 mask 内给 R/B 增加 .03。协方差为声明的合成 PSD 矩阵，不冒充两张实拍的完整局部协方差。

- D-1：18/18 外侧受影响。例：曲线、核亮度3、外侧.5、方差基数1e-5，外侧 `min(deltaR-deltaG,deltaB-deltaG)` 峰值 .005126953125（场景线性值，不是最终 JPEG 的 /255）。
- P4：2/18 外侧受影响，其余16组在 half-float 输出精度下未检测到变化；不能把 P4 说成本组高反差边缘的主因。
- 中性对照始终中性；掩码中心 RGB 原样保留。说明已复现的是异常色度的传递，不是纯中性输入凭空生成品红。
- 另做一个合成 1px 曲线紫环：输入色差峰 .1000，当前 P4+D1 后 .09814，单独前置处理后 .01465，再接 P4+D1 后 .00879。未运行 PC3D，也没有证明此改接能保住实拍粉色花瓣或细密彩纹。

JSON verdict 明确为 `DIAGNOSTIC_COMPLETED_NOT_A_FIX`，不是修复验收 PASS。

## 8. 完整原版 RCD 核对

## 13. 未裁切中心也会受已裁切邻域影响

`tools/analyze-lamp-native-edge.py` 新增逐峰值原始码值检查。以各单帧自身生产 RCD baseline 的
D4 灯边定位，f0/f3 各 400 个品红峰值中心 photosite **全部未裁切**，但两像素方形邻域内
**全部存在已裁切 photosite**；一像素邻域比例分别为 90.0% / 91.25%。
这是邻域事实，不是完整 RCD 采样依赖，也不意味着某个单 photosite 是完整有效 RGB。

新增 `tools/check-lamp-clipped-influence.py`：真实单帧、无融合/P0/P4，通过已固定的完整原版 CPU RCD，
保留原有 WB/LSC/source-white/CCM 域和 half 边界，只对原始已裁切 G 或 R/B sites 做 +/-1/4/16 code
对称扰动。高于白阶的值为**假想输入敏感性试验**，不是传感器测量、恢复真值或生产候选。
32px halo 裁剪与先前整图原版 baseline 的 D4 mean abs 分别为 2.58e-9 / 3.00e-9，
p99 均 0，最大 .000244 / .000122，证明本地实验没有用缺边界的短核替代完整参考。

| 单帧 / 原版 CPU RCD | 原值紫边总量 | 已裁切 G +4 code | 已裁切 G +16 code |
|---|---:|---:|---:|
| f0 | 151.7587 | 149.3158 | 143.8365 |
| f3 | 191.9236 | 189.3596 | 183.6938 |

f3 的已裁切 G +4 code 已改变 78.5% 的原 baseline 紫边峰值 RGB，+16 改变 82.5%；
改变的不是原峰值中心 RAW，而是邻域中原来已裁切的绿色观测。负向扰动会加重该指标。
这证明实际输入上存在“裁切样本变化影响外侧未裁切中心颜色”的通路，不再只靠方形 footprint 推断。
**它不证明真实丢失的 G 应该加多少，也不证明相应增量能消除该灯罩紫边**：+16 后仍残留明显，
原版也不是只要补一点 G 就能根治。小扰动不响应也不能证明不存在数学依赖（half 量化可掩盖响应）。

同时核对固定 RawTherapee 原版 `rawimagesource.cc` 的 preprocess WB、`scale_mul` 与
`rcd_demosaic.cc` 输入：原版同样有去马赛克前的颜色缩放，不能把我们的 WB 前置直接定成接线错误。
完整参考算法与完整 RawTherapee 显影工作流仍是两回事，不声称已复原后者。

当前可成立的表述是：**紫边可由原生 RAW 的采样/裁切边界经去马赛克形成，裁切邻域确能影响边外；
不能说采集已直接记录了一条紫线，也尚未把真实颜色/光谱/光学过渡与插值残差唯一拆开。**
因此不以扩 mask、旧 CS 固定去色、重新启用 RAW opposed 或全局压暗作为本轮修复。
