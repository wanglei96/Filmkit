## 1. 架构原则（不可违背）

1. **单一参数源**：编辑器、预设、拍摄三条路径共用同一份 `FilmParams` 槽位语义。禁止为编辑器另立一套参数模型（历史教训：预览链/成片链只接两条 = 第三条静默漏）。
2. **契约三处同改**：加槽位必须同时改 `FilmParams.h::kCount` + `CameraPresets.neutral()` 的 `DoubleArray(N)` + `fromArray` 解析的 `if (n > idx)`；下发点必须有 `size` 兜底。漏一处 = 启动崩溃（v0.10.196 真实事故）。
3. **参数快照**：成片落盘时把"这张片子用的参数 + LUT 选择"存下来，编辑器以此为起点。没有快照的编辑器等于每次从零猜参数。
4. **域必须正确**：给 shader 定阈值前，必须用 `tools/engine-shader-offline.py` 真跑引擎 shader 量该域的分布。历史事故：在显示域量的阈值 5.0 拿去比线性域（恒 false，三版无效）。
5. **移动 GPU 三禁**：数组作函数参数、循环内动态索引、多行宏（`\` 续行）—— 都是**静默失败**。新 pass 必须过 `tools/validate-shaders.sh`，且必须带诊断字段（`prog_ != 0` + 本帧是否执行）。
6. **真机是唯一判据**：离线链路不含 PC3D/P4 ⇒ 后链判据的离线指标**不可用于决策**。每轮必须真机 A/B + 裁图目视复核（统计只作辅证）。
7. **出包必验版本**：`aapt dump badging <apk> | grep versionName`；出包前跑 `tools/check-diag-fields.py`。
8. **A/B 通路纪律**：每个新功能/新 pass 必须自带可关闭开关（默认值按实测决定，不按推演决定）。

## 2. 关键架构决策

### ADR-1 编辑器入口与导航
`MainActivity` 是简单 `when (screen)` 状态机（90 行）。新增 `"editor"` 分支即可，不改导航框架。
入口 = `CameraScreen` 胶卷位（约 1232-1260 行）点击回调。**一期只接本 App 最近成片**，二期接系统相册选择器（用户已确认分期）。

### ADR-2 素材源分级（决定接口设计上限）
| 素材 | 可调范围 | 状态 |
|---|---|---|
| **DNG 底片** | WB/曝光/影调/LUT/颗粒全链可逆（真正的专业后期） | **E5，本轮不做**；接口预留 |
| **成片 JPEG** | OETF 之后的后段：3D LUT、颗粒、暗角、halation、边框 | **本轮（E1–E4）** |
| 预览降载 | 编辑器交互用，同后段、低分辨率 | 本轮 |

**结论：本轮编辑器 = "成片再风格化"，不是"重新显影"。** 这个分级必须写进 UI 文案，避免用户误以为能改 WB。

### ADR-3 导出策略
默认**另存为新片**（`Pictures/FilmKit`，文件名带来源标记，如 `_edit`），原片不动；界面提供「覆盖原片」显式按钮（MediaStore 覆盖写入需处理 `IS_PENDING` 与兼容性，实现时单列一个子任务）。

### ADR-4 参数快照
成片落盘时保存该片的 FilmParams + LUT 选择与强度。

- **落点**：`SharedPreferences("filmkit")`（现有 prefs，见 `MainActivity.kt:43`）里的**一个 JSON 字符串**，键 `still_snapshots`。不写 MediaStore、不写 sidecar 文件（避免污染相册、避免权限）。
- **格式**：`{ "<成片文件名>": { "p": [60 个 double], "lut": "<id 或空>", "lutK": 1.0, "t": <epochMs> }, ... }`
  - 用**文件名**而非完整 URI 做键：MediaStore URI 可能因重扫/迁移变化，文件名是稳定标识（现有命名已带时间戳与后缀，见 `CameraController.kt` 约 3428 行）。
- **JSON 库**：用 Android 内置 `org.json`（生产代码可用；JVM 单测不可用——纯逻辑解析代码若要单测，需避免依赖 `org.json`，或该逻辑不做单测）。**不引入任何 JSON 依赖**。
- **清理**：不设上限、不主动清理（单条约 1KB；1000 张约 1MB，prefs 完全可承受）。YAGNI。
- **读取失败/无快照**：编辑器回退到 `CameraPresets.standard()` 并明确提示"这张没有参数记录，已用标准基线"。

### ADR-12 E2 参数面板的硬约束：不许"假滑杆"
**背景**：E4-0 报告 R4 指出 `[4] contrast`、`[11..19] cross`、`[5..10] shoulder/toe` 曾经是**死参数**（shader 零引用）—— 如果照调研文档直接做 UI 滑杆，结果是**用户滑了毫无反应**，而且因为默认值是 0，连"看起来生效了"的假象都没有。

**拍板**：
1. **面板只暴露"引擎已实现且已验证"的参数。** 每接入一个滑杆前，必须在离线脚本或真机上证明"改这个槽位 ⇒ 输出确实变化"。
2. **E2 先做框架**（分组抽屉 / 滑杆组件 / before-after 对比 / 节流），**按 E4 的实现进度逐个接入滑杆**，不阻塞、也不提前暴露。
3. **参数分组与归属**（基于 ADR-2 素材分级 + ADR-6a 风格层）：

| 面板组 | 滑杆（槽位） | 实现卡 | 接入条件 |

4. ~~**前段参数一律不进编辑器面板**：曝光 `[0]`、WB `[1..3]`、影调 `[28][37][38]`、锐化 `[39]` 等在 JPEG 输入下**改不了**（ADR-2）—— 不是"没做"，是"物理上不可逆"。~~

### ADR-6 预设存储（E3 用，先定）
预设列表同样存 `SharedPreferences("filmkit")` 的一个 JSON 字符串（键 `presets`），schema 见 E4 设计文档。**预设与快照共用同一套槽位语义**（ADR-1 单一参数源）。

#### ADR-6a 预设与设置页的管辖划分（★ 架构师拍板 2026-10-08，E3 必读）
**问题**（勘察报告 R6 / F15）：现状语义是"`CameraPresets` 提供基线 + 默认值，**真正的当前值由 prefs 覆盖层决定**" —— `setFilmParams` 之后会连续调 `applyBaseEvPref` / `applyTonePref` / `applyZebraPref` / `applyLutStrengthPref` / `applyFilmicRangePrefs` / `applyAutoTonePref` / `applyLocalTonePref` / `applySharpenPref` / `applyGamutPref` / `applyHrWaveletPref` / `applyColorSmoothPref` 等一整套覆盖。
⇒ 如果预设"存完整 78 槽快照"，那么选中预设后，**设置页的开关会把预设的值覆盖回去**（用户看到"选了预设没生效"）；反之若让预设覆盖一切，设置页就集体失效。

**拍板：按"谁决定观感、谁决定管线行为"划分管辖范围，两者不重叠 ⇒ 无仲裁冲突。**

| 层 | 槽位 | 归谁管 | 理由 |
|---|---|---|---|
| **风格层**（预设管） | [5..10] 趾肩 latitude、[20..22] 分区饱和、[23][24] split、[25] mono、[26][27][60][61] 颗粒、[62..65] halation、[66..68] 暗角、[69..77] 层间效应、[34] LUT 强度 | **预设** | 这些决定"看起来像哪种胶片"（型号差异的来源：层间耦合 ⇒ Kodak 暖 / Fuji 冷；颗粒的 ISO 特性；halation 的有无 remjet） |
| **基础层**（设置页管，预设**不碰**） | [0] 曝光、[1..3] WB、[28] 影调强度、[35] auto_tone、[36] 局部映射、[37][38] filmic 黑白点、[39] 锐化、[40] gamut、[41][45] 高光重建、[46] RCD、[47][48..59] 各专项开关 | **prefs / 设置页** | 这些决定"管线怎么跑"（设备相关、调试开关、画质取舍），与胶片风格无关 |
| **LUT 资产**（预设管） | 不进 FilmParams，独立 JNI 上传；预设 JSON 存 `lut` id + `lutK`（= [34]） | **预设** | LUT 是色彩风格的主体 |

**实现要求**：
- 预设 JSON = **稀疏的"风格层"参数集**（只含上表风格层槽位）+ `lut` id，**不是**完整 78 槽快照。
- 应用预设 = **只写风格层槽位**，然后**不动**基础层（不调基础层的 `applyXxxPref`）。
- 快照（ADR-4）与预设的区别：**快照存完整 78 槽**（它是"这张片子的完整状态"，供编辑器复现）；**预设存风格层**（它是"可复用的风格"）。两者语义不同，不要混用。
- 这样 `[54] pc3d`、`[45] hr_raw` 这类**拍照链路开关**天然不会被预设改动 ⇒ 换预设不会改变画质管线（符合用户预期）。

### ADR-7 编辑器的域约定（★ 最关键，返工代价最大）
**输入素材 = 已经过 OETF 的 sRGB 成片（8bit JPEG）。这是既定事实，域约定必须服从它，而不是服从"管线顺序看起来该怎样"。**

### ADR-7 编辑器的域约定（★ 最关键，返工代价最大）
> **2026-10-08 订正 v2（用户指出错误）**：原版把"JPEG 不能重新显影"误述为"JPEG 不能调曝光/WB/对比度/饱和度/清晰度"，
> 并据此把编辑器范围裁到只剩 LUT/颗粒/暗角。**这是错的** —— 那些调整所有相册编辑器都在 JPEG 上做。
> 根因：调研文档 §4.2 写"只有 JPEG 时退化为 OETF 后的有限调节（LUT/颗粒/暗角/边框）"，该表述**过窄**，我照抄了它。

**必须分清的两件事**：
| | 内容 | 结论 |
|---|---|---|
| **能做** | 在成片像素上做调整：曝光、白平衡、对比度、饱和度、清晰度、影调曲线、LUT、颗粒、暗角 | ✅ 相册编辑器标配，**编辑器就该提供** |
| **做不到** | **恢复已丢失的信息**：已裁切（clip）的高光、被降噪/去马赛克抹掉的细节 | ❌ 数据在拍照时就没了，任何调整都变不回来（但不等于"不能调曝光"） |

**域约定（订正版）**：

| 操作 | 域 | 说明 |
|---|---|---|
| **曝光 / 白平衡** | **线性域（成对往返）** | `srgbDecode → 乘增益 → srgbEncode`，用**真 sRGB**（IEC 61966-2-1）曲线。**必须走线性域**：两者都是线性光域的物理量，在显示域直接乘会因 gamma 非线性产生偏差。往返误差 ≤1 LSB（项目记录的"暗部 9/255"来自早期 `pow(2.2)` 近似，**不是**真 sRGB 曲线的问题） |
| **对比度 / 饱和度 / 清晰度** | **显示域** | 感知域操作，直接做即正确（Lightroom 等同类做法） |
| **影调曲线** | 显示域 | |
| **3D LUT** | 显示域 | LUT 资产本就是 display 域（与现有语义一致，零转换） |
| **颗粒 / 暗角 / halation** | 显示域 | 见 ADR-9 |
| 去马赛克 / filmic | **不做**（真的做不到） | 已在成片里烘焙；从成片反推 RAW 信息是不可能的（见上表"做不到"一行） |
| 输出 | RGBA8 → JPEG | 显示域 |

**硬约束（订正版）**：
- **禁止单程转换**：对已编码的值再编码一次、或对线性值直接套显示域公式 ⇒ 画面发灰 / 变暗 / 错色。**这才是原版要防的真问题。**
- **允许成对往返**：`decode → 操作 → encode`，用**同一套**曲线，数学恒等（仅浮点精度）。**这是线性域操作的唯一正确路径**，曝光/WB 必须走它。
- 代码里必须注释说明"这是**成对往返**，不是单程转换"，避免下一个人按旧版 ADR 把它当违规删掉。
- 往返段必须验证：**输入不调整（ev=0、wb=1,1,1）时输出与输入逐像素一致**（≤1 LSB）。

### ADR-9 编辑链路与拍照链路的落点差异（★ E4 派工必读，架构师拍板 2026-10-08）
E4 设计文档把 halation 落在 **`kFsFilm` 之后、`kFsOut` 之前**（线性显示域，理由：emulsion 在线性光里模糊、能量守恒、`kFsFilm` 输出正好是线性显示域）。

**但编辑器链路（E1-3）里没有 `kFsFilm`** —— 链路是 `JPEG(sRGB) → kFsStyle(LUT/颗粒/dither) → 输出`。JPEG 已过 OETF，不存在"线性显示域中间态"。

**拍板：halation 实现一次，两条链路各自有落点，共用同一套参数语义。**

| 链路 | 落点 | 域 | 说明 |
|---|---|---|---|
| 拍照（E4） | `kFsFilm` 之后、`kFsOut` 之前 | **线性显示域** | E4 设计原方案，物理正确 |
| 编辑器（E4 的编辑器侧） | `kFsStyle` 内（在线性往返段之后、LUT 之前） | **显示域 sRGB** | 保持显示域近似（报告 §3.2.2 方案）；若真机发现暗部光晕偏弱，可改用 ADR-7 的**成对往返**移到线性域（能力已具备） |

**统一口径（必须写进实现注释）**：
- 参数 `[63] halation_threshold` 的单位**统一为"显示域 sRGB 编码值 0..1"**（用户直觉："多亮算高光"）。
- 拍照链路：引擎内部做 `thr_linear = srgbToLinear(v)`（E4 设计已如此）。
- 编辑器链路：**直接用 v 比较**（输入本来就是 sRGB 编码值），**零转换**。
- 算法本体（阈值 → 5 级降采样金字塔 → 模糊 → 按通道权重合成 → 加回）**两条链路逐行一致**，只有"域"与"阈值是否转换"两处不同。

**代价（诚实记录）**：编辑器链路的 halation 在显示域做，与真实银盐散射（线性光）**不等价**——暗部光晕的相对强度会偏弱。这是 ADR-7 的必然结果，接受；E5（DNG 全链）时两条链路自然统一到线性域。

**颗粒同理但更简单**：E4 的颗粒落在 `kFsOut`（OETF 之后 = 显示域），与编辑器链路的 `kFsStyle` **同域**，算法可直接共用，无需双落点。

**暗角（vignette）也不需要双落点**（2026-10-08 补充核实）：E4-0 报告 §3.3.3 的落点 = `kFsOut` 内 **OETF 之后、3D LUT 之前、sRGB 显示域、乘法**，理由充分（darktable `vignette.c` 的声明域本身就是 `non-linear, RGB, display-referred`；且暗角放在 LUT 前可避免不同 LUT 把同一暗角渐变的形状改掉）。**两条链路同域同序 ⇒ 共用同一段逻辑，参数语义完全一致**。

### ADR-11 预览与导出的分辨率差异（★ E4-3 颗粒必须处理）
**背景**：E1-4 定下编辑器的分辨率分级 —— 预览用降采样图（长边 ≤1600），导出用全分辨率。这样内存与实时性可控。

**隐患**：`kFsStyle` 的颗粒按 **`gl_FragCoord`（像素坐标）** 计算：
```glsl
vec2 gp = gl_FragCoord.xy * 6.0 / max(uGrainSize, 0.25) + uSeed;
```
⇒ 同一个 `uGrainSize`，在 1600px 预览与 4080px 全分辨率上，颗粒的**相对空间频率不同**（预览里颗粒显得更粗）。这会让用户看到"预览与导出不一致"（WYSIWYG 破绽）。

**当前不显现**：ADR-10 决定 `[26] grain_amount` 默认 0（颗粒整段跳过）⇒ E1-4 阶段用户看不到颗粒。

**E4-3（颗粒重写）必须一并处理**，二选一：
1. 加分辨率归一化 uniform（如 `uGrainScale = 参考长边 / 当前画幅长边`，`passStyle`/`passOutput` 各自下发），使颗粒的相对尺寸与画幅挂钩而非与像素数挂钩；
2. 或明确把颗粒尺寸语义定义为"相对画幅"（darktable 的 `scale`=ISO 本身就是相对量，重写时应自然落在这个语义上）。

**验收**：同一参数在预览尺寸与全分辨率上渲染 ⇒ 颗粒的**相对空间频率一致**（离线可量化：两种分辨率各渲染一次，缩放到同尺寸后比较颗粒功率谱）。

#### ADR-11 的解决路径（2026-10-08 补充，架构师核实报告 §3.1.1 后确认）
**该隐患会随"对齐 darktable"自然消失**：darktable `grain.c` 的噪声坐标是 **按短边归一化**的 ——
```
x = 像素世界坐标 / wd,   wd = min(图宽, 图高)
zoom = (1 + 8·(ISO/213.2)/100) / 800
```
⇒ 同一个 ISO 值，在 1600px 预览与 4080px 导出上，噪声的**相对空间频率相同**（都挂在短边比例上，与像素数无关）。

**残留注意（E4-3 需说明，不必修）**：预览分辨率较低（如短边 1200）时，最高八度（f=1.7280 ⇒ 短边 3072 时周期 ≈2.6px，预览时 ≈1.0px）可能落在 Nyquist 附近 ⇒ 轻微混叠（颗粒观感略粗）。这是**采样固有**的，不是 bug；若真机上肉眼可见，再考虑预览端降八度（记入 E4-3 的"待实测"）。

#### 移植陷阱（E4-3 必须处理，架构师预判）
darktable 的 simplex 噪声依赖 `permutation[256]` 查找表。**GLSL ES 3.0 不支持数组初始化器**（本项目已踩坑两次，`FrameRenderer.cpp:4499` 有注释）。
⇒ **不要**写 `const int perm[256] = int[256](...)`。三个可行替代（按推荐序）：
1. **用整数 hash 函数代替表**（如位运算 hash，`perm[i] = hash(i)` 的等价语义）——无数组、无额外纹理、性能最好。需在注释里说明"这是平台限制下的等价移植"（表与 hash 都是确定性伪随机，用途只是打散梯度索引）。
2. 把表放进 256×1 的纹理，`texelFetch` 读取 —— 多一次采样，但**逐字对齐原版**。
3. CPU 侧展开成 256 个 uniform —— 丑陋，不推荐。

**决策**：优先方案 1（说明理由），若发现 hash 质量导致可见图案，退回方案 2。

### ADR-10 颗粒默认值变更的回归风险（E4 派工必读）
E4 设计把 `[27] grain_size` 的语义从"当前值（越大越细，倒置）"改为 **darktable `scale` = ISO（20..6400，默认 400）**，并把 `[26] grain_amount` 语义改为 darktable `strength`。

**风险**：`neutral()` 当前**没有设置** [26][27]，走 C++ 默认 `0.0 / 1.0` ⇒ 颗粒**当前完全关**（amount=0）。开放后若默认值给成"darktable 默认强度"，会让**所有用户的现有拍摄立刻带上颗粒** = 成片外观回归。

**拍板**：
- `[26] grain_amount` 默认**保持 0.0**（= 关），颗粒只由预设/编辑器显式开启 —— **不允许默认给非零**。
- `[27] grain_size` 默认值按新语义填 **400**（此时 amount=0，无效果，但语义自洽；同时修掉勘察报告 R9 指出的 `neutral()` 未设置与 C++ 兜底不一致问题）。
- E4 派工必须带一条验收：**颗粒关闭时（amount=0）成片与改动前逐位一致**。

### ADR-8 编辑器渲染走引擎，不在 Kotlin 侧做后段
3D LUT（`nativeEngineSetLut` 上传 3D 纹理）、颗粒、halation 的实现都在 C++ 引擎里，Kotlin 侧没有等价能力。**编辑器必须新增一条引擎输入通路**（成片图像 → 后段 pass → 输出 RGBA），而不是在 Kotlin 里用 `ColorMatrix`/`RenderScript` 之类凑。具体接口形态由可行性勘察报告确定（E1-3 定稿）。

### ADR-13 「无修改导出」必须直通原片（★ 2026-10-09 真机实测归因）

**现象**（用户反馈）：编辑器不做任何修改直接导出，比原片体积大 33.6%，且"看起来细节更好"。

**实测**（用户真机成片 3072×4080；用仓库真实 `stb_image_write.h` 复现，模型解释真实导出的 **99.63%**）：

| 项 | 字节 | 占总增长 |
|---|---|---|
| 原片 | 5,617,678 | — |
| 编辑器导出 | 7,507,423 | **+33.64%** |
| ↳ **JPEG 二次编码** | +1,042,296 | **55.16%** |
| ↳ **多叠加一次 dither** | +819,446 | **43.40%**（独立分量 31.63% + 相干增强 11.74%） |
| ↳ 未解释（Android 解码器差异，**推断非实测**） | +28,003 | 1.48% |

**三条实测结论**：
1. **编码参数逐项相同**：SOF0 采样因子全 1×1（4:4:4）、DQT id0/id1 全 1（q100）、单段标准 DHT。⇒ 体积差异 **100% 来自 DCT 系数熵**，不是编码器配置问题。
2. **dither 是相干叠加**：两条链路用同一个确定性哈希 `dhash`（坐标函数，非随机数）。实测有效坐标为 **`gy = row + 0.5`** —— 引擎渲染时图像在 framebuffer 内上下倒置存放；**不是** GL 左下原点（用错坐标命中率从 79.95% 掉到 53.35%，相干性判断会**完全反转**）。⇒ 噪声相对真值 ~0.5 → ~0.91 LSB，而非 √2 增长。
3. **"细节更好"是错觉**：局部 std 增量在极平坦区 **+0.3926** / 平坦区 **+0.4089**，而**强纹理区仅 +0.0164**。细节恢复不会这样分布，噪声才会。dither 的真实收益是量化台阶被打散（水平相邻 luma 完全相同占比 **37.55% → 25.06%**，−12.5pp），代价是平坦区噪声 +68%、体积 +33.6%，并**破坏纯黑**（luma=0 像素 26→337）。

**日志佐证**：`render.style` 的 `lutK=0, grain=0`（LUT/颗粒均旁路）；`inMean=148 == outMean=148` ⇒ 编辑器除 dither 外未改图像，与"不做修改"一致。

**决策**：
- **编辑器导出分流**：
  - **无修改**（参数与快照逐槽相同）⇒ **直接复制原片字节**：零二代损失、零体积膨胀、零耗时。
  - **有修改** ⇒ 正常渲染 + 编码（**dither 必须保留** —— LUT/颗粒/暗角会产生新的浮点值，量化前需要它抑制条带）。
- **拍照链路不动**：成片已是 4:4:4 + q100 + 全 1 量化表（最高档，日志实证 `chroma=444, q=100`）。**不存在"让拍照达到导出质量"的空间——导出反而更差**（多一次二代损失 + 多一次噪声）。用户感受到的"导出更好"是平坦区噪声被读成质感的视觉现象。
- **新卡 E2-9**（排队等 E2-8，两者同改 `EditorScreen.kt`）：实现上述分流。
- 归因产物：`tools/jpeg-dither-exp/`（报告 txt/json、实验脚本、4 个对照 JPEG、可视化 PNG）。

### ADR-14 编辑器「专业面板」重做规格（2026-10-09，以用户提供的 Filmix 实机截图为准）

**背景**：用户验收 v0.11.3 后反馈「调节功能不全」「面板太 low，不够专业」，并提供了 **Filmix 编辑器实机截图**作为参考基准。

**⚠ 规格来源**：调研子代理**看不到图片**（`web_fetch` 只取文本），Dazz / Filmix 闭源且无像素级公开资料。所以 **Filmix 的 UI 细节以架构师对截图的直接观察为准**（下表）；PC 的数值来自其开源源码（已 clone 到 `/tmp/pc_probe` 逐文件读过）。

**Filmix 面板的五层结构（截图实测）**：

| 层 | 内容 | 关键设计 |
|---|---|---|
| ① 顶部栏 | 取消 ｜ 撤销 / 重做 ｜ 保存预设 + **完成** | 「完成」= **黄色圆角矩形 + 黑字**（主操作）；「保存预设」= 深灰圆角 + 白字 |
| ② 预览区 | 图片全宽 | 约占屏高 55%，上下留黑 |
| ③ 参数名 | 居中大字（如「曝光」） | 白字，约 18–20sp |
| ④ 滑杆 | **带密集刻度** + 黄色位置标记 | 一排细竖线（专业仪器感）；当前值处一条黄色竖线 |
| ⑤ 参数图标行 | 横向滚动，一屏约 5 个 | 圆形按钮 ~56–64dp；未选中 = 深灰圆 + 白图标；**选中 = 深灰圆 + 黄色描边 + 黄色图标**；下方白色小字 |
| ⑥ 底部导航 | 调整 / 预设 / 滤镜 / 裁剪 / 相框 / 转化 | **选中 = 黄色圆角矩形底 + 黄色图标 + 黄色文字** |

**最关键的结构差异（"专业感"的真正来源）**：
- Filmix：**底部导航（功能大类）→ 参数图标行（具体参数）→ 只显示当前选中参数的那一条滑杆**
- 我们：纵向堆叠全部滑杆（一屏 7 条）
- ⇒ **一屏只出一条滑杆**（聚焦 + 精确），这是移动端专业编辑器的标准做法

**我们的差距**（调研报告 `editor-pro-features-RESEARCH.md` §3.1 共 15 条，头三条最关键）：
1. **三段式表单行 → 满宽滑杆 + 标签在上方**（结构级）
2. **无中点标记**（对比度 / 饱和度 / 色温的"不变点"看不见）
3. **读数恒为 `%`**（曝光显示 `100%` 而非 `+1.0 EV`）—— **这条最直接决定"专业感"**，必须改成物理量单位

**从 PC 源码抄到的可复用数值**（`/tmp/pc_probe`）：
- 配色：`cam_surface #CC121417`、`cam_on_surface_variant #B3FFFFFF`(70%)、`cam_outline #4DFFFFFF`(30%)、`cam_panel_corner_radius 28dp`
- 刻度盘：刻度线 **8dp 长 / 11dp 间距 / 线宽 2.0f**；文字带 **1px 黑阴影**（叠加预览时的可读性技巧）
- **不要抄弧形旋钮本体**（96dp 高，20+ 参数装不下），抄刻度密度 / 文字阴影 / 选中色

**架构师裁决（四项）**：

1. **色温 / 色调新增槽位 `[88] temp_mired` / `[89] tint`，不由 `[1..3]` 反解。**
   理由：2 自由度 → 3 增益**非双射**（E2-3 已论证），反解会让读数跳；且 mired / tint 是**独立物理量**。引擎侧把 temp / tint 转成增益后**与 `[1..3]` 相乘**（同属线性域增益，**并入已有的成对往返 ⇒ 零额外 GPU 成本**）。
2. **契约改动一次做完**：`kCount` 88 → **96**（`[88] temp_mired`、`[89] tint`、`[90] highlights`、`[91] shadows`、`[92] whites`、`[93] blacks`、`[94] fade`、`[95] 备用`）。
   理由：`FilmParams.h` 注释记着 v0.10.196 的**真实事故** —— 漏改一处 = **装包后启动即崩**。三次小改 = 三次崩溃风险。
3. **裁剪在引擎输入侧做**（UV 子矩形），**不是**最后对输出位图裁。
   理由：暗角 `[66..68]` 与局部调整 `[79..87]` 都按画面归一化坐标计算，裁剪后不换算 ⇒ **暗角跑到画面外、局部调整中心偏移**。
4. **排期**：E2-7（局部调整 UI，在跑）→ **E2-10 面板骨架重做**（P0，纯 UI）→ **E2-11 契约一次扩到 96 + 影调分区 / 色温色调引擎** → **E2-12 裁剪** → 颗粒接线 / 撤销重做。

**颗粒接线的前置**（调研 §A）：当前 `kFsStyle` 的颗粒用 `gl_FragCoord.xy * 6.0 / uGrainSize`（**屏幕像素坐标**）⇒ 预览与全分辨率导出的颗粒**物理尺度不同**（ADR-11）。接 UI 前必须先定口径 —— 按 darktable 的**短边归一化**改（那样分辨率无关，ADR-11 自然消失）。

架构师独立复跑：①–⑭ 全绿（⑭a 零回归 `max|Δ| = 1 LSB`；⑭b–⑭f 与 numpy 解析对照全部 ≤1.6 LSB，三项区分度对照有效）；`vignette=14`、`srgbDecode(=3`（色温/色调并入已有往返，**无第二次往返**）；契约 `kCount=96` / `COUNT=96` 已同步。

| 槽 | 名 | 语义 | 建议 UI 范围 | 恒等值 |
|---|---|---|---|---|
| `[88]` | temp_mired | **目标白点**的 mired 偏移（基准 6500K） | **UI 用 K：2500–12000K，默认 6500K** | 0 |
| `[89]` | tint | 绿 ↔ 品红（正 = 品红） | −0.5 … +0.5 | 0 |
| `[90]` | highlights | 高光（乘性 luma 增益） | −1 … +1 | 0 |
| `[91]` | shadows | 阴影 | −1 … +1 | 0 |

**⚠ 方向约定（E2-14 UI 卡必须照做）**：`temp_mired` 存的是**目标白点的 mired**（`mired_target = 153.846 + 槽位值`）⇒ **槽位值正 = 目标 K 更低 = 画面变冷**。所以 **UI 滑杆必须直接用 K**（右移 = K 大 = 变暖），写入时换算成 mired；**若直接把 mired 当滑杆值，滑杆方向与读数方向相反**。下端建议 2500K（< 2000K 时 B 增益撞 3.0 clamp）。

**模型依据**：Tanner Helland 黑体近似 + **参考点差分**（`gain = wbGain(K_target) / wbGain(6500)` ⇒ mired = 0 时逐位 = 1.0f，这是零回归的关键）。选它的首要理由：**与拍照链路 `CameraController.kt:648 wbGains()` 逐行同式** —— 同一 App 只能有一套"色温"语义，否则编辑器 +500K 与拍照 +500K 观感不同。

**已知瑕疵**：该模型在 6600K 处 G 通道不连续（实测台阶 1.32% ≈ **1.7 LSB**）。架构师裁决：**接受**（K 滑杆跨 6600K 时可感知度低；修它需更精确模型，属后续升级）。

**影调分区为乘性**（`g = 1 + hl·l² + sh·s² + wh·l³ + bl·s³`；端点与一阶连续、无硬边）。选乘性而非加性的理由：**保色度比**（加性抬亮会把暗部灰化、拉低饱和度 —— 与 E2-2 clarity 那条同型事故）。代价：阴影提亮在极暗处偏弱（`+1` 时 luma16 仅 +14 LSB、luma64 +36 LSB）。**真机看效果再定是否改加性**。

**新卡 E2-14**（排队等 E2-10）：把 `[88..94]` 七个参数接进新面板。

### ADR-16 裁剪规格（E2-12 预研，2026-10-09）

**定位**：裁剪是**几何变换**，与色彩参数无关 ⇒ **不进 `FilmParams` 契约**（避免为几何量再扩一次契约），走 `submitDisplay` 的**独立参数通道**。

**引擎侧做法（关键）**：在 `kFsStyle` 采样输入纹理时做 UV 变换：

```glsl
vec2 uv = uCropOrigin + vUV0 * uCropSize;   // 裁剪后 UV → 原图 UV
vec3 c = texture(uTex, uv).rgb;
// 后续所有处理（暗角 / 局部调整 / LUT / 颗粒）继续用 vUV0（= 裁剪后的归一化坐标）
```

**为什么这样暗角与局部调整会自动正确**：它们的坐标基准都是 `vUV0`，而 `vUV0` 在裁剪后仍覆盖 [0,1]（即裁剪后的整幅画面）⇒ 暗角自动相对裁剪后画面居中、局部调整中心自动落在用户拖的位置。**这正是 ADR-14 裁决 3 要求"裁剪在引擎输入侧做"的原因** —— 若改为最后裁输出位图，暗角会跑到画面外、局部调整中心会偏。

**输出尺寸**：裁剪改变宽高比 ⇒ 输出尺寸按裁剪比例调整（4080×3072 裁中间 50% ⇒ 输出 2040×1536）。`w/h` 由 Kotlin 算好传给引擎（`submitDisplay` 已有 `w,h` 入参）。

**首版范围**：
- ✅ 裁剪框（拖动 + 比例锁定：自由 / 1:1 / 4:3 / 3:4 / 16:9 / 原图）
- ✅ **90° 步进旋转**（4 个方向；UV 变换 + 输出尺寸交换）
- ❌ 自由角度拉直（水平校正）—— 后续卡（需要旋转矩阵 + 边缘填充策略）

**验收**：
- 裁剪后暗角仍相对画面居中（数值：角落衰减与未裁剪时同值）
- 裁剪后局部调整中心仍在用户拖的位置（拖动往返一致）
- 90° 旋转后画面方向正确、无拉伸（输出尺寸交换）
- 不裁剪时（默认全幅）输出与输入 `max|Δ| ≤ 1 LSB`（零回归）

**E2-14 交付后的两个待改 UI 点**（架构师记录，等真机反馈一并处理）：

1. **色彩组的图标行把 LUT 与参数挤在同一行** —— LUT 有 42 个内置，横滚很深，色温 / 色调 / 褪色可能被埋在后面。若真机上"找不到色温"，改为**两行**（LUT 一行 + 参数一行）。
2. **色彩组「重置本组」会同时清掉 LUT** —— 架构师判定**不该**：LUT 是用户选的"风格素材"，而色温 / 色调 / 褪色是"参数"；重置参数不该丢掉素材选择（类比：修图软件"重置调整"不会删掉你选的滤镜）。修法 = 去掉 `resetColor` 里清 LUT 那一行（1 行）。

### ADR-17 LUT 分类 UI 规格（E2-16 预研，2026-10-09 用户提供 Filmix 第三张截图）

**背景**：用户原话「**lut 可参考截图把分类同步过来**」，并提供 Filmix 滤镜界面截图。

**我们的实现规格**：

5. 分类前可加彩色圆点（按分类名哈希取色，纯装饰）—— 可选，优先级 2

**验收**：分类行数据 = `LutLibrary` 的分类列表；点分类过滤正确、「全部」恢复；空分类不显示（或显示空态提示）；**分类与数量对得上**（徕卡 12 / 富士 11 / 柯达 7 / 理光 6 / CineStill 2 / 哈苏 2 / MI 2）。

**E2-17 交付后的两个待观察点**（架构师记录，等真机反馈）：

1. **原图按钮首次按下会重建 12MP 输入位图**（20–40ms，松手即回收）⇒ 极短按可能来不及切到原图。改成缓存可消除，代价是 **+50MB 常驻**。**先不动**（真机看是否真有"按了没反应"的感觉）。
2. **面板收起后 `selKey`（选中参数）被 dispose，重新展开回落到第一个参数** —— 这是 E2-15 起的既有行为。若用户觉得"我选了色温，收起再展开变回曝光"别扭，改成把 `selKey` 提到面板外保存。

**E2-9 直通路径对 DNG 的缺陷（2026-10-09 架构师发现，待 E2-18b 一并修）**：

`exportNow` 的"无修改直通"分支**直接复制原片字节，没有判断源图类型**。若用户在编辑器里打开的是 **DNG**，
直通会把 **DNG 字节**复制成一个 `.jpg` 文件（MediaStore MIME 也写 `image/jpeg`）⇒ **内容与扩展名不符**，
相册可能无法显示或显示异常。

**修法**：直通分支加条件 —— **只有源图是 JPEG 时才直通**；DNG（及其他非 JPEG 格式）必须走渲染 + 编码路径
（DNG 本来就不是 JPEG，必须重新编码）。

**E2-18a 交付后的三个待观察点**（架构师记录）：

1. **网格缩略图性能**：从"平台 API + 系统缓存"改为"自解码 + 转正"（3 次 `openInputStream`）。
   典型手机（thumbPx≈359）⇒ 采样率 8 ⇒ **0.75 MiB/张**，24MiB 缓存约 32 张（原 48），影响小；
   **大屏/平板**（thumbPx 顶到 512）⇒ 采样率只到 4 ⇒ **2.99 MiB/张**，缓存仅 8 张 ⇒ 滚动可能频繁重解码。
   **架构师裁决：先不动**（典型手机影响小，不过度设计）。真机若卡顿，首选 `ImageDecoder.setTargetSize`(API 28+) 精确缩放。
2. **API 26/27 的 HEIF**：`BitmapFactory` 从 API 28 才支持 HEIF ⇒ 这类图在网格显示占位符（原来平台缩略图能显示）。
   **裁决：接受**（极老设备 + 少见格式）。
3. **DNG 在查看页的内存峰值**：需转正的图在 `createBitmap` 时两份同时在 ⇒ 12MP 约 **100MB 峰值**
   （JPEG 成片无此成本，直接返回原图）；OOM 时按设计降一档重试（不崩但会糊）。

**E2-2 的关键验收（技术风险点）**：
1. **往返无损**：`ev = 0` 且 `wb = (1,1,1)` 时，输出与输入**逐像素一致**（≤1 LSB）—— 这是"成对往返没写错"的结构性证明；
2. **域正确**：曝光/WB 必须在**线性域**生效（在显示域直接乘是错的）—— 可用"同一 ev 值下，线性域实现的亮部/暗部增量比符合 gamma 关系"来验证；
3. **默认零回归**：所有新参数默认值 = 无效果 ⇒ 现有编辑器输出逐位不变；
4. 契约三处同改 + `CameraPresetsTest` 护栏同步更新（79 槽 + `[78]` 默认值）。

**为什么清晰度要新槽位**：`[39] sharpen` 是**拍照链路**的轻度锐化（`kFsOut` 内、OETF **前**、小半径），语义与"清晰度"（显示域、中半径局部对比）不同；复用同一槽位会让两条链路语义打架。

#### E2-2 技术规格（架构师预研，2026-10-08）

**① 真 sRGB 曲线的解码（`kFsOut` 里已有 `srgbEncode`，需补对应的 decode）**
```glsl
// 与 kFsOut:4533 的 srgbEncode 严格互逆（IEC 61966-2-1）
// 分段点：线性 0.0031308 ↔ 编码 0.04045
vec3 srgbDecode(vec3 c) {
    c = clamp(c, 0.0, 1.0);
    vec3 hi = pow((c + 0.055) / 1.055, vec3(2.4));
    vec3 lo = c / 12.92;
    return mix(hi, lo, step(c, vec3(0.04045)));
}
```

**② 线性往返段（曝光 + WB 合并为一次往返 —— 省一次转换）**
```glsl
// ADR-7 订正 v2：这是**成对往返**，不是单程转换。门控保证零回归。
if (uExpWbOn > 0.5) {                       // 仅当 ev≠0 或 wb≠(1,1,1) 时启用
    vec3 lin = srgbDecode(c);
    lin *= exp2(uEv) * uWbGain;             // uWbGain = vec3(wb_r, wb_g, wb_b)
    c = srgbEncode(lin);
}
```
- **为什么合并**：曝光与 WB 都是线性域乘性操作，一次解码/编码即可，省一半转换开销。
- **门控**：`uExpWbOn` 由 CPU 侧算（`ev != 0 || wb != (1,1,1)`）⇒ 默认恒等时**整段跳过**，输出逐位不变。

**③ 显示域调整段（顺序：对比度 → 饱和度 → 清晰度）**
```glsl
// 对比度：绕中灰线性拉伸（k=1 恒等）
if (uContrastOn > 0.5) c = clamp((c - 0.5) * uContrast + 0.5, 0.0, 1.0);
// 饱和度：绕 luma 插值（s=1 恒等）；用现有 luma 权重 0.299/0.587/0.114
if (uSatOn > 0.5) {
    float l = dot(c, vec3(0.299, 0.587, 0.114));
    c = mix(vec3(l), c, uSat);
}
// 清晰度：中半径 USM（局部对比），只加差值 ⇒ 保色度坐标
if (uClarity > 0.0) c += (c - blurApprox) * uClarity;
```
- **清晰度的模糊**：**shader 内多 tap 近似**（建议 2 环 × 8 方向 = 16 tap，或沿用 `sharpenLuma` 的手动展开风格），**不要引入额外全分辨率 pass**（预览是实时路径）。
- 三项都加门控 ⇒ 默认值（对比度 1、饱和度 1、清晰度 0）时**整段跳过**。

**④ 槽位映射（尽量复用已有槽位，只新增 1 个）**

**架构师裁决（2026-10-09，E2-2 交付并独立验证通过后）**：

E2-2 交付了 `kFsStyle` 的四段（往返[曝光×WB] → 对比度 → 饱和度 → 清晰度），七项门禁全绿；架构师**独立复跑** ①–⑫ 全部通过（含往返无损 `max|Δ| = 1 LSB`、超差 0/27648；真 sRGB 相对误差 8.5e-4 / 8.7e-4，且 `pow(2.2)` 对照组能被判据抓住，证明判据有效）。两条待裁决事项：

#### E2-6 局部调整规格（架构师预研，2026-10-08 用户拍板要做）

**★ 一个必须先说清的 GLSL 约束（它决定功能形态）**
Mali 上禁用"**数组作为函数参数**"与"**循环内动态索引**"（项目实测：**静默失败**，不报错）。
⇒ **首版只支持一个局部调整**（径向 **或** 线性，二选一）。多个局部调整的两条实现路径见本节末"扩展路径"，都可行，但**等首版跑通后再评估**（铁律：先跑通一版，用数据决定）。

**mask 程序化生成**（无额外纹理、无额外 pass、零采样 —— 纯算术）：
```glsl
float localMask(vec2 uv) {
    if (uLocalType < 0.5) return 0.0;                       // 0 = 关（默认）
    vec2 p = uv - uLocalCenter;
    float d;
    if (uLocalType < 1.5) {                                 // 1 = 径向
        d = length(p / max(uLocalRadius, 1e-3));            // 半径归一化距离
    } else {                                                // 2 = 线性
        vec2 dir = vec2(cos(uLocalAngle), sin(uLocalAngle));
        d = abs(dot(p, dir)) / max(uLocalWidth, 1e-3);      // 到轴线的归一化距离
    }
    return 1.0 - smoothstep(1.0, 1.0 + max(uLocalFeather, 1e-3), d);  // 中心 1 → 羽化边 0
}
```

**调整量：局部曝光与全局曝光合并成一次往返（★ 关键）**
```glsl
float m = localMask(vUV0);
float totalEv = uEv + uLocalEv * m;          // 局部曝光按 mask 加权后与全局"相加"
if (uExpWbOn > 0.5 || m > 0.0) {
    vec3 lin = srgbDecode(c);
    lin *= exp2(totalEv) * uWbGain;
    c = srgbEncode(lin);                     // 全局+局部曝光：线性域一次完成
}
if (m > 0.0 && abs(uLocalSat - 1.0) > 1e-4) {   // 局部饱和度：显示域按 mask 混合
    float l = dot(c, vec3(0.299, 0.587, 0.114));
    c = mix(c, mix(vec3(l), c, uLocalSat), m);
}
```
- **为什么合并曝光**：若全局与局部各做一次往返 ⇒ 两次量化（误差累积）+ 多一次转换开销。合并后在**线性域一次完成**，数学正确。
- **零回归**：`uLocalType = 0`（默认）⇒ mask 恒 0 ⇒ 整段无副作用。

**扩展路径（多局部调整，首版不做）**
- **方案 A**：展开 N 份代码（每份一套 uniform + 一段 mask/混合）—— 简单，但代码量 ×N、编译变慢；
- **方案 B**：把 N 个局部调整的参数存进一张 N×1（或 256×1）的 RGBA16F 纹理，shader 里按 index 采样 —— 需一次采样 + 一张小纹理，可支持较多局部调整；
- 两者都**避开**数组/动态索引。等首版真机验证后再定。

**架构师裁决（2026-10-09，E2-6 交付并独立验证通过后）**：

E2-6 交付了单个局部调整（径向 / 线性 mask + 局部曝光 / 饱和度）。架构师**独立复跑** ①–⑬ 全绿：⑬a 零回归 `max|Δ| = 1 LSB`（关闭时其余 9 个 local 参数取极端值也不影响）；⑬b / ⑬d 径向与线性均与 numpy 解析解 ≤1.5 LSB；⑬c 边界平滑（剖面最大跳变 8.0 vs 解析 7.2，回落 0 次）；⑬g 全局 + 局部曝光合并为**一次往返**（指数相加，1.4 LSB）；⑬f `srgbDecode(` = 3 ⇒ 无第二次往返；`vignette` = 14 ⇒ E4-2 零丢失。三条待裁决：

1. **非方形画幅下 mask 是椭圆 —— 裁决：改成正圆**（并入 E2-7）。用户拖"径向调整"看到椭圆会困惑（竖拍 3:4 尤其明显）。做法：CPU 侧把 radius 拆成 `vec2(rx, ry)`（约 1 行），使 `d = length(p / r)` 在像素空间等距。**E2-7 必须同步更新 numpy 解析对照**，否则 ⑬b / ⑬c 会失配。
2. **局部饱和度按 mask 插值（偏离 ADR 伪代码的字面叠加）—— 批准**。全局饱和度恒等时两者**数学严格等价**（已推导）；非恒等时插值更连贯，符合"这个区域里饱和度是 X"的用户直觉。
3. **`chainLuma` 用中心像素的 mask 做域提升（不逐 tap 算 mask）—— 批准**。逐 tap = 16× mask 成本（length + smoothstep），移动 GPU 不划算；一阶近似只影响 clarity 斜率标定（二阶效应）。

**附带结论**：编辑器链路**没有**直方图 / 斑马纹（`kFsHist` 只服务拍照链路）⇒ ADR 里 T-1「辅助工具不含新效果」的缺口在编辑器侧**不存在**，无需处理。

### 5.3 E3 预设的仲裁约束（勘察报告 R6，派工时必带）

### I-4 决策（★ 参数快照的取值口径，E1-2/E3/E5 通用）**快照存的必须是"真正下发给引擎的那一份参数"，不是成员字段的裸值。** 已确认的差异点：

| 字段 | 预览用 | **成片用（快照要存这个）** |
|---|---|---|
| EV / 参数数组 | `filmParams`（`CameraController.kt:77` 成员） | `filmParamsForStill()`（`:179`）—— 它把**高光保护欠曝量**加到 `[0] exposure_ev`（`q[0] = filmParams[0] + u`） |

- 成片渲染实际用 `filmParamsForStill()`（`:2880` 与 `:2951` 两处）。
- **存错这一处 ⇒ 编辑器起点与成片实际观感对不上**（EV 差一个欠曝量）。
- 快照时机 = **入队时**（`queueJpegSave`，`:3341`），不是后台 `saveJpeg` 里读成员 —— 现有代码已有先例：`val iso = liveIso` / `val secNs = liveExposureNs` 的注释写明"拍摄瞬间的快照，**不能用成员变量**"。
- ⚠ 线程语义：`filmParams` 的写入全在 `render.looper` 上，而 `queueJpegSave` 由主线程/渲染回调调用 ⇒ 读取点必须在注释里说明，或改为在已捕获 `filmStill` 的路径上显式传参。**不允许留下未说明的数据竞争。**
- `queueJpegSave` 有 4 个调用点（`:2498`、`:2878`、`:2992`、`:2993`），其中只有 `:2878` 那条路径能直接拿到局部 `filmStill` —— 这是"在 `queueJpegSave` 内部统一取"更省事的原因（`filmParamsForStill()` 是幂等的：`copyOf()` 后改 `[0]`，不动成员）。

### I-2 决策（E1-3 用）
编辑器渲染**复用同一份 `DoubleArray(60)`**（ADR-1 单一参数源），不新建第二套参数语义。
- 编辑链路只读取它真正会用到的槽位；**无关槽位一律不得影响输出**（例如 `[54] pc3d`、`[45] hr_raw` 这些拍照链路的槽位在编辑链路里必须被忽略，不能因为数组里有值就意外生效）。
- 这条要求写进 E1-3 的验收：**同一个输入图 + 只改一个无关槽位 ⇒ 输出逐像素一致**（可离线验证，是"没串味"的结构性证明）。

### 7.2 P0：编辑器图像全黑 —— 排查方向（架构师预判）
**已知**：离线 `check-style-passthrough.py` ①-⑨ **全绿** ⇒ **`kFsStyle` 的 shader 数学是对的**，问题在 **C++/GL 环境层**（纹理/FBO/读回/EGL），不在算法。`passStyle` 与 `passOutput` 的 GL 状态设置结构一致，引擎全局不用 VAO ⇒ 排除 VAO。

**最可疑（按可能性）**：
1. **`still_tex_` 内部格式 `GL_RGB8` + 上传格式 `GL_RGBA` 不匹配** —— 部分驱动拒绝（`GL_INVALID_OPERATION`）或产生未初始化内容 ⇒ 采样恒 0 ⇒ 全黑。注意 `still_tex_` 是**与 `submitStill`（YUV 拍照）共用的成员** ⇒ 修法是**编辑器用自己的 `GL_RGBA8` 纹理**，不动共用成员（拍照链路零影响）。
2. **`glReadPixels` 静默失败** —— `out_rgba->resize()` 零填充 ⇒ 输出全黑且不报错。
3. FBO 完整但 draw 无效（program/uniform/绑定）。
4. 编辑器自建 EGL context 的差异。

**要求**：修复卡必须**同时加"一次定位"诊断**（输入图均值/首像素、各步骤 `glGetError`、输出图均值/首像素、纹理与 FBO 实际参数）—— 真机验证机会宝贵，必须一次运行就能定位失败环节。

### 7.3 新需求：相册浏览（用户 2026-10-08 明确）
**用户原话**：左上角要有菜单图标，点击可查看相册所有图片；未拍摄前首次点胶卷位也应该能跳转查看所有照片；**编辑器查看的图片要是相册原图，不可用缩略图**；菜单点击后查看所有照片缩略图（传统相册逻辑）。

**拆解与决策**：
| 项 | 决策 |
|---|---|
| 相册页 | 网格显示**所有照片缩略图**（按时间倒序；日期分组有余力再做） |
| 入口 A | 编辑器左上角**菜单图标** → 相册页 |
| 入口 B | 相机页**胶卷位恒可点** → 相册页（去掉 `photoUri != null` 的限制） |
| 点缩略图 | 进编辑器，**加载该图原图** |
| **编辑器素材** | **必须是原图**（`BitmapFactory` 全尺寸解码 + `inSampleSize` 降采样出预览尺寸）。**禁止**把 `loadThumbnail`/`Thumbnails` 的结果当编辑器素材 —— 缩略图只用于相册网格 |
| 照片范围 | 用户要"所有照片" ⇒ 查整个 MediaStore，需 `READ_MEDIA_IMAGES`(33+) / `READ_EXTERNAL_STORAGE`(<33) **权限请求**；**拒绝时降级**为只显示本 App 的 `Pictures/FilmKit`（不得空白或崩溃） |
| 非本 App 图片 | 无参数快照 ⇒ 编辑器用标准基线（现有回退逻辑已覆盖，ADR-4） |

**已确认（用户 2026-10-08）**：**预览也用全分辨率；拖动时不渲染，松手后才渲染一次**（用户原话："预览也建议全分辨率，可以拖完松手再渲染不用实时渲染"）。

⇒ 这条决定**简化**了实现：不需要"拖动降采样 + 松手全分辨率"的分级逻辑，直接**松手 → 全分辨率渲染一次**。同时**消除了"预览与导出不一致"**这一整类问题（两者同分辨率、同参数、同 shader）。

**新增卡 E2-8（待派）**：
- `EditorScreen` 的预览渲染改为**全分辨率**（输入用原图全尺寸，不再降采样到长边 1600）
- 滑杆**拖动中不触发渲染**（只更新参数与 UI 读数），**`onFinished`（松手）时触发一次**渲染
- **内存影响（必须处理）**：全分辨率预览会把常驻内存从 ~9.4MB 抬到 ~150MB 级（12MP：Bitmap 50MB + 输入 buffer 50MB + 输出 Bitmap 50MB）。要求：① 渲染后**及时释放**临时 buffer；② 输出 Bitmap 替换旧的时先 recycle 旧的；③ 保留 OOM 兜底（提示"图片过大"，原片不动）
- **耗时预期**：后段全分辨率实测 <55ms（E4-0 报告 §B6，含 50MB 读回）；加上基础调整段后仍应在百毫秒内 ⇒ "松手即出图"的体验可接受
- **验收**：拖动中画面不动（不闪、不卡）；松手后画面更新为全分辨率结果；同一参数下预览与导出的像素一致

### 附：编辑器参数口径必须对照拍照页既有量程（2026-10-09 用户发现）

**事故**：编辑器把 LUT 强度做成 `0..1`（100%），而拍照页一直是 `0..1.5`（150%）——
拍照页的 `RelativeSlider` **默认** `range = 0f..1.5f`（`CameraScreen.kt:2284` / `:2428`），
编辑器显式传了 `0f..1f` 覆盖掉。用户报：**"LUT强度应该统一可调至150"**。

**规则**：新增或修改编辑器参数时，**先查拍照页同名参数的既有量程**，以它为准（同一 App 只能有一套口径）。
编辑器与拍照页重叠的参数目前只有 LUT 强度这一处，已修。
