## 0. 结论速览（TL;DR）

> ⚠️ 本节的每个数字在第 1~4 章都有对应的原始输出。凡跨图结论，强度标注在括号里。

1. **口径已锁定并自证**：`前向差分 + 亮度=(R+G+B)/3 + ∇>60 + chroma=(R+B)/2−G + clip(x,0)`
   在 PC 成片上复现 **3.68413 / 0.44607%（n=18707）**，与目标 3.684 / 0.446% 完全一致。
   72 个候选变体扫描中，只有该组合（及其 `>=60` 孪生）落入 ±0.01。
2. **旧数字 7.39 的来源已定位**：换一个同样"合理"的 chroma 定义（`max(R,B)−G`）就能把同一张 PC 图从 **3.684 抬到 7.31**（§1.3）。
   换梯度定义（中心差分）能把 PC 的占比从 0.446% 砍到 0.222%。
   ⇒ **7.39 / 5.43 / 1.47× 那一整套数字是口径产物，不是成像质量产物**，本报告不再使用它们。
3. **"我们的 ∇>60 占比只有 PC 的 1/4.5"是分辨率假象**（§3.1）。
   把我们的成片下采样到 PC 的 1777×2360 后，占比升到 **0.334%~0.446%**（PC 0.446%）；把 PC 放大到 3072×4080 后，它的占比塌到 **0.029%~0.062%**。
4. **读数上的 ~3× 差距无法用分辨率解释**（§3.1），但它**绝大部分由高频噪声/伪影贡献，而不是宽缓的结构性色偏**（§3.3、§4）。
5. **剖面形状**（§4）：两边的紫边都是**紧贴边缘的窄峰（1~3px）**，不是跨十几 px 的宽缓偏移。
   ⇒ 指向高频环节（去马赛克/锐化/编码/横向色差），**不是**色度降噪尺度或色调链。

## 1. 第一步：口径固定与自证

### 1.1 唯一尺子的完整定义（伪代码级）

实现见 `/tmp/pcfix/metric.py`（`measure()`），**之后所有图、所有实验都只走这一个函数**。

```
输入: JPEG/PNG 文件
rgb  = PIL.convert('RGB') -> float64          # 显示域(gamma 编码) 0..255, 未做任何线性化/白平衡/降噪
lum  = (R + G + B) / 3                        # 用户指定权重, 非 rec601/709

fx[:, 0:-1] = |lum[:, 1:] - lum[:, 0:-1]|      # 前向差分 x
fy[0:-1, :] = |lum[1:, :] - lum[0:-1, :]|      # 前向差分 y
fx[:, -1] = 0 ; fy[-1, :] = 0                  # 边界处理: 最后一列/行置 0 -> 永不入选
grad = max(fx, fy)

chroma = (R + B)/2 - G                         # 紫边方向为正
mask   = grad > 60                             # 严格大于
value  = mean( max(chroma[mask], 0) )          # = E[max(x,0)], clip 在取均值之前
frac   = mask.mean() * 100                     # 占全图百分比
```

**三个容易踩的口径陷阱（本报告全部固定为左侧写法）：**

| 项 | 本报告（已自证） | 另一种"同样合理"的写法 | 对 PC 读数的影响 |
|---|---|---|---|
| 梯度 | **前向差分** `|I(x+1,y)−I(x,y)|` | 中心差分 `|I(x+1,y)−I(x−1,y)|/2` | 3.684 → **3.644**，占比 0.446% → **0.222%** |
| 色度 | **`(R+B)/2 − G`** | `max(R,B) − G` | 3.684 → **7.307** |
| 截断 | **`clip(x,0)` 后再取均值** | 先取均值 | 3.684 → **1.908** |

### 1.2 自证结果（`python3 /tmp/pcfix/metric.py` 的 assert）

```
metric.py self-check OK: {'v': 3.6841289356925215, 'n': 18707, 'frac': 0.4460717453716509,
                          'thr': 60.0, 'lum_med': 72.666..., 'g_p999': 91.666..., 'px': 4193720}
```
- 目标：`3.684 ± 0.01`、`0.446% ± 0.002%` → **命中**（3.68413 / 0.44607%）。
- **读到的**：PC 附件图尺寸 1777×2360，亮度中位 72.67，∇ 的 p99.9 = 91.67。
- 边界处理经检验**不敏感**：`fx`/`fy` 末列置 0 与"直接丢弃边界一列"等价（0 不满足 `>60`），对读数无影响（推算，因末列永不入 mask）。
- `>` vs `>=` 有微小差异：`>=60` 给 3.679 / 0.450%（因为梯度是 1/3 的整数倍，恰好等于 60.0 的像素极少）。**本报告用 `>`**。

### 1.3 变体扫描：为什么"换口径=换结论"（`/tmp/pcfix/selfcheck_variants.py`）

72 个变体，按与目标的距离排序，最接近的 8 个：

| value | frac% | n | 口径 |
|---|---|---|---|
| **3.684** | **0.446** | **18707** | `lum=mean(RGB) grad=fwd-max >60 chroma=(R+B)/2-G` ← **本报告口径** |
| 3.679 | 0.450 | 18891 | 同上但 `>=60` |
| 3.673 | 0.451 | 18896 | `lum=rec601` + fwd + `>60` |
| 3.699 | 0.453 | 19012 | `lum=rec709` + fwd + `>60` |
| 3.644 | **0.222** | 9310 | `lum=mean(RGB)` + **central-max** + `>60` |
| 7.307 | 0.446 | 18707 | 同本报告但 chroma = **`max(R,B)-G`** |
| 1.908 | 0.446 | 18707 | 同本报告但 **不 clip**（直接取均值） |

**读到的**：`lum=` 权重只造成 0.4% 的漂移（3.673~3.699），**梯度定义和 chroma 定义才是量级级别的开关**（0.222% vs 0.446%；3.68 vs 7.31）。

## 3. 第三步：差距的构成（四维消融）

脚本：`/tmp/pcfix/run_step3.py`、`run_step3b.py`。所有读数都出自 `metric.py` 的同一个 `measure()`。

### 3.1 分辨率（最大的单一笑混淆项）

| 处理 | ∇>60 占比 | 紫边 v | n |
|---|---|---|---|
| PC 原生 1777×2360 | **0.446%** | 3.684 | 18707 |
| ours 152207 原生 3072×4080 | 0.099% | 12.155 | 12470 |
| **ours 152207 → 1777 (BOX)** | **0.334%** | **11.422** | 14024 |
| ours 152207 → 1777 (LANCZOS) | 0.366% | 11.881 | 15336 |
| ours 161514 → 1777 (LANCZOS) | **0.446%** | 7.117 | 18711 |
| ours 161533 → 1777 (BOX) | 0.398% | 5.084 | 16706 |
| **PC → 3072 (BILINEAR)** | **0.029%** | 3.308 | 3639 |
| **PC → 3072 (LANCZOS)** | **0.062%** | 3.589 | 7762 |

**读到的结论（强度：高，纯几何操作，无场景依赖）：**

- **"我们的 ∇>60 占比只有 PC 的 1/4.5" 是分辨率假象。**
  把我们的成片下采样到 PC 的 1777×2360 后，占比从 0.099% 升到 **0.334%~0.446%** —— 与 PC 的 0.446% 持平（161514 甚至精确相等）。
- **反向验证**：把 PC 放大到 3072×4080，它的占比从 0.446% 塌到 **0.029%~0.062%（1/7 ~ 1/15）**。
  ⇒ 同一张 PC 图，仅因重采样，占比就能变动 15 倍。**这个指标跨分辨率不可比**。
- 机理（推算，但机理明确）：我们的 3072 成片在边缘处是**跨约 2px 的过渡**，下采样到 1777 后同样的亮度落差被压缩进更少的像素 ⇒ 单位像素梯度变大 ⇒ 更多像素越过 60。PC 的 1777 输出本身就是"过渡已被压缩"的状态。
- **尺度归一化阈值（`∇ > 60×scale`，我们侧 34.7 / PC 侧 103.7）是必须做的**：
  - ours → 1777 用 34.7 时占比 1.11%~1.33%，**是 PC 的 2.5~3.0 倍**；
  - PC → 3072 用 103.7 时占比 **0.000%（仅 36 个像素）**，即 **PC 的成片里根本不存在"物理上等效于我们 3072 尺度 ∇>60"的陡边缘**。
  ⇒ 一旦把 ∇ 的物理含义归一化，"PC 边缘更多/更强"这个印象**完全反转**。

**但注意**：分辨率**解释不了读数 v 的差距** —— 我们的图缩到 PC 尺寸后 v 仍有 11.42（BOX）/11.88（LANCZ），是 PC 3.684 的 **3.1~3.2×**。这个 3× 需要 3.2/3.3 来解释。

## 4. 第四步：剖面形状 → 指向哪一环

脚本：`run_step4.py`（剖面）、`run_encode.py`（编码对照）。
**边缘对齐平均色度剖面**：取 ∇ 的 3×3 山脊且 ∇>60 的点，沿中心差分梯度方向、以边缘为原点、把"亮侧"统一对齐到 +t，累加 ±12px 的平均 chroma，再扣掉远端基线（|t|∈[8,12] 的均值）。

### 5.1 `CorrectingFlow` 是什么（读到的，`CorrectingFlow.java` + `correctingflow.glsl`）

**它校正横向色差（lateral chromatic aberration, LCA）。**

Shader 全文的核心（`correctingflow.glsl`，无 `#include`）：

```glsl
uv     = (gl_FragCoord.xy + u_tileOrigin) / SIZE;
center = (uv - C) * abs(uv - C);          // 以 C 为中心的二次径向项, C 默认 (0.5,0.5)
Output.r = texture(InputBuffer, clamp(uv + center*RC, 0, 1)).r;   // 逐通道
Output.g = texture(InputBuffer, clamp(uv + center*GC, 0, 1)).g;   // 独立的径向位移
Output.b = texture(InputBuffer, clamp(uv + center*BC, 0, 1)).b;
```

| 问题 | 答案 |
|---|---|
| 校正什么 | 横向色差：R/B 通道相对 G 通道的径向缩放不一致造成的边缘紫/青边 |
| 算法 | 每通道二次径向位移（`center = (uv−C)·\|uv−C\|`，`dxy = center·K`），K 来自设备标定表；**按通道重采样，不是空间滤波** |
| 输入/输出域 | post-pipeline 末端的**显示域 RGB**（`Sharpen2` 之前）；逐像素、无邻域采样、无色彩空间变换 |
| 分辨率 | 在输出分辨率上跑（`SIZE` = 输出尺寸），不是 mip |
| **是否影响强边缘色度** | **是** —— LCA 的症状就是强边缘处的窄色度边；但这个 shader 只是把通道对齐，**不抑制**边缘色度 |
| 谁在用 | 只被 `PostPipeline.BuildDefaultPipeline()` 装配一次（`PostPipeline.java:1538`） |
| 何时生效 | `CorrectingFlow.willCorrect()`：`sensorSpecifics.aberrationCorrection` 非 null **且** `c[0]!=0 \|\| c[1]!=0` |
| 数据来源 | `pro/SensorSpecifics.java:127` 从**设备专用表**解析 8 个 float；`SpecificSettingSensor.java:57` 默认 `new float[8]`（全 0） |

**关键事实（read + verified）**：
- 全仓库**只有 OnePlus 设备表**带非零值，且所有 OnePlus 的值完全相同：
  `aberrationCorrection = { 0.5, 0.5, 0.00017, 0.00017, 0.0, 0.0, 0.00005, 0.00005 }`
  （即 C=(0.5,0.5)、RC=GC=0.00017、BC=0.00005）。
- `SpecificList.txt` 只有 **34 行**，**没有 vivo**。
- **样片设备 = vivo V2509A**（读到的：DNG 元数据 `kMDItemAcquisitionMake = "vivo"`, `kMDItemAcquisitionModel = "V2509A"`）。
- ⇒ **在 vivo V2509A 上 `willCorrect()` 返回 false，`CorrectingFlow` 是 passthrough（`WorkingTexture = previousNode.WorkingTexture`）。PC 的成片里没有任何横向色差校正。**
- 另外 PC 自己的注释也印证它是被当作直通对待的：`PostPipeline.java:1543-1544` "CorrectingFlow must stay passthrough: tiling through its unproven warp is out of scope."
- 即便在 OnePlus 上启用，位移量也极小：|center| 最大约 0.25（角部），RC=0.00017 ⇒ 位移 ≈ 4.3e-5 归一化单位 ≈ **0.076 px @1777**（推算）。

## 6. 旧数字溯源（为什么会有 7.39）

**读到的**：`/tmp/pc3d/user_metric.py` 的 docstring 与实现对"用户指定口径"的定义是：

```python
L = 0.2126*r + 0.7152*g + 0.0722*b        # ← Rec.709 亮度（不是 (R+G+B)/3）
gy, gx = np.gradient(L)                    # ← 中心差分（不是前向差分）
mask = np.maximum(np.abs(gx), np.abs(gy)) > 60
fr = clip((r+b)/2 - g, 0)
img = load_linear(p, ds=3)                 # ← 关键：成片反推线性 + ds=3 降采样(≈1024×1360)
```

**⇒ `7.39` 是"离线模拟链 + 1/3 降采样"下的值，不是真机全分辨率成片的直接读数。**
同一张 152207，同一族口径下的读数矩阵（本任务实测）：

| 口径 | 152207 | PC |
|---|---|---|
| **本报告口径**：fwd-max + `(R+G+B)/3` + `>60` | **12.155** | **3.684** |
| fwd-max + mean + `>=60` | 12.142 | 3.679 |
| cen-max + mean + `>60` | 12.890 | 3.636 |
| cen-hypot + mean + `>60`（`/tmp/chromagate2` 口径） | 14.620 | 3.865 |
| + chroma 换成 `max(R,B)−G`（**本任务实测**） | **20.024** | 7.307 |
| 离线链 + ds=3（`/tmp/pc3d` 口径） | **7.389**（`base` 行，读到的） | — |

**读到的结论**：
1. **7.39 与 12.155 的差主要来自 `ds=3` 降采样**（下采样会显著改变读数，§3.1 已量化同一效应）。
2. **PC 的 3.684 也只在"fwd-max + mean-luma + >60"这一把尺子下成立**；换到 `/tmp/pc3d` 的口径（cen-max + rec709 + ds=3）它会变，换到 hypot 口径变成 3.865。
3. ⇒ **此前所有跨图比值（7.39/3.684 = 2.0×、5.43、1.47× 等）都是"两边用不同尺子"的产物，不可用。** 本报告全部结论统一在 §1.1 那一把尺子下。

## 7. 结论：差距的构成 + 指向 + 建议

### 7.1 逐项回答用户提的四个维度

| 维度 | 消除混淆后的结果 | 判定 |
|---|---|---|
| **① 分辨率** | 我们的缩到 1777：占比 0.099% → **0.334~0.446%**（PC 0.446%）；PC 放大到 3072：占比 → **0.029~0.062%**。**"占比只有 PC 的 1/4.5"是纯分辨率假象，归零。** 但**读数 v 只从 3.30× 动到 3.10×** | 占比：**完全解释**；读数：**完全不解释** |
| **② 边缘样本构成** | 改成同分位数（top 0.446%）：3.30× → **1.38×~3.02×（中位 1.9×）**。且发现 **PC 的读数对分位数几乎不敏感**（0.05%→1% 只动 ±6%），**我们的强敏感** | 部分解释（约 30%） |
| **③ 噪声 vs 真紫边** | PC 的 mask σ/平坦 σ = **1.01**（边缘处无任何额外色度结构）；我们 = **2.74~3.30**。零假设下 PC 只有 **+1.67** 与边缘有关（另 2.02 是全局偏置），我们 **+3.37~+9.72** | **不解释，反而放大差距**（见下） |
| **④ 曝光** | 增益对齐到 PC 亮度后 152207: 12.155 → 10.752（−11%），161533: 6.161 → 6.051 | **只解释约 10%** |
| **⑤ 帧数** | **无法判定** | — |

### 7.2 ⇒ "扣除噪声与分辨率后我们还差多少"（直接回答）

**差距不会消失。** 收敛过程（以 152207 为例，其余四张见 §3.3c）：

```
3.30×  原始
3.10×  分辨率归一（都到 1777×2360）
3.01×  边缘样本归一（同分位数 top 0.446%）
2.03×  再扣高频噪声（V_low）
5.83×  改为扣"与边缘无关的全局偏置"（选择超额）  ← 差距反而变大，因为 PC 的 3.684 里 55% 是偏置
─────────
最终判定（最严格指标：边缘对齐剖面的局域超额 core）
PC core = 1.08 ;  我们 = 4.62 / 2.81 / 2.61 / 2.52 / −0.25
⇒ 边缘局域紫边 = PC 的 2.3× ~ 4.3×（中位 2.4×），且 5 张里有 1 张（161533）没有紫边
```

**⚠️ 一个重要的基准修正（本审计最有行动价值的发现）**：
**`3.684` 不是"PC 的紫边水平"** —— 其中只有 `+1.668` 与边缘有关，另外 `2.017` 是**与边缘无关的全局色度偏置**（零假设检验：同数量随机像素的读数就是 2.017）。而**我们的全局偏置更低（1.66~1.77）**。
⇒ 项目此前把 `3.68` 当作对标目标（见 `CameraPresets.kt:183-186`："收益…**达不到 PC 的 3.68**"），**这个目标值把 PC 高估了约 2.2 倍**。按正确目标（边缘局域超额 `1.67`、剖面 core `1.08`），要追的距离比原先认为的**大**（我们现在是 9.72 / 4.62），但**这个目标是可达的、且定义清楚了**。

### 7.3 ⇒ 指向哪一环（直接回答用户的问题）

**形状证据给出的答案**：我们的紫边是**紧贴边缘的窄峰（FWHM 4px@1777、前沿斜率 1.80/px，峰在暗侧 1px 处）**，PC 的是一条**跨 20+px 的宽缓斜坡（斜率 0.15/px，无局部峰）**。

| 候选环节 | 频率尺度 | 是否匹配我们的形状 | 依据强度 |
|---|---|---|---|
| **去马赛克伪彩 / 色度锐化 / 小尺度色度处理** | 1~3px | ✅ **匹配**（FWHM 4px、斜率 12× PC） | 剖面形状（高）+ 同一镜头推理（中高） |
| 编码 4:2:0 | 2px | ❌ 已受控 A/B 排除（−0.8%~−9.3%，形状不变） | 高 |
| 分辨率 | — | ❌ 已排除（归一后 3.10×，形状不变） | 高 |
| 横向色差（`CorrectingFlow` / [50]） | 1~3px | ⚠️ 尺度匹配，但**两边都没启用** | 高（源码） |
| 色度降噪尺度 / 色调链 / 局部对比度 | >10px | ❌ 不是**我们**的形状（**但正是 PC 那道斜坡的尺度**） | 高 |

**"剩余差距是不是只能靠降噪策略改进？"—— 分两半回答：**

- **方向对了一半**：PC 用来消除这类窄峰的工具**确实**是降噪 —— `ESD3D2`（`PostPipeline.java:1504`，紧跟去马赛克之后，核尺寸 PC 公式给 11，作用在**全分辨率**上）。也就是说，**在"去马赛克之后立刻做大核的边缘感知色度平滑"这件事上，PC 有、而我们默认没有**（我们的移植 `FilmParams[54]` **默认关**，`CameraPresets.kt:189`）。
- **但不是"只能"**：窄峰（1~3px）同样可以从**源头**减少 —— 去马赛克伪彩抑制（[46]/[48] 已在做）、**不让锐化碰到色度**（`Sharpen2`/`CaptureSharpening` 的色度处理需要逐行对照 PC）、以及 [47] defringe/[51] 色度门的参数。**"降噪"是治症，"源头"是治因，两者都在同一个高频环节里。**

**⇒ 建议的下一步（按性价比排序，全部可用同场景真机 A/B 验证）**：
1. **重新评估 `[54]`（PC ESD3D2 移植）**：它当初被关闭的依据是"离线收益达不到 PC 的 **3.68**"（`CameraPresets.kt:183-186`）。既然 3.68 已被证明是虚高目标（含 2.02 全局偏置），**应当用 `边缘局域超额` 或 `剖面 core` 重跑那次离线评估**。这是唯一一条"照抄 PC 的机制、代码已就绪、只差一个开关"的路。
2. **同场景真机 A/B 矩阵**（一次拍完，成本最低、证据最强）：同场景、同曝光，依次 `[47]` 开/关、`[51]` 开/关、`[54]`=0/1/2、`[50]` 开/关，各一张。用 `剖面 core` 作为判据（不是 `∇>60` 均值 —— 见 §3.6）。
3. **逐行对照 `Sharpen2` / `CaptureSharpening`**：确认它们是否对色度通道做了锐化（PC 的对应阶段是本任务未对照的项）。
4. 把 `剖面的边缘局域超额（core）` 和 `零假设选择超额` 固化成项目的标准 KPI；**废弃 `∇>60` 均值**作为跨图指标（§3.6）。

### 7.4 对"测量方法"本身的结论（可能比紫边数字更重要）

1. **`∇>60` 紫边均值不能被当作跨图 KPI**：同一地点相隔 7 秒的两张成片，在曝光、噪声 σ、`∇>60` 占比几乎完全相同的情况下，读数差 **25.8×**（§3.6）。
2. **它还会被分辨率和全局白平衡线性平移**（§3.1、§3.6结尾）。
3. **可用的替代指标**（本报告已验证、且都对噪声和曝光免疫）：
   - **零假设选择超额** = `V(∇>60 mask) − V(同数量随机像素)` —— 免疫全局白平衡与噪声；
   - **边缘对齐剖面的局域超额 core** = `mean(profile, |t|≤2) − mean(profile, |t|≥8)` —— 免疫零均值噪声（N≈4000 次平均），且**形状本身**能区分高频/低频环节。
