# 0.14.11--0.14.13 性能实测（2026-11-16）

> 后续资源分配实测、预热修复和最新候选见 `performance-0.14.16-20261116.md`。
> 本文0.14.13为该轮结束时点的历史版本。

## 结论

目标仍为快门至相册保存 3--5s，优选不超过 4s，计算期间预览几乎不掉帧。
**尚未达标**。0.14.13(810) 三张为 **6.742 / 4.875 / 5.016s**，中位 5.016s。
热身后的完整处理窗口最低约 27 FPS，但仍有 142--163ms 帧间隔；首拍仍有明显长尾。
本文承接 `performance-0.14.9-20261116.md`。下述是版本分组观测，不是同输入、同温控 A/B 加速比。

## 已确认的问题与改动

### 0.14.11：绘制内的非同步计时

`preview.slow_draw` 分解 targets/OES/TEQ/film/output，以及 film 内嵌的 histogram
提交、同步读回等待、CPU 完整统计。仅对缩放预览、host 总时长 >=40ms 记录，不新增
GPU fence、finish 或 readback。histogram 的读回等待包含前序排队工作，不等于传输时间；
嵌套字段不能重复相加，阈值样本的中位数不能冒称全帧分位。

### 0.14.12：still 诊断状态串入预览线程

`g_diag_chain` 原为进程全局 bool。still 链打开它后，预览 `passFilm` 也跑
`diagStatsTex("HR-filmsrc")`，每帧多做 786432 点 GPU 统计和 glFinish。
0.14.11 每张 HR 诊断为 59 / 64 / 69 次；注释声称“不在预览跑”但未被线程所有权保证。

改为 thread_local 的 chain/params/seq，原子生成唯一序列号，以 RAII 在所有出口关闭。
still 的完整诊断保留；0.14.12 实际 HR 次数成为 3 / 1 / 3，属于 still 曝光校正重绘。
`check-diag-threading.py` 提取生产定义，500 个并发 scope 验证隔离、唯一 ID、早退和关闭模式。

### 0.14.13：精确固定权重缓存与预览同步边界

512x288 中心权重只依赖几何。`HistogramWeights.h` 按原 float 表达式预计算不可变表
（约 576KB）；每帧仍读取全部 147456 个当帧像素，顺序、分箱、中心门、高光网格/聚类及
所有消费点不变，不缓存上一帧统计。147456 个权重与 16 组完整 histogram 均逐位一致。
Android 单组件测试由 1.12--1.25ms 降到 0.094--0.123ms；另一较凉组为
0.574--0.650ms 到 0.079ms。这不是 App 总耗时加速比。

预览 TEQ 末尾不再额外 glFinish；同一 GL 命令流保证顺序，随后的当帧完整读回仍同步。
still 计时边界保留。等待可能移至 histogram，不能把 TEQ host 缩短当作总 GPU 工作消失。

没有减帧、减核、降精度、删统计、改高光接受门或使用旧帧测光。

## 首拍线索

0.14.13 app.start=11:31:51.945；still 初始化 192ms；预热在 11:31:55.387 成功完成，
快门 11:32:08.931，render queuedMs=0。**不是快门等预热**。
首张还发生两次既有曝光校正重绘（HR 次数3）；不能全部归因 PC3D。
预热已建 full-size PC3D 两张输出，scale=2 改为实际 scale=1 本身不强制重建这些输出。
新增高光 RGBA32F noise/cov 及部分 program 未纳入预热，是待测线索，不是已证实根因。
下一步仅加首次分配/编译 host 计时，不引入新同步；host 分配计时不能代表首次 GPU 触页成本。
