# PhotonCamera ML-AE 离线验证报告

- 日期：2026-11-04
- 目的：回答「能不能用 PC 的 ML 模型替代启发式 AE」，而不是先写判据再验证
- 样本：`test_temp/` 5 张 FilmKit DNG（152558 = 日志 `15:26:01` 那张，点测 `aeMid=0` 的带天空场景）
- 结论先行：**模型能跑、能用、给出的量和我们独立算出的缺口吻合到 0.2 EV；但它回答的是「曝光该补偿多少」，不回答「这个场景该不该亮」**

---

## 1. 复刻口径（逐条对照源码，非推测）

来源：`PhotonCamera/app/src/main/java/com/hinnka/mycamera/raw/RawSceneExposureEstimator.kt`

| 项 | 定义 | 出处 |
|---|---|---|
| 输入 | `[1,64,64,9]` = `[ln(R), ln(G), ln(B), ln(scene), face, 0, 0, saliency, 0]` | `writeCombinedModelInput()` |
| RGB | `ln(max(u15_linear,0) + 1e-6)`，u15 = `floor(v*32767+0.5)/32768` | `modelLogColor()` / `toMeteringU15()` |
| logScene | `ln(geoSignal / normalizedExposure + 1e-4)` | `measureSceneBrightness()` |
| normalizedExposure | `(17.61/14.6) * (tetMs/1000)`，`tetMs = exposureMs * iso/100` | 同上 |
| geoSignal | `exp(mean(ln(max(r,g,b,0) + 10/32768))) - 10/32768` | 同上 |
| 语义哨兵 | saliency 缺省填 `0.05`（其余语义通道 0） | 常量注释 |
| 输出 | `logGain` → `gain = exp(logGain) - 1e-6`，即 `idealTet = currentTet * gain` | `resolveIdealExposure()` |
| long 分支 | 拆成两个输入：`[1,64,64,4]` + `[1,64,64,5]` | `writeSplitModelInputs()` |

DNG 侧：rawpy 读 10bit RAW（black≈64 / white=1023），2×2 合并成 RGB，area 平均到 64×64，乘
AWB（`camera_whitebalance` 绿归一），再 U15 量化。exposure/ISO 从 TIFF 标签
`0x829A`/`0x8827` 读。

> **一处已知偏差**：我们喂的是**融合后**的 DNG，PC 喂的是 `exact RAW frame`（base 帧）。
> 融合图的暗部已经被长帧抬过，几何均值偏高 ⇒ 模型会**低估**该补的量。下表结果因此是保守下限。

## 2. 结果

| 样片 | 曝光 | ISO | 场景 geo | ML short | ML long | ML portrait |
|---|---|---|---|---|---|---|
| 134653 阴天建筑 | 3.76 ms | 50 | 0.0429 | +0.41 | **+2.06** | +1.93 |
| 134722 室内绿植 | 81.6 ms | 50 | 0.1304 | +0.90 | +0.81 | +1.23 |
| 134759 | 42.4 ms | 50 | 0.0400 | +1.02 | +1.89 | +2.00 |
| 134821 白墙 | 100 ms | 266 | 0.1987 | +0.52 | +0.33 | +1.32 |
| **152558 带天空** | 3.78 ms | 50 | 0.0439 | **−0.03** | **+1.99** | +2.08 |

模型推理成本：3 个模型一套 **5.99 ms**（Mac CPU / XNNPACK），体积 60 KB / 61 KB / 62 KB。

### 2.1 和引擎现状对比（152558，日志里 `15:26:01` 那次渲染）

| | 值 |
|---|---|
| 日志 `aeGeo`（15:26:01 帧） | 0.0623 |
| 本次复算 `geoSignal` | 0.0439（同量级，差 0.5 EV：我们的缩放/AWB 与引擎口径不完全一致） |
| ML 建议 short | **−0.03 EV（不动）** |
| ML 建议 long | **+1.99 EV（长帧 ×4）** |
| 引擎 点测 `aeMid`（该帧） | **0.000** |
| 引擎 系统测光 `aeMid`（16:19:08 同场景另一张） | 1.210 |
| 按该帧 geo 补到标准中灰 0.1845 | log2(0.1845/0.0623) = **1.57 EV** |

**ML 的 +1.99 EV 落在「补到标准中灰 1.57 EV」和「系统测光 1.21 EV」之上 0.4~0.8 EV。**
两条完全不同的路径（一条从 `log2(target/geo)` 推，一条从神经网络推）指向同一量级，
说明这个场景确实缺 1.5~2 EV，而不是我们的公式算错。

而且它给的不是「整体加 2 EV」：

- short 分支说 **不动**（−0.03 EV）⇒ 高光不用再压
- long 分支说 **×4**（+1.99 EV）⇒ 只把长帧拉长

这正是「短帧保高光 + 长帧提暗部」的 bracket 压 DR，**不是我们原来那种整体增益**。

### 2.2 另外两张的解读

- **134821 白墙（100 ms / ISO 266）**：曝光相对场景已经够长，模型只给 long +0.33 EV。
  说明它不会见暗就抬。
- **134722 室内绿植（81.6 ms）**：long +0.81 EV、short +0.90 EV，两者几乎相等 ⇒
  它认为「这张只是整体略欠，不需要拉 DR」。和我们「这张发灰但不是暗」的观感一致。

## 3. 稳健性消融（152558）

| 变体 | short | long |
|---|---|---|
| 基线 | −0.03 | +1.99 |
| 去 AWB | −0.66 | +2.26 |
| 去掉 logScene 通道（置 0） | −0.17 | +1.97 |
| saliency = 0 | −0.23 | +2.04 |
| saliency = 1.0 | −0.17 | +2.16 |

- **long 分支对输入细节不敏感**（±0.3 EV），结论稳。
- **short 分支对 AWB 敏感**（0.6 EV）：因为 short 本来就接近 0，色彩比例一变就跨过零点。
  要落地必须先接对 AWB/CCM。
- `logScene` 通道影响只有 0.1~0.2 EV ⇒ PC 那套 Pixel 标定常数（17.61 / 14.6）即使在我们
  设备上偏了，也不会把结论带飞。**RGB 通道才是主因。**

## 4. 极暗输入扫描（回答「会不会误伤夜景」）

把 152558 整图按倍数压暗，模拟「曝光更不足」（2026-11-04 已补真实暗光样本，见 §4.1）：

| 输入缩放 | short | long |
|---|---|---|
| ×1 | −0.03 | +1.99 |
| ×0.5 | +0.49 | +2.80 |
| ×0.25 | +1.26 | +3.61 |
| ×0.125 | +2.09 | +4.39 |
| ×1/16 | +3.31 | +5.25 |
| ×1/32 | +4.63 | +6.28 |
| ×1/64 | +5.49 | +7.34 |

**单调、1:1 补偿**：输入少 2 EV，long 就多要 2 EV。

这说明模型不是「场景分类器」，是「曝光补偿器」——它**不区分**「这是夜景，本来就该暗」和
「这是白天，HAL 给少了」。对真夜景它同样会说「加 7 EV」。

所以「ML 会不会误伤夜景」这个问题问错了对象：

- 模型只回答「曝光该给多久」
- 「给不给」由**上限**决定：PC 那边是 `shotMax`（手持 TET 上限）+ `maxHdrRatio`(9.8) +
  `safeUnderexposure`
- 我们要不要接夜景长曝，是产品策略，不是模型能替我们决定的

§4.1 用真实暗光样本验证了这个推断：模型知道「ISO 10113 / 100 ms 已经用掉曝光预算」，
只给 long +1.39 EV，而不是扫描里那个 +7 EV。


## 4.1 暗光真样本（2026-11-04 补充）

样本：`filmkit_20261104-143158.dng`（室内暗光，100 ms / ISO 10113），成片
`filmkit_20261104-143202_理光负片标定.jpg`（mean 74.1 / P50 79.3 / P95 125.9 / 死黑 2.6%）。

| 样本 | 曝光 / ISO | geoSignal | logScene | short | long | portrait |
|---|---|---|---|---|---|---|
| 152558 白天带天空 | 3.78 ms / 50 | 0.0439 | **+2.96** | −0.03 | +1.99 | +2.08 |
| **143158 室内暗光** | 100 ms / 10113 | 0.0434 | **−5.61** | **+0.96** | **+1.39** | +1.79 |

**两者的 `geoSignal` 几乎相同（0.0439 vs 0.0434），但模型给出了完全不同的建议。**
区别只在 `logSceneBrightness`（+2.96 vs −5.61，即「当前的曝光坐标够不够」）。

这说明模型不是「看到暗就给大 gain」，而是先算「这张图的曝光预算用了多少」：

- 白天：short **不动**、long +2 EV ⇒ 判定为「整体曝光够，只是暗部缺」，要拉 DR
- 暗光：short **+0.96**、long +1.39 ⇒ 判定为「整体都欠」，两个分支一起抬

### logScene 通道消融（同一张暗光图，只改这个通道）

| logScene | short | long |
|---|---|---|
| −5.61（真实值） | +0.96 | **+1.39** |
| −3.00 | +1.78 | +2.02 |
| 0.00 | +1.84 | +2.16 |
| +2.96（白天值） | +1.90 | **+2.44** |

**在暗光样本上这个通道值 1.05 EV**——上一轮在白天样本上只值 0.1~0.2 EV，所以
「logScene 不重要」的结论只对白天成立。暗光下它是主要判据，**ISO / 曝光时间必须准**，
否则输出会偏 1 EV 量级。

### 但这条建议在本机上不可执行

+1.39 EV ⇒ 长帧 ×2.63。当前是 100 ms / ISO 10113：

- 走快门 ⇒ **263 ms**，手持必糊
- 走 ISO ⇒ **ISO 26600**，噪点爆炸

也就是说模型给的是「物理上正确、当前采集能力做不到」的答案。**这正是「上限必须由我们自己定」
的实证**：模型回答「曝光该给多久」，但「给不给得起」是 shot planning 的事。这个场景该走的是
多帧堆叠/夜景模式，而不是把单帧曝光再拉 1.4 EV。

### 离线模拟（×2.63 后走 filmic，仅为相对参考）

| | mean | P5 | P50 | P95 | 死黑<10 |
|---|---|---|---|---|---|
| 现在（×1） | 37.0 | 4.8 | 28.2 | 98.6 | 19.9% |
| ×2.63 | 100.1 | 17.6 | 100.2 | 185.1 | 1.6% |

> 绝对值与实拍成片不可比（该模拟不含 LUT / gainmap / 渲染端 AE），只用来看方向和量级：
> 1.4 EV 确实能把这张从「暗到发死」救回正常暗光。

## 5. 结论

1. **技术上没有障碍**：3 个 60 KB 模型，手机 CPU 上一套 <30 ms，输入我们全都有。
2. **语义要先讲清**：它输出的是 TET 倍率（采集端曝光），不是渲染端 target，也不是亮度增益。
   直接把它接到 `aeMid` 上是接错位置。
3. **它给出的量是对的**：152558 上 short 不动 / long +2 EV，比「补到标准中灰」的 1.57 EV
   多 0.4 EV，比系统测光的 1.21 EV 多 0.8 EV；并且它选的是「拉长帧压 DR」而不是「整体提亮」
   ——正是我们缺的那个自由度。
4. **`target` 0.12→0.1845 的方案量级不够**：这个场景只补 0.6 EV，ML 要 2 EV。
5. **它不解决审美判断**：极暗输入照样给 +7 EV，必须由我们自己设上限。真实暗光样本
   （§4.1）上它给 +1.39 EV，因为它读得到 ISO/曝光坐标——比启发式强，但 +1.39 EV 对应
   263 ms 或 ISO 26600，本机做不到，所以「给不给」仍是我们的事。

## 6. 落地风险（按优先级）

| 风险 | 说明 | 缓解 |
|---|---|---|
| **许可** | PC README 写「第三方模型 carry their own license notices」，但 `assets/mgc_ae/` 下**没有单独许可文件**；这批是 Google MGC 9.7 的资产 | 商用前必须确认；不能因为「PC 有」就搬 |
| **接错位置** | 输出是采集端 TET，不是渲染端 EV | 只能改 shot planning / bracket 比率，不能塞进 `decideAe` |
| **AWB/CCM 域** | short 分支对 AWB 敏感 0.6 EV | 接之前先对齐我们的 AWB/CCM 输出，做 A/B |
| **样本偏差** | 我们喂融合图，PC 喂 base 帧 | 真实 gain 可能比本次更大（本次是下限） |
| **设备常数** | 17.61/14.6 是 Pixel V25 标定 | 影响仅 0.1~0.2 EV，可接受，但建议按本机重标 |

## 7. 复现

```bash
python3 tools/tuning/ml-ae-offline.py test_temp/FILMKIT_20261103-152558.dng
```

模型需预先下载到 `tools/tuning/mgc_ae/`（三个 tflite，见报告 §1 来源路径）。

---

**一句话**：模型不是黑盒魔法，它给出的数和我们从曝光公式推出来的数只差 0.2 EV；
真正需要拍板的是「要不要为它改采集端的 shot planning」，以及「夜景的上限谁来定」。
