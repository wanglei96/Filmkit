## 1. 项目定位与目标

### 1.1 目标

| # | 目标 | 验收口径 |
|---|------|----------|
| G1 | RAW 路径：Camera2 `RAW_SENSOR` → 胶片风格成片（JPEG/HEIF），保留 DNG 原片 | 12MP RAW 全链路导出 ≤ 900ms（中端 SoC），高质量档 ≤ 2.5s |
| G2 | YUV 路径：`YUV_420_888` → 实时胶片预览与成片 | 1080p 预览（含胶片模拟 + 效果）≥ 30fps |
| G3 | 解析力：自研去马赛克 + 全链路半精度处理 | ISO12233 测试卡 MTF50 不低于系统相机直出，盲测优于 bilinear 基线 |
| G4 | 胶片模拟内核 + 3D LUT 可嵌套组合 | 嵌套后预览帧率不因 LUT 数量下降（链式 LUT 融合为单一 LUT） |
| G5 | 资产互通：LUT（.cube / Hald PNG）、预设（JSON/zip 包）、整体设置（JSON）导入导出 | 与 Resolve / PS / 手机调色 App 互通 |
| G6 | 全链路结构化日志 + 逐阶段性能计时 + 一键导出诊断包 | 每次成像可复现参数与耗时 |
| G7 | **专项机型适配：vivo X300** 作为 Tier-0 参考机型全链路达标 | RAW 采集/成片正确、200MP tile 导出成功、§3.3 性能表在 X300 实测达标（详见 §9.2） |

### 1.2 非目标（本期不做）

- 不做视频录制胶片化（仅照片；预览实时效果为视频化打基础）。
- ~~不做多帧堆栈~~ → 移入 **Backlog（M6 后评估，见 §0-D12）**。
- 不做 RAW 编辑器（去马赛克结果不回存为可编辑工程，DNG 原片即"底片"）。
- 不承诺逆向某真实胶片品牌配方（预设为风格化近似，命名中性化避免商标风险）。

### 1.3 平台与技术选型（假设与理由）

> 「raw / YUV」对应 Android Camera2 的 `RAW_SENSOR` 与 `YUV_420_888`，**首发平台为 Android**（评审确认：本期仅 Android，iOS 不在范围）。

| 层 | 选型 | 理由 |
|----|------|------|
| UI | Kotlin + Jetpack Compose | 现代声明式 UI，相机预览绑定成熟 |
| 采集 | Camera2 API（不用 CameraX 高层封装，保留对 per-frame 元数据的完全控制） | RAW 管线需要 dynamicBlackLevel、lensShadingMap、noiseProfile 等逐帧元数据 |
| 核心引擎 | **C++20（NDK）+ OpenGL ES 3.1 Compute Shader**，引擎层不依赖 Android 类型 | 性能主战场；GLES 3.1 覆盖率远高于 Vulkan Compute，兼容性优先，Vulkan 后置 |
| 中间格式 | 全链路 half-float（RGBA16F / R16F），仅最终输出量化到 8bit | 位深是解析力与层次的前提（见 §3.4） |
| 色彩工作空间 | 线性 Rec.709/sRGB 原色（可选 Rec.2020 域） | 与 .cube LUT 生态、显示输出兼容 |
| YUV 转换 | GPU shader 直采样平面（备选 libyuv CPU 路径） | 避免 CPU 中转开销 |
| 第三方 | glm、stb_image、libjpeg-turbo、libheif、moodycamel::ConcurrentQueue | 授权干净（BSD/Zlib/MIT）；**不引入 GPL 代码**（darktable/RawTherapee 仅参考论文与算法思路） |

## 2. 总体架构

### 2.1 分层

```
┌─────────────────────────────────────────────────────┐
│ UI 层 (Compose)：取景器 / 参数面板 / 资产管理 / 日志页  │
├─────────────────────────────────────────────────────┤
│ 应用服务层 (Kotlin)：采集会话 / 资产仓库 / 设置 / 日志  │
├─────────────────────────────────────────────────────┤
│ 引擎层 (C++20 + GLSL)  ←  本项目核心                  │
│  ┌──────────┐   ┌──────────────────────────────────┐│
│  │ RawSource │──▶│                                  ││
│  └──────────┘   │   共享后段 FilmRenderer           ││
│  ┌──────────┐   │  白平衡/曝光 → 胶片模拟内核        ││
│  │ YuvSource │──▶│  → 效果层 → LUT 链 → 输出变换     ││
│  └──────────┘   └──────────────────────────────────┘│
├─────────────────────────────────────────────────────┤
│ 平台适配：GL context / AHardwareBuffer / ImageReader  │
└─────────────────────────────────────────────────────┘
```

**关键架构决策：RAW 与 YUV 两条入口管线在「场景线性 RGB」处汇流，共用同一 FilmRenderer。** 两条路径的差异（去马赛克、降噪、位深、白平衡来源）全部收敛在前段 Source 内，后段胶片风格化代码零重复、观感一致。

### 2.2 关键决策记录

| 决策点 | 结论 | 备选与理由 |
|--------|------|-----------|
| GPU API | OpenGL ES 3.1 Compute | Vulkan Compute 更快但碎片化与开发成本高；后置 v2 |
| 去马赛克默认 | 预览用 GPU bilinear/AHD，成片默认 GPU PPG，高质量档 GPU RCD（评审确认：全 GPU，无 CPU 回退） | 见 §3.2/§3.4 |
| LUT 应用位置 | 引擎维护**域感知 LUT**：声明为 display 域的 LUT 插在输出 OETF 之后，scene-linear 域的插在胶片模拟之后 | 绝大多数 .cube 是显示域 LUT，直接放线性域会错色（行业常见坑） |
| 胶片模拟实现 | 参数化分析模型（曲线 + 染料矩阵），支持烘焙为 LUT | 纯 LUT 无法随 ISO/曝光自适应，且无法导出参数 |
| 预设格式 | JSON（schemaVersion 化）+ zip 预设包（内嵌 LUT 与预览图） | 纯 JSON 无法携带 LUT 资产 |
| 日志 | 自研轻量 JSONL 结构化日志（不引入 spdlog） | 需要与性能计时、参数指纹深度集成，自研更可控 |

## 3. RAW 管线重点设计

### 3.1 采集

- 能力探测：`REQUEST_AVAILABLE_CAPABILITIES` 含 `RAW`；无 RAW 设备自动降级 YUV 并在 UI 标注。
- 逐帧元数据（`CaptureResult`）全程随帧流转：`sensor.blackLevelPattern`、`sensor.dynamicBlackLevel`（逐帧）、`sensor.neutralColorPoint`、`sensor.colorTransform1/2`、`sensor.forwardMatrix1/2`、`sensor.calibrationTransform1/2`、`statistics.lensShadingMap`、`sensor.noiseProfile`。
- 原片保存：M2 用系统 `DngCreator` 快速落地；M4 自研 DNG Writer（写入完整色彩矩阵与噪声档案，支持曝光偏置），保证"底片"可被第三方 Raw 冲图软件正确打开。

### 3.2 处理链（质量主线，阶段顺序即依赖顺序）

| # | 阶段 | 内容 | 执行域 |
|---|------|------|--------|
| 0 | 解包 Unpack | 10/12/14bit 传感器流 → 16bit（SIMD/位移），Sensor 16bit 直读 | CPU SIMD → GPU 上传 |
| 1 | 黑阶扣除 | `blackLevelPattern` 分通道 + 逐帧 `dynamicBlackLevel` | GPU（合并进阶段2） |
| 2 | 白平衡 | 线性域分通道增益（as-shot `neutralColorPoint` 或用户色温 CCT 推导） | GPU（合并进阶段1 pass） |
| 3 | 镜头阴影校正 | `lensShadingMap` 网格纹理双线性采样 | GPU（同一 pass） |
| 4 | 高光重建 | G 通道饱和区用 R/B 线性外推恢复色彩，强度可调 | GPU |
| 5 | 去马赛克 Demosaic | 三档：bilinear+中值抗伪彩（预览）/ PPG+AHD 混合（标准）/ RCD 单趟三段管线（高质量，v0.5.28 调研更正：参考实现无迭代） | GPU（全 GPU） |
| 6 | 降噪 | 按 `noiseProfile` 自适应启用；demosaic 后 RGB 域引导滤波 + NLM-lite；ISO 与快门联合调参 | GPU |
| 7 | 色彩空间转换 | camera native → XYZ(D50) → Bradford 适应 D65 → 线性 sRGB 工作域（DNG 标准矩阵链）；clip 到工作域原色 | GPU（3×3 矩阵合并） |
| 8 | 曝光/基础影调 | 线性域曝光补偿、黑点抬升 | GPU（合并进阶段7 pass） |
| — | **汇流点：场景线性 RGB** | 以下与 YUV 路径完全共享 | — |
| 9 | 胶片模拟内核 | 见 §5 | GPU |
| 10 | 效果层 | grain / halation / bloom / 暗角 | GPU |
| 11 | LUT 链 | 见 §6 | GPU |
| 12 | 输出变换 | 线性 → sRGB/P3 OETF（胶片曲线已含 tone 时可跳过 filmic 映射）+ 蓝噪声 dither 量化 8bit | GPU |
| 13 | 编码 | JPEG（libjpeg-turbo）/ HEIF / PNG；可选 16bit TIFF（M6） | CPU |

### 3.3 高性能设计（成像速度）

1. **全 GPU 半精度管线**：所有中间结果 RGBA16F 纹理；仅输出量化 8bit。避免任何 CPU 中转往返。
2. **Pass 合并**：阶段 1–3 合并为一个 pass；7–8 合并；10–12 中无依赖的效果尽量合并。目标：12MP 全链路 **≤ 8 个 pass**。
3. **异步流水线**：
   - 预览链：低分辨率（≤1080p）+ 低档去马赛克，30fps；
   - 成片链：全分辨率 + 高质量档，后台队列执行，GL 纹理池复用（杜绝每帧分配）；
   - 参数变更防抖 300ms 后增量刷新成片。
4. **零拷贝/快上传**：YUV 走 SurfaceTexture/AHardwareBuffer 零拷贝；RAW 走 ImageReader + PBO 环形上传。
5. **LUT 融合**（嵌套不降速的关键）：LUT 链在参数提交后由 CPU 用四面体插值链式采样，**烘焙为单个 65³ 3D 纹理**，运行时只做一次 3D 采样；参数再变更则后台重烘焙。GPU 成本与 LUT 数量无关（G4 验收项）。
6. **grain 旁路**：颗粒使用预生成平铺噪声图集（蓝噪声 + 高斯金字塔）+ 随机偏移采样，不逐帧全屏生成噪声。
7. **计时闭环**：`EXT_disjoint_timer_query` 逐 pass 计时 + CPU 段计时，全部进日志（§8），性能回归有据可查。
8. **tile 化导出**：≥ 24MP 时按 tile（如 2048²，带重叠区）处理，控制内存峰值；tile 边界使用扩边保证去马赛克/模糊类效果无缝。

**性能指标（中端机，如 Snapdragon 7s / Dimensity 8200 级）：**

> 出口标准：下表指标以 **vivo X300（天玑 9500，Tier-0 参考机型）** 实测确认为准，中端机数值作为底线。

| 指标 | 目标 | 底线 |
|------|------|------|
| 12MP RAW 标准档全链路 | ≤ 900ms | ≤ 1.5s |
| 12MP RAW 高质量档（RCD） | ≤ 2.5s | ≤ 4s |
| 1080p 预览帧率 | ≥ 30fps | ≥ 24fps |
| 内存峰值（12MP） | ≤ 400MB | ≤ 600MB；tile 后 ≤ 250MB |
| LUT 链加入（≤5 个）后帧率损失 | 0 | ≤ 5% |

### 3.4 高质量设计（解析力与层次）

1. **位深策略**：从传感器位深（≥10bit）到最终 dither 前全程 ≥ half-float，禁止中途 8bit 量化——banding 与解析力损失的主要来源。
2. **去马赛克分级**：
   - 预览档：bilinear + 3×3 中值抗伪彩（GPU，1 pass）；
   - 标准档：PPG（梯度修正）+ AHD 方向插值混合（GPU）；
   - 高质量档：**RCD（Ratio Corrected Demosaic）** 单趟三段管线 + 伪彩抑制——RCD 在高频区边缘恢复显著优于 bilinear/AHD，是"解析力"验收的核心（v0.5.28 调研更正：出处为 Luis Sanz Rodriguez 开源算法而非"Karacan 论文"，参考实现无迭代）。评审确认**全 GPU 实现**：重点控制 shader 分支发散（比值共用采样、方向场一次算全图复用），已按此落地 v0.5.28；M3 调优按 `raw.render` 分段计时数据收敛。
3. **高光重建**：饱和通道用未饱和通道外推（比值法），避免胶片曲线前就丢高光色彩。
4. **色彩流水线符合 DNG 标准**：calibrationTransform → colorTransform（插值 CCT）→ forwardMatrix 路径，保证与 Adobe 冲图观感可比。
5. **四面体插值**：3D LUT 全部使用 tetrahedral 采样（三线性在 33³ 下有明显色差）。
6. **输出 dither**：蓝噪声抖动量化，消除 8bit 输出 banding。
7. **效果域正确**：grain/halation 在显示域叠加（贴近扫描负片观感），胶片曲线在 log/density 域计算（见 §5），不出现"先 gamma 后饱和"式的双重饱和。
8. **量化评价体系**：
   - ColorChecker 24 色：标定模式下平均 ΔE2000 ≤ 3（胶片模式不做此约束）；
   - 20 级灰阶梯：无可见 banding（梯度方差阈值）；
   - ISO12233 卡：MTF50 相对基线不劣化；
   - golden image 回归：固定输入 + 固定参数，SSIM ≥ 0.999。

## 4. YUV 管线设计

- 输入：`YUV_420_888`（shader 直采样 Y 平面 + 交叠/平面 UV），自动识别 BT.601/709 与 limited/full range（取自采集色彩空间元数据），备选 libyuv CPU 路径兜底。
- 线性化：反 OETF 到近似线性域（8bit 源，动态范围有限）→ **汇流进共享 FilmRenderer**。
- 差异补偿：无 demosaic/降噪需求；白平衡信任相机 AWB 结果；因动态范围窄，胶片曲线前加 soft-roll-off 保护高光，负片 toe 适当减弱。
- 定位：预览、连拍、不支持 RAW 的设备成片；后续 P010（10bit HDR YUV）作为 v2 扩展。
- 交付顺序：**YUV 路径先行（M1）**，用低成本路径先把共享后段（胶片内核、LUT、资产系统）跑通，RAW 再接入同一后段。

## 5. 胶片模拟内核（共享核心）

参数化分析模型，全部参数可入预设：

| 组件 | 数学模型 | 说明 |
|------|----------|------|
| 特性曲线 | per-channel density 域 S 曲线：D = f(logE)，slope / toe / shoulder 三参数平滑函数 | 负片：toe 柔和 + 肩部缓压；正片：高反差陡曲线 |
| 染料串扰 | log 域 3×3 矩阵（负片色罩修正） | 负片橙罩/层间串扰的来源，决定"胶片味" |
| 分区色彩 | 阴影/中间调/高光三段独立饱和度与色相偏移 | 按亮度加权 |
| 颗粒 grain | 预生成高斯噪声图集；强度按亮度中间调加权；尺寸 0.5–2px 随 ISO 参数缩放；亮度颗粒 / RGB 颗粒两种模式 | 显示域叠加 |
| 光晕 halation | 红通道高光阈值 → 多级可分离高斯模糊 → 加性复合 | 胶片基底透光特征 |
| 柔光 bloom | 全通道小半径高光柔化 | 正片/夜景风格 |
| 暗角 vignette | 径向乘性衰减 + 可选边缘色偏 | |

- 域选择：曲线与串扰在 log/density 域；颗粒/halation/暗角在显示域。中间转换由内核内部管理。
- **烘焙导出**：整套胶片模型（曲线+矩阵+分区色彩，不含 grain/halation 等空间效果）可烘焙为 .cube LUT 导出，供第三方软件使用（亮点功能，复用 §6 烘焙器）。

## 6. LUT 引擎：嵌套与导入导出

### 6.1 嵌套模型

- LUT 链：`L1 → L2 → … → Ln`，每级节点 = `{LUT 资产, 强度 opacity, 混合模式(normal/linear-light/soft-light), 域标签(scene-linear|display), clip 开关}`。
- **域感知插桩**：display 域 LUT 自动插到输出 OETF 之后，scene-linear 域插在胶片模拟之后——用户导入任意来源 LUT 都不会错域。
- **胶片模拟 × LUT 三种嵌套顺序**（可切换）：`胶片 → LUT`（默认）、`LUT → 胶片`、`胶片烘焙 + LUT 融合为单 LUT`。
- 执行优化：链式融合为单一 65³ LUT（§3.3-5）；节点数 > 5 或 65³ 精度不足时退化为 GPU 链式两级采样（仍单 pass）。

### 6.2 导入 / 导出

| 格式 | 导入 | 导出 | 备注 |
|------|------|------|------|
| .cube（Iridas/Resolve） | ✅ 1D/3D，解析 TITLE/LUT_3D_SIZE/DOMAIN_MIN/MAX | ✅ 3D | 主格式 |
| Hald CLUT PNG | ✅ Level 8/12 自动识别 | ✅ | 与 PS / 手机调色 App 互通 |
| .3dl | ✅（可选，M6） | ❌ | 兼容老工作流 |

- 解析器要求：容错（大小写/空白/CRLF）、尺寸上限 128³、非法文件白名单校验、导入即生成缩略图预览（标准色卡图）。
- 导出选项：源域标签自动写入 .cube 注释（域感知依据）。

## 7. 预设系统与整体设置

### 7.1 预设（Preset）

- 内容 = 胶片模拟全参数 + 效果参数 + LUT 链引用 + 基础影调（曝光/白平衡偏移）。**不含**设备相关项（降噪 ISO 阈值等由引擎自适应）。
- 单文件预设：JSON，带 `schemaVersion`、参数范围声明（版本迁移函数链升级）。
- 预设包（推荐交换格式）：zip = `manifest.json + lut/*.cube + preview.jpg`，扩展名 `.filmkit`（自定义）。
- 内置预设（M4 交付约 10 个，命名中性）：人像负片 400 / 风光反转 50 / 街拍黑白 400 / 高感报道 800T 风格 / 柔焦清新 100 等。
- 导入：单文件 / 批量 / 冲突策略（重命名/覆盖）；导出：单个或打包合集。

### 7.2 整体设置（Settings Backup）

- 范围：相机默认参数、质量档、UI 偏好、预设库索引与哈希、LUT 库索引、日志策略。
- 格式：JSON + `schemaVersion`，导入时逐级迁移；敏感项（路径等）不导出。
- 与预设包共用 zip 打包器；支持"仅设置不含资产"的轻量模式。

## 8. 日志系统与诊断导出

- **分层模块**：`app`（UI 事件）、`engine`（管线事件/错误）、`perf`（逐 pass 耗时）、`io`（文件/导入导出）、`camera`（采集元数据摘要）。

## 色彩引擎调研结论（2026-09-21 轮，问题："直拍 RAW 没有色彩"）

**量化诊断**（同场景：我们 165345 vs libraw 完整 DNG 链，均 ISO 176 同机位）：

| 指标 | 我们 v0.5.39 | libraw 完整链路 | 判定 |
|---|---|---|---|
| 近中性像素 R/G | 0.9870 | 0.9861 | 白平衡/矩阵**一致（准）** |
| 近中性像素 B/G | 0.9918 | 0.9893 | 一致（准） |
| 饱和度 S 均值 | 0.1269 | 0.1612 | **-21%** |
| 通道分离度 | 5.12 | 7.21 | **-29%** |
| 近中性像素占比 | 24.3% | 13.8% | **+10pp（颜色抱团）** |

> **2026-09-21 复核订正**：本节的量化参照用了 rawpy 默认 `auto_bright=on`（亮度被自动拉高约 2.5×），"饱和 −21% / 分离 −29%"里混入了亮度差；在各自原生输出下用 C* 比较，我们的感知色度并不低于 libraw 标准链（详见 v0.5.44 节的复核）。下列"根因"结论**仅作历史记录**。

→ **根因不是矩阵错，而是缺"色彩外观层"**：颜色挤在中性附近、饱和度不足。代码侧对应：`kFsFilm` 的 `uSat`（阴影/中/高光饱和度）默认全 1.0、`uCross` 单位阵、无任何 hue/sat twist 或 LUT —— **整链没有外观层**。

**现状 vs 规划 gap**：

| 规划项 | 状态 |
|---|---|
| §3.2-3 镜头阴影校正 | ✅ v0.5.43-m3（HAL 增益网格 17×13 手写双线性，CCM 前；均匀白柜面角落/中心 0.61–0.67 → 0.90–0.99）|
| §3.2-7 + §3.4-4 DNG 标准矩阵链 | ✅ v0.5.46-m3（`StdColorMatrix`：ColorMatrix/ForwardMatrix 双光源插值 + Bradford D50→sRGB，A/B 开关 `ccm_std`）。**订正**：v0.5.45 曾据"DNG 文件里没有 ForwardMatrix"推断引擎拿不到 —— 实为 **DngCreator 不写**；`CameraCharacteristics` 侧 ForwardMatrix1/2 齐全 |
| §3.2-8 曝光/基础影调 | ✅ v0.5.36–41（黑位 + S + rolloff + 中间调提亮）|
| §3.2-9 / §5 胶片内核完整模型 | ⚠️ M1 简化模型，风格参数全中性 |
| §6 LUT 引擎 | ❌ M4 |
| §3.4-8 ColorChecker ΔE2000 ≤3 量化评价 | ❌ 未建立 |

**DCP 调研（一手核验）**：
- **ColorMatrix1/2 不参与颜色校正**（dcamprof 明示），只用于反推光源 CCT；决定成色的是 **ForwardMatrix + HueSatMap/LookTable**，作用在**已白平衡**的线性数据上。（**2026-09-21 实测**：X300 的 `CameraCharacteristics` 提供 ForwardMatrix1/2；只是 DngCreator 未写进 DNG 文件。）Adobe DNG SDK 顺序（`dng_render.cpp`）：线性化→Camera↔XYZ→AWB→ForwardMatrix→HueSatMap→BaselineExposure→LookTable→ToneCurve。
- **DCP 硬限制**：其 LUT **不能改灰度、不能提升饱和度、不能改 lightness** → **单靠 DCP 做不出"浓郁"**。
- 自建 DCP 可行且合法（dcamprof 仅离线生成，GPL 不传染其输出）；**厂商 DCP 不可随包分发（红线）**；Adobe DNG SDK 许可宽松（可再分发，商业需 indemnify）。
- HueSatMap 本质是 3D LUT（默认 90×30 或 2.5D 90×30），ES 3.0 用 `GL_TEXTURE_3D` + LINEAR 一次采样，约 1.5MB 显存、每帧开销可忽略；**移动端 GPU 实现 DCP 未见公开先例**（事实空缺）。Adobe 参考实现插值是**双线性**，不是四面体。

**开源做法要点**：RawTherapee/libraw 默认＝"矩阵 + 标定 gamma"（天生寡淡），要厂商感必须开 Auto-Matched DCP；darktable 顺序＝input profile（增强矩阵/ICC）→ exposure → **color calibration（CAT16 感知白平衡，放在 CCM 之后）** → AgX/filmic → 输出，并推荐 **demosaic 只做粗白平衡、感知白平衡后移**；现代 display transform（AgX/OpenDRT）的核心是**在曲线前做 primaries 变换**，使高光自然去饱和、避免 per-channel tonemap 的色相扭曲（OpenDRT 把 chroma compression 列为必需环节）。移动端参照：PhotonCamera 用 `ColorCorrectionTransform`（双光源矩阵或 cube 按白点插值＝自建 DCP 简化版）+ ACR3 多项式 tone + Equalization 局部色调。

**建议优先级（2026-09-21 用户拍板更新：外观层归 M4）**：

| 版本 | commit | 改动与结论 |

**方向与画幅链路的教训**（两次都栽在同一类问题上）：

1. **"竖拍正确"会掩盖一切**：旋转语义错 180°、画幅方向源取错，在竖拍下都表现正常。判据必须**四姿态全验**（已固化为单测）。
2. **不要用 Activity 的 configuration 判断设备姿态**：`LocalConfiguration.orientation` 反映的是**窗口**方向，而系统"自动旋转"关闭时窗口方向与设备姿态**解耦**。相机类 App 必须自己听设备物理方向（PC 用 `OrientationObserver`，我们用 `OrientationEventListener`）。
3. **先看日志再动手**：本次两个独立缺陷（旋转语义 / 画幅方向源）此前被混成一个"方向不对"，`photo.crop` 一行日志即分清 —— 该日志本就在代码里（`CameraController` 1611–1620），早该先取。**JPG 与 DNG 是两条独立的方向链路**（前者旋转像素 + EXIF 恒 1，后者存传感器像素 + EXIF 表达方向），改一处必须同时检查另一处。

#### 七、影调曲线换底与"太亮"排查（v0.6.50 → v0.7.2-m4）

**背景**：用户复核 v0.7.1 报"默认太亮，只能靠拍片压 EV，太简单粗暴、不是通解"。先按**零代码验证**
（设置页关掉"自适应影调"）做 A/B，结果**与假设相反** —— 关掉反而更亮，据此把账算清。

| 版本 | 改动与结论 |
|---|---|
| v0.6.50-m4 | **高光发红修复**：v0.6.49 的色度保护只用 `rel` 一刀切，把台灯灯管也保护了（R/B 饱和、G 未饱和 ⇒ rel 高）→ 灯管保持粉紫，**重现 v0.5.37"过曝灯泡变红"**。DNG 重建把两者分开：灯管 luma **1.04** / RGB (1.49,0.83,1.84)，红杯 < 0.4 → 保护加 **luma 门限** |
| v0.7.0-m4 | **换底**：`baseTone` 由"`blk 0.008` 黑点 + 以 mn=0.2184 为不动点的 S 曲线"换成**哈苏形状的 Reinhard 曲线** `y=(1+k)x/(1+kx)`（k=5）。旧曲线暗部比哈苏（HNCS）低 **565×**（x=0.01：哈苏 0.0455 / 我们 0.0001；x=0.05 → 23×；x=0.10 → 9.2×），是"暗部死黑 / 室内糊了一层 / 白物无层次 / 红杯被推白"的**总根源**。**不复制其数据资产**（`filmcurve_type6_companding2.hcurve` 来自哈苏专有 SDK），改用标准数学形式自研；结构仍是"按 max 通道等比缩放"（哈苏是逐通道查表，但它有 YCbCr 色度映射补偿，我们没有） |
| v0.7.1-m4 | **压暗恢复对比度**：`kTarget 0.07 → 0.04`（显示中位 150→123） |
| v0.7.2-m4 | **"太亮"排查止血**（本节重点，见下） |

**A/B 实测**（2026-09-24 15:04:51 vs 15:05:36，同场景，ISO 3666→3236，均 1/60s，全图分位）：

| | ag | 平均 | P1 | P50 | 死黑占比 |
|---|---|---|---|---|---|
| 自适应**开** | **0.448** | 122.8 | 53.3 | 130.7 | 0.0% |
| 自适应**关** | **1.274** | 165.5 | 82.5 | 179.6 | 0.0% |
| PC 哈苏（同场景参照） | — | 66.9 | **1.0** | 68.8 | **17.1%** |

1. **自适应是唯一在压暗的机制**（ag 0.448 = 压到 45%），"太亮"的锅不在它 —— 它只是**压得不够**；
2. **真问题是"画面里没有黑"**：我们最暗的 1% 还有 53–82/255，PC 有 17% 像素接近全黑。账能算平 —— 桌面
   RAW 0.028 × 0.448 = 0.0125 → Reinhard 提亮 **5.6×** → 0.0706 → gamma 2.2 → 显示 **78**（与实测 P1 吻合）；
3. **关掉自适应时的固定基线 `exp2(0.35)=1.274` 是旧 S 曲线时代的遗留**：那条曲线压暗部，所以要 +0.35EV
   抬回来；换 Reinhard（暗部自带 4–6× 提亮）后它变成**重复提亮** → 实测"关掉比开着更亮"正是它干的。

**改动（v0.7.2）**：
- `kTarget 0.04 → 0.02`（目标显示中位 131 → 93）：0.04 会被 Reinhard 放大 5×（`baseTone(0.04)=0.1996` → 显示 122），
  目标值必须按**目标显示中位**反推；
- `kMinGain 0.35 → 0.20`：实测场景 lin_mid 0.0891 要落到 0.02 需要 ag **0.224**，**被 0.35 卡住就等于 kTarget 白改**；
- 关掉自适应时的固定基线 `1.274 → 0.5`（`exp2(-1.0)`）：止血值，真正的锚点应随曲线重构改成 EV 形式；
- `measureLinMid()` 从 `updateAutoGain` 抽出并**在自适应开关两边都调用** —— 原先关掉后日志 `linMid` 恒为 0，诊断有盲区；
- 设置页文案同步（原文"归一到中间调不动点、限幅 1–4×、只提亮不压暗"与 v0.7.0 后的实现不符）。

**已知未尽**：换曲线**不解决"没有黑"** —— Reinhard / sigmoid / Hable 这类**无黑点**曲线同理（哈苏自身也是提亮型：
0.01→0.0455 = 4.55×）。解法是**带黑白相对曝光**的曲线（darktable filmic rgb：black −7.65EV / white +4.56EV，
把黑点做成 **toe 端点**而非硬截断 —— 旧实现的 `blk=0.008` 就是硬截断，代价是暗部信息丢失）；
PC 仓库有 Apache-2.0 的现成 GLSL 转写（`DarktableFilmicToneAlgorithm.kt` 397 行 / `DarktableSigmoidToneAlgorithm.kt` 140 行）。
根因仍在**曝光**（HAL 的 AE 比 PC 高约 3EV），见待办"曝光方案 A/B/C"。

#### 八、filmic 基准影调上引擎（v0.7.3-m4）

**背景**：v0.7.2 止血后复核"有更暗一些，但还是傻亮"。量化定位到**画面里没有黑**：同场景死黑占比
我们 **0.3%** vs PhotonCamera **16.8%**（P1 39.3 vs 1.0）。Reinhard 无黑点 —— **"压暗"与"变黑"是两件事**
（曝光/增益是整体乘除，改不了"暗部相对中位的位置"）。

**决策：换 darktable filmic rgb（v3 spline），自适应对象从"亮度"改为"动态范围"**：
- 旧的 `kTarget` 中位锚定把"曝光"这一维抹掉了（压 EV / 降 AE 都会被 gain 补偿回来，这正是
  "只能靠拍片压 EV 却压不动"的机制）；filmic 的参数是 **EV（相对中灰 18.45%）**，与机型无关，
  自适应的是**场景动态范围**而非绝对亮度 ⇒ 暗的地方才真的暗。
- **不复制数据资产**：按 darktable 公式自研 C++（GPL 代码不逐行翻译）。

**上引擎前的核对（PC vs darktable 原版 commit 92f6c28）**：

| 环节 | 结论 |
|---|---|
| spline 系数求解 5×5（f(0)/f'(0)/f(T)/f'(T)/f''(T)） | **逐字一致** |
| log 编码、Yrg/Ych 色彩链、grey/black 常数 | 一致 |
| PC 的改动 | 固化 `output_power`（其实是派生量 `log(grey)/log(-black/DR)`）、删 v1/v2 与 balance、contrast 写成显式 DR 缩放；**不用 auto-tune，写死 −7.65/+4.56** |
| 关键空白 | darktable 的 auto-tune 是**交互式**（取色器点白/黑点），手机端没有 ⇒ 只能自己用直方图分位补 |

**离线验证（10 个 DNG，8bit 显示域，完整链）**：

| 方案 | P50 | 死黑 |
|---|---|---|
| 现链 v0.7.2 | 85–100（被归一拉平） | 0.0–0.4% |
| filmic + 自动 EV | **37–64（跟随场景）** | **4.6–17.7%** |
| PC 参照 | 67.5 | 16.8% |

- blackEV 自动算出 −5.1 ~ −6.5（稳，与 darktable 默认 −7.65 同量级）
- **whiteEV 必须加下限保护**：窄动态范围场景（画面无高光）会被拉满 → 死黑 30%+；
  `clamp[3,6]` 后 11.7%/8.1%，死黑波动极差 24.6 → **13.0**

**实现（`FrameRenderer.{h,cpp}`）**：
- CPU：`computeFilmicSpline()`（**全程 double** —— shoulder 的 5×5 系统条件数差，float 中间量会把
  1e-7 舍入放大到 1e-5）+ `solve5()` 列主元高斯消元
- 统计：`measureSceneStats()` 一次直方图出 P0.5/P50/P99.5，**取 max 通道**（filmic 按 max RGB 归一，
  用 luma 会系统性偏低）→ `kFsHist` 加 `uStatCh`（0 = luma 供 UI 直方图，1 = max）
- 标定：`updateFilmicEV()`；开关语义改为"是否按场景分位自动标定黑白点"；静拍直通不 EMA
- 删除：`updateAutoGain` / `baseTone` / `uExposureGain` 整套中位锚定（含 `kTarget` / `kMinGain`）
- **顺序（踩坑换来的硬约束）**：
  `out3 → n0 → filmic → 高光去饱和(rel + luma 门限) → pass3 rolloff → OETF → LUT`
  —— filmic 只压亮度、**保色相**，缺去饱和时高光 R/G **1.277**（品红，即 v0.5.37 老问题），补上后 **1.000**

**自检（可执行）**：`tools/tuning/filmic_verify.py` 读真机日志 `raw.render` 的 `blackEv/whiteEv + fM1..fM5`，
用 `filmic_offline.py` 的同一组公式复算系数逐项对拍（判据 1e-4；实测差异 ~4e-6 = float32 存储精度）。
出包前另做抽取编译对拍：默认参数下 `power 3.614816 / contrast 1.433801` 与 PhotonCamera 固化的
`3.614815775 / 1.433801098` **逐位吻合**。

**本轮两个坑（已进 lessons）**：
1. **离线链必须与引擎同口径**：我出图时漏了 pass3 的 rolloff 与 kFsFilm 的去饱和 → 高光发红，被用户一眼看出。
2. **`rolloff` 漏 `if (l <= knee) return c;` 短路**（`test_temp/chain_probe.py` 同样中招）：漏掉等于给全图乘
   `knee/l`，暗部被顶亮到 0.8，产出"高光像素 4.8%→63.8%"这种**与机制自相矛盾**的假数据 —— 这类数字必须当场停下核查。

#### 九、本轮沉淀的通用教训

1. **判据类改动先问「这个功能的意图是什么」**；手段（判据形式）与推导（目标值怎么来的）必须**分开判断**。
2. **参考实现的显示域数值不可直接当作目标** —— 域的归属（提亮前/后）必须先确认；基准必须是**同机位同场景**的成片。
3. **跨亮度比 C\* 会得出假结论**（C\* 随 L\* 增长）；跨链比较只用亮度无关的 `rel`。
4. **提亮是噪声的乘性放大器**：`ag 2.0 × lt 1.6 ≈ 3.2×` —— "暗部更亮"与"彩噪更低"物理对立。
5. **判据用 max 通道还是 luma 决定了谁被命中**：蓝色天空 luma 只有 198/255 却因 B 通道高而进高光区。
6. **改 shader 必跑 `tools/validate-shaders.sh` 且必须真机验证**（构建/单测/静态校验全绿仍可能设备端全黑）。

#### 十三、「基准曝光」设置项（v0.8.1-m4，2026-09-27）

**背景**：v0.8.0 域映射上线后预览/成片一致（用户确认），但用户质疑"每次手动拉 EV 算不算通解"——
不是。HAL 的 AE 基准比参照策略暗 0.5–0.9 EV（室外晴天 0.67 / 室内逆光 ~0.9，跨场景浮动），
影调引擎只做映射、不产生曝光，这个差只能在校准层补；X300 的 HAL AE 补偿已被实测证伪（+0.7 只执行 0.1）。

**改动**：设置页新增「基准曝光」滑杆（**−2..+2 EV，步进由 EvSliderRow 连续**，默认 0），与
Lightroom/DNG 的 **BaselineExposure** 同语义——机型校准常量，用户按同场景参照对齐一次即可，
EV 滑杆归零。实现：`FilmParams[0] = base_ev + 用户 EV`（`applyBaseEvPref` + `setEv`/`setFilmParams`

#### 十四、域比持久化与局部色调映射 A/B 定案（v0.8.2-m4，2026-09-27）

**基准曝光真机验收通过**：用户标定 `base_ev = +0.50`（`settings.base_ev v:0.498`），EV 归 0 时
`raw.render ev:0.498` 生效，成片亮度对齐参照。"每次拉 EV"问题闭环。

**域映射 ratio 冷启动缺陷（日志发现并修复）**：`nativeEngineStart` 每次 `new FrameRenderer`，
`domain_ratio_/pv_mid_ema_` 是成员变量 → engine stop/start（离开相机页、切后台）后归零，
真机日志实测 ratio 长期钉在初值 2.0、仅一次在同会话静拍后收敛到 2.19。修复：两值提为
**进程级 static**（`.cpp` 匿名命名空间 `g_pv_mid_ema/g_domain_ratio`），跨 engine 会话存活；
App 冷启动回落 2.0、拍一张静拍即重新收敛（EMA α=0.3）。彻底持久化（prefs+JNI 回传）收益
边际小，不做。

**局部色调映射 A/B 定案（同场景同曝光，ISO 50，lt 0.25 vs 0）**：

| 指标 | lt=0.25（开） | lt=0（关） | 结论 |
|---|---|---|---|
| 亮度 P5/P25/P50/P75/P95 | 14.5/48.2/85.5/121.4/253 | 11.1/42.6/78.9/119.5/253 | **暗部+中间调提亮、高光零影响**（P5 相对 +31%，P95 ±0，设计意图精确达成） |
| 平坦块噪声 σ(luma) | 0.68 | 0.71 | **无噪声代价**（旧链"室内噪声爆炸"是 0.6 强度+旧曲线时代的问题） |
| 彩噪 σ | 0.38 | 0.47 | 不升反平 |
| C* 中位(彩色) | 11.48 | 10.94 | 提亮使彩色像素自然 +5%，a\*/b\* 中性偏移 ≈0（无偏色） |

**结论：保留，filmic 链下功能健康**——0.25 强度 + filmic 的组合下"提亮是噪声乘性放大器"的
旧顾虑不成立。用户可在设置页自选开/关。


#### 十五、MFNR 阶段一立项落地（v0.9.0-m4，2026-09-27）

**立项**（上轮拍板，优先于 AgX）：多帧融合降噪 P0——彩噪跨帧独立、信号跨帧相关，时域均值
√N 提 SNR，是空间降噪给不了的低频彩噪根治手段；落地后可下调 P4 色度平滑、恢复色度边缘。

**调研定案**（`docs/research/07-取证清单-HDR+夜景多帧.md` 逐字取证）：
- **HDR+**（Hasinoff 2016 §4）：对齐 = 2×2 Bayer 块平均→灰度，四层金字塔 coarse-to-fine，
  tile 32×32，恒定曝光 burst 使对齐鲁棒；**Night Sight**（Liba 2019 §3.1）：tile 16/32/64
  随噪声增大、参考帧最锐、方差 σ²/N。开源参照：IPOL HDR+ 分析、timothybrooks/hdr-plus、
  PhotonCamera（GPU 对齐，**算法可学代码不可抄**——沿用 RCD 先例）。
- 结论：**tile 级金字塔对齐是业界共识**（手持下全局单一位移不成立，HDR+ Fig.5 明示
  hierarchical 是必须）——阶段一直接上 tile 对齐（用户拍板），P2 剩 mismatch/运动检测。

**实现**（N=4，prefs `mfnr` 三档 **0 关 / 1 自动暗光（ISO≥600 或曝光≥25ms）/ 2 强制**）：
- 采集：`captureBurst` 4×同参 request（恒曝光）；ImageReader maxImages 2→**5**、burst 期间
  `acquireNextImage`（`acquireLatestImage` 的丢旧帧语义会吃掉 4 帧中的 3 帧）；Image/Result
  双桶按回调序配对（同 looper 串行），5s 超时兜底；DNG 仍写帧 0。
- 对齐（`Align.cpp`，纯 CPU）：GPU 金字塔（2×2 Bayer 块平均→1/2 灰度 + sqrt 预编码→box
  下采样至 1/4、1/8、1/16）→ readback ~0.5MB/帧 → L4 全局粗搜 ±16 → L3/L2 每 tile ±2
  精化 + 亚像素 → **位移场以 mosaic 域表示，融合采样 round 到最近偶数**（1/2 域整数位移
  ×2 恒为偶数，Bayer 相位不翻转）；置信度 = 对齐残差/ref tile 梯度，弱纹理回退参考帧。
- 融合：`kFsMfnrFuse` 4 帧 RAW + 3 位移场纹理（RGBA16F，手写双线性——X300 无 16F 线性
  过滤）→ 置信度加权均值 → `tex_fused_`（R16F 线性 mosaic）；P0 换 **fused 变体**
  （`kFsRawDenoiseFused`，完整独立 shader——字符串拼接会逃过 validate-shaders）→ 之后
  RCD/P4/filmic 链零改动。元数据统一取帧 0（burst 恒曝光，逐帧黑阶/WB 视为一致）。
- 复用：`submitRaw` 抽出 `ensureRawTex/uploadRawTex/prepareRawCommon/denoiseParams/
  finishStillChain`（成片链 + 日志共享），两条静拍路径零重复。
- UI：设置页「多帧融合」三档行（RAW 降噪后）；拍摄时取景框内「多帧合成中…」提示
  （`capturePhase` Compose state）。
- 日志：`mfnr.trigger`（档位/判据）、`mfnr.capture`（**逐帧实际曝光**——HAL 是否逐帧重 AE
  用它核对）、对齐统计并入 `raw.render`（alignMs/fuseMs/gx/gy/confMed/fbTiles）。

**新增 JNI**：`nativeEngineSubmitRawBurst(frames[], count, strides[], meta…)`——4 张 Image
的 plane buffer **零拷贝**直传，拍完 DNG 后统一 close（HAL 槽位 5 满足 4+headroom）。

**质量闸**：validate-shaders 19/19 全绿（新增 4 条）；单测 26/26（新增 `MfnrTriggerTest`
三档判定 4 断言）；CMakeLists 显式加 `Align.cpp`；出包前清 APK 输出目录。

**待真机验收**（v0.9.0-m4）：① 冒烟——`mfnr.capture` 4 帧到齐、逐帧曝光一致、≤2s、无锁
快门；② 对齐——位移合理、fbTiles 占比低；③ 暗光 A/B（自动/关各 3+ 张）——暗部噪声/彩噪
显著下降（目标 √4≈2×）、色度边缘优于现 P4、无鬼影；④ 回归——关档画质时延与 v0.8.2 无差、
白天自动档不触发。P0/P4 参数是否随 MFNR 下调：验收数据出来后单独决策。

**真机验收与三轮迭代（v0.9.1–v0.9.5，2026-09-27）**：v0.9.0 首装闪退——进程存活但 Activity 被

**8–21px**，2px 偶数量化残差 ±1px 被 4 帧均值磨掉——v0.9.4 改 1px 取整+phaseFix 仍不足，

**补充：纯融合降噪量的严格测量（v0.9.5，2026-09-27 晚）**——「MFNR 开+降噪关」×3 vs 「MFNR
关+降噪关」×3（同场景同曝光 ISO 1370/1338，raw.render 均无 dn 字段，完美隔离融合贡献）。首测
（JPG 域自适应梯度 mask）得比值 0.81，疑似 FPN；复测发现该口径有**幸存者偏差**：裸帧噪声大、
平坦块被梯度阈值大量排除（400/77K），σ 被低估。改**低频判据选块**（32×32 box 低频图的梯度
判据与噪声水平解耦，两组块数 2600-2930 相当）：纯融合 σ 2.88-2.90 vs 裸帧 σ 6.38-6.42，
**比值 0.442-0.451 ≈ √4 理论 0.500**——融合降噪量达到理论最优，FPN 假设否定（帧间噪声基本
独立）。**教训入库：噪声测量必须用与噪声水平无关的选块判据；自适应 mask 跨噪声水平比较无效。**
DNG（参考帧底片）不含融合结果，raw 域测量只能验证输入噪声一致性（0.377-0.395 = ISO 差异）。

  1. **pass1 重写为与 spike 已验证着色器同构**：双采样器（Y:R8 + UV:RG8）、无分支、无显式 sampler 精度；全平面输入由 CPU 交错化统一为 semi；
  2. **「填充测试」开关**（相机页）：pass1 用 spike 同构梯度填充替代 YUV 采样，真机二分「YUV 采样问题 vs 写入问题」；
  3. 拍照路径每次输出 `pass3_cap` 诊断（capture 曾独有全黑）。

### M1 追加修复（v0.2.6）：根因定案——预设白平衡增益为零

- v0.2.5 填充测试实验五信息互证定案：**pass1 输出全黑的根因是预设 `DoubleArray(28)` 中白平衡增益（索引 1–3）从未赋值（=0）**，`lin = rgb × wb × exposure` 整帧乘零；填充测试着色器不含 uWb 故能看到内容。「负片蓝/标准白」= pass2 串扰与分离色调作用在黑输入抬升后的灰上，预设响应正确的旁证。
- 修复：三个内置预设补 `wb=1,1,1`；C++ `FilmParams::fromDoubles` 加防呆（wb 全零回退中性）。
- 经验沉淀：跨语言参数数组的「沉默零值」是高危模式——M4 预设系统必须带参数范围校验（§7.1 schema 已含）+ 单测覆盖默认值。

### M1 追加修复（v0.2.7）：log 域映射范围错误（灰白画面根因）

- v0.2.6 验证：wb 修复后 pass1 输出真实画面（diag (0, 0.11, 0) 反推矩阵方程为真实暗像素），pass2/pass3 依然正确执行——但「负片发灰看不清、标准一片白」。
- 根因：**log 域映射 `lg=log2(lin)*0.5+0.5` 仅覆盖 lin∈[0.25, 4.0]**；YUV 经 gamma 2.2 解码后的场景线性值绝大部分 < 0.25（中灰≈0.21），整个暗部被夹断到 lg=0 后映射回 0.5 中灰——暗部整体灰化。
- 修复：log 域改为以 0.18 中灰为轴、±4EV 标准映射（`lg=log2(lin/0.18)/8+0.5`，逆映射 `0.18·exp2((lg−0.5)·8)`），黑不再被抬升；帧首消费残留 GL 错误，使 `pass3_cap` 诊断只反映本帧问题。

### M1 架构修正（v0.3.0）：预览改走 SurfaceTexture 系统路径

- v0.2.7 验证：负片已见画面（wb + log 域修复生效），但 pass1 采样仍异常——**UV 纹理恒读 (0,0)**（反推：G = yv+0.602、R/B 被 clip，与「绿主导」现象完全吻合），间歇 `render.upload_glerr 1282`。结论：RG8 TexSubImage2D 在该 Mali 驱动上静默失败。
- 参照用户指出的 PhotonCamera (github.com/bjzhou/PhotonCamera) 的做法：**预览不做 YUV 平面手动上传，改走 SurfaceTexture 系统路径**——Camera2 → SurfaceTexture（厂商 GPU 完成 YUV→RGB）→ `samplerExternalOES` + `getTransformMatrix` 采样 → 胶片链 → 上屏。该路径是所有相机 App 验证过的最稳方案，同时天然解决行翻转/旋转/裁剪（STMatrix）。
- 变更：删除手动 YUV 上传模块（yuv/YuvUploader）；pass1 改 OES 采样；拍照改为取最近预览帧渲染结果（全分辨率静拍流由 M2 RAW 路径取代，M1 记录为已知偏差）；「填充测试」保留（绕过 OES 采样的二分开关）。
- 方向修正：此前「左右颠倒」为 Y 平面行序（顶行在上）与 GL 纹理原点（底行）不一致 + 旋转叠加所致；STMatrix 路径下由生产者矩阵接管。

### M1 追加修复（v0.3.4）：静拍颜色量纲 + 方向跟随

### M2 追加修复（v0.4.4）：触屏对焦生效 + 镜头切换黑屏 + 焦段条按镜头生成

- **触屏对焦从不触发**：SurfaceView 的 `setOnTouchListener` 只处理 `ACTION_UP` 却返回 `false`——不消费触摸流则 `ACTION_UP` 永不送达，`focusAt()` 从未被调用（日志零条 `focus.set`）。修复：返回 `true` 消费事件。另：重建去重签名只记 `focusRect != null` 不记坐标，第二次点击不同位置会被跳过，签名改为含对焦区域坐标。

### DNG 标准链回填探针（v0.5.45-m3，评估性改动）

P2 的前置探针：`raw.meta` 日志新增 `SENSOR_COLOR_TRANSFORM1/2`、`SENSOR_CALIBRATION_TRANSFORM1/2`、`SENSOR_FORWARD_MATRIX1/2`（各 9 元素行主序，缺失记 `none`）与 `SENSOR_REFERENCE_ILLUMINANT1/2`；`ccm` 从只记 6 个改为**完整 9 个**（P2 要与自建矩阵逐元素对比）。

**为什么先探针**：`tools/dng-color-dump.py` 实测两个 DNG（165344/165447）的 IFD0 里**没有 ForwardMatrix1/2**，当时据此推断"引擎拿不到 ForwardMatrix"。**真机探针推翻了该推断** —— 键在 `CameraCharacteristics` 里给全了（见 v0.5.46）。教训：**"文件里没有" ≠ "API 拿不到"**；数据可得性问题必须直接探 API，别从产物反推。

另外踩到两次同类坑（值得记住）：这些矩阵键**只在 `CameraCharacteristics`**（静态标定），不在 `CaptureResult`；`SENSOR_REFERENCE_ILLUMINANT2` 的类型是 **Byte** 而非 Integer。都是 javap 一查就清楚的事——Camera2 键名/归属凭记忆写必错（记忆库里已有同款教训）。

### P2 DNG 标准色彩链（v0.5.46-m3）

**探针结论（v0.5.45 真机 191459）**：X300 在 **CameraCharacteristics** 里给全了标定数据 —— `SENSOR_COLOR_TRANSFORM1/2`（ColorMatrix，D65/A）、`SENSOR_FORWARD_MATRIX1/2`、`SENSOR_CALIBRATION_TRANSFORM1/2`（单位阵）、`SENSOR_REFERENCE_ILLUMINANT1/2`（21/17）。

**实现**：新增 `camera/StdColorMatrix.kt`，用标定数据自建「相机白平衡后 → 线性 sRGB」矩阵：
`cam(wb) →[CameraCalibration]→ 参考相机 →[ForwardMatrix(t)]→ XYZ(D50) →[Bradford D50→D65 + sRGB 原色]→ 线性 sRGB`。
插值权重 t 由 `asShotNeutral` 在两标定光源的**相机白点**间扫描匹配（0..1 步长 0.01）。**关键性质**：fm1/fm2 都把 (1,1,1) 映到 D50 白点，插值后依然如此 → **白点与整体亮度跟 t 无关**（实测 M·(1,1,1) = 0.9997/1.0002/0.9998），t 只影响色彩形状。

**与 HAL `COLOR_CORRECTION_TRANSFORM` 的实测差异**（同一次拍摄，均白点保持）：标准链对角增益更大 —— **1.62/1.34/1.57 vs 1.39/1.19/1.55**；方向上正对应"libraw 完整链更亮、通道分离更高"（同场景我们 sat 0.2256 / sep 17.26 / 近中性 20.2% vs libraw 0.3072 / 33.39 / 4.4%）。

**A/B 通路**：设置页「DNG 标准色彩链」（`prefs ccm_std`，默认开；日志 `settings.ccm_std`，`raw.meta ccmSrc=std|hal`）；标定数据缺失或光源码未知 → 自动回退 HAL 矩阵（跨机型兜底）。

**真机 A/B（同机位 9s 间隔：2613 std / 2622 hal）**：
- 日志确认：`ccmSrc=std` 时 ccm = `1.622,-0.554,-0.068,-0.141,1.343,-0.202,0.008,-0.576,1.568`，与单测期望逐元素一致；
- 同亮度（63.6）下：sat 0.2189 → **0.2480**、sep 16.79 → **19.49**、近中性 26.7% → **16.0%**、CIELAB **C\* 7.98 → 9.09** —— 标准链补上约 1/3 的差距，全指标同向改善。

**量化口径教训（重要）**：`sep` / `neutral` 是绝对量，**跨图比较必须先统一亮度**。libraw 侧 rawpy 默认 `auto_bright=on` 会把亮度自动拉到 ~2.5×（本场景 37.6 → 94.4），据此得出的"通道分离 −48%"是夸大的。公平口径（统一亮度 63.6 + `no_auto_bright=True`）下：C\* 9.09 vs libraw 13.57（**−33%**）、sep 19.49 vs 28.59、近中性 16.0% vs 7.9% —— **"寡淡"结论成立**（三种口径一致），但**强提饱和不是解法**：追加 1.3× 饱和增益只把 sat 推到 0.31 且已开始失真。真正的嫌疑是**色域裁剪**（CCM 后负值被 `clamp(0,64)` 截断，饱和色首当其冲，见 §3.2-7 规划里的 "clip 到工作域原色"）与**影调**（中间调提亮会稀释感知色度）——需要在 P1 里分步定位，而不是盲目加饱和。

**自检**：`app/src/test/java/com/filmkit/app/StdColorMatrixTest.kt` —— 用真机探针数据比对离线 numpy 结果（1e-3）并断言白点保持（第一版参照值正因为 Python 参照用了不同的插值公式而被单测抓出，已统一）。

### 成片 EXIF 曝光时间落盘修复（v0.5.48-m3）

**起因**：用户报"对电脑屏幕拍时自动曝光压不下来"。核对成片 EXIF 时发现 **21 张成片全部缺 `ExposureTime`（33434）**，只有 ISO/光圈/焦距/白平衡落盘 —— 曝光核对因此只能靠 ISO 推断。该现象本身最终确认为**用户为测试手动固定 ISO 1225** 所致（手动档 `CONTROL_AE_MODE_OFF`，AE 不参与，属预期行为、非缺陷）；但排查过程暴露了下面这个真实的 EXIF 缺陷。

**根因（ExifInterface 兼容标签的静默丢弃）**：`androidx.exifinterface` 1.3.7 有
`sTagSetForCompatibility = {FNumber, DigitalZoomRatio, ExposureTime, SubjectDistance, GPSTimeStamp}`，
这些标签的 `setAttribute` 内部走 **`Double.parseDouble(value)`**。原实现传的是分数串（`"1/${(1/sec).roundToInt()}"`，且 `liveExposureNs = 0` 时会退化成 `"1/2147483647"`）→ **`NumberFormatException` → `catch` → `Log.w("Invalid value for ExposureTime")` → 静默 `return`**：标签被丢弃，既不抛异常也不影响同批其他标签，所以从上线起一直无人察觉。

**修复**（`app/src/main/java/com/filmkit/app/camera/CameraController.kt`）：改传**十进制秒数** `"%.6f".format(Locale.US, sec)`，由 ExifInterface 自行转 Rational —— `Rational(double)` 固定分母 10000，1/125s 落盘为 `80/10000`；`guessDataFormat("80/10000")` 返回 `(SRATIONAL, URATIONAL)`，与 `ExposureTime` 的 `primaryFormat = URATIONAL` 匹配 → 正常写入。取值改为 `liveExposureNs > 0 ? liveExposureNs : exposureNs`（手动档 `SENSOR_EXPOSURE_TIME` 不回填时回退用户设定值），两者皆不可得则**跳过写入**，不再产生非法值。

**自检**：编译 + 单测通过；真机验证项 —— 装 v0.5.48-m3 拍一张，确认成片 EXIF 出现 `ExposureTime`（`exiftool`/`PIL` 读 33434），自动档与手动档各验一次。

**教训**：ExifInterface 对**兼容标签**只接受十进制数，传分数串会**静默失败**（`Log.w` + `return`，无异常外露）；"成片缺某个 EXIF 标签"的正确排查顺序是先查该标签是否在兼容集合内，再查值格式。

### 热修：内置 LUT 导致预览全黑（v0.6.1-m4）

**现象**（v0.6.0-m4 装机即现）：预览全黑、无图像。日志里**没有** shader 编译/链接错误，`render.diag` 显示 `pass1_oes` / `pass2_film` 正常（r/g/b ≈ 0.34/0.40/0.40），但 **`pass3_out` glErr = 1282（GL_INVALID_OPERATION）、r = g = b = 0、a = 255** —— 输出 pass 的整帧被丢弃。

**根因**：`kFsOut` 新增了 `uniform highp sampler3D uLut`，而 `bindLut()` 在「LUT 关闭」时提前 `return`，**从不绑定 3D 纹理**。此时纹理单元 1 里残留的是上一个 pass 绑定的 **2D 纹理**（RAW 路径的 `tex_mos_` 等），sampler3D 指向类型不匹配的单元；Mali 会预测执行 `if (uLutOn > 0.5)` 分支里的 `texelFetch(uLut, …)` → draw 报 `INVALID_OPERATION`、丢弃整帧 → 全黑。这与 LSC 当初「关闭档绑 1×1 全 1 网格」是**同一类坑**：sampler 必须始终有合法绑定，不能指望"分支里不用就不用绑"。

**修复**（`core/engine/src/render/FrameRenderer.cpp`）：
1. `init()` 创建**默认 1×1×1 恒等 3D 纹理**并置 `lut_size_ = 1` —— 保证单元 1 任何时候都是一张完整 3D 纹理；
2. `bindLut()` **无论开关都绑定纹理并下发全部 uniform**（关闭时 `uLutOn = 0`、`uLutStrength = 0`、`uLutSize = 1`，采样坐标恒为原点，不会越界）；
3. `applyPendingLut()` 关闭态置 `lut_size_ = 1`（而非 0）；`release()` 一并清 `lut_tex_` / `lut_size_`。

**教训**：给既有 shader 链加 sampler 时，必须同时保证「始终绑定合法纹理」，而不是「不用时不绑」。设备端表现是整帧丢弃（`glErr 1282`）+ 全黑，构建、单测、glslang 全绿都拦不住 —— 项目「shader 改动必须真机验证」铁律的又一例证。

### M4-4 渲染引擎：黑位/对比/色度对齐标准 DNG 链（v0.6.14-m4，2026-09-22）

**症状（用户肉眼）**：真机成片"原片整体发灰"，叠加 LUT 后效果也不好。

**量化（同场景 DNG 对照 —— 这是本轮能做准的前提）**：

| 渲染路径 | 黑位 P0.1 | 对比 P95−P5 | 色度 C\* |
|---|---|---|---|
| **我们的 RAW 成片** | **L\* 35.4** | 46.9 | **2.77** |
| libraw 标准链（`no_auto_bright`） | L\* 6.3 | 64.1 | 5.57 |
| 厂商 ISP 普通 jpg 直出 | L\* 0.0 | 66.7 | 4.37 |

**根因**：`baseTone` 的旧参数**几乎不压暗部** —— `blk 0.0020` 换算到显示域只有 L\*27，
**比场景实际黑位还高，等于没压**；`p 1.20` 在中灰附近斜率仅 1.02（几乎不加对比）。
旧注释写的"黑点 ≈ −6.5EV（去暗部雾感）"是**线性域**的说法，落到显示域并不成立。

**修复**（两处，A/B 通路都保留：`FilmParams[28]` 关基准影调、`[31]` 关外观层）：
- `FrameRenderer.cpp` 的 `baseTone`：`blk 0.0020→0.0060`、`p 1.20→2.00`、`g 0.90→0.85`
- `CameraPresets` 的色彩外观层**由"中性占位"改为启用**：`uLook 1.0` / `uLookSat 1.5` / `uLookChroma 1.15`
  —— 影调扫参上限只能把 C\* 补到 4.6（libraw 5.6），**缺口只能在色彩层补**

**验证**（DNG 线性 + 引擎数学离线复现）：黑位 6.0 / 对比 62.2 / C\* 4.94，对齐 libraw 的 6.3 / 61.3 / 5.57；
叠加理光负片后黑位 3.4 / 对比 71.5 —— 对照"现行 + 同一 LUT"的黑位 27.7 / 对比 50.5。

**订正（重要）**：2026-09-21 那轮"寡淡是伪结论"的复核，参照是 **libraw 默认链**（rawpy 默认
`auto_bright=on`，把亮度拉高约 2.5×）；本轮改用 **libraw 标准链 + 同场景 DNG** 后，色度差距
（我们 2.77 vs 5.57）是**真实**的。当时"色彩外观层回中性 = 占位"的决定据此**撤销**。

**v0.6.15 回退（外观层）**：v0.6.14 同时启用了色彩外观层（饱和 ×1.5）去补 C\* 缺口，真机复拍后
用户报"严重偏色"。**离线分离（同一张 DNG）证明偏色只来自外观层**：

| 组合 | 全图 b\* | 白墙 b\* | C\* |
|---|---|---|---|
| 旧 baseTone，无外观层（0.6.13） | +1.47 | +1.63 | 3.53 |
| **新 baseTone，无外观层**（0.6.15） | **+1.49** | **+1.63** | 3.12 |
| 新 baseTone + 外观层 1.5（0.6.14） | **+2.56** | **+2.31** | 4.94 |

影调修复对色偏**零影响**（白墙 b\* 一模一样），外观层把暖偏放大了 **72%**。外观层已回中性 ——
**乘性放大（饱和增益）是放大器，会把白平衡的残余误差一起放大**；基础引擎的第一要务是
"不引入偏差"。C\* 缺口暂不追：libraw 的 C\* 只是它自己的偏好，不等于"正确"。
回退后白墙 b\* +1.63，比 libraw 标准链的 +1.89 更中性。

**v0.6.16 二次修正（S 曲线不动点）**：回退外观层后用户复拍报"简直没眼看"（画面又暗又闷）。
根因是 v0.6.14 用"提高 `p` 到 2.00"去压黑位——**错的旋钮**：旧归一化把 `[mn,1]` 映射成
`t∈[0,1]` 后再套标准 S 曲线，**右半段的不动点跑到 xn≈0.609**，于是中灰以上（画面主体）
落进"S 曲线下半段"被**压暗**（实测 `baseTone(0.4)=0.34 < 0.4`、显示域 `0.70→0.66`）。
修法：把 xn 归一化到"以 mn 为 0.5"的坐标再套 S 曲线，**不动点恒为 mn** —— 暗部压暗、
中灰不动、高光提亮；压黑位改用 `blk`，`p` 退回 1.20。定稿 `blk 0.0080 / p 1.20 / g 0.82`：

| 版本 | L\* | 黑位 | P95 | 对比 |
|---|---|---|---|---|
| 0.6.13 旧包 | 64.4 | 32.1 | 83.5 | 45.1 |
| 0.6.15（p 2.0，旧归一化） | 59.6 | 8.6 | **81.0** | 61.6 |
| **0.6.16（不动点归一化）** | **64.1** | **0.0** | **86.8** | 54.2 |

**教训**：`p` **不是**"压黑位"的旋钮，它同时改变中灰以上的落点；压黑位只能用 `blk`。
调影调必须**同时约束** L\* / 黑位 / P95 / 对比 / C\* 五项——只看"黑位+对比"会做出
"黑位达标但画面更暗"的方案（v0.6.14 就是这么翻车的）。

### M4-5 基准影调旋钮正交化（v0.6.17-m4，2026-09-22）

**问题**：v0.6.16 用户复拍仍报"画面整体还是闷"。真机量化——标准预设下整链 = `baseTone` + OETF
（filmCurve 中性恒等、`uSat`=1、`uSplit`=0、外观层恒等），所以可直接**从成片反推** `baseTone`
的输入，不必复现前级（也就绕开了 2026-09-21「离线参照与实现不同式」的坑）：

| | 对比 | 黑位 P5 | 白位 P95 | C\* |
|---|---|---|---|---|
| 我们 0.6.13 | 68.4 | 13.1 | 81.5 | 4.14 |
| **厂商直出（同场景同时刻）** | **89.2** | **2.1** | **91.4** | 5.96 |

**根因**：v0.6.16 仍留着 `g=0.82` 幂提亮，而**线性域幂提亮是"降对比"的旋钮** ——
`pow(x,0.82)` 把 0.01 放大 2.35×、把 0.5 只放大 1.13×，等于抬暗部、压缩动态范围。
"亮度靠 `g` 补"的代价就是画面变平。

**修法**：提亮改用**线性域曝光**（`x * exp2(ev)`，与 PhotonCamera 的
`exposureCompensationDomain=Linear` 同一约定），对比交给 `p`，`g` 整段删除。
至此三个旋钮**正交**：`ev` 管亮度 / `p` 管对比 / `blk` 管黑位。
定稿 `ev 0.35 / blk 0.0080 / p 1.60`：

| 方案 | 对比 | P5 | P95 | C\* |
|---|---|---|---|---|
| 旧包 0.6.13 | 68.4 | 13.1 | 81.5 | 4.14 |
| **0.6.17（ev+0.35 p1.60）** | **93.1** | **1.9** | 95.0 | 5.58 |
| 厂商直出 336 | 89.2 | 2.1 | 91.4 | 5.96 |

`p` 取 1.60 而非 2.00：p2.0 时 P95 已达 97.2（逼近硬截断溢出）——**`ev` 与 `p` 都受
"高光硬截断"约束**，高光滚降是下一步，做完才能放开这两个旋钮。

**工具**：`tools/tone-scan.py`（成片反推 + 参数扫描 + 对照图；`--legacy` 用于 ≤0.6.13 的旧
归一化公式反推）。**离线脚本必须落盘**：上一轮的复现脚本丢在 /tmp 被清掉，本轮只能重建。

### M4-6 自适应影调与高光滚降（v0.6.18-m4，2026-09-22）

**背景**：v0.6.17 删掉 `g` 幂提亮后，真机实拍**暗场景被整体压暗** —— 阳台 L\* 38.3→24.5、
书桌 22.5、卧室 44.6（**厂商同场景直出 62.1**）。根因是 lesson 里早写过的机制：
**S 曲线对"中灰以下为主"的场景必然整体压暗，而原来的提亮手段正是 `g`**。

**关键量化：场景欠曝 1–1.2EV**（显示域白点仅 0.38–0.42，正确曝光应约 0.9）。
固定曝光补偿救不了 —— 暗场景需要 +1.2EV、亮场景只能承受 +0.3EV，**差 4 倍**；
合成压力测试：`ev+1.00` 时正常曝光场景 **27% 像素溢出**。

**做法（两条腿）**：

1. **自适应影调**（`FilmParams[35]`，设置页「自适应影调」可关）：引擎从**场景纹理**统计
   显示域亮度直方图（新增 `histogramFrom`，与 UI 直方图共用 `kFsHist`），取 **P95** 折回
   线性得场景白点 → 归一到目标 0.90 得曝光增益，**限幅 [1,4]×（只提亮不压暗）**，EMA
   平滑防抖。统计刻意放在 `passFilm` 内部 —— 预览 / YUV 静拍 / RAW 静拍三条路径一处覆盖。
2. **高光滚降**（`kFsOut.highlightRolloff`）：`clamp` 硬截断 → **软压缩 + 去饱和**
   （knee 0.75，`t/(1+t)` 压进 1 以内，越亮越趋白）。它顺带治了"过曝灯变红/粉"
   （v0.5.37 反馈），也是放开增益上限的前提。

**分位选型实测**（真机三场景 + 合成亮场景压力测试）：

| 白点分位 | 阳台 | 卧室（厂商 62.1） | 书桌 | clip |
|---|---|---|---|---|
| P90 | 52.7（**gain 打满 4.0×**，过亮）| 64.8 | 50.5 | 0% |
| **P95** | **45.6** | **63.5** | **32.3** | **0%** |
| P99 | 36.6 | 61.3 | 20.3（被屏幕高光骗）| 0% |

**离线验证（本轮最关键的一条）**：自适应让输出与场景**绝对亮度解耦** —— 阳台/卧室在
x×1.0 / ×1.5 / ×2.0 下 L\* 恒定（36.6 / 61.3），clip 全 0%。这是任何固定参数做不到的。

**教训**：① **单一场景的验证不可外推** —— v0.6.17 只在卧室（x 中位 0.158，最接近枢轴、
最不敏感）上验证就推广到全部场景；② **"亮度不掉"≠"亮度够"** —— 44.6 vs 45.6 我判为达标，
而用户要的是对齐厂商 62.1；③ **离线脚本必须落盘**，否则下一轮只能重建。

### M4-8 色度 S 曲线判据修正（域错误 → 亮度相对）+ 调研结论二次复核（v0.6.21→v0.6.22-m4，2026-09-22）

**背景**：M4-7 为治"饱和度低 23%"把 `FilmParams[33]` 由 1.0 提到 1.25，并声明"只放大已经浓的色
（|cc| > 0.25）、**不动近中性色**"。**该声明的前提是错的** —— knee 0.25 是**线性域**色度偏离
`max|cc|`，而代码注释把它标成"≈ 显示域 64/255"；0.25 线性实为**显示域 136/255**（差 72 灰阶）。

**实测（真机 10 张成片）**：`max|cc|` 分布 P50 **0.022** / P75 0.039 / P90 **0.057** / P99 0.179
⇒ 旧 knee 下 **99.8% 像素落在 knee 以下**，中位像素只拿到 **0.5%** 增益（名义 25%）。
即 **v0.6.19 的饱和度修正实际上没有生效** —— 这解释了"色彩淡"为何延续到 v0.6.20 仍未解决。

**修正**：knee `0.25 → 0.06`（取实测 **P90**：ramp 覆盖 90% 像素使曲线真正生效，最鲜艳的 10% 封顶，
满足"不让已浓郁的色块过冲"）。全图平均增益 **1.07% → 12.71%**。

**风险核验（防重演 v0.6.14 偏色）**：v0.6.14 用全局 ×1.5 使近中性色色度被放大 **50%**
（白墙 b\* +1.63→+2.31）。按"最中性的 20% 像素"（WB 残余误差所在）实测，knee=0.06 下放大仅 **0.74%**
—— **保护来自 smoothstep 的 t² 形状，而非 knee 数值**，故降 knee 不会重演该事故。
强度仍是标定旋钮：设备端过浓/过淡调 `uLookChroma`（1.25 = 满额 +25%）；`uLook` 是 A/B 开关。

#### v0.6.22：判据由「绝对线性色度」改为「亮度相对饱和」

**真机复验暴露的问题**：用户拍两组（树叶 / 易拉罐），报"树叶绿仍不准，易拉罐绿好得多"。
日志核对（`settings.color_look` 20:32:16 关 / 20:32:57 开）后逐张比对：

| 样张 | L\* | C\* | h\* | 说明 |
|---|---|---|---|---|
| 树叶①(开) | 22.2 | **14.4** | 132.4° | 与②亮度匹配 ⇒ **A/B 有效** |
| 树叶②(关) | 22.8 | **14.4** | 132.6° | **色度零变化 ⇒ 色度层对树叶无效果** |
| 易拉罐①(关) | 25.0 | 18.5 | 159.0° | 与②差 7.5 个 L\* ⇒ **曝光变了，A/B 无效** |
| 易拉罐②(开) | 32.5 | 17.3 | 157.3° | 不能归因于色度层 |

**已排除的原因**：① **白平衡干净** —— 四张近中性像素 **a\*≈0.00 / b\*≈0.00**，无全局黄偏；
② **不是色域到顶** —— 树叶实测 C\*14.4 而该 L\*/h\* 的 sRGB 上限为 **56.6**（仅到 **25%**；
罐体 18.5/36.4 = **51%**），树叶离上限**更远**。

**根因**：`max|cc|` 是**绝对**线性偏离，把"饱和度"与"亮度水平"混在一起 —— 暗色物体即使很绿，
绝对色度也小。实测（均 look=关）：

| 绿色区 | `max\|cc\|` P50 | P90 | 旧判据实际增益 |
|---|---|---|---|
| 树叶 | **0.0173** | 0.0432 | **5.05%** |
| 易拉罐 | **0.0321** | 0.1843 | **13.70%** |

树叶的 P90（0.0432）**仍低于 knee 0.06** ⇒ 永远吃不满，增强是罐体的 1/2.7。

**修正**：判据改 **`rel = max|cc| / luma`**（0 = 中性，≈3.7 = 纯原色），`t = clamp(rel/1.0)`；
`luma` 加 0.02 下限防除零与暗部噪声放大。这与 darktable `vibrance.c` 的"增益 ∝ 当前饱和度"同构。
效果：树叶 **5.05%→12.50%**、罐体 **13.70%→22.11%**，差距 2.7× 收窄到 **1.8×**。

**噪声/偏色安全性（关键）**：暗部**中性**像素 `rel` 很小 ⇒ 增益仅 **0.06%**。
即**相对判据天然保护近中性色**，不必再让 knee 承担该职责 —— 故 v0.6.14 的偏色事故与暗部色噪
都不会因此回归（实测暗块色度 σ 中位 0.0014，远低于树叶的 dev 0.0173，目标区信噪比充足）。

#### v0.6.23：knee 1.0→0.4 定向补"中间调弱彩"（真机 DNG 对照定案）

**用户反馈**（v0.6.22 装机后三场景）：「整体色彩比之前好，只比肉眼看到的淡一点，只有 456 比真实场景暗」。

**参照物到手**：用户提供三场景 DNG，用 libraw 出标准链（`use_camera_wb` + `no_auto_bright`）逐像素配对。
先排除混淆项：DNG 的 `AsShotNeutral [0.4354,1.0,0.5005]` 与 `raw.meta` 21:14:45 记录**逐位一致** ⇒
两条链白平衡相同，对比不被 WB 污染。

**实测缺口剖面（我们 rel / 参照 rel，逐像素配对）**：

| rel 区间 | 445 树叶 | 453 衣架 | 456 床 |
|---|---|---|---|
| 0.15–0.25 | **0.68** | **0.63** | **0.46** |
| 0.25–0.4 | 0.69 | 0.84 | 0.91 |
| 0.4–0.7 | 0.88 | 0.73 | 0.98 |
| 0.7–1.2 | 0.91 | 0.98 | 1.10 |

⇒ **缺口集中在低饱和段，高饱和段已达或超过参照** —— 即"淡"的是**中间调弱彩**，不是鲜艳主体。
（v0.6.22 的修正让高饱和端达标：这正是用户说"比之前好"的部分。）

**为什么不直接对齐 libraw**：DNG 里 **`ForwardMatrix1/2` 缺失**（`tools/dng-color-dump.py` 实测），
libraw 只能退回 `ColorMatrix1/2`；而本 App 走的是 `CameraCharacteristics` 的 ForwardMatrix（DNG 标准路径，
`FM·(1,1,1)` = D50 白点自洽）。这与 `CameraPresets.kt` 既有结论一致：**libraw 的 C\* 是它的偏好，不等于"正确"**。

**修正**：`kRelKnee 1.0 → 0.4`（`FrameRenderer.cpp`）+ `FilmParams[33] 1.25 → 1.35`（`CameraPresets`）。
knee=1.0 时低饱和像素落在 smoothstep 的 t² 慢段只拿 1.5–2.6% 增益；降 knee 把这段推上 ramp：

| rel | 0.15 | 0.20 | 0.30 | 0.50 | 0.80 | 1.20 |
|---|---|---|---|---|---|---|
| 增益变化 | +9.4% | +14.5% | +22.9% | +20.0% | +10.3% | +8.0% |

**低饱和段被加权最多（正是缺口所在），高饱和段只 +8%**；近中性（rel ≤0.08）仍只 +0.3~3.6%
（v0.6.14 偏色事故是 +50%），保护未失。

**456「比真实场景暗」——机制已定，但本轮不改**：456 是**暗场景 + 高动态范围**（显示域中位 0.356、
线性 DR 8.4EV），衣柜把 P95 顶到 0.877，而 auto-tone 的目标就是 P95→线性 0.80（显示 ≈0.90）——
**已在目标上、高光接近硬顶**。实测我们已把 456 相对计量值抬了约 **1.9×**（按亮度分箱比 1.6–2.6×）。
+0.3EV 会使 5.9% 像素越过 1.0（比 445 的 7.4% 还低，说明仍有少量余量），但**真正的解法是
局部色调映射**（压高光 + 提中间调），即 roadmap 的「基础引擎第二批」——全局曲线做不到。

**仍待定案**：树叶绿"准不准"缺少参照物（两组是不同场景/照度，非受控对比）。需用户提供该组 **DNG**，
用 libraw 出标准链参照后对比同一叶片的 C\*/h\*，才能区分"管线不足"与"场景本色"。
另实测树叶 h\* 随亮度有 ~7° 漂移（131.3→138.0），罐体仅 ~2.5°，原因待 DNG 对照。

**v0.6.23 装机复验（5 张新样片 + 各自 DNG 对照，用户反馈"效果不错"）**：

| 缺口剖面（我们 rel / 参照 rel） | 0.15–0.25 | 0.25–0.4 | 0.4–0.7 | 0.7–1.2 |
|---|---|---|---|---|
| v0.6.22（旧批次平均） | 0.59 | 0.81 | 0.86 | 1.00 |
| **v0.6.23（新批次平均）** | **0.68** | **0.93** | **1.07** | **1.03** |

⇒ 中段（0.25–0.7）改善最大（+15~24%），与预测一致；树叶绿已由"低于参照"变为 **C\* 20.3 vs 参照 15.8**。
亮度：相对 libraw `auto_bright` 平均 **+2.2 L\***（散布 −4.9~+15.0），**五张 clip 全 0%**；
暗场景（213634 床）仍偏暗 −4.9 L\*，与「456 暗」同源，待局部色调映射。

**⚠️ 仍未解决的独立问题：黄绿带色相偏差 −3~8°**。按色相带统计（我们 h\* − 参照 h\*）：
黄绿 **−5.6°**（n=3）/ 青蓝 −2.3° / 紫品红 −2.8° / **黄橙 +1.0°**（n=5）——
**偏差集中在黄绿带、黄橙几乎为零 ⇒ 不是全局色偏，是色相相关的误差**，正是用户最初说的"树叶绿不准"。
已排除是色度层引入：把偏差按 `rel` 分箱后**不随增强量增大**（213639 各箱 −4.7~−7.7 基本恒定）。
⇒ 归因到 **CCM 路径差异**（我们 ForwardMatrix / libraw 因 DNG 无 FM 退回 ColorMatrix），
但**参照不具权威性**（见上），故本轮不动，列为待定案。

**同轮调研结论二次复核**（`docs/research/00-synthesis.md` 已就地订正）：
- **① OETF 改 sRGB 分段：仍做，但理由改**。实测中间调仅 **+1.27/255**（"viewing gamma 治发闷"
  的中间调机制数值上可忽略），真实收益是**暗部压深**（−7.57/255 ⇒ 无 LUT 对比 **+9.87**、
  饱和 +2.01pp）＋**域正确性**（sRGB 是标准显示编码、也是本仓库 LUT 的设计域）；
  原"喂 2.2 会削弱 LUT"**被实测证伪**（喂 2.2 时 LUT 反而更用力：对比 +11.46/+14.80pp vs +5.41/+12.83pp）。
  ⛔ 实现须**三处同步**：`FrameRenderer.cpp:780`(kFsOut) / `:845`(kFsHist) / `:2013`(反解码)
- **③ AE：只做「切镜头重置 + 死区」**。「改区域加权锚定 0.16」**降级为待真机 A/B 的选项** ——
  libcamera 的 0.16 是区域加权**平均**（rkisp1 `estimateLuminance` 一手核实），
  与我们"显示域 P95=0.80 白点"是**不同目标语义**，非可直接照搬
- **④ LUT 纹素中心校正 ❌ 废弃**：**恒等 LUT 实测**证明现行 `t=c*(N-1)` 与硬件 `texture()` 路径
  数学等价（差 ≤2e-17；`texelFetch` 取整数索引绕过过滤，`setLut` 的 `GL_LINEAR` 惰性）。
  报告公式逐字来自 PhotonCamera `BasicToneLutShader.kt:20-22` 的**纹理坐标**补偿，照搬会二次偏移

**过程教训**：给 `kFsFilm` 加注释时写了「显示域 0.25(=64/255)」，其中 `)"` 正是 C++ 原始字符串
`R"(...)"` 的**结束标记** → GLSL 被截断，`validate-shaders.sh` 报 `shader_11.frag:126 syntax error,
unexpected end of file`。构建与单测全绿都拦不住，**只有校验脚本能拦**。

### M4-2 LUT 库扩容与强度外推（v0.6.9-m4，2026-09-22）

**范围**：把用户自备的 64³ 原始 LUT 全量接入（去重后 **42 个**），强度滑杆上限 100% → 150%。

**资产格式：内置二进制 ≠ 交换格式**。`app/src/main/assets/luts/*.lut` 是 33³ uint8 二进制
（`[size:1][titleLen:1][title][catLen:1][category][size³×3 RGB]`，分类见 M4-3），由 `tools/gen-lut-assets.py` 从
`~/Downloads/LUT/滤镜.cube/*.cube`（64³）三线性重采样生成；`Ricoh-HDF` 与 `Ricoh-Positive`
内容完全相同，去重掉一个。**为什么不用 ASCII .cube**：42 个 ASCII 资产要 40MB，uint8 只要
**4.3MB**；源数据本身是 8-bit 精度（值落在 1/255 或 1/512 网格）、成片也是 8-bit JPEG，
量化误差 ≤0.5 LSB 不可见。**§6.2 的 .cube 导入导出不受影响** —— `CubeLutParser.parse`（ASCII）
与它的合成用例完整保留，二进制走独立的 `parseBinary`。

**清单不硬编码**：`LutLibrary.entries(context)` 扫目录 + 只读头部拿 TITLE（进程内缓存一次），
显示名 = 资产内 TITLE（当前为原文件名，如 `Ricoh-Negative`）；`byId` / `load` / `preload` 都改为
接收 Context。卡片预览仍是"固定测试图 × 一次性生成 + 磁盘缓存"，42 张首次生成约数秒（IO 线程）。

**强度外推**：`FilmParams[34]` 上限 1.0 → 1.5（`CameraController` 的 `coerceIn` + 滑杆
`valueRange`）。引擎公式 `mix(c, lutApply(c), s)` 对 s>1 天然是**沿 LUT 色差外推**，与
PhotonCamera 的 >100% 强度语义一致（其上限 200%）。**代价（离线量化）**：s=2.0 时富士NC 的
clip 像素达 14.8%、黑白 LUT 会外推出色彩 —— 故上限取 150%。

**为什么不是"基线层"**：本轮量化显示 baseTone 对 LUT 结果影响极小（同一 LUT 在 baseTone 与
中性基线下 ΔE 差异 **<1**），真正让效果变淡的是**内置资产本身**：PhotonCamera raw 导出版比
64³ 原始包弱（fuji_cc ΔE **3.4 → 7.1**、ricoh_neg 7.8 → 9.4、ricoh_pos 6.7 → 7.9、
fuji_nc 8.3 → 9.6），故先换资产、强度上限作为可调余量。

**教训（PhotonCamera 侧，一手核实）**：
- `.cube` 导出有 **raw / baked** 两种：baked 会把色彩配方烘焙进去（identity CLUT 过一遍
  `LutImageProcessor`），raw 只有 LUT 本身。但实测 baked 反而**降**饱和（C\* 13.33 vs 基线
  14.08）→ "导出版偏淡"不是 recipe 丢失。
- 导入 .cube 时会走 `resampleLut(cubeData, curve)`（sRGB→linear→目标曲线域），默认
  `curve = SRGB` 时是恒等变换。**用 11 种曲线反推内置资产的实际域**：SRGB 的 ΔE 最小
  （9.07），所有 log 曲线 16.9–29.0 → 内置资产确实是标准 sRGB 编码域，§0-D10 的域假设正确。
- 它的"厂家色彩"**不是 DCP**：8 个渲染引擎里只有 AdobeCurve 用 DCP，哈苏/松下/佳能的风格
  走**原厂数据**（HNCS 表 / PhotoStyle / Picture Style + ICC）；用户 LUT 一律在最终 sRGB
  编码域，且支持 **RAW 基线层 + 创作层两级栈**（§6.1 的嵌套模型可据此细化）。

**范围**（§6 LUT 引擎第一步）：把用户自备的 6 个 .cube 接成**相机内置 LUT**（原版名，暂不中性化 —— 2026-09-21 拍板）；含域感知插桩与四面体插值。链式融合烘焙、Hald、导入导出、预设包留后续。

**引擎**（`FrameRenderer`）：`setLut()` 任意线程可调（只暂存），渲染线程在 `passOutput` / `histogram` 前 `applyPendingLut()` 上传 **RGBA16F `GL_TEXTURE_3D`**（CLAMP/LINEAR；选 RGBA16F 而非 RGB16F —— ES 3.0 required 且项目已在用）。shader 内手写 **tetrahedral** 六例权重式（§3.3-5：三线性在 33³ 下有可见色差），**插桩点在输出 OETF 之后**（§0-D10：display 域 LUT 放线性域会错色），且 **`kFsHist` 走同一条 LUT** —— 否则选 LUT 后直方图/斑马纹会与画面不符。强度走 `FilmParams[34]`（0 = 旁路，保留 A/B 通路），`FilmParams.kCount` 34 → 35。

**接线**：`EngineBridge.nativeEngineSetLut` → `RenderClient.setLut`（渲染线程排队）→ `CameraController.setLut`（缓存当前 LUT，**会话重建后 start() 自动重传** —— 切镜头会释放引擎纹理）。UI：`LutMenu` 新增「LUT · 内置」区（无 + 6 项，选中持久化 `prefs lut_id`），解析在 IO 线程（`LaunchedEffect` + `Dispatchers.IO`），菜单超高时纵向滚动。

**待真机验收**：6 个 LUT 逐个切换（预览与成片一致、无明显色偏）；直方图与画面同步（LUT 联动）；12MP 成片与预览的开销（§3.3 验收目标：LUT ≤5 个时帧率损失 ≤5%）；`lut.parse` / `lut.load` 日志核对（size/title/ms/err）。

**教训**：Kotlin 的块注释**支持嵌套** —— KDoc 里写 `assets/luts/*.cube` 时那个 `/*` 会开启嵌套注释，把整个文件吞进注释（`Unclosed comment`，报错指向文件末尾而非真凶行）。写路径通配时避开 `/*` 序列。

### M3 实时直方图 + P1 色彩外观层（v0.5.44-m3）

**实时直方图（M3 补齐）**：此前只有开关和"直方图 · M3 接入"占位。

**P1 色彩外观层 v1**：调研结论里"寡淡"的量化 = 中性色准（R/G 0.987）但饱和 −21% / 通道分离 −29% / 近中性像素 +10pp（颜色全挤在中性附近）。本轮按**参数化外观层**落地（不引入资产系统；3D LUT 引擎仍归 M4）：

- `kFsFilm` 在暖冷分离之后、单色化之前插入：① **亮度保持的饱和增益**（luma 不动、色差整体放大）；② **色度 S 曲线**（knee 0.25 线性 ≈ 显示域 64/255，之上加速）——把"灰"推离中性，同时不让已浓郁的色块过冲。
- 参数：`FilmParams[31]` 强度（0 = 恒等，A/B 通路）、`[32]` 饱和增益 1.18、`[33]` 色度端点 1.15；设置页新增「色彩外观层」开关（`prefs color_look`，日志 `settings.color_look`）。
- 工具 `tools/color-metrics.py`：sat / sep / neutral 三项度量 + 外观层参数扫描（P5 对标 harness 雏形）。
- **2026-09-21 复核（推翻"寡淡"前提，重要）**：用 CIELAB C*（与亮度解耦）在**各自原生输出**下比较 —— 我们 **9.25 @ 亮度 63.5**，libraw 标准链（`no_auto_bright=True`）**8.42 @ 37.6**：**我们的感知色度不低于 libraw 标准链**。此前"饱和 −21% / 通道分离 −29%"的诊断主要来自 libraw 侧 rawpy 默认 `auto_bright=on`（把亮度自动拉到 **94.4**）——**亮度差被当成了色彩差**；"先统一亮度再比"同样不严谨（把偏暗的一方拉亮，本身会抬高它的 C*）。另两项嫌疑也已排除：**色域裁剪**（CCM 后负值像素仅 0.7%、被 clamp 掉的能量 0.02%）、**影调**（base_tone 开/关 A/B：开反而 C* 略高 9.25 vs 8.52）。→ **差异主要是色调映射策略**（我们 63.5 落在 libraw 的 37.6 与 94.4 之间），不是色彩链缺陷。**外观层（提饱和）的前提不成立**；浓淡属风格，按 §0-D8/D9 应交给 M4 的 LUT。
- **定标口径（2026-09-21 用户更正）**：参照物是 **libraw / Adobe 标准 DNG 链**（§3.2-7、§3.4-4「与 Adobe 冲图观感可比」），**不是厂商直出** —— X300 有自研 V3+ ISP + AI，其成片是另一种风格化结果；本项目 RAW 路径的意义正是绕过 vendor ISP，拿它当色彩目标自相矛盾（§1.2 非目标、§9.2）。
- **定标缺口**：现有样张是暗光中性桌面（近中性占比 70%），不足以定标；需要"**色彩丰富场景的同一次拍摄（我们的成片 + 同期 DNG）**"，再用 `tools/color-metrics.py` 与 libraw 同口径比较、调参。

### M3 P0 镜头阴影校正（LSC，v0.5.43-m3）

**背景**：v0.5.42 探针确认 X300 提供 `STATISTICS_LENS_SHADING_CORRECTION_MAP`（17×13、mode=ON、中心 1.000、角落 **6.236**）—— 未校正时角落原始亮度只有中心的 ~16%。这既是"暗角"，也是**角落色偏**（R/G/B 通道增益不同）与"整体偏暗"观感的共同来源。

**接入点**：RAW 解码链的 **CCM 之前**，两个出口 pass 各一行乘法：
- bilinear 档 `kFsRaw`：`uCcm * (rgb * uGain * lscAt(p))`；
- RCD 档 `kFsRcdChroma`：`uCcm * (hlRecon(rgb) * lscAt(p))` —— 放在 `hlRecon` **之后**，饱和判定仍用未校正值（原语义不变，否则角落会被误判饱和触发错误重建）。

选在**去马赛克之后**乘：LSC 是低频网格（17 列 → 单元 ≈240px），与在 mosaic 域逐像素应用差异 <1%，却省掉 5 个 shader（含降噪 P0 的 mosaic 出口）的改动。

**采样**：网格上传为 RGB16F 纹理（Java 侧把 HAL 的 R/Gr/Gb/B 四平面折成 RGB 交错，Gr/Gb 取均值），shader 内**手写 4-tap 双线性**（float 纹理过滤在 X300 上不可依赖，见 `makeTex` 注释；网格 NEAREST + 手动插值）。`prefs lsc` 关 → Java 传 null → 引擎上传 1×1 全 1 网格 = 恒等，**shader 无分支**——A/B 通路（教训：影调/色彩类改动必须自带可关闭通路）。

**入口**：快捷设置「镜头阴影校正」（`prefs lsc` 默认开，日志 `quick.lsc`）；引擎 `raw.render` 记 `lsc`（网格尺寸 / `"off"`）。

**验收**：暗角消失 + 角落色偏改善 —— 同机位 `lsc` 开/关 A/B 对，量角落/中心亮度比与角落 R/G、B/G。

**真机 A/B（两组，同机位开/关）**：

组 1 · 台灯桌面（174940 开 / 174943 关，间隔 3s）：角落/中心亮度比 0.11–0.22 → 0.23–0.62；逐像素增益场 中心 1.05 / 四角 1.93（径向递增 = 方向正确）。但两张中心亮度 106.4 vs 125.8（-15%）说明并非严格同曝光 → 仅作方向性证据。

**组 2 · 均匀白柜面（184019 开 / 184028 关，间隔 9s）——主验收，通过**：
- 中心亮度 160.1 vs 160.2（**1.00**）→ 网格口径正确，中心既不过校正也不欠校正；
- 白柜面角落/中心比：右上 **0.669 → 0.992**、左下 **0.613 → 0.903** → **暗角基本消失**；
- 8×8 分块 开/关 增益：中心 1.01–1.03，向外单调递增至边缘 **1.4–1.8**（标准径向增益场）；

### M3 高光重建（RAW 域饱和通道外推，v0.5.39-m3）

**问题**：传感器饱和后像素被截断在满阱（`s()` 里 raw=white → `1.0×gain`），而 **CCM 是 3×3 混合**，会把这种截断失真按矩阵扩散到其它通道。真机实测（164015，关 tone）：灯泡高光 `R>250` 与 `B>250` 各占 1.39%、`G>250` 仅 0.31% → **高光偏品红**，正是 R/B 先饱和、G 未饱和的截断特征。

**实现**：在 RCD P3 的 **CCM 之前**插入 `hlRecon()`（`uHlK` = `FilmParams.hl_recon`，索引 29，默认 1.0，设置页「高光重建」可关）：

- 饱和阈值 = 该通道 WB 增益 × 0.99（`s()` 的映射决定 raw=white ⇔ lin=gain）；
- 部分饱和（1~2 个通道）时，用**未饱和通道反推辐照度** `x = lin_c / gain_c`（raw 归一化域，1.0 = 满阱），把饱和通道替换为 `x × gain_c` —— 中性高光假设下最保守的估计（宁可趋白，也不停在截断点）；
- 全饱和（3 通道）时没有可信参考，保持原值，交由后段 pass2 的高光 rolloff + 去饱和；
- 只走 RCD 路径（bilinear 保持纯净基线）。

**局限**：这是"最保守版"——消除截断造成的偏色，但**无法恢复截断前的真实色彩**（信息已丢）。真正保色的做法是"局部比值外推"（用邻域未饱和像素的通道比），需要 RAW 数据离线实验后再实现（§3.2 阶段 4 的完整形态）。`raw.render` 日志加 `hl`。

**DNG 实测（165344，rawpy，WB 域饱和统计）**：R 1.131% / G 1.206% / B 1.158%（三者接近 → 高光以中性为主），其中**三通道同时饱和占 1.0890%**（没有任何可信参考，重建无从下手）；**部分饱和合计仅 0.128%**（G+R 0.038%、G+B 0.062%、仅G 0.017%、仅R 0.005%、仅B 0.007%）；而 **R+B 饱和而 G 未饱和 = 0.0000%**。饱和像素邻域内未饱和像素的 R/G 中位 0.916、B/G 0.952（略偏暖的中性光）。

→ **结论**：重建只覆盖 0.128% 的像素，所以开/关成片差异极小（`>240` 区 253.9/254.3/254.3 → 254.8/254.7/254.6）属于**预期，不是失效**；灯泡的观感问题实际由 v0.5.38 的高光去饱和解决。局部比值外推（邻域 R/G、B/G）也只对这 0.128% 有意义 → **列为低优先**。

**教训（重要）**：v0.5.39 提交信息里"R/B 先饱和 → 品红"是**从 JPEG 反推的错误推断**——成片的通道饱和度受 WB 增益/CCM/tone 影响，无法反推 RAW 饱和。RAW 饱和必须在 **WB 域**判定（阈值 = black + (white−black)/gain：本例 R≥520、G≥1023、B≥747，而不是各通道自己的 1023），且**先拿 DNG 再下结论**。

**待验证**：同场景高光重建 开/关 A/B（灯泡/高光是否回到中性、有无副作用）；并回传一张 **DNG**（设置页 DNG 开关）供离线分析 RAW 真实饱和情况。

**缺陷（用户反馈）**：开 tone 后**台灯灯泡变红/变粉**（162927 vs 162920）。成因：`norm-controlled` 的等比压缩 `out3 * (n1/n0)` **保住了高光的暖色比例**（R>G>B 原样保留），而关 tone 的硬截断把三通道一起顶到 1（白）；等比压缩下 R 先抵 1、G/B 仍低 → 过曝区偏红。**亮度压缩与去饱和必须成对出现**（Filmic/AgX 的高光处理皆如此），只做前者等于让过曝区过饱和。

### M3 基准色彩内核 v1：三点锚定 S 曲线 + norm-controlled（v0.5.36-m3）

**问题（量化）**：中性预设下 pass2 在数学上**恒等**（`out3 = lin`）——整条链没有任何影调工程，只有 pass3 的 `pow(1/2.2)`。实测成片：P0.1≈20、<16 占 0.02%、>224 占 0.00%、P99≈169 → **无真黑无真白、直方图挤中间**（"整体发灰"的根因，与 demosaic/降噪无关）。

**实现**：pass2 在 `out3`（线性显示域）之后加入由 `uToneK`（`FilmParams.tone_strength`，索引 28，默认 1.0）控制的基准影调：

- **三点锚定 S**：黑点 0.0030（≈-5.9EV）→0、中灰 0.18→0.18、白点 1.0→1.0；形式 `t^p/(t^p+(1-t)^p)`（p=1.35，以中灰为枢轴）——端点导数→0 是 rolloff 而非硬截断（"硬截断把暗部 14% 钉死出尖峰色带"是既有教训）。
- **norm-controlled**：只对亮度范数 `max(R,G,B)` 取曲线、再按比例缩 RGB —— 避免 per-channel 压缩在暗部造成的色偏（Filmic RGB/AgX 思路自研）。
- **参数化/防呆**：`tone_strength = 0` 即旧行为（可回退）；契约 28→29，`fromDoubles` 改为按实际长度读取（旧长度不再"整包静默丢弃"，同 lessons「跨语言参数沉默零值」）。
- `raw.render` 日志加 `tone`。

**预期**：暗部压深（线性 0.02 → 8bit 27，原 45）、亮部提亮（0.72 → 225，原 219）、出现真黑与近白。

**待验证（真机）**：同场景与 v0.5.35 对比（或开关 tone_strength）——"发灰"是否改善、高光是否自然不脏、暗部是否丢层次或出色带；另确认预览与成片一致（pass2 为共用链）。

**根因**：P0 值域 σ 远大于真实噪声（回退 ns=0.030 × 系数 1.1），9 点权重里值域项≈常数 → P0 **退化成无条件 9 点平均**。佐证：σY 恰降 1/2.8≈**1/3 正是 9 点平均的理论值**；uDnK 1.0→1.45 只是让权重更均匀、故无差别；JPEG 体积腰斩是高频被抹掉的直接后果。

**重标定**（Laplacian 损失全部来自 P0——P4 输出保留 Y，色度平滑不动亮度）：

- **P0 收温和**：值域 σ 系数 标准 **0.50** / 强 **2.20**（原 1.1 已落在饱和区，0.5 才恢复选择性）。
- **P4 保持较强**：标准 **1.80**（不变）/ 强 **2.60**——色度可以激进，压彩噪不损细节。
- 两档改为各 pass 各自的 σ 系数（引擎分别下发），不再是单一乘子；`raw.render` 日志改记 `srK`/`scK`/`ns`/`nsHal`。
- **防呆**：ns 夹紧 `[0.008, 0.040]`——修好噪声解包后 HAL 值可能首次真正生效，避免异常值让降噪失效或过猛。

**真机验证项**：同场景 关/标准/强 3 张（ISO 尽量一致），出口仍是**细节损失 <20% 且 σ(chroma) ≤1.0**；重点确认两档产生真实差距、`dnMs` 不随档位显著变化。

**方法论教训（细节指标口径）**：全图 Laplacian 会把**噪声当细节**计入（梯度 P90≈5.7 恰等于 σY 2.30 的高斯噪声梯度 P90），降噪必然压低它 → 用它判"细节损失"会系统性高估（v0.5.33 的"-59%"即此）。正确口径是**强边缘锐度 = 梯度 top 0.5% 均值**：噪声进不了该分位，只有真实结构在其中。同指标回测 v0.5.33：标准 -23%、强 -31%（印证"退化为无条件平均"的假说）；v0.5.34 标准 0% ✅。

### 静默失效修复：SENSOR_NOISE_PROFILE 解包（v0.5.34-m3）

`CameraController.extractRawMeta` 的 `result.get(CaptureResult.SENSOR_NOISE_PROFILE) as? List<Any?>` 是**永远失败**的 cast：该 tag 返回 `Pair<Double, Double[]>[]`（Java **数组**，不是 List），编译器 "This cast can never succeed" 警告即此 → `noiseSigma` 恒为 0 → **σ 自适应从未生效**，一律走引擎回退 0.030；历史结论"X300 不回填 SENSOR_NOISE_PROFILE"建立在坏代码之上，**修复后须真机复核 `raw.meta` 的 `noise`**。修复：改按 `Array<*>` + 防御性解包（`android.util.Pair<*,*>` 逐元素）。

**教训**：泛型/跨语言边界上的 `as?` 失败是静默的——编译警告必须清零（同 lessons「跨语言参数沉默零值」一类）。

### M3-2 降噪第一版：RAW 域 bilateral + 色度平滑（v0.5.32-m3）

**噪声基线（v0.5.31 真机样张 652/640，平坦区 8×8 块大样本，8bit 域）**：亮噪 σ(Y) 1.5–1.8（**达标优**，亮度分层线性合理）；彩噪 σ(chroma) 1.78（RCD）/2.13（bilinear），**未达优（目标 ≤1.0），B-Y 分量最重**（与蓝通道 WB 增益 1.65 相关）——彩噪定为 M3-2 主攻。RCD 亮噪高 18% 是细节保留的代价（bilinear 假平滑），彩噪低 16% 是色差域插值优势——降噪须保 RCD 细节。

**实现（两 pass，仅 RCD 质量档生效；bilinear 保持纯净基线）**：

- **P0 RAW 域同色联合 bilateral**：线性化+WB 后，任意 Bayer 相位下"步长 2 的 3×3 网格"恰为 9 个同色位（无需相位条件，数学自洽）；值域 σ 随信号 √ 增长（shot noise 主导，`σr = ns·1.6·√(0.2+4v)`）；空间 σs=1.8。输出线性 mosaic 纹理（`tex_mos_`），P1–P3 经 `uMosaic` 开关读取——顺带免去整型解码/黑阶/WB 重复计算。
- **P4 色度平滑（彩噪主修）**：CCM 后场景线性域，色差 = RGB−Y(luma)，色差联合 bilateral（Y 值域防边缘色溢 + 色差值域 + 空间 5×5），**Y 原样保留（亮度细节零损失）**，输出 `tex_dn_` 接胶片链。
- **噪声 σ 自适应**：提取 `SENSOR_NOISE_PROFILE`（按当前感度取最近增益条目，σ_data/whiteLevel 归一化，泛型 JNI 擦除需防御性解包），HAL 不回填时引擎内回退 0.030；`raw.meta` 日志记录 `noise` 值供真机核对。
- prefs `noise_reduction`（默认开，设置页「RAW 降噪」行 关/标准）；`raw.render` 加 `dn`/`ns`/`dnMs`。shader 校验 11→**13 条全过**，构建+单测绿。

**真机验证项**：同场景 652 基线 vs 新版（降噪开/关）平坦区彩噪/亮噪复测；`raw.render` 确认 P0+P4 增时（估 +150–250ms，总预算余量足）；观察细节保留（RCD 优势不能被钝化）。

### 发红真因：CFA LUT 位序反（v0.5.31-m3）

v0.5.30 的 G 位修复方向正确但没打中红移主因。231（RCD，整体橙红、蓝衣变棕红）vs 237（bilinear 正常）+ 三轮现象闭环后定位：**v0.5.29 引入的 `cfaLutOf` 把 k1/k2 位写反**——GRBG 被编码成 GBRG 的 0x49，物理 R 位判定为 B（乘 B 增益 1.65、进 B 通道）、物理 B 位判定为 R（乘 R 增益 2.19、进 R 通道）。白平衡域下净效果 = **R 通道 ×1.33、B 通道 ×0.75 = 系统性发红**（R/G 实测 1.086 vs bilinear 1.000）。

**三轮现象完整闭环**：bilinear 用旧分支链 chanAt（正确）从不发红；936（v0.5.28 RCD）无 LUT 不发红（其灰 = G 位填充 bug）；149/231（v0.5.29+ RCD 用 LUT）发红，v0.5.30 修掉 G 位稀释后红得更纯粹。修复 = 编码改按 k 低位在前（GRBG→0x61），最小脚本验证四个相位的解码/增益映射全部正确。教训：**逐相位解码表要在引入时用最小脚本验证，而非只验"编码意图"**；离线复现要选彩色显著区域（中性区域对 R/B 对调不敏感，v0.5.30 的复现因此漏检）。

### RCD 色偏修复：P3 G 位填充的 Bayer 结构错误（v0.5.30-m3）

**v0.5.29 真机复验**：RCD totalMs **417ms**（dirMs 54 / gMs 7 / 色度+胶片链 ~238）vs bilinear 230ms——**≤900ms 出口标准达标**（gMs 1414→7：G 位像素走轻路径 + LPF/方向图 L2 命中，P2 优化生效）。但 RCD 成片偏红（R/G=1.086 vs bilinear 1.000），且上一轮 936 的"饱和度减半"同源——定位到 **P3 色度填充的 Bayer 结构性错误**：

- 断言"R/B 位的对角是目标色"正确（chromaDiag 无恙）；
- 断言"G 位对角是 R、轴向 ±2 是 B"**错误**——任意 Bayer 相位下 **G 位的 R/B 都在四正邻 ±1**（GRBG 下 G 位的对角与轴向 ±2 全是 G）。原实现把 G 的实测值当 R/B 色差源填入 → G 位 R/B≈G，色彩被系统性稀释/污染（随场景漂移方向），正是 936"饱和度 3.15→1.48"与 149 偏红的共同根因。

**修复（axialFill）**：G 位按 `chanAt(p±1,0)` 实测分派目标色所在轴，取该轴 ±1 同色对（反梯度加权为主）+ ±3 同色对（弱混合），色差限幅不变；DNG 离线复现（rawpy 解 RAW + Python 三版对比）确认修复版 G 位 R/G 与 bilinear 基准对齐。shader 校验 11/11 过。

**遗留认知修正**：936/149 的色偏不是 WB 或 CCM 问题（两次 raw.meta neutral 差 <0.5%），色彩内核（基准影调+WB 精调）仍是 M3 下一站，但 RCD 的结构性色污染已先行消除。

### RCD 真机首轮 + 性能定向优化（v0.5.29-m3）

**v0.5.28 真机 A/B（2026-09-20 晚，12MP X300，`raw.render` 实测）**：RCD totalMs **1969**（dirMs 108 / gMs **1414** / 色度+胶片链 ~264）vs bilinear 359——远超 ≤900ms 出口标准，瓶颈清晰定位在 P2（estAx 内联 9-tap LPF ×4 方向未共享 + 四项式梯度 + chanAt 分支链）。

**性能优化（P2 采样 ~91→~24 taps）**：

- CFA 相位判定改 **uniform 查表**（`uCfaLut`，2bit×4，C++ 侧 `cfaLutOf` 编码），替代 shader 内逐次分支链；
- P1 输出**预归一化** `(vConf, pConf, lpf)`：方向置信度与 CFA 低通图一次算全图，P2/P3 读纹理 1 tap，免每像素重复 9-tap 卷积（预归一化均值≈启发式近似，注释在案）；

### M3-1 RCD 质量档去马赛克（v0.5.28-m3）：三段管线 + 伪彩抑制 + 质量档开关

**算法出处更正（调研证伪原表述）**：RCD 并非"Karacan 2013 论文"——该论文不存在（Crossref 多轮检索无果）。RCD（Ratio Corrected Demosaicing）真实出处是 **Luis Sanz Rodriguez 的开源算法**（GPL-3.0，2017），后经作者参与移植进 RawTherapee（`rcd_demosaic.cc`）/darktable/Siril；RawPedia 评价其圆形边缘表现极佳、细节保持接近 AMaZE。参考实现是**单趟四步流水（方向判别 → CFA 低通 → G@RB → 色度填充），无迭代**——此前的"两遍迭代"表述作废（§3.2/§3.4 已同步更正）。代码 GPL-3.0 隔离不抄，仅采用公开数学思想自写 GLSL。

**引擎实现（FrameRenderer.cpp，全部 fragment pass，中间纹理 RGBA16F）**：

- **P1 方向场**：五点修正高通（消常数/线性项，跨色对色偏不敏感）沿 V/H 轴向 + P/Q 对角各取相邻 3 行(列)平方和，一次输出 `tex_dir_` 四通道方向统计；P2/P3 复用，避免重复全屏梯度扫描。
- **P2 G@RB**：CFA 低通图（十字½+对角¼）的**乘性比值**迁移轴向邻居（"Ratio Corrected" 得名处，硬边缘不过冲），梯度反比交叉加权；V/H 方向置信度连续混合，中心值比 3×3 邻域更不确定时改用邻域（噪声区防翻转）；G 结果限幅到四邻实测范围（伪彩抑制①）。
- **P3 色度填充 + CCM**：R/B 位补对侧色度、G 位补 R/B，全走"色差 + 方向加权"（色差带宽窄，天然低 zippering）；对角色差轴向/对角梯度交叉加权 + P/Q、V/H 方向混合；**色差限幅到邻域同色实测范围**（伪彩抑制②）；末级 CCM → 场景线性汇流 pass2/3。
- WB 在线性化时前置（色差恒定假设要求白平衡域，PhotonCamera 同款处理）；边界 texelFetch clamp。

**产品与度量**：

- 质量档：`prefs demosaic_quality`（默认 RCD 质量档），设置页「RAW 去马赛克」行切换 RCD/快速（bilinear 保留为 A/B 基线与速度档）；`submitRaw` 签名加 `demosaic` 参数贯通 Kotlin→JNI→引擎。
- `raw.render` 日志新增 `demosaic`("rcd"/"bilinear") 与 RCD 路径分段 `dirMs`/`gMs`（各插一次 glFinish，真机定位 pass 瓶颈用）。
- shader 静态校验 8→**11 条全通过**；构建+单测全绿。

**真机验证项**（下一窗口）：M 档拍摄看 `raw.render`（12MP ≤900ms 出口基线，RCD 预算 ~250–400ms）；RCD vs bilinear 同场景 A/B（高频细节、边缘伪彩）；DNG Lightroom 打开确认（M2 尾巴）。

- **降噪**：业界 SOTA 已转向轻量 NN + 物理噪声模型（AIM 2025；CVPRW 移动端 NN RAW 降噪先例），传统引导滤波/NLM 高 ISO 明显落后；移动端夜噪的一流解是多帧合成（HDR+ 路线，PhotonCamera 的 stage0-3/pyramidalign/fusion 是完整开源参照）。**M3 先落传统 RAW 域方法守住 ≤900ms 预算**；NN 降噪与多帧融合列为 **M6 后立项评估项**（冲计算摄影第一梯队的门票，需 NNAPI/NPU 可行性预研）。
- **胶片色彩**：现代开源色彩科学 = darktable Filmic RGB / AgX / OpenDRT 一系（norm-controlled 色调映射、对比与饱和解耦、高光 rolloff 保饱和）——自研 film curve 与其有系统差距，M3 补 norm-controlled 高光处理（思路自研实现）；风格层维持「中性基准 + LUT」架构，M4 LUT 引擎直接吃社区胶片资产（G'MIC 1100+ 预设、Hald CLUT 库）；Filmulator（显影物理模拟）为 M3/M4 质感方向参考。
- **一流水平边界（如实结论）**：M 档体验 / RAW+DNG 正确性 / GPU 单帧性能 / 胶片风格层 → 可达开源一流；夜景高 ISO（多帧）与学习型算法 → 按现计划与 GCam/Motion Cam 有代差，依赖 M6 后立项。

### M2-3 RAW 端到端（v0.5.20-m2）：RAW_SENSOR 采集 + DngCreator 底片 + 引擎 submitRaw 胶片链

- **DNG 底片**：`DngCreator(characteristics, result)` 直写 MediaStore（MIME `image/x-adobe-dng`，API<29 落 app 目录）；`setOrientation(sensorOrientation)` 交第三方 Raw 软件转正。**口径既定：DNG 只含 HAL 元数据（asShotNeutral/黑阶/CCM 全在其中），用户手动 WB 的引擎补偿不进 DNG**。
- **引擎 submitRaw**：u16 Bayer 上传 `GL_R16UI` 整型纹理（`GL_UNPACK_ROW_LENGTH` 处理 rowStride 对齐；texelFetch 无过滤，绕开 X300 16F 无线性过滤 quirk）→ shader 内黑阶扣除（`SENSOR_DYNAMIC_BLACK_LEVEL` [R,Ge,Go,B] 按相位重排，`blackLevelPattern` 兜底）→ 白阶归一（dynamic → characteristics）→ WB（`SENSOR_NEUTRAL_COLOR_POINT` 倒数 G 归一；缺失回退 AWB 实时增益估计，再兜底中性）→ **bilinear demosaic**（CFA 四相位通式：自身/双邻加权/4 邻/4 角；X300 主摄 GRBG、id5 GBRG 皆支持）→ CCM（`COLOR_CORRECTION_TRANSFORM` 行主序，缺失单位阵）→ 场景线性，汇流 pass2/3 胶片链 → JPEG（EXIF/质量/画幅裁切复用既有链路）。RAW 为线性传感器读数，pass1 无 pow(2.2) 展开（与 YUV 路径本质差异）。

- 预览不变（YUV/SurfaceTexture 路径）；WB 补偿照常作用于 RAW 胶片 JPEG 与预览。真机验收点：session_ready `stillFormat=RAW_SENSOR`、`dng.saved`/`photo.saved` 成对出现、DNG 可被 Lightroom 打开、胶片 JPEG 无偏色无拼图伪彩。

### 成像质量专项（v0.5.13-m2）：暗部截断/偏色/EXIF 修复 + 预设收敛

### 采集/UI 迭代（v0.5.11-m2）：跨镜头切换提速 + 轮盘惯性手感

第十三轮真机反馈（镜头切换卡顿；轮盘滑动手感不佳）：

- **切镜头资源复用**：原实现每次切换销毁重建 SurfaceTexture + OES 纹理 + ImageReader，渲染端还要重新绑定纹理源——改为跨镜头复用（新镜头 preview/still 尺寸不匹配时才重建，SurfaceTexture 用 setDefaultBufferSize 适配），切换期间渲染端持续输出最后一帧（画面冻结而非黑屏），新会话首帧到达即恢复。
- **重开串行化**：setFocal/setLens/setZoomEquiv 的跨镜头路径改为 `stopInternalKeepClient(lens.id)` 记 pending，旧设备 `onClosed`（Surface 已释放）后才 `openCamera`——消除新旧 session 抢 Surface 的窗口，也避免先开后关的资源冲突。
- **覆盖则留 + 双向迟滞（无缝变焦）**：目标等效焦段落在当前镜头数码范围 [equiv×0.97, equiv×maxZoom] 内时留在当前镜头（zoomRatio 撑住）——主摄数码变焦撑到上限才切长焦，与缩小方向的切换点（长焦 1x）自然错开，拖动在切换点附近抖动不再反复重开会话；超广不数码延展（小底裁切画质差）。仅 setZoomEquiv（轮盘/捏合连续变焦）适用；点焦段条（setFocal）保持显式切镜头语义。
- **轮盘手感**：拖动只写 wheelFrac 普通状态（手势 scope 是 restricted suspension），变焦请求经 snapshotFlow 按帧节拍派生（触摸 120Hz → setZoomEquiv 每帧至多一次）+ 0.2% 量化防 rebuildRepeating 刷屏；松手按惯性滚动（EMA 估速 + 指数衰减 τ≈220ms + 端点即停），fling 停止后收起轮盘。

### 采集/UI 迭代（v0.5.10-m2）：半圆变焦轮盘 + 缩小跳变根因修复

### 采集/UI 迭代（v0.5.9-m2）：WB 改引擎侧补偿 + 倍率基线主摄 + 自定义焦段 + EV 自适应范围

第十一轮真机反馈（WB 列缩放仍无效；倍率与 EV 语义问题）：

### 采集/UI 迭代（v0.5.8-m2）：WB 列缩放修发绿 + 倍率显示修复 + 长按轮盘变焦

第十轮真机反馈：

### M1 追加修复（v0.3.5）：预览双重裁剪 + 静拍旋转/镜像 + 关页崩溃

- 预览「压缩拉伸」根因：**STMatrix 已含生产者裁剪/翻转，引擎又叠加自算 center-crop（按名义 1440×1080 算出 0.56 水平裁剪）→ 双重裁剪 → 横向拉伸**。修复：预览完全不自行裁剪（sx=sy=1），几何完全信任 STMatrix。
- 静拍「旋转 90° + 镜像」根因：① CPU 帧是传感器原始方向（未旋转，X300 sensorOrientation=90），静拍旋转需 = 界面方向 + 传感器旋转（+1）；② 普通 RGB 纹理 (0,0) 在左上、OES 在左下，静拍 shader vUV0.y 取反对齐 OES 习惯。两修正合成恰为原缺陷（转置）的逆变换。
- 关页 `updateTexImage` 崩溃：stop 后迟到帧回调仍到达，RenderClient 加 `acceptingFrames` 门闸。
- X300 方向结论固化：预览界面方向 0 正确；静拍 = 0 + 传感器 1。

### M1 追加修复（v0.3.6）：后台恢复黑屏（生命周期）

- 根因：启动依赖 Compose `LaunchedEffect(surface)`（对象相等性 key）——部分系统（OriginOS）后台恢复时不产生新 Surface 实例或只回调 `surfaceChanged`，启动不触发 → 停在已销毁的 GL 环境 → 黑屏。
- 修复：surface 回调内**直接调用** `controller.start`（幂等）；新增生命周期感知（ON_PAUSE stop / ON_RESUME 重启）；`surfaceChanged` 兼作拉起点；埋 `lifecycle.pause/resume`、`surface.created/destroyed` 日志确认设备回调序列。

### M1 追加修复（v0.3.7）：静拍画布交换缺失 + 帧闸竞态

- v0.3.7 X300 用户验收：**预览/拍照/方向/颜色/比例/后台恢复全部正常，M1 ✅ 完成**。
- X300 沉淀的驱动/系统 quirk 清单（已指导后续里程碑）：RG8 TexSub 静默失败（弃用，SurfaceTexture/CPU 转换替代）；16F 无线性过滤（NEAREST）；RGBA8 纹理类型必须 UNSIGNED_BYTE；坐标原点差异（OES 左下 vs 2D 左上）；STMatrix 为几何权威（勿叠加自算 crop）；参数数组沉默零值（引擎侧防呆兜底）；Surface 生命周期（回调内直接启动 + 生命周期感知，勿依赖对象相等性）。

- v0.3.6 验证：预览与成像方向正常，但**照片 4096×3072 且内容压扁**——`photo.saved w=4096` 暴露：静拍采样旋转改为「界面方向+1」后，输出尺寸的横竖交换仍用旧值，竖向内容旋转 90° 后塞进横画布。修复：swap 判断与采样统一用 effective rotation（C++ 与 Kotlin 两侧对齐）。
- 后台恢复黑屏（二轮）：日志显示恢复会话引擎/相机全部正常启动但**无 first_frame** → 帧被静默丢弃。根因：`pending` 排队闸竞态——stop 期间帧任务 post 失败（线程退出中）时 pending 永久卡 true，新会话所有帧被丢。修复：post 失败回滚 pending + stopInternal 结束时强制复位。
