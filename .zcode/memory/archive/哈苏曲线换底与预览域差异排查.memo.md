# 哈苏曲线换底与预览域差异排查

## Summary

本窗口从"天空观感仍过饱和"出发，先把高光去饱和区间按**成片反推的实测分布**重标定（v0.6.45），再修自适应影调（v0.6.46）；随后排查用户报的"预览过曝、成片正常"，定位到**预览走 HAL 的 OES 流、静拍走 RAW 链，两条源的线性亮度差 1.70–3.87×**，经三版迭代改为预览直通（v0.6.47/48）。用户随后建议"参考 PhotonCamera 的哈苏基础影调"，据此扒出 **HNCS 引擎的完整实现**，发现我们的 `baseTone` 暗部比哈苏低 **565×** —— 这是所有翻车的总根源，于是**换底**：曲线改成哈苏形状的 Reinhard 形式（v0.7.0），再按对标结果压暗恢复对比度（v0.7.1）。

## Done

- **v0.6.45 天空去饱和重标定**（`117c605`）：`smoothstep(0.40,0.75)` → **(0.32,0.60)**。旧区间实测只触发 **7.7%**（成片逐像素反推得天空 n0 中位 **0.460**，P10 0.397/P90 0.599，距起点 0.40 仅 0.06）。新区间使天空 C\* 24.55/18.80 → **14.15/8.55**（PC 哈苏 14.08/9.47），中间调 n0 中位 0.148 → w=0 不受影响
- **v0.6.46 自适应影调重标定**（`691b060`）：`kTarget 0.38→0.26`、`kMax 1.9→3.0`。双场景 ag 扫描：室外需 ag 1.2（实际 1.576，过亮 19/255）、阳台逆光需 3.0（实际 1.9 打满，欠曝 43/255）。根因是 `gain=kTarget/lin_mid` 是**前馈**，而 S 曲线在 mn=0.2184 以下压暗、以上提亮，同一 gain 在暗/亮场景效果相反
- **预览过曝排查与修复**（`ce76c3c`/`0411a14`/`142b2c9`）：加 `preview.ag`/`raw.render.linMid` 观测后定位 —— **预览的 OES 流已被 ISP tone 过**，同场景同曝光（pvSec/stSec 逐位相同）下线性中位是 RAW 链的 **1.70×（室外 0.410 vs 0.241）/ 3.08×（阳台 0.274 vs 0.0891）/ 3.87×（0.310 vs 0.0801）**。截图实测预览中位 **225/255 vs 成片 161/255**。v0.6.47 先放开增益下限（1.0→0.35）使中位对齐（154.5 vs 154.3 ✓），v0.6.48 再加 `uPreviewBypass` **预览直通**（HAL 流是 8bit 显示域，套 baseTone 会**压 59×**：pass1 0.0174 → pass2 0.000295，暗部死黑 11.4%）
- **v0.6.49 室内两修**（`306f605`）：① **去饱和加色度保护** —— max 通道判据把"单通道高的浓色物体"误判成高光（红杯 R 高但 G/B 低，**根本没过曝**），室内 n0 中位 0.357（远高于室外 0.148）使区间正好压在中间调；按 `rel=max|cc|/luma` 保护（>0.45 衰减、0.85 全保护）② **ag 高光淡出** —— 全局增益在暗场景打满 3.0 会把局部亮区推过滚降白点（实测 n0 P90 0.399×2.386=0.95 > 0.80）
- **v0.6.50 高光发红修复**（`82f7ca2`）：v0.6.49 的保护**只用 rel 一刀切**，把台灯灯管也保护了（R/B 饱和、G 未饱和 ⇒ rel 高）→ 灯管保持粉紫，**重现 v0.5.37"过曝灯泡变红"的老 bug**。DNG 重建把两者分开：灯管 luma **1.04** / RGB (1.49,0.83,1.84)，红杯 < 0.4 → 加 luma 门限
- **v0.7.0 换底**（`ce3f5f9`）：`baseTone` 从"S 曲线 + blk=0.008 黑点"换成**哈苏形状的 Reinhard 曲线** `y=(1+k)x/(1+kx)`（k=5）；`kTarget 0.26→0.07`；增益下限静拍也放开到 0.35
- **v0.7.1 压暗**（`af4cead`）：`kTarget 0.07→0.04`（显示中位 150→123），恢复明暗对比
- **扒出 PhotonCamera HNCS（哈苏）引擎**（见 Pitfalls/Refs）：`HncsToneAlgorithm.kt` 的 `applyEngineTone` 只有三步（YCbCr 色彩映射 + **逐通道 65536 项胶片曲线** + gamma），**没有高光去饱和**；`FILM_CURVE_GAIN = 1f` **固定不随场景变**
- **工具**（`test_temp/`，已 gitignore）：`whole_cmp.py`（全图分位/色相带对比）、`ag_scan.py`（成片反推 + ag 扫描，自检"原 ag 重放必须还原成片"）、`desat_scan.py`（反推 out3 + 去饱和区间扫描）、`preview_domain.py`、`sky.py`、`chain_probe.py`

## Decisions

- [2026-09-24] **基础影调换成哈苏形状的 Reinhard 曲线（k=5）** —— 我们的旧 `baseTone` 暗部比哈苏低 565×，是所有翻车的总根源。**不复制其数据资产**（`filmcurve_type6_companding2.hcurve` 来自哈苏专有 SDK；PC 的 Apache-2.0 只覆盖代码），改用标准数学形式自研参数化实现
- [2026-09-24] **`kTarget` 0.04 + 增益下限 0.35（静拍同样允许压暗）** —— 新曲线自带 2–4EV 暗部提亮，亮场景必须能压暗；旧链"只许提亮"在新曲线下会让亮场景过曝
- [2026-09-24] **预览直通（方案 A）**，域映射曲线（方案 B）留待后续 —— HAL 流与 RAW 链的域根本不同，线性增益无法同时对齐中位与暗部（ag 0.838 中位对/暗部 11；ag 1.95 暗部对/中位 195）
- [2026-09-24] **"打包成可切换的渲染引擎"（用户要求，待办）** —— 像 PC 一样把我们的做法与哈苏式做法各做一个引擎，设置里切换
- [2026-09-24] **曝光差异归属相机侧**（待用户定 A/B/C）—— 同场景对标显示 PC 用**低曝光**保住暗部再靠曲线提亮，我们是 HAL 的 AE 高曝光 + 曲线又提亮一次

## Pitfalls

- **判据用 `max` 通道 ⇒ 必然误伤"单通道高的浓色物体"**：红杯 R 高（n0 0.300）而 G/B 低（0.076/0.059，R/G=3.97），**完全没过曝**却被整段去饱和。v0.6.38 选 max 通道是为了让"B 通道高的天空"命中，代价就是这个
- **保护"浓色"与保护"过曝高光"是两件事，用 `rel` 一刀切会保护错对象**：灯管 R/B 饱和、G 未饱和 ⇒ rel 高 ⇒ 被保护 ⇒ 保持粉紫（v0.5.37 老 bug 重现）。必须加 **luma 门限**（灯管 1.04 vs 红杯 <0.4）
- **`ag` 是全局增益，暗场景打满时必然推爆局部亮区**：红杯 n0 0.300×3.0=0.90 → 显示 245；白水壶 0.215×3.0=0.65 → 229；而木桌只有 0.028×3.0=0.09 → 56。**一压一抬**（旧曲线压暗部 + ag 抬全局）是"室内糊了一层"的完整机制
- **旧 `baseTone` 的暗部压缩是 565×**：x=0.01 哈苏 0.0455 / 我们 0.0001；x=0.05 → 0.2700/0.0120（23×）；x=0.10 → 0.4380/0.0478（9.2×）
- **预览与成片不是同一条源**：预览走 HAL 的 OES 流（已被 ISP tone 过、8bit 显示域），静拍走 RAW 链（14bit）。**同场景同曝光下线性中位差 1.70–3.87×**，且预览的动态范围已被 ISP 花掉，再套 baseTone 会压死暗部 —— 这是"预览无法 WYSIWYG"的根，不是参数问题
- **"按单张/单场景标定"本窗口又犯了两次**：去饱和区间按单张反推定、ag 按两个场景标定 —— 换场景即翻车。**判据取值必须来自跨场景实测分布**
- **成片反推法对过曝区域失效**：`rolloff_inv` 的 `valid` 掩码会排除完全趋白的像素（信息已丢失），所以 P95/P99 反推值不可信（会出现 4.000 的截断值）
- **自检能抓出真 bug**：本轮靠"用原参数重放必须还原成片"抓到两处 —— `rolloff` 漏了源码的 `if (l <= knee) return c;` 分支（暗部被 knee=0.8 顶亮）、外观层判据取自**输入**而非输出（需迭代解增益）

## Next

1. **等用户定曝光方案**（A 加 AE 补偿 / B 保持现状 / C 先手动拉 EV 验证）：引擎侧只能压 tone（v0.7.1 已做），要真正"暗的地方暗"需降低 HAL 的 AE 曝光
2. **预览域映射曲线**（用户定"先 A 后 B"）：把 HAL 线性映射回 RAW 等效域以恢复 WYSIWYG。`preview.ag` 与 `raw.render.linMid` 日志持续记录配对，现有 3 对中两对非单调（0.274→0.0891 / 0.310→0.0801），**需 6–8 对跨亮度场景**才能拟合
3. **打包成可切换的渲染引擎**（用户要求）：我们的引擎 / 哈苏式引擎，设置里切换
4. **去饱和区间 (0.32,0.60) 需在新曲线下重标定** —— 该区间是旧曲线时代的取值
5. **真机复核 v0.7.1**：重点看暗部是否通透、白色物体是否有质感、红杯是否够红；并注意 kTarget 0.04 让所有场景（含此前认可的室外/阳台）一起变暗约 20%
