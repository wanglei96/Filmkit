# 拍照独立线程落地与连拍崩溃定案

## Summary

拍照侧「独立线程 + 独立 EGL context」按 PC 同构重做并落地（开关默认关、失败回退、
空闲释放 2GB）；**连拍闪退定案**：Java 堆 OOM 发生在 JNI 回传成片处，pending
exception 未清 → ART 直接 abort（tombstone 有、crash-latest 无），largeHeap +
ExceptionCheck 修复后连拍 7 张全成功、零丢失。同帧 A/B（CRC32）证明独立线程与
预览线程的成片**逐字节相同**。帧率尝试（DFT 分片 / glFlush / 真 sleep / 线程降
优先级）四种调度手段**全部无效且负优化**，已完整回退；卡顿定性为 GPU 资源硬约束，
下一步靠"用现成开关做瓶颈定位"，不再在调度上投入。

## Done

- **0.10.85 独立线程重做**（对照 0.10.83 的失败）：`StillRenderClient` 单例、线程
  与实例**只启动不销毁**、所有 native 调用排在同一条 Handler 队列串行；native 侧
  独立 `EglCore` + `FrameRenderer` + 1×1 pbuffer；`use_still` 路由三条静拍入口；
  `startAsync` 与 burst 采集并行预热；失败回退预览线程；崩溃前关键节点强制 flush。
- **0.10.85 同帧 A/B（prefs `still_ab`）**：同一帧数据跑两遍（still 线程 / 预览
  线程），companion 级 `outDigest`（CRC32 + 16×16 采样）比对 →
  **`same=true`、crc 3615113902 vs 3615113902、均值 109.455 完全一致**；
  两张 `raw.render` 的画质指标（p0w 19.093、nzPreMed/nzPostMed）也逐项相同。
- **独立审查后修复六项**：A/B 第二遍 post 到已退出的 looper 致"成片已算出却不落盘
  + 在飞计数永久泄漏"（RenderClient 三个提交函数补 post 失败回调）；预览路径失败
  静默（补 `render.raw_burst_failed` 等）；`g_renderer_still` 跨线程读改写
  `std::atomic`；`nativeEngineSetYuvMatrix` 的既存 UAF（改进程级快照 + start 下发）；
  CameraController 持 Activity context 泄漏（改 `applicationContext`）；
  `preview_gap` 阈值 250→400ms（避开采集期正常停顿）。
- **0.10.86 连拍崩溃修复**：`largeHeap` + `rgbaToJavaArray()` 的 `ExceptionCheck`
  防护（清异常 + 返回 nullptr）。修后连拍 `burst[still]` **7 张全部成功**、
  `queued=4/saved=4` **零丢失**、`capture.busy` 正常拒绝第 3 张。
- **0.10.87 帧率诊断**：`render.fps` 每 5 秒一条（数组 = 逐秒**实际渲染**帧数），
  把"轻微卡顿"变成数字：空闲 30~32fps、拍照期间最低 13~25fps。
- **0.10.88/89 空闲释放**：拍完 10s 无任务则销毁拍照实例。首版只销毁
  FrameRenderer（保留 context）→ **重建后首次合成失败**（`raw.upload_failed`：
  同 context 内反复建/销全分辨率纹理后 Mali 的 `glTexImage2D` 分配失败），进而
  回退预览线程造成 3.4s 停更；改为**连 context 一起销毁** + 失败自愈（重建重试
  一次）。修后实测：释放→重建→首次合成直接 `ok=true`，无回退、无停更。
- **0.10.90~0.92 让路实验与回退**：DFT 分片（64 段）+ `glFlush` 无效；再加真
  `usleep(2ms)` + 成片链 5 个 pass 让路 + 合成线程降优先级 → **负优化**
  （totalMs 5133 vs 2091、最低 fps 20 vs 27）。全部删除，引擎侧 diff 归零。
- **工具**：`tools/still-thread-verify.py`（按 `settings.still_thread` 切换点分组，
  输出预览停更 / 每路 burst 中位耗时 / CRC 等价 / 落盘计数 / 帧率曲线）、
  `tools/still-thread-run.sh`（install / pull+分析 / meminfo）。
- **入库**：`bd37095`（功能）+ `0a2801c`（工具），已 push。

## Decisions

- [2026-10-01] **拍照侧实例只启动不销毁**：0.10.83 的根因是"stop 时旧线程仍在跑
  合成，新线程复用同一实例"，本版**取消整条销毁路径**，从根上消除竞态。
- [2026-10-01] **空闲释放要连 context 一起销毁**：只销毁 FrameRenderer 会让 Mali
  在建/销后分配不出全分辨率纹理；整条重建与"首次启动"同构（实测首次 59ms、
  重建 67~98ms，代价相同）。
- [2026-10-01] **进程级设置必须能被后建实例补齐**：LUT / YUV 矩阵走快照，
  `nativeStillStart` 与 `nativeEngineStart` 里下发——否则独立线程拍出的照片会
  静默丢掉风格层（画质红线）。
- [2026-10-01] **largeHeap 作为连拍内存兜底**：MFNR 每张在飞要持 4 帧 direct
  buffer（100MB），而 `ByteBuffer.allocateDirect` 走 `trackExternalAllocation`
  **计入 ART 的 OOM 额度**；在飞 2 张 200MB + 成片回传 50MB 撞默认 256MB。
- [2026-10-01] **OOM 时"这张失败"优于"进程 abort"**：JNI 回传加 ExceptionCheck
  防护 + 失败自愈重试一次，仍失败才回退预览线程（用户红线：失败不以丢照片为代价）。
- [2026-10-01] **调度类优化在本平台不再投入**：分片 / glFlush / sleep / 线程优先级
  四种手段全部实测无效（Mali 不在 context 间轮转命令流），sleep 还拉长卡顿窗口 →
  帧率问题定性为 GPU 算力/带宽硬约束，改走"定位主因 + 按主因优化或降预览负载"。

## Pitfalls

- **Java OOM 会绕过 Java 崩溃捕获**：OOM 发生在 JNI `SetByteArrayRegion` 里 →
  pending exception 未清 → ART abort（`Fatal signal 6 in tid FilmStill`）。
  `crash-latest.txt` **不会更新**（那份还是 0.5.6-m2 的陈年记录），只能靠
  `adb logcat -b crash/events` + tombstone 定位。排障时"文件没更新"≠"没发生"。
- **direct buffer 计入 ART 额度**：OOM 消息 `target footprint 248965720 (237MB) /
  growth limit 268435456 (256MB)`，而 Java 侧只有 direct buffer 在涨 ——
  `ByteBuffer.allocateDirect` 的外部内存**照样吃 OOM 判定**。
- **同 context 内销毁重建 FrameRenderer 会让 Mali 分配失败**：表现为
  `raw.upload_failed`（`glTexImage2D` 4080×3072 R16UI 失败）→ 合成失败 → 回退。
  注意 `uploadRawTex` 的 `glGetError()` 会抓到上一步 `ensureRawTex` 留下的错误，
  报错位置会骗人。
- **Mali 不按 context 轮转**：DFT 分片开/关的 `dftGpu` 几乎相同（881/904 vs
  855/922），帧率也没变 —— `glFlush` 交出去的活照样排队。**真 sleep** 能让出但
  代价是合成变慢、卡顿窗口拉长（用户体感"关掉开关反而更好"，数据证实）。
- **性能结论必须同条件对比**：本轮 `totalMs` 5133 vs 2091 的差里混了冷热机
  （首次合成 vs 热机），先用同条件数据才敢下"负优化"结论。
- **别在调度上反复试**：四轮实验证明方向错误后，正确动作是回退 + 换定位手段
  （用现成开关做瓶颈定位），而不是继续微调参数。

## Next

1. **瓶颈定位实验**（方案已交用户，用现成开关各拍一张）：基线 / 降噪强度→0 /
   去马赛克→bilinear / MFNR→关；看哪一项让最低 fps 回到 28+，主因就在哪
   （MFNR 四帧链路 / RCD 三段 / P0·P4 降噪）。
2. 按定位结果三选一：**A** 拍照期间降预览分辨率（成片无损、取景可见变糊、最快
   见效）/ **B** 针对主因做 GPU 优化（不动画质但需 A/B、周期长）/ **C** 接受现状
   （已从"完全冻住 1~2 秒"改善到 20~27fps）。
3. 遗留：**单帧 RAW / YUV 静拍路径仍在预览线程**（本开关只覆盖 MFNR），迁移时
   注意 YUV 矩阵也要同步给拍照实例。
4. 可选：把 `render.fps` 扩展成帧耗时 p50/p95（区分"帧变慢"与"帧被丢"）。
