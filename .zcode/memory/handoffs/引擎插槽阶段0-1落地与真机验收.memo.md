# 引擎插槽阶段0-1落地与真机验收

本窗口从 `/recall` 载入「引擎切换调研与插槽方案定案」后，完成了**引擎插槽重构的阶段 0 与阶段 1**（`[98] engine_slot` 契约 + `EngineRegistry` 骨架 → `kFsFilm` 三段拆解 + 引擎注入段），并补上了阶段 1 的前置阻塞项（离线执行器接 `kFsFilm` + PC3D）。出包 `filmkit-0.11.27.apk`（376 / 0.11.27）**真机验收通过**：`engine.film_src` 六条全为 `identical:true` / 35154 字节 / `0x4fa1ebd3`。**下一步 = 阶段 2（sigmoid 引擎）**，判据链已就绪。

## Decisions

- **阶段 1 用"单真源 + 运行时切片"，不物理拆三段字面量**：物理拆会让 25140 字符出现 3 处人为接缝 ⇒ 逐字节等价无法由构造保证；切片是连续区间划分 ⇒ 恒等是构造性的，且 `kFsFilm` 保持单一真源不会漂移。代价 = 锚点与注释耦合，锚点缺失时退回整体字面量 + `kError`。
- **`[98]` 是"第三种东西"**（进预设、拍照链路读、但不是可调参数）⇒ 新增 `CAMERA_ENGINE_SELECT_SLOTS`，**不塞进 `CAMERA_NO_SLIDER_SLOTS`**（后者语义是"是参数但暂无滑杆"）；靠 `fullEditReadonlySlots()` 里既有的 `it !in CAMERA_PATH_SLOTS` 天然挡在参数面板外 ⇒ **零 UI 变化**。
- **离线链缺口优先于阶段 1 开工**（A 方案）：不接受"用部分链的绿主张整链零回归"。
- **阶段 1 的判据口径 = `film_d5.npy` 的 CRC32**（默认 `0x589f8364` / 白点 4.0 `0xd46d7b5e`），**成片零回归仍需真机同帧 A/B**（HR/`uLocal*`/`kFsOut`/MFNR 不在离线链内）。
- **`engine_slot != 0` 的降级必须显式**：`engine.slot_unavailable` WARN（atomic 去重）+ 回落引擎 0，不静默、不崩、不做 identity 伪装（契约 5）。

## Pitfalls

- **扩一个契约槽位会牵动 8 个守卫，且它们各自钉着"里程碑事实"**：`[98]` 一进 `CAMERA_PATH_SLOTS`，红的不止 1 条 —— "U-2 起单侧槽位数必须 = 0"（5 条）、"只读组 == NO_SLIDER 全集"（2 条）、"可拖 == PATH − NO_SLIDER"（1 条）。**正确修法不是改数字，而是升级为"与文档矩阵 §1.6 一致"**（强度不变、不硬编码）。
- **架构师的结构推断会被实测推翻**：我预判"98 塞进 `CAMERA_NO_SLIDER_SLOTS` 后守卫仍绿（有别的过滤挡住）"，实测**变红** —— 该集合在 `fullEditReadonlySlots()` 里是**无条件并入**的。**派卡给的"预期结果"要标明是推断，并要求执行者用实测覆盖。**
- **验证工具自身会假绿，只有负向自检能抓**（本阶段抓到两条）：① 只锚"整体摘要"抓不到切分点整体偏移（边界行都是注释）⇒ 必须**块级锚点**；② `validate-shaders.sh` 的"真拆"形态里逐段过滤 `#version` ⇒ filmic **实际未校验**（glslang 对缺 `main` 不报错）⇒ 必须**先拼回整份再判断**。
- **字符数 vs 字节数口径混淆**：`kFsFilm` 是 496 行 / **25140 字符** / **35154 字节**（UTF-8 中文注释）。我派卡时写成"25140 字节"⇒ C++ 自检（`std::string::size()`）会误报不等。**给判据值必须标口径。**
- **文件头注释会撒谎**：`tools/engine-shader-offline.py` 头部写着"已接入 4. FILM kFsFilm"，实读 295 行**没有 FILM 段**（只到 CCM）⇒ 阶段 1 的核心判据差点建立在不存在的 pass 上。
- **PC 源码路径的包名不是仓库名**：`bjzhou/PhotonCamera` 的包名是 **`com.hinnka.mycamera`** ⇒ `DarktableSigmoidToneAlgorithm.kt` 在 `/tmp/pc-tone/app/src/main/java/com/hinnka/mycamera/raw/`。**按 `com.bjzhou.*` 去找会找不到。**
- **子代理会如实上报"与架构师预期相反"**（本窗口两次），这是最该鼓励的行为；架构师必须以实测为准并公开更正自己的推断。

## Next

1. **阶段 2 开工：加引擎 1 = sigmoid**。落点：`EngineRegistry` 表加第二项（`{1, "sigmoid", <working_space>, <ExposureDomain>, <defaultEV>}`）；阶段 1 的 `filmSlices()`/`filmSource(slot)` **已预留注入点**（`engine_def` 与 `engine_main` 两个位置），只需让 `filmSource(1)` 返回"公共三段 + 引擎 1 的注入段"。
2. **读参照的顺序**：先读我们自己的 `docs/research/16-影调科学前沿与自动白点.md`（懂原理与公式）→ 再对照 PC 的 `/tmp/pc-tone/app/src/main/java/com/hinnka/mycamera/raw/DarktableSigmoidToneAlgorithm.kt`（140 行，含 `DT_SIGMOID_PAPER_EXPOSURE = 0.354355423` / `DT_SIGMOID_FILM_FOG = 0.00142637086`）→ 需要时联网读 darktable `sigmoid.c`（**本地无 darktable 源码副本**）。
3. **CPU 侧新增 `computeSigmoidParams(contrast, skew, displayWhiteTarget, displayBlackTarget)`**：由三锚点解析求解（~20 次 pow，亚毫秒），取代引擎 1 路径上的 `computeFilmicSpline`；`FilmicSpline` 结构体不删（引擎 0 仍用）。GLSL 侧 = generalized log-logistic + 负值去饱和 + per-channel hue preservation。
4. **判据 = 方案 §7 五条**：① 可分辨跨度 ≥ 引擎 0（**同白纸亮度口径**）② 中灰 0EV 偏差 ≤ 1.3 LSB ③ 线性域严格单调（数值扫描无平台段）④ 真机 A/B（白瓷/釉面红杯/白墙逆光/阴天天空/暗光室内/高饱和红光 × 3 曝光）⑤ **`engine_slot=0` 时 `film_d5.npy` 仍为 `0x589f8364`**（阶段 1 基线不得被阶段 2 改动）。用 `python3 tools/engine-shader-offline.py --verify-splice` + `--dng test_temp/FILMKIT_20261009-090803.dng --roi 1800,2100,600,1000` 复跑。
5. **待用户点头两项**：判据口径写死（「可分辨跨度」= 从白纸起每 0.1 EV ≥1 LSB 能持续多远）；公共工作空间切 Rec.2020 **单独一期**（与 10bit HEIF 交付链配套，不可与插槽重构同期）。
