# 引擎切换调研与插槽方案定案

## Summary

针对"黑白点反复真机调也找不到平衡点"发起的**换渲染引擎**专项：6 份调研报告（6 张卡 + 1 张独立复核；其中 3 张卡预算耗尽失败后重派并加"增量落盘"纪律）+ vivo X300 真机引擎取证 + `docs/engine-slots-design.md` 方案。**用户拍板：引擎切换要做、第 2 步直接对齐 PC、交付上 10bit HEIF**。核心结论：白点难调是 **filmic 参数化缺陷**（非调参水平）；工业界两个独立样本（vivo / Google）都把"自适应"与"外观"**分层**且成片路径零 NN；引擎插槽是把黑白点搬出公共管线的架构解。

## Done

- **调研（6 份报告，`docs/research/12–17`）**
  - **12 神经 ISP**：工业界形态 = 传统主链 + 旁路小模型 + 统一推理运行时（真机 `libvdnn` 被 20 模块引用；`libcamalgo.mfnr` 与 `libainr` **并存** = 加旁路非换主链）；**生成式（扩散）不做**（算力差两个数量级、幻觉 IoU 0.86→0.36、控制粒度仅 1 标量）；路线应是"**参数预测式**"而非"像素输出式"。
  - **13 学习型影调**：PC 的 HDRNet PGTM = 输入 `[1,192,256,4]`（第 4 通道为引导）→ 输出 `[1,12,16,8,1,2]` **bilateral grid 系数**（3072 floats，钳 [0.03,30]）→ **烘焙成 DNG `ProfileGainTableMap2`，成片路径零 NN**；权重是**逆向提取的 Google 专有资产（不可复制，只能自训练）**；`MGC` = **魔改 GCam**。`recipe-fit.py` 是"真引擎 in-the-loop"（clang++ 编译引擎函数体）。
  - **14 vivo 真机取证**（架构师接手完成）：相机 APK 396MB 内**无 .so**（native 外置 81 库）；app 层是 **ACES 式 GLSL 管线**（`OETF(OutputTransform(NormalizeLuminance(ToneMap(ScaleLuminance(InputTransform(EOTF(x)))))))`）+ **模式枚举** + 33³ f32 LUT（自有容器 `CUBEB2BIN8`）；**全量 dex 扫描：`autoTone` 0 命中、`histogram` 全是 UI ⇒ app 层无自适应影调**；自适应在 **HAL/3A 层**（`HDRStateEvaluator`、逐传感器 `chromatix`、`aiawb_params`；`/vendor` 未 root 读不到）。
  - **15 引擎架构**：PC 引擎 = **1 pass** + 5 方法接口 + shader **字符串注入公共模板** + **输出契约线性 sRGB**；Fuji 引擎下线 = 33 文件 + Room DB v49→v50（引擎私有参数不能进 DB）；框架建议 GLES 留用 / Vulkan 期权 / Halide 只离线。
  - **16 影调科学**：根因 = `output_power` 由白点算出（darktable `_compute_output_power` ≡ 本仓 `derive_power`，17 号证实 float32 逐位相同）；候选架构 = **sigmoid / ACES 2.0 tone scale**（白点参数从架构中消失）。
  - **17 独立复核**：修正 16 号量级 —— 统一白纸 204 LSB 后优势从 0.7~1.05 EV 缩到 **0.25~0.30 EV**；**判据阈值一换排序就翻转**；**filmic 的 plateau 是连续不可逆（任何位深都救不了）⇒ 这才是换架构最硬的理由**。
- **方案 `docs/engine-slots-design.md`**：`kFsFilm` 三段拆解（公共前段 / 引擎段含 gamut / 公共后段）、`[98] engine_slot` + 引擎私有 KV、引擎注册表（C++/Kotlin 对称 + 测试守卫）、4 阶段 + **CRC32 零回归判据**、ACES 预留接口。
- **真机与仓库素材**：`/tmp/x300-samples/`（vivo 81 库 + 10 dex + 8 张 LUT）；PC 全仓 clone（`/tmp/pc-tone`、`/tmp/pc-arch`、`/tmp/pc-forensics`）；复核脚本 `/tmp/verify-tone/`。
- 提交 `57d10e6`（6 份报告）+ `d3f2203`（方案），已 push。

## Decisions

- **引擎切换要做，第 2 步直接对齐 PC**（公共管线 + 引擎插槽），不做最小改动版。
- **切口 = gamut 归引擎、外观层归公共**：gamut 是 darktable filmic v5 的一部分，留公共会让 ACES 被套一层 filmic gamut（双份色域处理）。
- **`FilmParams` 只加 1 槽 `[98] engine_slot`**（0 = 内置 filmic，默认 ⇒ 旧预设行为不变）；引擎私有参数走**独立有序 KV**；加/删引擎**不改槽位布局、不改 Room DB schema**。
- **交付位深上 10bit HEIF**（用户拍板）。连带：① 引擎需 10bit 输出路径 + HEIF 编码（现为 8bit `JpegEncoder.cpp`）；② 交付色域与公共工作空间联动；③ **10bit 只能救 sigmoid/ACES 的"量化不可逆"，救不了 filmic 的连续不可逆 ⇒ "上 10bit"本身要求换掉 filmic**。
- **判据改用「可分辨跨度」**（从白纸起每 0.1 EV ≥1 LSB 能持续多远）作主判据；若保留"死白起点"**必须写明阈值**。
- **公共工作空间推荐 Rec.2020 线性**（PC 的 sigmoid/AgX/filmic 即在 BT2020 域，可直接对照其参数；且是 HEIF 标准宽色域容器），但**必须单独一期**——换工作空间 = 整链处理域定义变化、所有预设重标，与插槽重构同期会毁掉零回归判据。
- 阶段 0–1 的硬判据 = **`[98]=0` 时同帧 CRC32 逐字节等价**。

## Pitfalls

- **子代理预算耗尽会断在收尾**：5 张卡中 **3 张**（神经 ISP、学习型影调、工业界取证）跑到预算耗尽、**报告一个字都没落盘**；重派时加"先落盘骨架 + 每节即存 + 限制搜索次数"才成功。
- **二手当一手的风险**：架构师曾判断 `MGC` 是"某商业相机引擎"，被取证卡用文件头注释纠正为**魔改 GCam**；真机有 `libarmnn.so` 但 Arm NN 官方已停维护 ⇒ **"库在机器上"≠"路线是活的"**。
- **判据口径会翻转结论**：死白起点阈值 ≤1 → ≤2，filmic 与 sigmoid **互换排序**；"每 0.1 EV 恰好 1 LSB"的**理想均匀曲线**在 ≤1 判据下被判"从起点就死白"。
- **离线链路缺 PC3D**：`tools/engine-shader-offline.py` 头部把 ESD3D2 列为未接入，但 `:126` 有 `--pc3d`，其 help 自述"需 LSC，**暂用恒等**" ⇒ 即使打开，LSC 也是恒等的。
- **项目记忆本身会过时**：`facts.md` 原记 `kCount=59`，实为 **98**（`FilmParams.h:35`）—— 方案/实现前必须 grep 核实，不能凭记忆。
