# 自适应影调回归中间调与降噪换径

## Summary

本窗口从"画面边缘有高光时中央被压暗"的现象出发，落地 **M4-7 局部色调映射**；随后在真机多轮迭代中把**自适应影调的判据来回改了 5 次**（P95 → 中位 → P95 → P99 → 中位），最终回到**中间调锚定** —— 因为用户点明该功能的职责是"**提中间调以提色彩**"（C\* 随 L\* 上升），不是"校正曝光正确性"。同期把 P4 色度降噪的职责从**值域阈值 σc 换到空间半径**，并修掉三个真机暴露的缺陷（关降噪反而慢 4–7 倍、局部低频图固定尺寸致预览/成片提亮尺度不一致、`raw.wait_result` 误报）。预览流上限 1440→2160。**全程未打 tag**，等验收。

## Done

- **M4-7 局部色调映射落地**（v0.6.25–28）：复用直方图那次 draw 渲染到低频图（等效半径 ~128px），判据用"**局部 / 画面基准的比值**"（绝对阈值在普遍欠曝的实拍里会退化成全局提亮）；只提亮不压暗（无 bilateral 的 halo，失败模式温和）；强度 `FilmParams[36]` + 设置页开关
- **亮斑修复**（v0.6.27/28）：真凶**不是**点采样噪声，而是**提亮量的空间分布过陡** —— "大面积白墙 235–242 + 暗桌面"把基准（局部图中位）抬到 180，于是 27% 画面满额提亮、另一半几乎不动。knee 0.7→0.6/1.3、强度 0.6→0.4；下采样改 8×8 盒式平均（`kFsLocal`）、上采样改手写双线性（不赌 Mali 过滤）
- **静拍 EMA 直通**（v0.6.29）：静拍只有一帧可渲染，用历史增益 = 用错曝光（同场景 2 秒内 `ag` 3.042→1.164；福字被推进 rolloff 去饱和区变粉白）
- **噪声回退与增益上限重标定**（v0.6.31）：`ag` 上限 4.0→2.0；`ns` 回退 0.030→按 ISO 估算；固定 `abiFilters arm64-v8a`（CMake 有时混入 x86_64，APK 39.2→28.2MB）
- **P4 降噪换径**（v0.6.32/33/36）：半径 2→3（7×7）、σs 1.6→2.2、σc 地板 0.015→0.008。**主力是半径**（见 Pitfalls）
- **三个真机缺陷**（v0.6.34）：① 关降噪反而慢 4–7 倍（`dirMs 232–244` vs 34–60）—— `dn=false` 时 P1 直读 R16UI 整数纹理自己解码；P0 的 `raw0()` 与 P1 的 `s()` RAW 分支**逐字相同**，故让 P0 无条件执行、`k=0` 只线性化中心像素（1 fetch vs 9，零细节代价）② `raw.wait_result` 每次拍照误报 WARN 且字段空 `{}`（正常竞态），改为静默 + 超 50ms 才记 `waitMs` ③ **局部低频图固定 32×24** 致预览（每格 38×67px）与成片（每格 128px）提亮尺度差 3.4 倍
- **预览曝光可观测**（v0.6.34）：`raw.meta` 加 `pvIso/pvSec/stIso/stSec` → **实测预览与拍照曝光完全一致**（2460/2466、59/59、65/65），排除"曝光不同"的假设
- **预览分辨率**（v0.6.37）：流上限硬编码 1440 → **2160**（两级回退）。成因：1440×1080 旋转后 1080×1440 **比渲染目标 1216×1621 还小 1.13 倍**，一直在放大显示
- **新增工具** `tools/chroma-denoise-eval.py`：从 DNG 重建 P4 输入域，横向评估"彩噪残余 / 真实色度边缘保留"

## Decisions

- [2026-09-23] **自适应影调判据 = 中间调锚定**（`kTarget 0.26`、`gain = clamp(0.26/lin_mid, 1, 1.6)`，`binAt(0.50)`）—— 职责是**提中间调以提色彩**，不是曝光正确性。C\* 随 L\* 上升，所以"提中间调"才是让色彩读起来是色彩的手段
- [2026-09-23] **上限 1.6 是真正的控制量**（用户能直接感知、也直接说出口的数）；目标 0.26 让绝大多数场景打满，仅当中位线性 >0.163（显示域 116）才开始降
- [2026-09-23] **P4 降噪职责归空间半径，σc 只负责保住真实色度边缘** —— 半径只压高频噪声、不动低频真实色度；σc 调大则连真实色度一起吞
- [2026-09-23] **关降噪也走 P0**（`k=0` = 仅线性化+WB），与 P1 直读 RAW 数学等价
- [2026-09-23] **参考实现的显示域数值不可直接当作"提亮前"的目标** —— 域的归属（提亮前/后）必须先确认
- [2026-09-23] **局部色调映射低频图尺寸随渲染分辨率**（每格 ≈128px，clamp 4..64），保证预览/成片同尺度
- [2026-09-23] **预览流上限 2160**（原硬编码 1440 小于渲染目标）
- [2026-09-23] **M 档 RAW 所见即所得预览 = 立项**（用户拍板"先不做"）：卡点是**性能非功能**（RAW 全链路 210–500ms vs 实时 <33ms，差 6–15 倍）；决定性未知量 = **X300 的 RAW 输出尺寸列表**（若只有 4080×3072，"小尺寸 RAW + binning 免 demosaic"这条捷径不存在）。LUT/预设**已在预览生效**（`submitFrame` → `passFilm` → `passOutput` 与拍照同一函数），缺的只是 RAW 链

## Pitfalls

- **判据类改动必须先问"这个功能的意图是什么"** —— 我按"曝光正确性"把判据改成 P99，丢掉了"提中间调为色彩"的原始意图，室外因此发灰。**手段（判据形式）与推导（目标值怎么来的）必须分开判断**：中位锚定的目标值推导错了（域混淆），但方向是对的，我把两者一起毙了
- **σs 不是旋钮**：循环半径锁死 r 时，σs 超过半径即被截断 —— r=2 下 σs 1.6→2.2 只改善 **6%**（σs=3.0/4.0 同样停在 6%）。降噪量要靠**放半径**
- **σc 调大是错方向**：旧值 0.035 在暗部是"真实色度差 0.014"的 2.5 倍、逐像素噪声 0.0033 的 10 倍 ⇒ 真实色度被当噪声吞（"桌面颜色偏灰"的一半原因）
- **提亮是噪声的乘性放大器**：`ag 2.0 × lt 1.6 ≈ 3.2×` —— "暗部更亮"与"彩噪更低"在物理上直接对立，只能靠降噪能力换
- **edge（边缘保留）指标必须两边都平滑**：分子分母若含原始噪声，会把"降噪有效的变体"误判成"抹色严重"（踩过一次，结论反了）
- **大尺度色度平滑的真相**：亮度细节保留 **1.000**（只动色差），但色度边缘只剩 **8–20%**（k=4，等效 8px）；且收益在 k=2–4 就饱和（k=8 几乎无增益）。所以"糊"不会表现为画面发软，而是**彩色边界渗色**
- **增量打包会残留旧 so**：APK 33.7MB vs 28.2MB，zip 条目已不引用但数据仍在（空洞检测可查出：条目 offset 之间出现 5.5MB gap）。出包前 `rm -rf app/build/outputs/apk`
- **系统默认 java 是 8**：AGP 8.13 报 `Dependency requires at least JVM runtime version 11`；用 `JAVA_HOME=/opt/homebrew/opt/openjdk@23`（已写进 README）
- **`controls.applied` 的 `iso`/`sec` 是滑杆存量值**，AUTO 档下不代表实际 —— 我曾据此误判"预览用 ISO 100"
- **记忆库过时条目会实际误导**：`facts.md` 的"最新 v0.6.23"、"自适应影调 `clamp(0.80/lin,1,4)`"、"P4 系数 2.20"三处与仓库冲突
- **"彩噪"的形态要分清**：放大看是**大块低频色偏**（场景固有，归一化后我们比 libraw 还小 22%，只是被提亮 3.6 倍才可见）而非细碎噪点；bilateral 这类高频工具对前者无效

## Next

1. **M 档 RAW 所见即所得预览 / 多帧融合（MFNR）立项** —— 先导一步：导出 `files/audit/camera-audit-*.json` 确认 **X300 的 RAW 输出尺寸列表**（`CameraAudit.kt:86` 已记录该数据）。有 2040×1536 之类则可做（binning 后每像素已全色、连 demosaic 都省），只有 4080×3072 则不可行
2. **提亮方式与强度再标定** —— (a) 若室外仍偏灰，把提亮从"乘性增益"搬到 **中间调曲线** `pow(y, g)`（增益会把高光一起推高：实测室外 P90 线性 0.745 已进 rolloff 去饱和带，参照只有 0.19）；(b) 现 `kTarget 0.26` 让绝大多数场景打满，"自适应"只剩很亮的场景起作用 —— 若要真正的场景自适应需重标定目标值
3. **验证预览 2160 是否被 HAL 接受**：看日志 `camera.session_ready.preview`；若仍 1440×1080 说明 SurfaceTexture 输出列表没有更大的 4:3 尺寸
4. **两件便宜的老活**：① 输出 OETF 改精确 sRGB 分段（⛔ 三处必须同步 `FrameRenderer.cpp:780` kFsOut / `:845` kFsHist / `:2013` 反解码，改完跑 `tools/validate-shaders.sh`）；③ 切镜头 AE 重置（`setFocal`/`setLens` 路径把 `auto_gain_` 置 0，复用"首帧直通"分支 + 死区）
5. **黄绿带色相偏差定案**（用户最初的"树叶绿不准"）：动手前须先定基准（灰卡/色卡或厂商同场景直出），libraw 不作绝对标尺
