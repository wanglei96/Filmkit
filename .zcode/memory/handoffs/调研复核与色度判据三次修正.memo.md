# 调研复核与色度判据三次修正

## Summary

本窗口从"先核验调研结论再执行"出发，独立复核发现四项修正里 **④ 完全错误、① 的机制被实测推翻、③ 需拆分**，并订正了报告与记忆库的误导性表述。随后把 ② 色度 S 曲线做了**三次修正**（域错误 → 亮度相对判据 → knee 定向调参），用 DNG + libraw 对照建立"缺口剖面"方法定案"淡在中间调弱彩"。v0.6.23 真机验收通过并打 tag 推送。

## Done

- **调研结论独立复核**（子代理逐条核引证 + 本人复算）：7 个源码树全部在本地且 commit 与报告一致；DNG 规范 p.57/51/63/64/79 逐字属实。**④ LUT 纹素中心校正证伪** —— 恒等 LUT 实测现行 `t=c*(N-1)` 与硬件 `texture()` 路径差 ≤2e-17（`texelFetch` 绕过过滤，`setLut` 的 `GL_LINEAR` 惰性），报告公式是 PhotonCamera `BasicToneLutShader.kt:20-22` 的**纹理坐标**补偿
- **① 的机制被实测推翻**：换 sRGB 分段后**中间调仅 +1.27/255**（"viewing gamma 治发闷"数值上可忽略）；原"喂 2.2 削弱 LUT"**反向**（喂 2.2 时 LUT 更用力：对比 +11.46/+14.80pp vs +5.41/+12.83pp）。真实收益＝**暗部压深**（−7.57/255 ⇒ 无 LUT 对比 **+9.87**、饱和 +2.01pp）＋域正确性
- **② 色度判据三次修正**（`core/engine/src/render/FrameRenderer.cpp` + `app/src/main/java/com/filmkit/app/ui/CameraPresets.kt`）：(a) knee `0.25→0.06`（域错误：0.25 线性 = 显示域 **136/255** 非注释所称 64/255；实测 99.8% 像素在 knee 下、中位仅得 0.5% 增益 ⇒ v0.6.19 的饱和度修正**实际未生效**）→ (b) 判据改**亮度相对** `rel=max|cc|/luma` → (c) `kRelKnee 1.0→0.4` + `FilmParams[33] 1.25→1.35`
- **建立 DNG 对照方法并定案**：用户提供三场景 + 5 张 DNG，libraw 出标准链（`use_camera_wb` + `no_auto_bright`）逐像素配对。**缺口剖面**（我们 rel/参照 rel）：低饱和 0.15–0.25 只有 **0.46–0.68**，高饱和 0.7–1.2 已达 **1.10–1.22** ⇒ 淡的是**中间调弱彩**。新剖面低饱和 **+9~23%**、高饱和仅 +8%、近中性 ≤3.6%
- **真机复验**（v0.6.23，5 张新样片 + DNG）：剖面 0.59/0.81/0.86/1.00 → **0.68/0.93/1.07/1.03**；五张 **clip 全 0%**；相对 auto_bright 平均 +2.2 L\*；树叶绿 C\* 由低于参照变为 **20.3 vs 15.8**
- **出包与发版**：`filmkit-0.6.21-m4.apk` / `-0.6.22-m4.apk` / **`-0.6.23-m4.apk`**（versionCode 103）；提交 `82d9f05`(engine) / `cbe2bc3`(docs) / `431fac4`(memory)；**tag `v0.6.23-m4` 已推送**
- **文档订正**：`docs/research/00-synthesis.md` 3 处（假 grep 断言、colorout 缺限定词、① 机制）；`docs/开发计划.md` 新增 **M4-8** 节
- **工程杂项**：版本号改为单一来源 `FilmKitApp.VERSION`（原先陈旧在 0.6.16）；`test_temp/` 加入 `.gitignore`（用户指定临时样片目录不入库）

## Decisions

- [2026-09-22] **色度增强判据用"亮度相对饱和"而非绝对线性色度** —— 绝对 `max|cc|` 把**饱和度**与**亮度水平**混在一起：暗色物体即使很绿，绝对色度也小。真机实测同一曲线下树叶只得 5.05%、罐体 13.70%（差 2.7×）。相对判据还**天然保护近中性色**（暗部中性像素增益仅 0.06%），不必再靠 knee 承担该职责
- [2026-09-22] **knee 1.0→0.4 定向补低饱和，不追求对齐 libraw** —— 缺口剖面显示低饱和重、高饱和轻，故要"低饱和补得多、高饱和补得少"。**libraw 的 C\* 是它的偏好不是"正确"**（与 `CameraPresets.kt:44` 既有结论一致）
- [2026-09-22] **DNG 对照只能定位缺口、不能当绝对标尺** —— 我们的 DNG **`ForwardMatrix1/2` 缺失**（DngCreator 不写），libraw 只能退回 `ColorMatrix1/2`；本 App 走 `CameraCharacteristics` 的 ForwardMatrix（DNG 标准路径，`FM·(1,1,1)`=D50 自洽）
- [2026-09-22] **④ LUT 纹素中心校正废弃** —— 恒等 LUT 实测证明现行实现已与硬件路径数学等价；照搬会二次偏移（纯白只能查到 0.985）
- [2026-09-22] **① 仍做但理由改** —— 不是"治发闷"（中间调可忽略）、不是"对齐 LUT 域"（机制证伪），而是**暗部压深**＋**域正确性**。⛔ 实现须**三处同步**：`FrameRenderer.cpp:780`(kFsOut) / `:845`(kFsHist) / `:2013`(反解码)
- [2026-09-22] **③ AE 拆分为两件** —— 只做「切镜头重置 + 死区」（`auto_gain_` 跨镜头存活，EMA 0.7/0.3 需 7–8 帧收敛；置 0 复用既有首帧直通分支）；「改区域加权锚定 0.16」降级为待 A/B 选项（libcamera 的 0.16 是区域加权**平均**，与我们 P95=0.80 白点不同语义）
- [2026-09-22] **每轮对话一个验收 tag；中间验证包只出 APK 不打 tag**（沿用既有约定，本轮 tag `v0.6.23-m4`）

## Pitfalls

- **C++ 原始字符串 `R"(...)"` 里写 `)"` 会提前终止字面量** —— 给 `kFsFilm` 加注释时写了「显示域 0.25(=64/255)」，其中 `)"` 正是结束标记 → GLSL 被截断。**构建与 Kotlin 单测全绿都拦不住**，只有 `tools/validate-shaders.sh` 报 `shader_11.frag:126 syntax error, unexpected end of file`。规避：注释里数字后接括号用全角（）或改写措辞
- **手搓色彩链矩阵对比极易出错（本轮我自己犯了）** —— 把 `XYZ2SRGB @ ColorMatrix1` 当 libraw 的 camera→sRGB 比饱和度，算出 G=12.1/R=15.5 的荒谬值，根因是 **WB 施了两次**（libraw 顺序是"先 WB 再矩阵"）且该孤立矩阵行和不为 1。**矩阵级对比必须先验证"中性进→中性出"**，否则宁可退回图像级对比
- **比 C\* 必须同亮度，否则把"亮"误读成"浓"** —— 新批次 C\* 比参照高 1.1–2.3×（黄橙带 1.93×）看似严重过饱和，实为我们的图更亮而 **C\* 随 L\* 增长**；换亮度无关的 `rel` 后是 0.68~1.07。**跨链比饱和度只用 rel**
- **色相误差要按色相带拆开看** —— 按带统计发现 **黄绿 −5.6° 而黄橙仅 +1.0°** ⇒ 是色相相关误差而非全局色偏。且偏差按 `rel` 分箱后**不随增强量增大** ⇒ 排除色度层，指向 CCM 路径
- **注释里的域标签会骗人** —— `knee(=0.25 线性 ≈ 显示域 64/255)` 实为 136/255，差 72 灰阶，导致 v0.6.19 的修正整体失效。**改色彩代码前必须回代码核实量纲/域**
- **判断"某色准不准"必须先排除三个混淆项** —— A/B 是否受控（易拉罐组 L\* 差 7.5 ⇒ 无效）、有无全局色偏（近中性 a\*≈b\*≈0 ⇒ 干净）、是否色域到顶（树叶仅达上限 25% ⇒ 不是）。**不同构图的"哪组更好看"不构成 A/B**
- **`git stash push -- <单文件>` 可判定 FAIL 是否本次引入** —— 本轮据此确认 `shader_11.frag` 失败确由改动引入（原文件 OK）

## Next

1. **① 输出 OETF 改精确 sRGB 分段**（治暗部、对齐显示域）：**三处必须同步改** —— `FrameRenderer.cpp:780`(kFsOut) / `:845`(kFsHist) / `:2013`(`std::pow(disp,2.2f)` 反解码)，否则违反"kFsHist 必须同源"决策。改完跑 `tools/validate-shaders.sh` + 真机 A/B（开关已存在）
2. **③ 切镜头 AE 重置（1 行）**：在 `setFocal`/`setLens` 走 `stopInternalKeepClient` 的路径上把 `auto_gain_` 置 0（`FrameRenderer.cpp`），复用既有"首帧直通"分支；顺带加死区防抖
3. **黄绿带色相偏差 −3~8° 定案**（用户最初的"树叶绿不准"）：已排除色度层与全局色偏，指向 CCM 路径。**动手前必须先定基准** —— 需要灰卡/色卡实拍，或厂商同场景直出做绝对参照；用 libraw 当基准不成立（见 Decisions）
4. **暗场景亮度**（"456 比真实场景暗"）：456 是暗场景 + 高 DR（显示域中位 0.356、线性 8.4EV），衣柜把 P95 顶到 0.877 而 auto-tone 目标就是 P95→线性 0.80 ⇒ **全局曲线已到高光硬顶**，只能靠**局部色调映射**（roadmap 第二批，强度 ≤0.2–0.3，须保住全局对比与黑位）
5. **M4 后续**：.cube / Hald 导入导出、链式融合烘焙 65³、预设包（`.filmkit` zip）
